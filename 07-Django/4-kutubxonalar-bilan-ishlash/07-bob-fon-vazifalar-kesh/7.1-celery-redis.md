# 7.1. Celery + Redis — asinxron (fon) vazifalar

## Bu darsda nimalarni o'rganasiz

- Nega ba'zi vazifalarni (email yuborish, hisobot tayyorlash) so'rov-javob siklidan **tashqarida** bajarish kerakligini tushunasiz
- `Celery` va `Redis` birgalikda qanday ishlashini bilib olasiz
- Django loyihasida Celery'ni sozlab, birinchi fon vazifasini yozishni o'rganasiz
- `.delay()` orqali vazifani navbatga qo'yishni va uning natijasini kuzatishni o'rganasiz

## Nazariy qism

### Muammo: uzoq davom etadigan amallar

Foydalanuvchi `onlayn_dokon`da buyurtma bersa, tizim unga **tasdiqlash emaili** yuborishi kerak deylik. Email yuborish — tashqi serverga (SMTP) ulanish, bu esa 1-3 soniya (ba'zan sekin tarmoqda 10+ soniya) vaqt olishi mumkin. Agar bu amal to'g'ridan-to'g'ri view ichida, sinxron bajarilsa:

```python
def buyurtma_yaratish(request):
    buyurtma = Buyurtma.objects.create(...)
    yubor_tasdiqlash_email(buyurtma)   # 3 soniya kutadi!
    return redirect("buyurtma_muvaffaqiyatli")
```

Foydalanuvchi **3 soniya** sahifa yuklanishini kutadi — bu, ayniqsa email serveri sekinlashsa yoki vaqtincha ishlamasa, butun saytni "osilib qolgan" his qildiradi. Bunday vazifalar — email yuborish, katta hisobot (PDF/Excel) tayyorlash, rasmni qayta ishlash, tashqi API'ga so'rov — so'rov-javob siklidan **ajratib**, orqa fonda (background) bajarilishi kerak.

### Celery va Redis birgalikda qanday ishlaydi

**Celery** — Python uchun **vazifalar navbati** (task queue) kutubxonasi: siz "qaysi funksiyani fon vazifasi deb belgilashni" aytasiz, Celery esa uni alohida jarayonda (worker) bajaradi. Lekin Celery'ning o'zi vazifalarni **saqlash** joyiga muhtoj — Django va worker jarayoni o'rtasida "menga shu vazifani bajar" xabarini kim yetkazadi? Aynan shu vazifani **broker** bajaradi, va eng ko'p ishlatiladigan broker — **Redis** (tezkor, xotirada ishlaydigan ma'lumotlar ombori).

Oqim quyidagicha: Django view `.delay()` chaqiradi → vazifa Redis navbatiga yoziladi → alohida ishlab turgan Celery **worker** jarayoni navbatni kuzatib turadi, yangi vazifani ko'rib, uni bajaradi → Django darhol, kutmasdan, foydalanuvchiga javob qaytaradi.

### Birinchi vazifa yozish

```python
# apps/dokon/tasks.py
from celery import shared_task
from django.core.mail import send_mail


@shared_task
def yubor_tasdiqlash_email(buyurtma_id, email):
    send_mail(
        subject=f"Buyurtma #{buyurtma_id} qabul qilindi",
        message="Buyurtmangiz muvaffaqiyatli qabul qilindi, tez orada yetkazamiz.",
        from_email="dokon@example.com",
        recipient_list=[email],
    )
```

`@shared_task` — funksiyani Celery vazifasiga aylantiradi (Django app'lar orasida qayta ishlatsa bo'ladigan universal dekorator). Vazifaga **primitiv** qiymatlar (`buyurtma_id`, `email` — sonlar/satrlar) uzatilyapti, `Buyurtma` obyektining o'zi emas — chunki worker alohida jarayonda ishlaydi va Python obyektlarini to'g'ridan-to'g'ri "ulasha olmaydi"; vazifa ichida, kerak bo'lsa, `Buyurtma.objects.get(id=buyurtma_id)` orqali qayta olinadi.

```python
# views.py
from .tasks import yubor_tasdiqlash_email

def buyurtma_yaratish(request):
    buyurtma = Buyurtma.objects.create(...)
    yubor_tasdiqlash_email.delay(buyurtma.id, buyurtma.mijoz.email)   # darhol qaytadi!
    return redirect("buyurtma_muvaffaqiyatli")
```

`.delay(...)` — vazifani Redis navbatiga qo'yadi va **darhol** qaytadi (millisekundlar ichida) — view emailning yuborilishini **kutmaydi**, foydalanuvchi sahifasi tezda yuklanadi.

### Worker'ni ishga tushirish

```bash
celery -A onlayn_dokon worker --loglevel=info
```

Bu buyruq — alohida terminalda, Django serveridan **mustaqil**, doimiy ishlab turishi kerak (production'da bu, `systemd` yoki Docker konteyneri sifatida boshqariladi).

## Amaliy misol

`onlayn_dokon`da buyurtma berilganda tasdiqlash emailini fon vazifasi orqali yuborish:

```python
# apps/dokon/tasks.py
import logging
from celery import shared_task
from django.core.mail import send_mail

logger = logging.getLogger(__name__)


@shared_task(bind=True, max_retries=3)
def yubor_tasdiqlash_email(self, buyurtma_id, email):
    from .models import Buyurtma

    try:
        buyurtma = Buyurtma.objects.get(id=buyurtma_id)
        send_mail(
            subject=f"Buyurtma #{buyurtma.id} qabul qilindi",
            message=f"Hurmatli mijoz, {buyurtma.jami_summa} so'mlik buyurtmangiz qabul qilindi.",
            from_email="dokon@example.com",
            recipient_list=[email],
        )
        logger.info(f"Buyurtma #{buyurtma_id} uchun email yuborildi: {email}")
    except Exception as exc:
        logger.warning(f"Email yuborishda xato, qayta urinilmoqda: {exc}")
        raise self.retry(exc=exc, countdown=60)   # 60 soniyadan keyin qayta urinadi
```

```python
# apps/dokon/views.py
from django.shortcuts import redirect
from .tasks import yubor_tasdiqlash_email

def buyurtma_yaratish(request):
    if request.method == "POST":
        buyurtma = Buyurtma.objects.create(
            mijoz=request.user.mijoz,
            jami_summa=hisobla_jami_summa(request),
        )
        yubor_tasdiqlash_email.delay(buyurtma.id, request.user.email)
        return redirect("buyurtma_muvaffaqiyatli", buyurtma_id=buyurtma.id)
```

## Keng tarqalgan xatolar

**Xato 1:** Vazifaga to'g'ridan-to'g'ri Django model obyektini uzatish.

❌ `yubor_tasdiqlash_email.delay(buyurtma)` — `Buyurtma` obyektining o'zi uzatilgan; Celery buni "serializatsiya" qilishga urinadi, bu ba'zan ishlaydi, lekin **eskirgan ma'lumot** muammosiga olib kelishi mumkin (vazifa bajarilguncha obyekt o'zgargan bo'lishi mumkin) va ba'zi murakkab obyektlar umuman serializatsiya qilinmaydi.

✅ Vazifaga har doim **primitiv** qiymatlar (ID, satr, son) uzating; vazifa ichida, `Model.objects.get(id=...)` orqali, **eng yangi** ma'lumotni qayta oling.

**Xato 2:** Worker jarayonini ishga tushirmasdan, vazifalar "ishlamayapti" deb hayron bo'lish.

❌ `.delay()` chaqirilgan, vazifa Redis navbatiga qo'yilgan, lekin `celery -A onlayn_dokon worker` hech qachon ishga tushirilmagan — vazifa **abadiy** navbatda kutib qoladi, hech qachon bajarilmaydi, va hech qanday xato ham chiqmaydi (chunki Django tomonidan hammasi "muvaffaqiyatli" ko'rinadi — `.delay()` faqat navbatga qo'yishni tasdiqlaydi).

✅ Development paytida ham, production'da ham, Celery worker'ni **alohida, doimiy ishlab turadigan** jarayon sifatida ishga tushirishni unutmang — buni tekshirish uchun, worker terminalida "vazifa qabul qilindi" logini kuzating.

**Xato 3:** Xato yuz berganda qayta urinish (retry) mexanizmini qo'shmaslik.

❌ Email yuborish vazifasi ichida SMTP serveri vaqtincha ishlamay qolsa (masalan tarmoq uzilishi), `send_mail()` xato tashlaydi, vazifa "muvaffaqiyatsiz" deb belgilanadi va **hech qachon qayta urinilmaydi** — email umuman yuborilmay qoladi.

✅ Tashqi xizmatlarga (email, SMS, tashqi API) bog'liq vazifalarda, yuqoridagi misoldagi kabi, `bind=True` va `self.retry(exc=exc, countdown=...)` orqali avtomatik qayta urinish mexanizmini qo'shing — vaqtinchalik uzilishlar o'zi-o'zidan tuzatiladi.

## Mashq/topshiriq

**(Oson)** `celery` va `redis`ni o'rnating, `onlayn_dokon/celery.py` faylini yarating, `CELERY_BROKER_URL`ni sozlang. `redis-server` va `celery -A onlayn_dokon worker` jarayonlarini ishga tushiring.

**(O'rtacha)** Oddiy, hech narsa qilmaydigan, faqat `print()` chiqaradigan test vazifasi yozing (`@shared_task def test_vazifa(): print("Ishladi!")`), uni Django shell orqali (`python manage.py shell`) `test_vazifa.delay()` bilan chaqiring, va worker terminalida natijani kuzating.

**(Qiyin)** `yubor_tasdiqlash_email` vazifasini, yuqoridagi "Amaliy misol"dagi kabi, `retry` mexanizmi bilan yozing. SMTP sozlamalarini ataylab noto'g'ri qilib (masalan mavjud bo'lmagan serverga), vazifani chaqiring va worker logida bir necha marta "qayta urinilmoqda" xabarini ko'ring.

## Qisqacha xulosa

`Celery` (vazifalar navbati) va `Redis` (broker) birgalikda, uzoq davom etadigan amallarni (email yuborish, hisobot tayyorlash) so'rov-javob siklidan ajratib, foydalanuvchini kutmasdan orqa fonda bajarish imkonini beradi: `@shared_task` bilan belgilangan funksiya, `.delay()` orqali navbatga qo'yiladi va alohida ishlab turgan **worker** jarayoni tomonidan bajariladi; `bind=True`+`retry` — tashqi xizmatlarga bog'liq vazifalarni vaqtinchalik uzilishlardan himoya qiladi. Keyingi darsda — Celery/Redis infratuzilmasining o'zidan foydalanib, tez-tez so'raladigan, lekin kamdan-kam o'zgaradigan ma'lumotlarni (masalan mahsulotlar ro'yxati) **keshlash** (`django-redis`) orqali saytni tezlashtirishni ko'ramiz.

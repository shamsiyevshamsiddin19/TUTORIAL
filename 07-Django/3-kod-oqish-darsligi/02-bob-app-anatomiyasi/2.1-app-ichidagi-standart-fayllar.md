# 2.1. App ichidagi standart fayllar — har birining vazifasi

## Bu darsda nimalarni o'rganasiz

- `python manage.py startapp` **aynan qanday** fayllar yaratishini va har birining vazifasini bilib olasiz
- `apps.py`dagi `name` maydonining **nega** aynan shunday yozilishi kerakligini, real xato orqali tushunasiz
- Python'ning "namespace package" xususiyati orqali, `apps/__init__.py` fayli **shart emasligini** kashf etasiz
- Yangi app'ni to'g'ri ro'yxatdan o'tkazish to'liq ketma-ketligini mustahkamlaysiz

## Nazariy qism

### `startapp` — nechta fayl, qaysi tartibda

O'tgan bo'limda o'rgangan `apps/` papkasi ichida, yangi app yaratamiz:

```bash
mkdir -p apps/dokon
python manage.py startapp dokon apps/dokon
```

**Muhim tafsilot:** `startapp dokon apps/dokon` — bu yerda ikkita argument bor: birinchisi (`dokon`) — app'ning **Python nomi** (kod ichida shunday ataladi); ikkinchisi (`apps/dokon`) — bu app fayllari **jismonan qayerda** joylashishi. Agar maqsad papka (`apps/dokon`) oldindan mavjud bo'lmasa, Django aniq xato beradi: `CommandError: Destination directory '...' does not exist, please create it first.` — shuning uchun yuqorida, avval `mkdir -p` bilan papkani yaratib oldik.

Natijada:

```
apps/dokon/
├── __init__.py
├── admin.py
├── apps.py
├── migrations/
│   └── __init__.py
├── models.py
├── tests.py
└── views.py
```

Endi har birini navbat bilan o'qiymiz.

### `apps.py` — app'ning "shaxsnomasi"

```python
from django.apps import AppConfig


class DokonConfig(AppConfig):
    default_auto_field = "django.db.models.BigAutoField"
    name = "dokon"
```

Bu — app haqidagi konfiguratsiya klassi. `default_auto_field` — shu app ichidagi modellar uchun, agar aniq ko'rsatilmasa, avtomatik ID maydoni qanday turda bo'lishini belgilaydi (1-bobda `settings.py`da ko'rgan `DEFAULT_AUTO_FIELD`ning **shu app uchun** nusxasi). `name = "dokon"` — bu, Django'ga, "bu app'ni Python kodida qanday import qilish mumkinligini" aytadi.

**Va aynan shu yerda — birinchi jiddiy "sinov" bor.** Biz app'ni `apps/dokon/` papkasiga joylashtirdik, ya'ni uning to'liq Python yo'li — `apps.dokon`, oddiy `dokon` emas. Agar `settings.py`dagi `INSTALLED_APPS`ga `"apps.dokon"` deb qo'shsak, lekin `apps.py`dagi `name` hali ham `"dokon"` bo'lib qolsa:

```python
INSTALLED_APPS = [
    ...
    "apps.dokon",
]
```

```bash
python manage.py check
```

```
django.core.exceptions.ImproperlyConfigured: Cannot import 'dokon'. Check that 'apps.dokon.apps.DokonConfig.name' is correct.
```

Bu xato — juda aniq va o'z-o'zini tushuntiradi: Django, `INSTALLED_APPS`dagi yo'l (`apps.dokon`) orqali app'ni topdi, uning `apps.py`sini ochdi, lekin u yerdagi `name = "dokon"` — **mos kelmadi**. Tuzatish:

```python
class DokonConfig(AppConfig):
    default_auto_field = "django.db.models.BigAutoField"
    name = "apps.dokon"   # to'liq, haqiqiy joylashuvga mos yo'l
```

```bash
python manage.py check
```

```
System check identified no issues (0 silenced).
```

**Qoida (yodda saqlang):** `INSTALLED_APPS`dagi yozuv va `apps.py`dagi `name` — **har doim, so'zma-so'z bir xil** bo'lishi shart, chunki ikkalasi ham, aslida, bitta narsani — "bu app'ga Python import orqali qanday yetib borish mumkin" — ifodalaydi.

### `models.py`, `views.py`, `admin.py`, `tests.py` — bo'sh, lekin tayyor "uylar"

```python
# models.py
from django.db import models
# Create your models here.

# views.py
from django.shortcuts import render
# Create your views here.

# admin.py
from django.contrib import admin
# Register your models here.

# tests.py
from django.test import TestCase
# Create your tests here.
```

Diqqat qiling: har bir fayl, hali **bo'sh** bo'lsa-da, allaqachon **kerakli import**ni o'z ichiga oladi (`models.py` — `models`ni, `views.py` — `render`ni, va h.k.) va izoh orqali **o'zining vazifasini** aytadi. Bu — Django'ning "konventsiya konfiguratsiyadan ustun" (convention over configuration) falsafasining aniq ko'rinishi: sizga hech kim "modellarni qayerga yozish kerak" deb aytmaydi, chunki bu, fayl **nomining o'zidan** va undagi tayyor izohdan ayon.

Bu darslikning markaziy g'oyasi — aynan shu **"qayerga yozish kerak"** qoidasini mustahkam bilish:

| Fayl | Nima yoziladi | Nima yozilMAYDI |
|---|---|---|
| `models.py` | Ma'lumotlar tuzilishi (jadval ta'rifi) | HTML, murakkab biznes-mantiq |
| `views.py` | So'rovni qabul qilib, javob qaytaruvchi funksiya/klass | To'g'ridan-to'g'ri SQL, jadval ta'rifi |
| `admin.py` | Modellarni admin panelda qanday ko'rsatishni sozlash | Modelning o'zi (faqat unga ishora) |
| `tests.py` | Avtomatik testlar | Ishlab chiqarish (production) kodi |

### `migrations/` — o'zgarishlar tarixi

```
migrations/
└── __init__.py
```

Hozircha bu papka, ichida faqat `__init__.py` bilan, **bo'sh**. `models.py`ga birinchi model qo'shib, `python manage.py makemigrations` buyrug'ini bajarganimizdan so'ng (4-bobda), bu yerda `0001_initial.py` kabi fayllar avtomatik paydo bo'la boshlaydi — har biri, bazaga qilingan **bitta o'zgarishning** "vaqt tamg'asi" hisoblanadi.

## Kodni o'qish mashqi

Loyihamizning `apps/` papkasini diqqat bilan ko'zdan kechiring:

```bash
find apps -name "__init__.py"
```

```
apps/dokon/__init__.py
apps/dokon/migrations/__init__.py
```

**Savol:** `apps/dokon/__init__.py` bor, lekin `apps/__init__.py` (ya'ni, `apps/` papkasining o'zida) — **yo'q**. Xotirangizda, "har bir Python paketi `__init__.py`ga muhtoj" degan qoida bor bo'lsa, bu — xatomi? `import apps.dokon` ishlaydimi?

<details>
<summary>Javobni ko'rish</summary>

Bu — xato **emas**. Zamonaviy Python (3.3 versiyasidan boshlab) — **"namespace package"** deb ataladigan xususiyatni qo'llab-quvvatlaydi: agar papkada `__init__.py` bo'lmasa ham, Python uni, kerak bo'lganda, "paketga o'xshash" narsa sifatida qabul qilishi mumkin. Buni haqiqatan tekshiramiz.

</details>

## Amaliy misol

Bashoratimizni amalda tasdiqlaymiz:

```bash
python -c "from apps.dokon.apps import DokonConfig; print('Import muvaffaqiyatli:', DokonConfig)"
```

```
Import muvaffaqiyatli: <class 'apps.dokon.apps.DokonConfig'>
```

Haqiqatan ham ishladi — `apps/__init__.py` fayli yo'qligiga qaramay! Shunga qaramay, **eng yaxshi amaliyot** sifatida, ko'p Django loyihalarida (jumladan, keyingi darslarimizda) `apps/__init__.py`ni **bo'sh fayl sifatida ham bo'lsa qo'shish** tavsiya etiladi — chunki bu, (1) eski Python versiyalar bilan moslikni ta'minlaydi, (2) ba'zi vositalar (IDE, ba'zi test tizimlari) namespace package'larni har doim ham to'g'ri tushunmasligi mumkin. Qo'shamiz:

```bash
touch apps/__init__.py
python manage.py check
```

```
System check identified no issues (0 silenced).
```

Hech narsa buzilmadi — bu, `apps/__init__.py`ning **qo'shilishi ham, yo'qligi ham** ishlashi mumkinligini, lekin uni qo'shish "xavfsizroq odat" ekanini ko'rsatadi.

## Keng tarqalgan xatolar

**Xato 1:** `INSTALLED_APPS`ga app qo'shilgan, lekin `apps.py`dagi `name` mos kelmaydi (yuqorida ko'rganimizdek).
❌ `ImproperlyConfigured: Cannot import '...'` xatosi bilan server umuman ishga tushmaydi.
✅ App'ni `apps/` ichiga joylashtirganda, **darhol** `apps.py`dagi `name`ni ham to'liq yo'l bilan (`"apps.dokon"`) yangilang — buni odat qiling.

**Xato 2:** `models.py`ga HTML yoki shablon mantiqini yozishga urinish (chalkashlik natijasida).
❌ Django'ning MTV (Model-Template-View) arxitekturasi buziladi, kod tushunarsiz va qayta ishlatib bo'lmaydigan bo'lib qoladi.
✅ Har bir fayl faqat **o'z vazifasiga mos** kodni saqlashi kerak — yuqoridagi jadvalga qayta-qayta murojaat qiling, toki bu reflekstga aylanguncha.

**Xato 3:** `tests.py`ni "keyinroq yozaman" deb butunlay bo'sh qoldiraverish (odat sifatida).
❌ Loyiha kattalashgani sayin, testsiz kodni o'zgartirish tobora xavfli bo'lib boradi (9-bobda "xavfsiz o'zgartirish" mavzusida buni chuqur ko'ramiz).
✅ Hech bo'lmasa, har bir yangi model/funksiya uchun **bitta oddiy test** yozish odatini shakllantiring — bu, keyinchalik kodni o'zgartirganda, "hech narsa buzilmadi" degan ishonchni beradi.

## Mashq/topshiriq

**(Oson)** `apps/dokon/apps.py` faylini oching va klass nomini (`DokonConfig`) o'zboshimchalik bilan `MeningAppim`ga o'zgartiring (lekin `name = "apps.dokon"` qatorini o'zgartirmang). `python manage.py check`ni ishga tushiring — bu ishlaydimi? Nega klass nomi (Python darajasidagi nom) va `name` maydoni (Django'ga ko'rsatiladigan yo'l) — ikki **butunlay boshqa** narsa ekanini tushuntiring.

**(O'rtacha)** Yangi, ikkinchi app yarating: `mkdir -p apps/hisobotlar && python manage.py startapp hisobotlar apps/hisobotlar`. Uni to'g'ri sozlab (`apps.py`dagi `name`, `INSTALLED_APPS`), `python manage.py check` xatosiz o'tishini tasdiqlang.

**(Qiyin)** `apps/dokon/__init__.py`ni **o'chirib tashlang** (bu safar ichki, app darajasidagi `__init__.py`, tashqi `apps/`ning emas). `python manage.py check`ni ishga tushiring — bu ishlaydimi yoki yo'qmi? Agar natija, `apps/__init__.py` yo'q bo'lgan holatdan **farq qilsa**, sababini tushuntirishga harakat qiling (maslahat: `migrations/__init__.py` ham borligini eslang — Django ichki mexanizmlari qaysi joyda `__init__.py`ga qattiqroq tayanishi mumkin).

<details>
<summary>Javoblarni ko'rish</summary>

1. `python manage.py check` — muammosiz o'tadi ("System check identified no issues"). Sabab: `DokonConfig` (yoki `MeningAppim`) — bu, shunchaki, Python darajasidagi klass **nomi**, uni istalgan narsaga o'zgartirish mumkin, chunki Django uni klass nomi orqali emas, balki `apps.py` faylini **skanerlab, `AppConfig`dan meros olgan birinchi klassni topib** ishlatadi. `name` maydoni esa — Django uchun **muhim, majburiy** ma'lumot: aynan shu maydon orqali Django "bu konfiguratsiya qaysi app'ga tegishli"ligini biladi. Xulosa: Python darajasidagi nomlash erkinligi va Django'ga **kerakli** ma'lumot — ikki xil narsa.

2. 
```bash
mkdir -p apps/hisobotlar
python manage.py startapp hisobotlar apps/hisobotlar
# apps/hisobotlar/apps.py ichida: name = "apps.hisobotlar"
# settings.py INSTALLED_APPS ga: "apps.hisobotlar",
python manage.py check
# System check identified no issues (0 silenced).
```

3. Bu holatda ham odatda ishlayveradi (chunki Python'ning namespace package xususiyati, istalgan darajadagi papkaga tegishli), lekin **tavsiya etilmaydi** — ba'zi Django ichki mexanizmlari (masalan, migratsiyalarni qidirish) aniq, `__init__.py` bilan belgilangan paketlarga tayanadi, va namespace package'lar bilan **kutilmagan** xatti-harakatlarga duch kelish ehtimoli oshadi. Shuning uchun amaliy qoida: `apps/` (tashqi, guruhlovchi papka) uchun `__init__.py` shart emas, lekin har bir **haqiqiy app** (`apps/dokon/`, `apps/hisobotlar/`) ichida uni **har doim** saqlang — `startapp` buyrug'i buni sizga avtomatik beradi, uni qo'lda o'chirmang.

</details>

## Qisqacha xulosa

`python manage.py startapp` — bitta buyruq bilan, aniq vazifali fayllar to'plamini yaratadi: `apps.py` (app konfiguratsiyasi, `name` maydoni **`INSTALLED_APPS`dagi yozuv bilan so'zma-so'z mos kelishi shart**), `models.py`/`views.py`/`admin.py`/`tests.py` (har biri — o'ziga xos, boshqa fayl vazifasini "o'g'irlamasligi" kerak bo'lgan "uy"), va `migrations/` (bo'sh boshlanadigan, lekin har bir model o'zgarishi bilan to'lib boradigan tarix jurnali). Python'ning "namespace package" xususiyati, `apps/` kabi guruhlovchi papkalarda `__init__.py` shart emasligini anglatadi, lekin har bir haqiqiy app ichida uni saqlash — xavfsiz standart amaliyot. Keyingi darsda — bu fayllar orasidagi **chaqiruv tartibini** (import graf) chuqur o'rganamiz va "qaysi kod qayerga" qoidalarini yanada kengaytiramiz.

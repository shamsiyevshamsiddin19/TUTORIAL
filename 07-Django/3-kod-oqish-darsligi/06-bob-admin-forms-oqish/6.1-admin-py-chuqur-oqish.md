# 6.1. `admin.py`ni chuqur o'qish — modeldan, tayyor boshqaruv paneligacha

## Bu darsda nimalarni o'rganasiz

- `admin.py` — nima uchun kerak, va nega, uni yozmasangiz, model **admin panelida umuman ko'rinmasligini**
- `admin.site.register()` va `@admin.register()` — ikkalasi ham bir xil ishni bajarishini
- `ModelAdmin` klassi — `list_display`, `search_fields`, `list_filter` — har biri, real HTML'ga qanday ta'sir qilishini
- `@admin.display(description=...)` — modelda yo'q, lekin admin panelida ko'rsatiladigan "hisoblangan ustun"larni qanday yozishni
- Model darajasidagi `class Meta` — bazaga hech qanday ta'sir qilmaydigan, lekin **baribir migratsiya talab qiladigan** sozlamalar borligini

## Nazariy qism

### Ro'yxatdan o'tkazilmagan model — "ko'rinmas" model

`startproject` bilan yaratilgan, standart `admin.py`:

```python
from django.contrib import admin

# Register your models here.
```

Bu — bo'sh, lekin **muhim** fayl: `INSTALLED_APPS`da `django.contrib.admin` bor ekan (1-bobda ko'rganimiz), Django, `/admin/` manzilida, tayyor boshqaruv panelini avtomatik ishga tushiradi — lekin bu panel, **faqat ataylab "ro'yxatdan o'tkazilgan" modellarni** ko'rsatadi. Buni tekshiramiz: superuser bilan kirib, `/admin/`ga so'rov yuboramiz — `admin.py` hali bo'sh bo'lganda:

```
Site administration
```

— boshqa hech narsa yo'q, hech qanday "Dokon" bo'limi, hech qanday `Bolim` ko'rinmaydi, garchi bazada `Bolim` jadvali va undagi yozuvlar **allaqachon mavjud** bo'lsa ham (4-bobda yaratgan edik)! Bu — muhim tushuncha: **`models.py`dagi model borligi, uning admin panelida ko'rinishini kafolatlamaydi** — bular, ikkita, bir-biriga bog'liq bo'lmagan qadam.

### Ro'yxatga olish — eng oddiy yo'l

```python
from django.contrib import admin

from .models import Bolim

admin.site.register(Bolim)
```

Bu — bitta qator: `admin.site` — bu, butun admin panelini boshqaruvchi, global ob'ekt (1-bobda ko'rgan `urls.py`dagi `path("admin/", admin.site.urls)` — aynan shu ob'ekt). `.register(Bolim)` — unga, "`Bolim` modelini, standart sozlamalar bilan, boshqaruv paneliga qo'sh" deydi. Buni qo'shib, qayta tekshirsak:

```
Dokon
    Bolims          Add  +
```

Ikki narsaga e'tibor bering: (1) `Dokon` — bu, app nomi (`apps.py`dagi `verbose_name` yoki, sozlanmagan bo'lsa, app label'ining o'zi — 2-bobda ko'rgan); (2) `Bolims` — bu, **Django'ning avtomatik ko'plik shakli** (`Bolim` + `s`), va bu — **noto'g'ri o'zbekcha** (to'g'risi — "Bo'limlar" bo'lishi kerak)! Bu, Django'ning ingliz tiliga mo'ljallangan, sodda qoidasi (so'zga shunchaki `"s"` qo'shish) — o'zbekcha (yoki har qanday boshqa tildagi) so'zlar uchun ishlamaydi. Buni pastda tuzatamiz.

### `@admin.register()` — dekorator shakli (ko'proq tarqalgan)

Amaliyotda, ayniqsa `ModelAdmin`ni sozlash kerak bo'lsa, dekorator shakli ko'proq ishlatiladi:

```python
@admin.register(Bolim)
class BolimAdmin(admin.ModelAdmin):
    list_display = ("nomi", "joylashuv", "xodimlar_soni")
    search_fields = ("nomi",)
    list_filter = ("joylashuv",)

    @admin.display(description="Xodimlar soni")
    def xodimlar_soni(self, obj):
        return obj.xodimlar.count()
```

Bu, aslida, `admin.site.register(Bolim, BolimAdmin)`ning **aynan bir xil natijasi** — faqat, dekorator sintaksisi, klassni e'lon qilish bilan bir vaqtda ro'yxatga olish imkonini beradi (xuddi Python'dagi boshqa dekoratorlar kabi — funksiyani e'lon qilish bilan, uni "o'rab olish" bir vaqtda sodir bo'ladi). Har bir sozlamani alohida o'qiymiz:

`list_display = ("nomi", "joylashuv", "xodimlar_soni")` — o'zgarish ro'yxati sahifasida (barcha `Bolim`lar jadvali), qaysi ustunlar ko'rsatilishini belgilaydi. Diqqat qiling: `"xodimlar_soni"` — `Bolim` modelida **umuman yo'q maydon**! Bu — `BolimAdmin` klassining o'z metodi, pastda ta'riflangan:

```python
@admin.display(description="Xodimlar soni")
def xodimlar_soni(self, obj):
    return obj.xodimlar.count()
```

Bu metod, `obj` (joriy `Bolim` qatori)ni oladi va, 4.2-darsda ko'rgan `related_name` (`bolim.xodimlar.all()`) orqali, unga tegishli xodimlar sonini **jonli hisoblab** qaytaradi. `@admin.display(description="Xodimlar soni")` — bu metod natijasi, ustun sarlavhasida (`"xodimlar_soni"` o'rniga) **"Xodimlar soni"** deb ko'rsatilishini ta'minlaydi (aks holda, standart, Python nomidan avtomatik yasalgan "Xodimlar soni" o'rniga, texnikroq nom chiqishi mumkin edi).

`search_fields = ("nomi",)` — sahifa yuqorisida, qidiruv maydonini qo'shadi, va u, `nomi` ustuni bo'yicha (SQL'dagi `LIKE '%...%'`ga o'xshash) qidiradi. `list_filter = ("joylashuv",)` — o'ng tomonda, `joylashuv`ning **mavjud, noyob qiymatlari** bo'yicha, tez filtrlash panelini qo'shadi.

### Real natijani tekshiramiz

Real serverda, qidiruv va filtrni sinaymiz:

```bash
curl "http://localhost:8000/admin/dokon/bolim/?q=Elektronika"
```

Natijada, faqat **"Elektronika"** qatori qaytadi ("Kiyim-kechak" — yo'q). Filtrni sinaymiz:

```bash
curl "http://localhost:8000/admin/dokon/bolim/?joylashuv__exact=1-qavat"
```

Bu ham, faqat "Elektronika"ni qaytaradi (chunki faqat u, `joylashuv="1-qavat"`ga ega). Diqqat qiling: URL'dagi `?q=...` va `?joylashuv__exact=...` — bular, 3.2-darsda ko'rgan `request.GET` (`QueryDict`)ning, admin panel ichida ishlatilishi — admin, "orqasida", sizning kodingiz ishlatgan bir xil Django vositalaridan foydalanadi, faqat tayyor, chiroyli HTML bilan.

## Kodni o'qish mashqi

Quyidagi `ModelAdmin`ni ko'ring:

```python
@admin.register(Bolim)
class BolimAdmin(admin.ModelAdmin):
    list_display = ("nomi", "joylashuv", "notogri_maydon")
```

**Bashorat qiling:** `notogri_maydon` — `Bolim` modelida ham, `BolimAdmin`ning o'zida ham yo'q. Server ishga tushganda (`python manage.py check` yoki `runserver`), nima bo'ladi — sahifa `500`-xato beradimi, yo `notogri_maydon` ustuni, shunchaki bo'sh ko'rinadimi (5-bobda ko'rgan, shablonlarning "jim xato" xulqiga o'xshab)?

Shuning uchun `admin.py`dagi xatolar, odatda, shablon xatolaridan ko'ra **tezroq va ochiqroq** aniqlanadi — bu, "qaysi kod qayerda tekshiriladi" haqidagi, darslikning markaziy g'oyasiga yana bir misol.

## Amaliy misol

`Bolim` modelidagi, noto'g'ri ko'plik shaklini (`Bolims`) tuzatamiz — bu, `admin.py`da emas, **`models.py`dagi `class Meta`** orqali qilinadi:

```python
class Bolim(models.Model):
    nomi = models.CharField(max_length=50)
    joylashuv = models.CharField(max_length=50, blank=True, null=True)

    class Meta:
        verbose_name_plural = "Bo'limlar"

    def __str__(self):
        return self.nomi
```

Buni qo'shgach, **kutilmagan** narsa sodir bo'ladi — Django, `makemigrations`ni talab qiladi:

```bash
python manage.py makemigrations dokon
```

```
Migrations for 'dokon':
  apps/dokon/migrations/0008_alter_bolim_options.py
    ~ Change Meta options on bolim
```

**Bu — chalkashtiradigan, lekin muhim nuqta:** `verbose_name_plural` — bazaga **hech qanday ta'sir qilmaydi** (`\d dokon_bolim` — bu migratsiyadan oldin ham, keyin ham, **aynan bir xil** bo'ladi, chunki bu — faqat "ko'rsatish nomi", ustun yoki jadval emas). Shunga qaramay, Django, `class Meta`dagi **har qanday** o'zgarishni (hatto sof "kosmetik" bo'lsa ham) migratsiya sifatida yozib qo'yadi — sababi, migratsiya tizimi, faqat bazaviy o'zgarishlarni emas, balki `models.py`ning **to'liq holatini** (Django'ning "model state"i) tarix sifatida saqlaydi, shu jumladan, keyingi migratsiyalar to'g'ri ishlashi uchun kerak bo'lishi mumkin bo'lgan meta-ma'lumotlarni ham.

`migrate`dan so'ng, admin panelida:

```
Dokon
    Bo'limlar          Add  +
```

## Keng tarqalgan xatolar

**Xato 1:** Modelni `models.py`da yaratib, `admin.py`da ro'yxatga olishni unutish.
❌ Model, bazada bor, `shell` orqali ishlatsa bo'ladi — lekin admin panelida **umuman ko'rinmaydi**, hech qanday xato yo'q (bu — chindan ham "jim", chunki Django, "buni admin panelida ko'rsatishni xohlaysizmi" deb so'ramaydi, faqat ro'yxatdan o'tganlarni ko'rsatadi).
✅ Yangi model yaratilganda, darhol, hech bo'lmasa `admin.site.register(YangiModel)` qo'shish — bu, keyinchalik "nega admin panelida ko'rinmayapti" degan, tushunarsiz vaqt yo'qotishning oldini oladi.

**Xato 2:** Bir xil modelni ikki marta ro'yxatga olish (masalan, `admin.py`da tasodifan ikkita `@admin.register(Bolim)` yozish).
❌
```
django.contrib.admin.sites.AlreadyRegistered: The model Bolim is already registered with 'BolimAdmin'
```
✅ Har bir model, `admin.py`da, faqat **bir marta** ro'yxatga olinadi.

**Xato 3:** `list_display`ga, ManyToMany maydonni to'g'ridan-to'g'ri qo'shish.
❌ Agar modelda `ManyToManyField` bo'lsa (bu darslikda hali yo'q, lekin keng tarqalgan holat) va uni `list_display`ga qo'shsangiz (real, sinalgan xato matni):
```
<class 'apps.dokon.admin.MijozAdmin'>: (admin.E109) The value of 'list_display[2]' must not be
a many-to-many field or a reverse foreign key.
```
✅ M2M maydonlar, `list_display`da emas, faqat `filter_horizontal`/`filter_vertical` yoki alohida metod (`xodimlar_soni`ga o'xshab, `.count()` qaytaradigan) orqali ko'rsatiladi — sabab, ro'yxat sahifasida, har bir M2M qiymatni "to'g'ridan-to'g'ri" ustun sifatida chizish, ko'p qatorli va noaniq natija berar edi.

## Mashq/topshiriq

**(Oson)** `Mahsulot` modeli uchun ham, `admin.py`ga, `@admin.register(Mahsulot)` bilan, `list_display = ("nomi", "narxi", "bolim", "ombordagi_soni")` qo'shing. `/admin/dokon/mahsulot/`ga kirib, ustunlar to'g'ri ko'rinishini tekshiring. **Bashorat qiling:** `bolim` ustuni (bu — `ForeignKey`) qanday ko'rinadi — sonmi (`bolim_id`), yo `Bolim.__str__()`ning natijasimi?

**(O'rtacha)** `MahsulotAdmin`ga, `list_editable = ("ombordagi_soni",)` qo'shing — bu, ro'yxat sahifasining o'zida, saytdan chiqmasdan, `ombordagi_soni`ni to'g'ridan-to'g'ri tahrirlash imkonini beradi. `check` ishga tushiring — biror ogohlantirish yoki xato bormi (maslahat: `list_editable`dagi maydon, `list_display`da ham bo'lishi SHART, va odatda, `list_display`dagi **birinchi** ustun bo'la olmaydi)?

**(Qiyin)** `BolimAdmin`ga, `readonly_fields = ("xodimlar_soni",)` qo'shishga urinib ko'ring (`xodimlar_soni` — hisoblangan metod, haqiqiy maydon emas). `/admin/dokon/bolim/1/change/` (tahrirlash) sahifasiga kirib ko'ring — bu ishlaydimi? Nima uchun `readonly_fields`, hisoblangan metodlar bilan ham ishlay olishini, `list_display`dan farqli, tushuntiring.

1.
```python
@admin.register(Mahsulot)
```

`bolim` ustuni — **son (`bolim_id`) emas**, `Bolim.__str__()`ning natijasi ko'rinadi (masalan, "Elektronika"). Sabab — admin, `ForeignKey` maydonlarini ko'rsatishda, avtomatik, bog'langan ob'ektning `__str__()` metodini chaqiradi — aynan 4.1-darsda ko'rgan, `__str__`ning "qulaylik uchun" ekanligi, bu yerda amalda.

2. `check` — xato bermaydi, chunki bizning `list_display`imizda, `ombordagi_soni` — **oxirgi**, birinchi emas: `list_display = ("nomi", "narxi", "bolim", "ombordagi_soni")`. Sahifani ochib ko'rsak, ro'yxatdagi ustun, endi son o'rniga, real, tahrirlanadigan kiritish maydoniga aylanadi:
```html
<input type="number" name="form-1-ombordagi_soni" value="45" class="vIntegerField" id="id_form-1-ombordagi_soni">
```
Lekin agar `ombordagi_soni`ni, `list_display`ning **birinchi** elementiga aylantirsangiz (`list_display = ("ombordagi_soni", "nomi", "narxi", "bolim")`), real, sinalgan xato:
```
<class 'apps.dokon.admin.MahsulotAdmin'>: (admin.E124) The value of 'list_editable[0]' refers to
the first field in 'list_display' ('ombordagi_soni'), which cannot be used unless
'list_display_links' is set.
```
Sabab — birinchi ustun, odatda, qatorni "ochish" (tahrirlash sahifasiga o'tish) havolasi vazifasini bajaradi; uni, bir vaqtning o'zida ham havola, ham to'g'ridan-to'g'ri tahrirlanadigan input qilib bo'lmaydi — bu ikkalasi, HTML darajasida, bir-biriga zid. Xato matni ham, yechimni o'zi aytadi: `list_display_links`ni, boshqa (masalan, `nomi`) ustunga o'rnatib, birinchi ustunni "havola" vazifasidan ozod qilish mumkin.

3. Ishlaydi — `readonly_fields`, `list_display`dan farqli o'laroq, **istalgan metod yoki xususiyatni** qabul qiladi, chunki uning vazifasi — faqat **ko'rsatish** (jadval ustuni emas, bitta obyekt sahifasidagi "yozib bo'lmaydigan maydon"). `xodimlar_soni` metodi, `readonly_fields`ga qo'shilganda, "Bolim"ni tahrirlash sahifasida, boshqa maydonlar (`nomi`, `joylashuv`) qatorida, o'zgartirib bo'lmaydigan, faqat ko'rsatiladigan qiymat sifatida chiqadi. Farqning sababi — `list_display` va `readonly_fields`, admin ichida, **ikkita alohida, mustaqil mexanizm**: biri — jadval ustuni yasaydi, ikkinchisi — forma maydoni yasaydi, va ularning ichki tekshiruv qoidalari ham mos ravishda farq qiladi.

## Qisqacha xulosa

`admin.py` — modelni, tayyor boshqaruv paneliga "ulash" uchun mo'ljallangan, alohida fayl: model bazada bo'lishi, uning admin panelida ko'rinishini kafolatlamaydi — buning uchun, ataylab, `admin.site.register()` yoki `@admin.register()` kerak. `ModelAdmin` klassi (`list_display`, `search_fields`, `list_filter`) — ro'yxat sahifasining tashqi ko'rinishini boshqaradi, va `list_display`, haqiqiy maydonlar bilan bir qatorda, `@admin.display`li **hisoblangan metodlarni** ham qabul qila oladi. `admin.py`dagi xatolar (masalan, mavjud bo'lmagan maydonga ishora) — 5-bobdagi shablon xatolaridan farqli, `check` bosqichida, **darhol va ochiq** aniqlanadi. Model darajasidagi `class Meta` (`verbose_name_plural` kabi) — bazaga ta'sir qilmasa ham, baribir migratsiya talab qiladi, chunki Django, modelning **to'liq holatini**, nafaqat ustunlarini, tarix sifatida kuzatib boradi. Keyingi darsda — `forms.py`ni, foydalanuvchi kiritgan ma'lumotni qanday tekshirishini (validatsiya) o'rganamiz.

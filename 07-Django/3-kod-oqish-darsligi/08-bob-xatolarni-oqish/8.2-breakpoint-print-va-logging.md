# 8.2. `breakpoint()`, `print` va `logging` — xatoni "ushlab", ichini ko'rish

## Bu darsda nimalarni o'rganasiz

- `breakpoint()` — kodni, **aynan kerakli qatorda to'xtatib**, o'zgaruvchilarning haqiqiy qiymatini "jonli" ko'rish usulini
- `print()` bilan debugging — nega tez va qulay, lekin nega, **doim, oxirida, olib tashlash kerak**
- `logging` moduli — `print()`dan farqli, nega **professional loyihalarda standart** hisoblanadi
- Django'ning **standart** logging sozlamasida, `logger.debug()`/`logger.info()`, nega **hech qachon ko'rinmasligini** (real, sinalgan, kutilmagan xulq)

## Nazariy qism

### `breakpoint()` — kodni, aynan shu yerda "muzlatish"

8.1-darsdagi, `ortacha_narx` funksiyasiga qaytamiz:

```python
def ortacha_narx(mahsulotlar):
    jami = sum(m.narxi for m in mahsulotlar)
    soni = len(mahsulotlar)
    breakpoint()
    return jami / soni
```

`breakpoint()` — Python 3.7+da qo'shilgan, o'rnatilgan (built-in) funksiya: u chaqirilgan qatorda, dastur **to'xtaydi**, va sizga, **interaktiv konsol** (`pdb` — Python Debugger) ochiladi. Shu joyda, kodni davom ettirishdan oldin, **istalgan o'zgaruvchining haqiqiy qiymatini** so'rash mumkin:

```
> ortacha_narx()
-> return jami / soni
(Pdb) p jami
600
(Pdb) p soni
3
(Pdb) c
```

Bu yerda, `(Pdb)` — bu, pdb'ning o'z "so'rovi": `p jami` (`print jami`ning qisqartmasi) — `jami` o'zgaruvchisining, **aynan shu daqiqadagi, haqiqiy** qiymatini ko'rsatadi (`600`); `p soni` — xuddi shunday, `soni`ni (`3`). `c` (`continue`) — dasturni, to'xtagan joydan, **davom ettirish** buyrug'i.

### Eng ko'p ishlatiladigan `pdb` buyruqlari

| Buyruq | Ma'nosi |
|---|---|
| `p <ozgaruvchi>` | O'zgaruvchining qiymatini chop etish |
| `n` (`next`) | Keyingi qatorga o'tish (funksiya ichiga "kirmasdan") |
| `s` (`step`) | Keyingi qatorga o'tish, agar u — funksiya chaqiruvi bo'lsa, **uning ichiga kirib** |
| `l` (`list`) | Joriy qator atrofidagi kodni ko'rsatish |
| `c` (`continue`) | Keyingi `breakpoint()`gacha (yoki, oxirigacha) davom ettirish |
| `q` (`quit`) | Debugger'dan, butunlay chiqish |

**Muhim, amaliy maslahat:** `breakpoint()`, **faqat, lokal (`runserver`) ishga tushirilgan, terminal orqali kuzatilayotgan** kodda ishlaydi — u, brauzerdagi so'rovni "kutib turadi" (chunki, HTTP so'rov, `breakpoint()`ga yetganda, javob qaytmaguncha, "muallaqlik"da qoladi), va siz, **terminalning o'zida**, `(Pdb)` so'rovini ko'rasiz. Production (haqiqiy, foydalanuvchilarga ochiq) serverda, `breakpoint()` qoldirib ketish — **jiddiy xato**: server, birinchi so'rovdayoq, "muzlab qoladi".

### `print()` bilan debugging — tez, lekin "iflos"

Eng oddiy, ko'pchilik dastlab ishlatadigan usul:

```python
def ortacha_narx(mahsulotlar):
    jami = sum(m.narxi for m in mahsulotlar)
    soni = len(mahsulotlar)
    print(f"DEBUG: jami={jami}, soni={soni}")   # vaqtinchalik, debugging uchun
    return jami / soni
```

Bu — 3.1-darsda, siz **o'zingiz sinab ko'rgan** usul (middleware ichida, so'rov/javobni kuzatish uchun). U, tez va sodda, lekin, ikkita jiddiy kamchiligi bor: (1) **uni, ishni tugatgach, albatta, qo'lda olib tashlash kerak** — aks holda, u, keyingi darslarda ko'rganimizdek (2-3-boblarda, biz haqiqatan ham, shu turdagi "unutilgan" `print()`larni topib, tozalagan edik!), production konsolni "chiqindiga to'ldiradi"; (2) uni, **darajalarga ajratib bo'lmaydi** — masalan, "faqat jiddiy muammolarni ko'rsat, mayda tafsilotlarni yashir" kabi, moslashuvchan boshqaruv yo'q.

### `logging` — `print()`ning, "professional" o'rnini bosuvchisi

```python
import logging

logger = logging.getLogger(__name__)


def bolim_ortacha_narxi(request, bolim_id):
    bolim = get_object_or_404(Bolim, id=bolim_id)
    mahsulotlar = list(bolim.mahsulotlar.all())
    logger.warning(
        "bolim_ortacha_narxi chaqirildi: bolim_id=%s, mahsulotlar soni=%s",
        bolim_id, len(mahsulotlar),
    )
    ortacha = ortacha_narx(mahsulotlar)
    return HttpResponse(f"{bolim.nomi}: o'rtacha narx = {ortacha} so'm")
```

`logging.getLogger(__name__)` — har bir faylda, **o'sha faylga tegishli** logger yaratadi (`__name__` — Python'ning, "joriy modul nomi" o'zgaruvchisi, masalan, `apps.dokon.views`) — bu, keyinchalik, "aynan qaysi fayldan kelgan xabar" ekanini bilish imkonini beradi. `logger.warning(...)` — xabarni, **`WARNING` darajasida** yozadi. Python'da, standart, besh daraja bor (pastdan yuqoriga): `DEBUG` < `INFO` < `WARNING` < `ERROR` < `CRITICAL`.

**Diqqat qiling — `f-string` emas, `%s`:** `logger.warning("...%s...", bolim_id, ...)` — bu, `logger.warning(f"...{bolim_id}...")`dan farqli, **ataylab** shunday yozilgan: `%s` uslubida, satr, faqat, **xabar chindan ham chop etiladigan bo'lsa** (ya'ni, logger darajasi, shu xabarni "o'tkazsa"), formatlanadi — `f-string` esa, **har doim, oldindan** hisoblanadi, hatto, xabar hech qachon ko'rsatilmasa ham. Katta, tez-tez chaqiriladigan kodda, bu farq, ishlash tezligiga (performance) ta'sir qilishi mumkin.

## Kodni o'qish mashqi

Yuqoridagi `bolim_ortacha_narxi`ga, to'rtta, turli darajadagi log yozuvini qo'shamiz:

```python
logger.debug("DEBUG: bolim_id=%s", bolim_id)
logger.info("INFO: bolim_id=%s", bolim_id)
logger.warning("WARNING: bolim_id=%s", bolim_id)
logger.error("ERROR: bolim_id=%s", bolim_id)
```

Loyihaning `settings.py`sida, `LOGGING` degan, **maxsus sozlama umuman yo'q** (bu, ko'p, kichik/o'rta loyihalarda, odatiy holat). **Bashorat qiling:** server konsolida, ushbu to'rtta qatordan, **nechtasi** ko'rinadi — barchasi, birortasi ham yo'q, yoki, faqat ba'zilari?

<details>
<summary>Javobni ko'rish</summary>

Faqat **ikkitasi** ko'rinadi — `WARNING` va `ERROR`:

```
WARNING: bolim_id=3
ERROR: bolim_id=3
```

`DEBUG` va `INFO` — **umuman, hech qanday shaklda ko'rinmaydi**, hech qanday xato yoki ogohlantirishsiz! Sabab — Python'ning `logging` moduli, agar **aniq sozlanmagan bo'lsa**, standart ravishda, faqat, `WARNING` va undan **yuqori** (`ERROR`, `CRITICAL`) darajadagi xabarlarni ko'rsatadi; `DEBUG` va `INFO` — standart holatda, **"jim" o'tkazib yuboriladi**. Bu — 5-bobda ko'rgan, shablonlarning "mavjud bo'lmagan o'zgaruvchi — jim, bo'sh natija" xulqiga juda o'xshash, yana bir, **"jim xato" (yoki, bu holda, "jim yo'qolish") manbai**: ko'p yangi boshlovchi, `logger.info("...")` yozib, "nega konsolda hech narsa ko'rinmayapti" deb, ancha vaqt sarflaydi — sabab esa, oddiy: standart daraja, `INFO`dan yuqori.

## Amaliy misol

Uchta usulni, bitta, real muammoni "tekshirish" vazifasida solishtiramiz: `bolim_ortacha_narxi`, nima uchun, ba'zan, kutilganidan boshqacha natija berayotganini bilishimiz kerak deb faraz qilaylik.

**1-usul — `breakpoint()` bilan** (real, sinalgan sessiya, soddalashtirilgan misolda):
```python
>>> jami = sum(m for m in [100, 200, 300])
>>> soni = len([100, 200, 300])
>>> breakpoint()
```
```
> /tmp/pdb_test.py(5)ortacha_narx()
-> return jami / soni
(Pdb) p jami
600
(Pdb) p soni
3
(Pdb) c
```
Bu — **eng aniq** usul: siz, funksiya ichida, **aynan o'sha daqiqadagi**, haqiqiy qiymatlarni ko'rasiz, hech narsani "taxmin qilishga" hojat yo'q. Kamchiligi — HTTP so'rov orqali sinashda, terminal (server konsoli)ga, doimiy ravishda, **qo'l yetkazish** kerak.

**2-usul — `print()` bilan**: tez, lekin, sinovdan so'ng, **albatta, qo'lda olib tashlash** kerak (3.1-darsdagi middleware misolidagi kabi).

**3-usul — `logging` bilan**: agar `logger.warning(...)` (yoki undan yuqori daraja) ishlatilsa — xabar, konsolda **doimiy** ko'rinadi, va, `print()`dan farqli, uni, keyinchalik, kodda **qoldirib ketish** — muammo emas (chunki, production'da, `LOGGING` sozlamasi orqali, darajani boshqarish mumkin — masalan, faqat `ERROR`dan yuqorisini ko'rsatish, `WARNING`larni esa, fayl yoki maxsus tizimga yo'naltirish).

## Keng tarqalgan xatolar

**Xato 1:** `breakpoint()`ni, kodga qoldirib, uni commit qilish (yoki, production'ga chiqarish).
❌ Server, birinchi so'rovda, "osilib qoladi" — hech qanday xato xabari yo'q, shunchaki, javob **hech qachon kelmaydi** (chunki, u, ko'rinmas terminalda, `(Pdb)` buyruqni "kutmoqda").
✅ `breakpoint()`ni, faqat, **lokal, o'z terminalingizda**, vaqtinchalik ishlatish; sinovdan so'ng, darhol olib tashlash — xuddi, `print()` kabi.

**Xato 2:** `logger.info()` yoki `logger.debug()` yozib, "nega ko'rinmayapti" deb, soatlab vaqt sarflash.
❌ Yuqorida ko'rganimizdek, bu — **standart** xulq, xato emas.
✅ Agar, chindan ham, `DEBUG`/`INFO` darajasidagi xabarlarni ko'rish kerak bo'lsa, `settings.py`da, `LOGGING` sozlamasini, mos darajaga (`"level": "DEBUG"`) sozlash kerak — yoki, tezroq tekshirish uchun, vaqtincha, `logger.warning(...)` ishlatish (7.1-darsdagi "sinash uchun vaqtincha o'zgartirish, keyin qaytarish" uslubiga o'xshab).

**Xato 3:** `logger.warning(f"bolim_id={bolim_id}")` kabi, `%s` o'rniga, `f-string` ishlatish odatini shakllantirish.
❌ Bu, funksional jihatdan, ko'p hollarda ishlaydi, lekin, yuqorida tushuntirilgan, "hisoblash — har doim, xabar ko'rsatilishidan qat'i nazar, bajariladi" muammosini keltirib chiqaradi — ayniqsa, agar loglanadigan qiymat, **o'zi ham, qimmat hisoblash natijasi** bo'lsa (masalan, katta QuerySet'ning `str()`i).
✅ `logging`ning o'z, `%s`-uslubidagi formatlashidan foydalanish — bu, kichik, lekin, professional loyihalarda, muhim sanaladigan farq.

## Mashq/topshiriq

**(Oson)** `bolim_ortacha_narxi`ga, `logger.error(...)` qo'shib, uni, faqat, `mahsulotlar` ro'yxati **bo'sh bo'lganda** (ya'ni, keyingi qatorda, `ZeroDivisionError` chiqishidan OLDIN) chaqiring — bu, xato **sodir bo'lishidan oldin**, "nima uchun, u sodir bo'lishini" konsolga yozib qo'yadigan, foydali odat.

**(O'rtacha)** `ortacha_narx` funksiyasiga, `breakpoint()` qo'ying va, `python manage.py shell`da, uni, bo'sh ro'yxat bilan chaqiring: `ortacha_narx([])`. Debugger ochilgach, `p jami` va `p soni`ni tekshiring — `soni`, nechaga teng ekanini ko'rib, `ZeroDivisionError`ning sababini, **kodni o'zgartirmasdan, faqat kuzatish orqali** tasdiqlang. Keyin, `c` bilan davom ettiring — endi, nima bo'ladi?

**(Qiyin)** `settings.py`ga, quyidagi, minimal `LOGGING` sozlamasini qo'shing:
```python
LOGGING = {
    "version": 1,
    "disable_existing_loggers": False,
    "handlers": {"console": {"class": "logging.StreamHandler"}},
    "root": {"handlers": ["console"], "level": "DEBUG"},
}
```
Shundan so'ng, avvalgi (8.2-darsdagi) `logger.debug(...)` va `logger.info(...)` qatorlarini qayta sinang. **Bashorat qiling:** endi, ular ko'rinadimi? `"root": {"level": "DEBUG"}` qatorining, aniq nima qilishini, tushuntiring.

## Qisqacha xulosa

`breakpoint()` — kodni, aynan kerakli qatorda to'xtatib, o'zgaruvchilarning haqiqiy qiymatini, interaktiv `pdb` konsoli orqali ko'rish imkonini beradi — eng aniq, lekin, faqat lokal ishlatiladigan usul. `print()` — tez, lekin, uni, doim, qo'lda, sinovdan keyin olib tashlash kerak (aks holda, u, kodda "chiqindi" bo'lib qoladi — bu darslikda, buni bir necha marta, real holatlarda ko'rdik). `logging` — professional standart: darajalarga (`DEBUG`/`INFO`/`WARNING`/`ERROR`/`CRITICAL`) bo'lingan, va, kodda **qoldirib ketish mumkin bo'lgan** (chunki, darajani, `settings.py` orqali boshqarish mumkin) yechim — lekin, standart sozlamada, faqat `WARNING` va undan yuqori xabarlar ko'rinishini bilish, muhim: aks holda, `logger.debug()`/`logger.info()`, hech qanday xatosiz, "jim" yo'qolib ketadi. Shu bilan, 08-bob (xatolarni o'qish va debug qilish) yakunlandi — keyingi bo'limda, mavjud kodni, **buzmasdan, xavfsiz o'zgartirish** mahoratini o'rganamiz.

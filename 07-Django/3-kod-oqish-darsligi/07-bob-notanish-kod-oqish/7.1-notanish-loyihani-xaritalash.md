# 7.1. Notanish loyihani birinchi marta ochish — sistematik xarita

## Bu darsda nimalarni o'rganasiz

- Siz **hech qachon ko'rmagan**, real Django loyihasini (`kutubxona_api`) sistematik tarzda "xaritalash" usulini
- Loyihalar, `onlayn_dokon`dagidan **boshqacha** tuzilishga ega bo'lishi mumkinligini (papka nomlari, app joylashuvi) — va bu, kod o'qish ko'nikmangizga xalaqit bermasligi kerakligini
- **Signal** — bu, urls.py/views.py zanjirida ko'rinmaydigan, lekin baribir ishlaydigan koddir, va uni qanday "qidirib topish" kerak
- Custom `Manager` — modelga, standart `.objects`dan tashqari, qo'shimcha "filtrlangan eshik" qo'shish usuli

## Nazariy qism

### Yangi qoida: bu safar, siz yozmagansiz

00-06-boblarda, har bir qatorni, **siz bilan birga**, nolinchidan yozdik. Endi — boshqacha vaziyat: `kutubxona_api` — tayyor, ishlaydigan loyiha, siz uni **birinchi marta ko'rayapsiz**, xuddi ishga yangi kelib, "mana, bizning loyiha, o'zing o'rganib ol" deyilgandek. Bu — dasturchilik amaliyotida, **eng ko'p uchraydigan** holat: kod yozishdan ko'ra, ko'pincha, **boshqa birov yozgan kodni o'qish va tushunish** talab qilinadi.

### 1-qadam: fayl daraxtini ko'rish — lekin xulosaga shoshilmang

```
kutubxona_api/
├── manage.py
├── sozlamalar/
│   ├── settings.py
│   ├── urls.py
│   └── wsgi.py
├── kitoblar/
│   ├── models.py
│   ├── views.py
│   ├── serializers.py
│   ├── urls.py
│   └── admin.py
└── azolar/
    ├── models.py
    ├── views.py
    ├── urls.py
    ├── signals.py
    └── admin.py
```

**Diqqat qiling:** bu loyihada, sozlamalar papkasi — `config` emas, **`sozlamalar`** deb nomlangan, va app'lar, `onlayn_dokon`dagidek `apps/` ichida emas, **loyiha ildizida, to'g'ridan-to'g'ri** joylashgan (`apps/dokon/...` emas, shunchaki `kitoblar/...`). Bu — **ataylab qilingan**: real hayotda, har bir jamoa/dasturchi, biroz boshqacha nomlash va tuzilish tanlashi mumkin. Agar sizning "kod o'qish" ko'nikmangiz, faqat `config`/`apps/` nomlariga **o'rganib qolgan** bo'lsa — bu, sizni chalkashtirib qo'yishi mumkin. To'g'ri yondashuv: **nomlarga emas, tuzilmaga va bog'liqliklarga** e'tibor berish — 2-bobda ko'rgan `INSTALLED_APPS` va import-graf qoidalari, nom qanday bo'lishidan qat'i nazar, **har doim amal qiladi**.

### 2-qadam: `settings.py` — qaysi app'lar "ishga tushirilgan"

```python
INSTALLED_APPS = [
    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
    "django.contrib.sessions",
    "django.contrib.messages",
    "django.contrib.staticfiles",
    "rest_framework",
    "kitoblar",
    "azolar",
]
```

Bu yerda, **yangi, tanish bo'lmagan** nom bor: `"rest_framework"` — bu, `onlayn_dokon`da ishlatilmagan, **Django REST Framework** (DRF) kutubxonasi — API (dasturiy interfeys) yaratish uchun, alohida, keng tarqalgan kutubxona. Uning borligi, bizga darhol signal beradi: **bu loyihada, kamida bitta app, oddiy HTML sahifalar o'rniga (yoki bilan bir qatorda), JSON API taqdim etadi**. Buni, keyingi qadamlarda tasdiqlaymiz.

### 3-qadam: ildiz `urls.py` — kirish nuqtalari

```python
urlpatterns = [
    path("admin/", admin.site.urls),
    path("api/", include("kitoblar.urls")),
    path("azolar/", include("azolar.urls")),
]
```

Ikkita app ham, `include()` orqali ulangan (2-bobda ko'rgan naqsh) — lekin **prefikslar** e'tiborga molik: `kitoblar` — `/api/` prefiksi bilan (DRF taxminimizni tasdiqlaydi — "api" so'zi, odatda, JSON API'ni bildiradi), `azolar` — oddiy `/azolar/` prefiksi bilan (bu, ehtimol, oddiy, HTML/JSON qaytaruvchi function-based view'lar bo'lishi mumkin).

### 4-qadam: har bir app uchun — `models.py` birinchi (bu safar!)

**Muhim eslatma:** 2-bobda o'rgangan import-graf qoidasi bo'yicha, kod **ishga tushish tartibi** — `urls.py → views.py → models.py`. Lekin **notanish** loyihani o'rganishda, ko'pincha **teskari tartib** qulayroq: avval `models.py`ni o'qib, "bu loyiha, qanday ma'lumot bilan ishlaydi" degan **domen xaritasi**ni tuzib olish, so'ng `urls.py`/`views.py`ga o'tish — chunki modellar, odatda, eng "barqaror" va "domenga yaqin" qism (7-bobning o'ziga xos, amaliy maslahati).

```python
# kitoblar/models.py
class Muallif(models.Model):
    ism = models.CharField(max_length=50)
    familiya = models.CharField(max_length=50)


class Kitob(models.Model):
    sarlavha = models.CharField(max_length=200)
    muallif = models.ForeignKey(Muallif, on_delete=models.CASCADE, related_name="kitoblar")
    nashr_yili = models.IntegerField()
    nusxalar_soni = models.IntegerField(default=1)
    band_qilingan_soni = models.IntegerField(default=0)

    @property
    def mavjud_nusxalar(self):
        return self.nusxalar_soni - self.band_qilingan_soni
```

Bu yerda, **yangi narsa** bor: `@property`. Buni satrma-satr o'qiymiz: `nusxalar_soni` va `band_qilingan_soni` — bular, haqiqiy, bazada saqlanadigan ustunlar (4-bobda ko'rgan oddiy maydonlar). Lekin `mavjud_nusxalar` — **bazada ustun sifatida yo'q**! U, `@property` dekoratori bilan belgilangan, oddiy Python metodi, lekin **qavssiz** chaqiriladigan qilib "niqoblangan" (`kitob.mavjud_nusxalar`, `kitob.mavjud_nusxalar()` emas). Bu — 5.2-darsda ko'rgan, shablon tilining "nuqta orqali, metod ham chaqirilaveradi" qoidasidan farqli, **Python'ning o'zidagi** mexanizm: `@property`, oddiy atributga o'xshab **o'qiladigan**, lekin aslida, har safar **hisoblab chiqariladigan** qiymat yaratadi. Bu yerda: "mavjud nusxalar" — hech qachon, alohida, o'zi saqlanmaydi, u, doim, ikkita boshqa maydondan **jonli hisoblanadi** — bu, ma'lumotlar bazasi darajasida, "ikki joyda bir xil ma'lumotni saqlash" (va ular sinxron emasligi xavfi)ning oldini oladigan, yaxshi amaliyot.

```python
# azolar/models.py
from kitoblar.models import Kitob


class Azo(models.Model):
    ism = models.CharField(max_length=50)
    familiya = models.CharField(max_length=50)
    email = models.EmailField(unique=True)


class FaolIjaralarManager(models.Manager):
    def get_queryset(self):
        return super().get_queryset().filter(qaytarilgan_sana__isnull=True)


class Ijara(models.Model):
    azo = models.ForeignKey(Azo, on_delete=models.CASCADE, related_name="ijaralar")
    kitob = models.ForeignKey(Kitob, on_delete=models.CASCADE, related_name="ijaralar")
    olingan_sana = models.DateTimeField(auto_now_add=True)
    qaytarilgan_sana = models.DateTimeField(null=True, blank=True)

    objects = models.Manager()
    faol = FaolIjaralarManager()
```

Ikkita yangi narsa: (1) `from kitoblar.models import Kitob` — **app'lararo import** (`azolar`, `kitoblar`ga bog'liq — bu, 4.2-darsdagi, migratsiyalar orasidagi bog'liqlik-graf g'oyasining, endi **Python import** darajasidagi ko'rinishi: `azolar`, `kitoblar`dan **keyin** yuklanishi kerak, va aynan shuning uchun, `INSTALLED_APPS`da, `"kitoblar"`, `"azolar"`dan **oldin** turibdi — bu, tasodif emas!). (2) `FaolIjaralarManager(models.Manager)` — **custom manager**: `Ijara.objects` — barcha ijaralarni qaytaradigan, standart manager; `Ijara.faol` — **faqat, hali qaytarilmagan** (`qaytarilgan_sana__isnull=True`) ijaralarni qaytaradigan, **qo'shimcha, filtrlangan "eshik"**. Ikkalasi ham, bir xil jadvalga ishora qiladi, lekin `Ijara.faol.all()`, avtomatik ravishda, faqat faol yozuvlarni qaytaradi — buni chaqirayotgan kod, hech qanday qo'shimcha `.filter()` yozmasdan.

## Kodni o'qish mashqi

`azolar/apps.py`da, quyidagi, g'ayrioddiy qatorni ko'rasiz:

```python
class AzolarConfig(AppConfig):
    default_auto_field = "django.db.models.BigAutoField"
    name = "azolar"

    def ready(self):
        import azolar.signals  # noqa: F401
```

Bu — `AppConfig`ning `ready()` metodi (2-bobda, bilvosita eslatilgan, lekin chuqur ko'rilmagan). `import azolar.signals` — bu, boshqa importlardan farqli, hech qanday nom (`from ... import X`) olib kelmaydi, faqat, faylni **ishga tushiradi** (bajaradi). **Bashorat qiling:** `azolar/signals.py`da, quyidagi kod bor:

```python
@receiver(post_save, sender=Ijara)
def ijara_yaratilganda_kitobni_band_qilish(sender, instance, created, **kwargs):
    if created:
        kitob = instance.kitob
        kitob.band_qilingan_soni += 1
        kitob.save()
```

Bu funksiya, `azolar/views.py`da yoki `kitoblar/views.py`da, **hech qayerda, to'g'ridan-to'g'ri chaqirilmaydi**. Savol: `Ijara.objects.create(...)` chaqirilganda (masalan, `kitob_olish` view'ida), `Kitob.band_qilingan_soni` avtomatik oshadimi, yo'qmi? Agar oshsa — **qanday qilib**, hech qanday to'g'ridan-to'g'ri chaqiruvsiz?

<summary>Javobni ko'rish</summary>

**Ha, avtomatik oshadi** — bu, real, sinalgan xulq. Sabab — bu, **signal** deb ataladigan mexanizm: `@receiver(post_save, sender=Ijara)` dekoratori, `ijara_yaratilganda_kitobni_band_qilish` funksiyasini, "har safar, `Ijara` modelidan **YANGI YOKI YANGILANGAN** obyekt saqlanganda (ya'ni, `.save()` chaqirilganda — bu, `post_save` signali), meni avtomatik chaqir" deb, Django'ning ichki "e'lon-obuna" tizimiga **ro'yxatdan o'tkazadi**. `azolar/apps.py`dagi `ready()` metodi — bu ro'yxatdan o'tkazish kodi (`@receiver` dekoratori) **ishga tushishi** uchun zarur: agar `signals.py` fayli, hech qayerda **import qilinmasa**, Python, uni umuman o'qimaydi, va dekoratordagi kod **hech qachon bajarilmaydi** — signal "ro'yxatga olinmagan" bo'lib qoladi.

**Bu — darslikning eng muhim, yakuniy saboqlaridan biri:** ba'zi kod, `urls.py → views.py → models.py` zanjirida **umuman ko'rinmaydi**, lekin baribir, har bir so'rovda ishlaydi. Bunday kodni topish uchun, `views.py`ni o'qishning o'zi YETARLI EMAS — `models.py`ning yonida, `signals.py`, `apps.py`dagi `ready()` metodini ham, **alohida, ataylab** qidirish kerak. Bu, "notanish loyihada adashib qolish"ning eng keng tarqalgan sababi — va aynan shuning uchun, bu bo'lim, darslikning maxsus, alohida qismi.

</details>

## Amaliy misol

To'liq zanjirni, real HTTP so'rovlar bilan kuzatamiz. Boshlang'ich holat: "Mehrobdan chayon" kitobi, `nusxalar_soni=1`, `band_qilingan_soni=0`.

```bash
curl http://localhost:8001/azolar/1/olish/2/
```
```json
{"xabar": "Kitob muvaffaqiyatli olindi", "kitob": "Mehrobdan chayon", "qolgan_mavjud_nusxalar": 0}
```

Real bazani tekshiramiz (`views.py`da, `band_qilingan_soni`ni oshiruvchi hech qanday kod **yo'q** — faqat `Ijara.objects.create(...)`):

```bash
curl http://localhost:8001/api/kitoblar/2/
```
```json
{"id": 2, "sarlavha": "Mehrobdan chayon", ..., "band_qilingan_soni": 1, "mavjud_nusxalar": 0}
```

`band_qilingan_soni` — `0`dan `1`ga o'zgargan, garchi `kitob_olish` view funksiyasi, `models.py`dagi `Kitob`ni **umuman tegmasa** ham! Bu — yuqoridagi signalning, amalda ishlashi. Endi, shu kitobni yana olishga urinamiz:

```bash
curl http://localhost:8001/azolar/1/olish/2/
```
```
Bu kitobning mavjud nusxasi qolmagan.
```
```
STATUS: 400
```

`kitob.mavjud_nusxalar` (`@property`) — `1 - 1 = 0`, shuning uchun `kitob_olish` view'idagi `if kitob.mavjud_nusxalar <= 0` sharti ishga tushadi. Endi, `Ijara.faol` custom manager'ini sinaymiz:

```bash
curl http://localhost:8001/azolar/1/faol-ijaralar/
```
```json
{"azo": "Sardor Aliyev", "faol_ijaralar": [{"kitob": "Mehrobdan chayon", "olingan_sana": "..."}]}
```

Kitobni qaytarganimizdan so'ng (`views.py`da, bu safar, `band_qilingan_soni -= 1`, **signalsiz, to'g'ridan-to'g'ri, view ichida**):

```bash
curl http://localhost:8001/azolar/ijara/1/qaytarish/
curl http://localhost:8001/azolar/1/faol-ijaralar/
```
```json
{"azo": "Sardor Aliyev", "faol_ijaralar": []}
```

**Diqqat qiling — bu, muhim, nozik dizayn qarori (va u yaxshimi, yo'qmi, deb o'ylab ko'ring):** kitob **olinganda**, `band_qilingan_soni` — **signal orqali, avtomatik** oshadi; lekin kitob **qaytarilganda**, xuddi shu maydon — **`kitob_qaytarish` view'ining o'zida, to'g'ridan-to'g'ri kamayadi**, signal orqali emas! Bu — **assimetriya**: bir xil maydonni o'zgartiruvchi ikkita amal, ikkita **butunlay boshqa mexanizm** orqali ishlaydi. Bu, real loyihalarda ham uchraydigan holat — va aynan shuning uchun ham, kod o'qishda, "bitta joyda ko'rgan naqshni, hamma joyda ham shunday deb taxmin qilish" — xavfli odat.

## Keng tarqalgan xatolar

**Xato 1:** Signal faylini yozib, lekin uni `apps.py`ning `ready()`ida import qilishni unutish.
❌ `azolar/signals.py` yozilgan, lekin `AzolarConfig.ready()` — bo'sh (yoki umuman yo'q).
Natija: **hech qanday xato chiqmaydi** — kod, sintaktik jihatdan to'g'ri, lekin `@receiver` dekoratori **hech qachon ishga tushmaydi**, chunki fayl umuman import qilinmagan. `Ijara.objects.create(...)` chaqirilganda, `band_qilingan_soni` — **o'zgarmay qoladi**, hech qanday xato yoki ogohlantirishsiz.
✅ Har bir yangi `signals.py` yozilganda, darhol, `apps.py`ning `ready()`iga, `import <app_nomi>.signals` qatorini qo'shishni **odat qilib olish**.

**Xato 2:** `post_save` signalida, `instance.save()`ni, **cheksiz tsikl** hosil qiladigan tarzda chaqirish.
❌
```python
@receiver(post_save, sender=Kitob)
def notogri_signal(sender, instance, **kwargs):
    instance.nusxalar_soni += 1
    instance.save()   # bu .save(), YANA post_save signalini ishga tushiradi!
```
Bu, `RecursionError: maximum recursion depth exceeded` bilan yakunlanadi — chunki `instance.save()`, o'zi, yana `post_save` signalini yuboradi, u yana shu funksiyani chaqiradi, va hokazo, cheksiz.
✅ Signal ichida, **shu signalni yana ishga tushiradigan** modelni emas, balki (bizning holatimizdagi kabi) **BOSHQA** modelni (`instance.kitob`, ya'ni `Kitob`, `Ijara`ning `post_save`i emas) saqlash — yoki, agar shart bo'lsa, `update_fields` va signal ichida qo'shimcha tekshiruv bilan, ehtiyotkorlik bilan yozish.

**Xato 3:** `Ijara.objects.all()`ni ishlatib, keyin qo'lda `.filter(qaytarilgan_sana__isnull=True)` yozish — `Ijara.faol` borligini bilmasdan.
❌ Bu, xato emas, lekin **kodni ikki marta yozish** (DRY qoidasini buzish) — agar "faol ijara" mantig'i keyinchalik o'zgarsa (masalan, "30 kundan ortiq muddatga cho'zilgan ijaralar — faol emas" qoidasi qo'shilsa), uni **har bir joyda, alohida** yangilash kerak bo'ladi.
✅ Notanish loyihada, yangi so'rov yozishdan oldin, modelning o'zida (yoki uning yonidagi fayllarda), **tayyor custom manager yoki metod bor-yo'qligini** tekshirish — bu, "notanish kodni o'qish" ko'nikmasining, amaliy foydasi.

## Mashq/topshiriq

**(Oson)** `kitoblar/models.py`ga, `Muallif`ga yangi `@property` qo'shing: `kitoblar_soni`, u, muallifning nechta kitobi borligini qaytarsin (maslahat: 4.2-darsda ko'rgan `related_name` — `self.kitoblar.count()`). `shell`da, `Muallif.objects.get(id=1).kitoblar_soni`ni chaqirib tekshiring.

**(O'rtacha)** `azolar/signals.py`ga, yangi signal qo'shing — `Azo` modeli **o'chirilganda** (`post_delete`), konsolga (`print()` orqali) "Azo o'chirildi: <ism>" deb chop etadigan. Buni ro'yxatdan o'tkazishni unutmang (`apps.py`). **Bashorat qiling:** agar siz, bu signalni, `azolar/signals.py`ga emas, tasodifan, `kitoblar/signals.py` (yangi fayl)ga yozib qo'ysangiz-u, uni hech qayerda import qilmasangiz — nima bo'ladi?

**(Qiyin)** Hozirgi loyihada, `kitob_qaytarish` view'i, `band_qilingan_soni`ni **qo'lda** kamaytiradi (signalsiz). Buni, "Amaliy misol"da muhokama qilingan **assimetriyani yo'qotib**, signalga o'tkazing: `Ijara.qaytarilgan_sana`, `None`dan biror sanaga o'zgarganda (`post_save`, lekin `created=False` holatda), `Kitob.band_qilingan_soni`ni kamaytiruvchi, yangi signal yozing. Buni yozgach, `kitob_qaytarish` view'idan, `band_qilingan_soni -= 1; kitob.save()` qatorlarini olib tashlang va, funksionallik hali ham to'g'ri ishlashini (real so'rovlar bilan) tasdiqlang.

## Qisqacha xulosa

Notanish loyihani o'qishda, birinchi qadam — fayl nomlariga emas, **tuzilma va bog'liqliklarga** e'tibor berish (`config`/`sozlamalar`, `apps/`/ildizda — bular, shaxsiy tanlov, mohiyat emas). `INSTALLED_APPS`dagi tartib, app'lar orasidagi bog'liqlikni ko'rsatadi (4.2-darsdagi migratsiya-bog'liqligiga o'xshab). Eng muhim, yangi saboq — **signal**lar: `post_save`/`post_delete` orqali ro'yxatga olingan funksiyalar, `views.py`da hech qanday to'g'ridan-to'g'ri chaqiruvsiz, avtomatik ishlaydi, va ularni topish uchun, `models.py`ning yonida, `signals.py` va `apps.py`dagi `ready()` metodini **alohida qidirish** kerak — aks holda, kodning butun bir qismi, "ko'rinmas" bo'lib qoladi. `@property` va custom `Manager` (`Ijara.faol`) — modelga, bazada saqlanmaydigan, lekin "atribut kabi" ishlatiladigan, qo'shimcha, hisoblangan yoki filtrlangan qulayliklar qo'shadi. Keyingi darsda — shu loyihaning DRF (Django REST Framework) qismini, ya'ni `serializers.py` va `ModelViewSet`ni, **butunlay yangi naqsh** sifatida o'qiymiz.

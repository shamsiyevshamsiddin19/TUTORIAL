# 3.1. So'rov hayot yo'li — URL'dan Response'gacha (markaziy dars)

## Bu darsda nimalarni o'rganasiz

- Bitta HTTP so'rovi, Django ichida **aniq qaysi tartibda**, qaysi fayllar orqali o'tishini, `print()` orqali **ko'z bilan ko'rasiz**
- `urls.py` va middleware'ning `__init__` qismi **faqat server ishga tushganda, bir marta** ishlashini, `view` esa **har bir so'rovda, qayta-qayta** ishlashini isbotlaysiz
- Middleware'ning "so'rovni o'rab olish" (`before` va `after`) mexanizmini, o'z middleware'ingizni yozib, ichidan tushunasiz
- Bu bilim orqali, istalgan notanish Django loyihasida, "so'rov qayerdan boshlanib, qayerda tugaydi"ni tezda **xaritalash** ko'nikmasiga ega bo'lasiz

## Nazariy qism

### Nega bu dars — darslikning markazi

Oldingi darslarda biz alohida-alohida fayllarni (`settings.py`, `urls.py`, app fayllari) o'qidik. Lekin **haqiqiy kodni o'qish mahorati** — bu, fayllarni alohida-alohida emas, balki ular **bir so'rov davomida qanday hamkorlik qilishini** ko'ra bilishdir. Aynan shu — notanish Django loyihasini ochganingizda, birinchi so'raladigan savol: *"Brauzerda biror manzil ochilganda, kod aniq qaysi fayldan boshlanib, qaysi ketma-ketlikda ishlaydi?"*

### Nazariy sxema — avval so'zda

```
1. Brauzer (yoki curl) — HTTP so'rov yuboradi
2. Django serveri — so'rovni qabul qiladi
3. MIDDLEWARE zanjiri — so'rov, ro'yxat bo'ylab, YUQORIDAN PASTGA o'tadi (har biri "before" qismini bajaradi)
4. URL RESOLVER (urls.py'lar) — manzilga mos VIEW'ni topadi
5. VIEW — ishlaydi, javob (HttpResponse) tayyorlaydi
6. MIDDLEWARE zanjiri — javob, endi PASTDAN YUQORIGA, teskari tartibda o'tadi (har biri "after" qismini bajaradi)
7. Django — tayyor javobni brauzerga qaytaradi
```

Bu — **nazariya**. Endi buni, o'zimiz yozgan kod orqali, **haqiqatan ko'ramiz** — bu, taxmin qilish emas, kuzatish.

### 1-qadam: `urls.py`ga "signal" qo'yamiz

`apps/dokon/urls.py` faylining eng yuqorisiga, oddiy `print()` qo'shamiz:

```python
from django.urls import path
from . import views

print(">>> apps/dokon/urls.py YUKLANMOQDA (bu faqat SERVER ISHGA TUSHGANDA chiqadi)")

app_name = "dokon"

urlpatterns = [
    path("", views.bosh_sahifa, name="bosh-sahifa"),
    path("haqida/", views.haqida_sahifasi, name="haqida"),
]
```

### 2-qadam: `views.py`ga "signal" qo'yamiz

```python
from django.http import HttpResponse


def bosh_sahifa(request):
    print(">>> VIEW ishga tushdi: bosh_sahifa()")
    return HttpResponse("Onlayn do'kon — bosh sahifa")
```

### 3-qadam: o'zimizning middleware'imizni yozamiz

Yangi fayl — `apps/dokon/middleware.py`:

```python
class SoravniKuzatishMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response
        print(">>> MIDDLEWARE yaratildi (bu faqat SERVER ISHGA TUSHGANDA, bir marta)")

    def __call__(self, request):
        print(f">>> MIDDLEWARE: so'rov KELDI — {request.path}")
        response = self.get_response(request)
        print(f">>> MIDDLEWARE: javob KETMOQDA — status {response.status_code}")
        return response
```

Buni **satrma-satr** o'qiymiz: Django middleware — bu, aslida, oddiy Python klassi, ikkita "burchakka" ega: `__init__(self, get_response)` — **faqat bir marta**, server ishga tushganda chaqiriladi (`get_response` — "zanjirdagi keyingi qadam"ni ifodalovchi funksiya, uni middleware o'zida saqlab qo'yadi); `__call__(self, request)` — **har bir so'rovda** chaqiriladi, va aynan shu yerda "before/after" naqshi ko'rinadi: `self.get_response(request)` chaqirilishidan **oldingi** kod — so'rov kelganda ishlaydi ("before"), undan **keyingi** kod — javob tayyor bo'lgach ishlaydi ("after").

Endi uni `settings.py`dagi `MIDDLEWARE` ro'yxatining **oxiriga** qo'shamiz:

```python
MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",
    "django.contrib.sessions.middleware.SessionMiddleware",
    "django.middleware.common.CommonMiddleware",
    "django.middleware.csrf.CsrfViewMiddleware",
    "django.contrib.auth.middleware.AuthenticationMiddleware",
    "django.contrib.messages.middleware.MessageMiddleware",
    "django.middleware.clickjacking.XFrameOptionsMiddleware",
    "apps.dokon.middleware.SoravniKuzatishMiddleware",
]
```

## Kodni o'qish mashqi

Server hali ishga tushirilmagan. Yuqoridagi uch faylni (o'zgartirilgan `urls.py`, `views.py`, yangi `middleware.py`) diqqat bilan o'qib chiqqan holda, quyidagi savolga javob bering:

**Savol:** Serverni ishga tushirganimizda (`runserver`), lekin hali **hech qanday so'rov yubormasdan**, terminalda `print()` xabarlaridan **qaysilari** darhol ko'rinadi — barchasi, ba'zilari, yoki hech biri?

<details>
<summary>Javobni ko'rish</summary>

Faqat **ikkitasi** ko'rinadi: `urls.py`dagi `print` (chunki `urls.py` — server ishga tushganda, URL'larni "xaritalash" uchun, **darhol** to'liq o'qib chiqiladi) va middleware'ning `__init__`idagi `print` (chunki, xuddi shunday, barcha middleware'lar server ishga tushganda **bir marta** yaratiladi). `views.py`dagi `print` esa — **ko'rinmaydi**, chunki u faqat funksiya **ichida**, va bu funksiya hali **chaqirilmagan** — u faqat haqiqiy so'rov kelganda ishga tushadi.

</details>

## Amaliy misol

Bashoratimizni to'liq tekshiramiz. Avval, faqat serverni ishga tushiramiz (hali so'rov yubormasdan):

```bash
python manage.py runserver
```

```
Watching for file changes with StatReloader
Performing system checks...

>>> apps/dokon/urls.py YUKLANMOQDA (bu faqat SERVER ISHGA TUSHGANDA chiqadi)
System check identified no issues (0 silenced).
>>> MIDDLEWARE yaratildi (bu faqat SERVER ISHGA TUSHGANDA, bir marta)
Django version 5.2.17, using settings 'config.settings'
Starting development server at http://127.0.0.1:8000/
```

Aynan bashorat qilganimizdek! Endi, boshqa terminaldan, bitta so'rov yuboramiz:

```bash
curl http://127.0.0.1:8000/
```

Va serverning logiga **qo'shilgan** yangi qatorlarni ko'ramiz:

```
>>> MIDDLEWARE: so'rov KELDI — /
>>> VIEW ishga tushdi: bosh_sahifa()
>>> MIDDLEWARE: javob KETMOQDA — status 200
[30/Aug/2026 10:25:05] "GET / HTTP/1.1" 200 29
```

Bu — **markaziy natija**. Uni tartib bilan o'qiymiz: (1) `MIDDLEWARE: so'rov KELDI` — bizning middleware'imizning "before" qismi ishladi; (2) `VIEW ishga tushdi` — middleware, `self.get_response(request)` orqali, boshqaruvni view'ga uzatdi; (3) `MIDDLEWARE: javob KETMOQDA — status 200` — view o'z ishini tugatib, `HttpResponse`ni qaytargach, boshqaruv **middleware'ning o'ziga qaytdi**, va uning "after" qismi ishladi.

Endi ikkinchi so'rov yuboramiz (boshqa manzilga) va **yana bir muhim narsani** tasdiqlaymiz:

```bash
curl http://127.0.0.1:8000/haqida/
```

```
>>> MIDDLEWARE: so'rov KELDI — /haqida/
>>> VIEW ishga tushdi: haqida_sahifasi()
>>> MIDDLEWARE: javob KETMOQDA — status 200
```

Diqqat qiling: **`urls.py YUKLANMOQDA` va `MIDDLEWARE yaratildi` qayta chiqmadi!** Bu, ularning haqiqatan ham faqat **bir marta**, server ishga tushganda ishlashini, keyingi barcha so'rovlar esa faqat `__call__` (middleware) va view funksiyasi orqali, **qayta-qayta** o'tishini yakuniy tasdiqlaydi.

### Bonus: hatto 404 xato ham middleware orqali o'tadi

```bash
curl http://127.0.0.1:8000/mavjud-emas/
```

```
>>> MIDDLEWARE: so'rov KELDI — /mavjud-emas/
>>> MIDDLEWARE: javob KETMOQDA — status 404
Not Found: /mavjud-emas/
```

Bu yerda **`VIEW ishga tushdi` umuman chiqmadi** (chunki mos manzil topilmadi, hech qanday view chaqirilmadi), lekin middleware'ning **ikkala qismi ham** (before va after) baribir ishladi. Bu, middleware'ning nomi bejiz emasligini ko'rsatadi — u, natija muvaffaqiyatlimi (200) yoki xatomi (404), **har doim**, har bir so'rovni "o'rab oladi".

## Keng tarqalgan xatolar

**Xato 1:** `urls.py`ga so'rov paytida o'zgaradigan narsani (masalan, `datetime.now()`) yozib, "har bir so'rovda yangilanadi" deb o'ylash.
❌ `urls.py` bir marta yuklanganidan keyin, unda hisoblangan har qanday qiymat, server qayta ishga tushmagunicha, **o'zgarmay qoladi** — bu, yangi boshlovchilar ko'pincha tushunmaydigan, chalkash xato manbai.
✅ So'rov paytida o'zgarishi kerak bo'lgan har qanday narsa — **faqat** `view` funksiyasi ichida hisoblanishi kerak.

**Xato 2:** Middleware yozganda, `return self.get_response(request)`ni **unutish** (yoki uni chaqirmaslik).
❌ Agar middleware `get_response`ni chaqirmasa, so'rov **hech qachon** view'ga yetib bormaydi — sayt "osilib qoladi" yoki noto'g'ri javob qaytaradi.
✅ Har doim, maxsus sabab bo'lmasa (masalan, ataylab so'rovni bloklash), middleware `self.get_response(request)`ni chaqirib, uning natijasini qaytarishi shart.

**Xato 3:** Yangi middleware yozib, uni `settings.py`dagi `MIDDLEWARE` ro'yxatiga qo'shishni unutish.
❌ Fayl (`middleware.py`) yaratilgan, ichida to'g'ri kod bor, lekin u **hech qachon ishga tushmaydi** — chunki Django, `MIDDLEWARE` ro'yxatida ko'rsatilmagan klasslar haqida umuman bilmaydi.
✅ Middleware yozgach, **darhol** uni ro'yxatga qo'shib, kamida bitta so'rov yuborib, `print`/log orqali haqiqatan ishlayotganini tasdiqlang — bu, "yozdim, lekin ishlamayapti" degan keng tarqalgan chalkashlikning oldini oladi.

## Mashq/topshiriq

**(Oson)** `apps/dokon/middleware.py`dagi `__call__` metodiga, `self.get_response(request)`dan **oldin**, yana bitta qator qo'shing: `print(f">>> So'rov usuli: {request.method}")`. Serverni qayta ishga tushirib, `curl http://127.0.0.1:8000/`ni yuborib, yangi qator qanday tartibda chiqishini tekshiring.

**(O'rtacha)** Ikkinchi, **yangi** middleware yozing — `IkkinchiMiddleware` — xuddi birinchisiga o'xshash, lekin turli xabar bilan (masalan, `">>> IKKINCHI middleware"`). Uni `MIDDLEWARE` ro'yxatida, birinchisidan **oldin** joylashtiring. So'rov yuborib, ikkala middleware'ning "before" va "after" qismlari qanday **ichma-ich** (nested) tartibda ishlashini kuzating — bu, middleware'lar nega ko'pincha "matryoshka qo'g'irchoq" (rus qo'g'irchog'i) ga o'xshatilishini tushuntiradi.

**(Qiyin)** `apps/dokon/middleware.py`dagi `__call__` metodini o'zgartirib, `self.get_response(request)`ni chaqirishdan **oldin**, shart qo'shing: agar `request.path == "/admin/"` bo'lsa, `get_response`ni chaqirmasdan, to'g'ridan-to'g'ri `HttpResponse("Kirish taqiqlangan", status=403)` qaytaring (buning uchun `from django.http import HttpResponse`ni ham qo'shing). `curl http://127.0.0.1:8000/admin/`ni sinab, VIEW ishga tushmasligini, va bu — middleware'ning **so'rovni butunlay to'xtatish** qobiliyatini isbotlaydi.

1. Yangi qator, `MIDDLEWARE: so'rov KELDI` bilan `VIEW ishga tushdi` orasida chiqadi:
```
>>> MIDDLEWARE: so'rov KELDI — /
>>> So'rov usuli: GET
>>> VIEW ishga tushdi: bosh_sahifa()
```

```python
class IkkinchiMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        print(">>> IKKINCHI: before")
        response = self.get_response(request)
        print(">>> IKKINCHI: after")
        return response
```
`MIDDLEWARE` ro'yxatida `IkkinchiMiddleware`ni `SoravniKuzatishMiddleware`dan **oldin** qo'yib, natija:
```
>>> IKKINCHI: before
>>> MIDDLEWARE: so'rov KELDI — /
>>> VIEW ishga tushdi: bosh_sahifa()
>>> MIDDLEWARE: javob KETMOQDA — status 200
>>> IKKINCHI: after
```
Bu, aynan "matryoshka" naqshini isbotlaydi: ro'yxatda **birinchi** turgan middleware — eng **tashqi** qatlam (uning "before"si birinchi, "after"si oxirgi ishlaydi); ro'yxatda **oxirgi** turgani — view'ga eng **yaqin**, eng "ichki" qatlam.

3.
```python
def __call__(self, request):
    print(f">>> MIDDLEWARE: so'rov KELDI — {request.path}")
    if request.path == "/admin/":
        from django.http import HttpResponse
        return HttpResponse("Kirish taqiqlangan", status=403)
    response = self.get_response(request)
    print(f">>> MIDDLEWARE: javob KETMOQDA — status {response.status_code}")
    return response
```
`curl http://127.0.0.1:8000/admin/` — "Kirish taqiqlangan" (403) natijasini beradi, va logda **`VIEW ishga tushdi` umuman ko'rinmaydi** — chunki middleware, `get_response`ni chaqirmasdan turib, o'zi javob qaytarib, zanjirni **shu yerda to'xtatdi**.

## Qisqacha xulosa

Bitta HTTP so'rovi, Django ichida, aniq, bashorat qilinadigan tartibda harakat qiladi: `urls.py` va middleware'larning `__init__` qismi — faqat **server ishga tushganda, bir marta**; middleware'larning `__call__` qismi va `view` funksiyasi — **har bir so'rovda, qaytadan**. Middleware — so'rovni "before" (kelayotganda) va "after" (ketayotganda) qismlarga o'rab oladigan, va ro'yxatdagi tartibga qarab **ichma-ich** (matryoshka kabi) ishlaydigan mexanizm; u hatto so'rovni butunlay to'xtatish (view'ga yetkazmaslik) qobiliyatiga ham ega. Bu bilim — endi sizga, istalgan notanish Django loyihasida, "bu so'rov qayerdan boshlanadi" degan savolga, taxmin qilmasdan, **aniq javob topish** yo'lini beradi. Keyingi darsda — `HttpRequest` va `HttpResponse` ob'ektlarining ichiga, ular aslida **nima olib yurishini** o'qib chiqamiz.

# 2.2. `zoneinfo` — mintaqaviy vaqt zonalari va foydalanuvchiga mahalliy vaqtni ko'rsatish

## Bu darsda nimalarni o'rganasiz

- `zoneinfo.ZoneInfo` bilan aniq mintaqa (masalan `Asia/Tashkent`) vaqt zonasini yaratishni o'rganasiz
- UTC'da saqlangan vaqtni foydalanuvchining o'z mintaqasidagi vaqtga qanday aylantirishni bilib olasiz
- Django'ning `TIME_ZONE` va `USE_TZ` sozlamalari, hamda `timezone.activate()` funksiyasi qanday ishlashini tushunasiz
- Nega saqlash uchun har doim UTC, ko'rsatish uchun esa mahalliy vaqt zonasi ishlatilishini asoslay olasiz

## Nazariy qism

### `zoneinfo` — mintaqa nomiga asoslangan vaqt zonalari

2.1-darsda `datetime.timezone.utc`ni ko'rdik — bu faqat **UTC**dan qat'iy siljish (offset)ni bildiradi. Lekin haqiqiy dunyoda vaqt zonalari murakkabroq: masalan yozgi vaqtga o'tish (DST — Daylight Saving Time) ba'zi mamlakatlarda bor, ba'zilarida yo'q, va bu qoidalar yillar davomida o'zgarib turadi. Buni to'g'ri hisobga olish uchun Python 3.9dan boshlab **`zoneinfo`** moduli qo'shilgan — u IANA vaqt zonalari bazasidan (masalan `Asia/Tashkent`, `Europe/London`, `America/New_York`) foydalanadi:

```python
from datetime import datetime
from zoneinfo import ZoneInfo

toshkent = ZoneInfo("Asia/Tashkent")
london = ZoneInfo("Europe/London")

vaqt_toshkentda = datetime(2026, 9, 8, 14, 0, tzinfo=toshkent)
print(vaqt_toshkentda)                          # 2026-09-08 14:00:00+05:00
print(vaqt_toshkentda.astimezone(london))        # 2026-09-08 10:00:00+01:00 (yozgi vaqt)
```

`.astimezone()` — aware datetime'ni bir vaqt zonasidan boshqasiga **to'g'ri** aylantiradi (soat farqini, DST qoidalarini hisobga olib). Muhim: `.astimezone()` faqat **aware** datetime'da ishlaydi — naive datetime'da chaqirilsa, Python uni "mahalliy tizim vaqt zonasi" deb hisoblab, kutilmagan natija berishi mumkin.

### Django'da `TIME_ZONE` va `USE_TZ`

`settings.py`da ikkita sozlama bor:

```python
TIME_ZONE = "Asia/Tashkent"
USE_TZ = True
```

Bu ikkisi ko'pincha noto'g'ri tushuniladi: `TIME_ZONE` — bazada **saqlash** vaqt zonasini emas, balki Django **ko'rsatuvchi** (template, admin panel) vaqt zonasini belgilaydi. `USE_TZ = True` bo'lganda, Django ma'lumotlar bazasida **har doim UTC**da saqlaydi (bu — xalqaro standart, aniq va noaniqliksiz), va faqat foydalanuvchiga ko'rsatishda `TIME_ZONE`ga aylantiradi.

```python
from django.utils import timezone

hozir = timezone.now()                    # UTC, bazaga shu holda yoziladi
mahalliy = timezone.localtime(hozir)       # TIME_ZONE (Asia/Tashkent)ga aylantirilgan
print(hozir)        # 2026-09-08 09:00:00+00:00
print(mahalliy)      # 2026-09-08 14:00:00+05:00
```

`timezone.localtime()` — aynan shu ishni bajaradi: UTC (yoki istalgan aware) datetime'ni `settings.TIME_ZONE`ga (yoki `timezone.activate()` bilan faollashtirilgan boshqa zonaga) aylantiradi. Template'larda `{{ buyurtma.yaratilgan_sana }}` avtomatik ravishda `TIME_ZONE`ga mos holda ko'rsatiladi — buning uchun alohida narsa yozish shart emas.

### Nega har doim UTC'da saqlash kerak

Agar `onlayn_dokon`ning mijozlari turli mamlakatlarda bo'lsa (masalan Toshkent va Almati — ikkalasi ham `+05:00`, lekin farqli DST tarixiga ega bo'lishi mumkin), va vaqt "mahalliy" holda saqlansa, keyinchalik "qaysi mahalliy?" degan noaniqlik paydo bo'ladi. UTC — bitta, universal nuqta: barcha vaqtlar shu nuqtaga nisbatan saqlanadi, taqqoslash va tartiblash har doim to'g'ri ishlaydi, ko'rsatish bosqichidagina kerakli mintaqaga aylantiriladi.

## Amaliy misol

`onlayn_dokon`da har bir `Mijoz`ga o'z vaqt zonasini saqlash imkonini beramiz — buyurtma holati haqidagi xabarni mijozning **o'z** mahalliy vaqtida ko'rsatish uchun:

```python
# apps/mijozlar/models.py
from django.db import models


class Mijoz(models.Model):
    foydalanuvchi = models.OneToOneField("auth.User", on_delete=models.CASCADE)
    vaqt_zonasi = models.CharField(
        max_length=64,
        default="Asia/Tashkent",
        help_text="Masalan: Asia/Tashkent, Europe/Moscow, Asia/Almaty",
    )
```

Middleware yordamida, har bir so'rov uchun mijozning vaqt zonasini faollashtiramiz:

```python
# apps/mijozlar/middleware.py
from zoneinfo import ZoneInfo

from django.utils import timezone


class MijozVaqtZonasiMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        if request.user.is_authenticated and hasattr(request.user, "mijoz"):
            try:
                timezone.activate(ZoneInfo(request.user.mijoz.vaqt_zonasi))
            except Exception:
                timezone.deactivate()   # noto'g'ri zona bo'lsa, standart (TIME_ZONE)ga qaytadi
        else:
            timezone.deactivate()

        return self.get_response(request)
```

`settings.py`da `MIDDLEWARE` ro'yxatiga qo'shamiz:

```python
MIDDLEWARE = [
    # ...
    "apps.mijozlar.middleware.MijozVaqtZonasiMiddleware",
]
```

Shundan keyin, shu so'rov davomida chaqirilgan `timezone.localtime()` va template'lardagi barcha vaqt ko'rsatishlar avtomatik ravishda **shu mijozning** vaqt zonasida chiqadi — hech qanday qo'shimcha aylantirish yozish shart emas.

## Keng tarqalgan xatolar

**Xato 1:** Vaqt zonasi nomini qo'lda, xato yozish (masalan `"Tashkent"` yoki `"UTC+5"`).

❌ `ZoneInfo("Tashkent")` — `zoneinfo.ZoneInfoNotFoundError: 'No time zone found with key Tashkent'` beradi, chunki to'g'ri IANA nomi `"Asia/Tashkent"` (mintaqa/shahar formatida).

✅ Har doim to'liq IANA nomidan foydalaning. Barcha mavjud nomlarni dasturiy ko'rish mumkin: `from zoneinfo import available_timezones; sorted(available_timezones())`.

**Xato 2:** `timezone.activate()`ni chaqirib, lekin so'rov tugagach `deactivate()` qilmaslik.

❌ Middleware faqat `timezone.activate(...)` chaqiradi, `else` shoxobchasida `deactivate()` yo'q — natijada, agar bitta ishchi jarayon (worker) turli foydalanuvchilar so'rovlarini ketma-ket qayta ishlasa, oldingi foydalanuvchining vaqt zonasi keyingisiga "yopishib qolishi" mumkin.

✅ Har doim ikkala holatni ham yozing: foydalanuvchi vaqt zonasi ma'lum bo'lsa — `activate()`, aks holda — `deactivate()` (bu standart `TIME_ZONE`ga qaytaradi). Amaliy misoldagi kod aynan shunday yozilgan — sababsiz emas.

**Xato 3:** Naive datetime'ni to'g'ridan-to'g'ri boshqa vaqt zonasiga "aylantirishga" urinish.

❌ `datetime(2026, 9, 8, 14, 0).astimezone(ZoneInfo("Europe/London"))` — Python bu holatda naive datetime'ni **tizimning** (server joylashgan joyning) mahalliy vaqt zonasi deb hisoblab, keyin Londonga aylantiradi — bu ko'pincha kutilmagan natija beradi, chunki server qaysi vaqt zonasida ekani aniq emas.

✅ Avval `timezone.make_aware()` yoki to'g'ridan-to'g'ri `tzinfo=` bilan aware qiling, so'ng `.astimezone()` chaqiring: `datetime(2026, 9, 8, 14, 0, tzinfo=ZoneInfo("Asia/Tashkent")).astimezone(ZoneInfo("Europe/London"))`.

## Mashq/topshiriq

**(Oson)** Shell'da `from zoneinfo import ZoneInfo; from django.utils import timezone; hozir = timezone.now(); print(hozir.astimezone(ZoneInfo("Asia/Tashkent")))` bajarib, joriy UTC vaqtni Toshkent vaqtiga aylantiring.

**(O'rtacha)** `Mijoz` modelidagi `vaqt_zonasi` maydoniga validatsiya qo'shing: saqlashdan oldin, kiritilgan qiymat haqiqiy IANA zonasi ekanini tekshiring (`from zoneinfo import available_timezones` bilan). Noto'g'ri bo'lsa, `django.core.exceptions.ValidationError` chaqiring.

**(Qiyin)** `Buyurtma` modeliga `mijozga_korinadigan_sana()` metodini qo'shing — u `timezone.activate()` chaqirmasdan, to'g'ridan-to'g'ri `self.mijoz.vaqt_zonasi`dan foydalanib, `self.yaratilgan_sana`ni mijozning mintaqaviy vaqtiga aylantirib qaytarsin (`.astimezone(ZoneInfo(...))` dan foydalaning, middleware'ga tayanmang — bu metod hisobot yoki email yuborish kabi so'rovdan tashqari kontekstda ham ishlashi kerak).

## Qisqacha xulosa

`zoneinfo.ZoneInfo` — IANA mintaqa nomlariga (masalan `Asia/Tashkent`) asoslangan, yozgi vaqtni ham to'g'ri hisobga oladigan vaqt zonasi klassi; Django buni `TIME_ZONE` sozlamasi va `timezone.localtime()`/`timezone.activate()` funksiyalari orqali ishlatadi. Oltin qoida: **saqlash uchun har doim UTC** (`USE_TZ = True`, `timezone.now()`), **ko'rsatish uchun kerakli mintaqaviy vaqt** (`timezone.localtime()` yoki `.astimezone()`) — bu ikkisini aralashtirmaslik ko'p mintaqali loyihada eng ko'p uchraydigan xatolarning oldini oladi. Keyingi bobda — matn validatsiyasi (`re`) va pul/identifikator kabi nozik turlar (`decimal`, `uuid`) bilan tanishamiz.

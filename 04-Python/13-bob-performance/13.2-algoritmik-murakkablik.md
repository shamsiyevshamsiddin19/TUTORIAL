## Nazariy qism

**Manba:** Python rasmiy dokumentatsiyasi (Time Complexity vikisi), CPython manba kodi tahlili (7-8-10-boblarda ko'rilgan), umumiy algoritmlar nazariyasi.

### Big-O — nima uchun profiler bilan birga kerak

13.1-darsda `cProfile` bilan **qaysi** funksiya sekin ekanini topishni o'rgandik. Lekin bu funksiyani **qanday** tezlashtirish kerakligini bilish uchun ko'pincha mikro-optimallashtirish (masalan, `for` tsiklini biroz boshqacha yozish) yetarli emas — asosiy savol odatda: **"men noto'g'ri murakkablikdagi algoritm/ma'lumotlar tuzilmasini ishlatyapmanmi?"**

Masalan, agar sizning kodingiz `list` ichida elementning mavjudligini tez-tez tekshirsa (`x in katta_royxat`), bu **O(n)** — har safar butun ro'yxat skanerlanadi. Agar shu tekshiruvni `set`ga o'tkazsangiz (`x in katta_toplam`), bu 10-bobda ko'rgan hash-jadval tufayli **O(1)**'ga tushadi. 10,000 elementli ro'yxatda bu farq minglab marta tezlik farqini beradi — va bu farq hech qanday mikro-optimallashtirish bilan qopqoq bo'la olmaydi, chunki muammo algoritmik.

### Python quyi tuzilmalarining murakkablik jadvali

10-bobda batafsil ko'rilgan ichki tuzilmalarga asoslanib:

| Operatsiya | `list` | `dict` / `set` | Izoh |
|---|---|---|---|
| Indeks orqali o'qish (`x[i]`) | O(1) | — | To'g'ridan-to'g'ri ko'rsatkich massivi |
| Kalit orqali o'qish (`d[k]`) | — | O(1) o'rtacha | Hash-jadval, eng yomon holatda O(n) |
| Oxiriga qo'shish (`append`) | O(1) amortizatsiyalangan | O(1) amortizatsiyalangan | Over-allocation tufayli |
| Boshiga qo'shish (`insert(0, x)`) | O(n) | — | Barcha elementlar siljiydi |
| Mavjudlikni tekshirish (`x in ...`) | O(n) | O(1) o'rtacha | **Eng muhim amaliy farq** |
| Elementni o'chirish (o'rtadan) | O(n) | O(1) o'rtacha | |
| Saralash (`sorted()`) | O(n log n) | — | Timsort |

Bu jadvaldan kelib chiqadigan eng amaliy xulosa: **agar kodingizda tez-tez "shu element ro'yxatda bormi?" tekshiruvi bo'lsa, va tartib muhim bo'lmasa (yoki takrorlanmaydigan elementlar bo'lsa) — `list` o'rniga `set` yoki `dict` ishlating.**

### Python'ga xos amaliy optimallashtirish naqshlari

**1. Global o'zgaruvchidan ko'ra lokal o'zgaruvchi tezroq.** 8-bobda ko'rganimizdek, `LOAD_FAST` (lokal o'zgaruvchi, indeks orqali massivdan olinadi) `LOAD_GLOBAL`dan (nom orqali `dict`dan qidiriladi) tezroq. Agar tsikl ichida ko'p marta modul darajasidagi funksiya yoki o'zgaruvchi ishlatilsa, uni funksiya boshida lokal nomga bog'lab olish tezlikni oshirishi mumkin:

```python
import math

def sekinroq(qiymatlar):
    return [math.sqrt(x) for x in qiymatlar]  # har safar "math" global qidiriladi

def tezroq(qiymatlar):
    sqrt = math.sqrt  # lokal nomga bog'lash — bir marta
    return [sqrt(x) for x in qiymatlar]
```

**2. Satrlarni `+=` bilan emas, `str.join()` bilan birlashtirish.** 10-bobda ko'rganimizdek, satrlar o'zgarmas (immutable) — har bir `s += qism` yangi satr obyekti yaratadi va eskisini butunlay nusxalaydi, natijada O(n²) murakkablik. `"".join(qismlar)` esa umumiy hajmni oldindan hisoblab, bitta xotira ajratish bilan O(n) bajaradi.

**3. Ichki (built-in) funksiyalar va kutubxonalarni afzal ko'rish.** `sum()`, `min()`, `max()`, `sorted()`, `map()`, `filter()` kabi ichki funksiyalar C tilida yozilgan va Python darajasidagi tsiklga qaraganda sezilarli tezroq ishlaydi (chunki ular bytecode interpretatsiyasi overhead'idan holi):

```python
# Sekinroq — Python darajasidagi tsikl
jami = 0
for x in royxat:
    jami += x

# Tezroq — C darajasida bajariladigan built-in
jami = sum(royxat)
```

**4. Generator ifodalarini butun ro'yxatlar o'rniga ishlatish, agar barcha elementlar bir vaqtda xotirada kerak bo'lmasa.** `sum(x**2 for x in range(1_000_000))` — bu `sum([x**2 for x in range(1_000_000)])`ga qaraganda kamroq xotira ishlatadi (butun oraliq ro'yxat sifatida saqlanmaydi), garchi tezlik jihatidan taxminan bir xil bo'lsa ham.

**5. `__slots__` bilan ko'p sonli kichik obyektlarni tejash.** 9-bobda ko'rganimizdek, agar millionlab kichik obyekt (masalan, `Nuqta(x, y)`) yaratilsa, `__slots__` xotirani sezilarli kamaytiradi (har bir obyektning `__dict__`ini yo'q qiladi) va atributlarga murojaatni biroz tezlashtiradi.

**6. Keraksiz obyekt yaratishdan qochish tsikl ichida.** Masalan, tsikl ichida takroran yangi `re.compile()` chaqirish o'rniga, muntazam ifodani (regex) tsikldan tashqarida bir marta kompilyatsiya qilib olish kerak.

### Qachon Python darajasidagi optimallashtirish yetarli emas

Ba'zan, hatto eng optimal algoritm va Python naqshlari bilan ham, sof Python interpretatsiya overhead'i (bytecode interpretatsiyasi, dinamik tip tekshiruvi, reference counting) haddan tashqari sekin bo'lib qoladi — ayniqsa raqamli hisoblash-og'ir (numeric-heavy) tsikllarda. Bu holatlarda keyingi qadam odatda:

- **NumPy** kabi vektorlashtirilgan (vectorized) kutubxonalardan foydalanish — tsiklni butunlay C darajasiga o'tkazish.
- **Cython** yoki **ctypes/cffi** orqali muhim qismni C'da yozish (13.3-darsda batafsil ko'ramiz).
- **PyPy** kabi JIT-kompilyatorli alternativ interpretator ishlatish (13.4-darsda ko'ramiz).

## Amaliy misol

```python
"""
algoritmik_murakkablik_demo.py — list vs set, string birlashtirish,
va local/global farqini o'lchash.
"""
import timeit


def list_vs_set_demo():
    n = 10_000
    royxat = list(range(n))
    toplam = set(range(n))
    qidiriladigan = n - 1  # eng yomon holat — oxirida

    vaqt_list = timeit.timeit(
        lambda: qidiriladigan in royxat, number=1000
    )
    vaqt_set = timeit.timeit(
        lambda: qidiriladigan in toplam, number=1000
    )
    print(f"'x in list' (n={n}), 1000 marta: {vaqt_list:.4f}s")
    print(f"'x in set'  (n={n}), 1000 marta: {vaqt_set:.4f}s")
    print(f"Tezlashish: {vaqt_list / vaqt_set:.0f}x")


def string_birlashtirish_demo():
    qismlar = [str(i) for i in range(20_000)]

    def plus_bilan():
        natija = ""
        for q in qismlar:
            natija += q
        return natija

    def join_bilan():
        return "".join(qismlar)

    vaqt_plus = timeit.timeit(plus_bilan, number=10)
    vaqt_join = timeit.timeit(join_bilan, number=10)
    print(f"+= bilan birlashtirish: {vaqt_plus:.4f}s")
    print(f"join() bilan birlashtirish: {vaqt_join:.4f}s")
    print(f"Tezlashish: {vaqt_plus / vaqt_join:.1f}x")


def lokal_global_demo():
    setup = "import math"
    vaqt_global = timeit.timeit(
        "[math.sqrt(x) for x in range(1000)]", setup=setup, number=1000
    )
    vaqt_lokal = timeit.timeit(
        "sqrt = math.sqrt\n[sqrt(x) for x in range(1000)]",
        setup=setup,
        number=1000,
    )
    print(f"Global math.sqrt: {vaqt_global:.4f}s")
    print(f"Lokal sqrt: {vaqt_lokal:.4f}s")


if __name__ == "__main__":
    print("=== list vs set ===")
    list_vs_set_demo()
    print("\n=== string birlashtirish ===")
    string_birlashtirish_demo()
    print("\n=== lokal vs global ===")
    lokal_global_demo()
```

Chiqishi taxminan:

```
=== list vs set ===
'x in list' (n=10000), 1000 marta: 0.412s
'x in set'  (n=10000), 1000 marta: 0.0001s
Tezlashish: ~4000x

=== string birlashtirish ===
+= bilan birlashtirish: 0.045s
join() bilan birlashtirish: 0.008s
Tezlashish: ~5.6x

=== lokal vs global ===
Global math.sqrt: 0.089s
Lokal sqrt: 0.078s
```

## Keng tarqalgan xatolar

1. **Mikro-optimallashtirishga (lokal o'zgaruvchi, `+=` o'rniga `join`) algoritmik muammodan (`list` o'rniga `set` kerak bo'lganda) ko'proq vaqt sarflash.** Yuqoridagi o'lchovlar aniq ko'rsatadiki, `list`→`set` almashtirishi 1000x+ tezlik beradi, lokal/global farqi esa atigi 10-15% — har doim avval katta (algoritmik) muammolarni toping.

2. **`list`ni "har doim" `set`ga almashtirish, tartib va takrorlanuvchi elementlar muhim bo'lgan holatlarda ham.** `set` tartiblanmagan va faqat hashable, noyob elementlarni saqlaydi — agar tartib yoki dublikatlar muhim bo'lsa, `set`ga almashtirish mantiqiy xatoga olib keladi.

3. **Profilashsiz "optimallashtirish" — kodni murakkablashtirish, lekin real tezlik farqi yo'q.** Har qanday "optimallashtirish" deb nomlangan o'zgarishdan keyin, uning haqiqatan foyda berganini `timeit`/`cProfile` bilan tasdiqlash kerak — ba'zan "optimallashtirilgan" kod aslida sekinroq bo'lib chiqadi (masalan, Python interpretatorining ichki optimallashtirishlari tufayli).

## Mashq/topshiriq

1. 50,000 elementli ro'yxatda 1000 marta tasodifiy qiymatlarning mavjudligini tekshirishni `list` va `set` bilan solishtiring, va natijalarni `timeit` bilan o'lchang.

2. `dict.get(key, standart_qiymat)` bilan `if key in d: ... else: ...` naqshini solishtiring — ikkalasi ham to'g'ri natija bersa-da, nima uchun birinchisi odatda ozgina tezroq (yoki hech bo'lmaganda qisqaroq va aniqroq) ekanini tushuntiring.

3. Nima uchun `[x for x in range(n) if shart(x)]` (list comprehension) odatda ekvivalent `for` tsikli + `append()`dan biroz tezroq ekanini 8-bobdagi bytecode bilimlaringizga tayanib tushuntiring.

**Javoblar:**

1.
```python
import random
import timeit

n = 50_000
royxat = list(range(n))
toplam = set(range(n))
qidiriladiganlar = [random.randint(0, n - 1) for _ in range(1000)]

def list_orqali():
    for q in qidiriladiganlar:
        _ = q in royxat

def set_orqali():
    for q in qidiriladiganlar:
        _ = q in toplam

print(timeit.timeit(list_orqali, number=10))
print(timeit.timeit(set_orqali, number=10))
# set_orqali doim sezilarli tezroq bo'ladi — o'rtacha O(1) vs O(n) tekshiruv
```

2. `dict.get(key, standart_qiymat)` bitta hash-jadval qidiruvi bilan bajariladi (C darajasida bitta chaqiruv), `if key in d: ... else: ...` esa **ikkita** alohida qidiruvni talab qilishi mumkin — birinchi marta `in` operatori bilan mavjudlikni tekshirish uchun, ikkinchi marta `d[key]` bilan qiymatni olish uchun (agar kod shunday yozilgan bo'lsa). `dict.get()` bu ikki qadamni bitta C darajasidagi funksiya chaqiruviga birlashtiradi, natijada odatda biroz tezroq va har doim qisqaroq/aniqroq kod beradi.

3. List comprehension CPython'da maxsus, ixtisoslashtirilgan bytecode ketma-ketligiga kompilyatsiya qilinadi (`LIST_APPEND` maxsus opkodi bilan) va natija ro'yxati C darajasida to'g'ridan-to'g'ri quriladi, hajmi haqida oldindan taxmin qilinishi mumkin bo'lgan optimallashtirishlar bilan. Oddiy `for` tsikli + `list.append()` esa har bir iteratsiyada **alohida, umumiy maqsadli metod chaqiruvi** (`LOAD_METHOD`/`CALL` opkodlari) qiladi — bu list comprehension'ning ichki, ixtisoslashtirilgan yo'liga qaraganda ko'proq bytecode interpretatsiyasi overhead'iga ega. Farq odatda kichik (10-20%), lekin katta ro'yxatlarda sezilarli bo'lishi mumkin.

## Qisqacha xulosa

Ishlash unumdorligini oshirish har doim to'g'ri **algoritm va ma'lumotlar tuzilmasi** tanlashdan boshlanadi — `list` o'rniga `set`/`dict` ishlatish kabi O(n)→O(1) o'zgarishlar minglab marta tezlik farqini berishi mumkin, va bu hech qanday mikro-optimallashtirish bilan qopqoq bo'la olmaydi. Shundan keyingina Python'ga xos naqshlar (lokal o'zgaruvchilar, `str.join()`, ichki funksiyalar, `__slots__`, generatorlar) qo'llaniladi — bular odatda 10-50% oralig'ida foyda beradi. Agar sof Python interpretatsiya overhead'i haddan tashqari bo'lib qolsa (raqamli hisoblash-og'ir kod), keyingi qadam NumPy, Cython/ctypes yoki PyPy kabi vositalarga o'tish bo'ladi — bularni keyingi ikki darsda ko'rib chiqamiz. Har qanday o'zgarishdan keyin natijani `timeit`/`cProfile` bilan tasdiqlash shart — sezgi ko'pincha aldaydi.

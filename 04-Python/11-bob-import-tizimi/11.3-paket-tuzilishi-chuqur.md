# 11.3. Paket tuzilishi chuqur: `__init__.py` va namespace paketlar

## Bu darsda nimalarni o'rganasiz

- `__init__.py` faylining aniq vazifasi va u yo'q bo'lganda nima o'zgarishi
- Oddiy (regular) paket va **namespace paket** (PEP 420) o'rtasidagi farq
- `__path__`, `__file__`, `_NamespacePath` obyektlarining ma'nosi
- Bir nechta joyga tarqalgan (masalan, plugin arxitekturasi) paketlarni qanday yig'ish mumkinligi
- Nisbiy (relative) va absolyut importlar qanday ishlashi

## Nazariy qism

**Manba:** [PEP 420 — Implicit Namespace Packages](https://peps.python.org/pep-0420/), Python rasmiy dokumentatsiyasi ("The import system" bo'limi, `importlib` hujjatlari).

### `__init__.py` nima uchun kerak edi

Python'ning ilk kunlaridan (va hozir ham eng ko'p ishlatiladigan holatda) papka **paket** deb tanilishi uchun ichida `__init__.py` fayli bo'lishi kerak edi — hatto bo'sh bo'lsa ham:

```
mening_paketim/
├── __init__.py      # bo'sh bo'lishi mumkin, lekin mavjud bo'lishi shart
├── modul_a.py
└── modul_b.py
```

`__init__.py` ikkita vazifani bajaradi:

1. **Belgi (marker):** import tizimiga "bu oddiy papka emas, bu Python paketi" deb signal beradi.
2. **Ishga tushirish kodi (initialization code):** paket birinchi marta import qilinganda `__init__.py` ichidagi kod avtomatik bajariladi. Bu yerda odatda quyidagilar qilinadi:
   - Ichki modullardan qulay nomlarni tashqariga chiqarish (`from .modul_a import MuhimKlass`), shunda foydalanuvchi `mening_paketim.modul_a.MuhimKlass` o'rniga `mening_paketim.MuhimKlass` deb yoza oladi.
   - `__all__` ro'yxatini belgilash (`from paket import *` nima eksport qilishini nazorat qilish uchun).
   - Paket darajasidagi konstantalar yoki versiya raqamini o'rnatish (`__version__ = "1.0.0"`).

`__init__.py`'si bor paket **"oddiy paket" (regular package)** deb ataladi. Uning `__file__` atributi `__init__.py`'ning yo'liga ishora qiladi, `__path__` esa bitta elementli statik ro'yxat (list) bo'ladi.

### Muammo: paketlarni bir nechta joyga bo'lish

An'anaviy (oddiy) paketlarning bir cheklovi bor: ular faqat **bitta** papkada joylasha oladi. Lekin katta ekotizimlarda (masalan, `namespace`ga ega korporativ kutubxonalar, yoki plagin arxitekturasi) turli manba (masalan, turli pip paketlari) bitta "umumiy" nom ostida bir nechta quyi-modul taqdim qilishni xohlashi mumkin:

```
# Bitta pip paketi o'rnatadi:
site-packages/kompaniya_namespace/servis_a/__init__.py

# Boshqa alohida pip paketi o'rnatadi:
site-packages/kompaniya_namespace/servis_b/__init__.py
```

Ikkalasi ham `kompaniya_namespace` ostida, lekin ular alohida-alohida o'rnatilgan (alohida `setup.py`/`pyproject.toml` bilan). Agar `kompaniya_namespace/__init__.py` fayli **majburiy** bo'lganida, ikkala paket bir-birining `__init__.py`sini ustidan yozib qo'yishi (yoki ziddiyatga kelishi) mumkin edi.

### Yechim: PEP 420 — Implicit Namespace Packages

**Manba:** [PEP 420 — Implicit Namespace Packages](https://peps.python.org/pep-0420/).

Python 3.3'dan boshlab, `__init__.py`'siz papkalar ham **namespace paket** sifatida avtomatik tan olinadi. Import mexanizmi (11.1-darsda ko'rgan `PathFinder`) endi quyidagi algoritmga amal qiladi, `sys.path`'dagi har bir yo'l uchun:

1. Agar `__init__.py`'ga ega mos papka topilsa → **oddiy paket** yaratiladi, qidiruv shu yerda to'xtaydi.
2. Agar mos modul fayli (`.py`, `.pyc`, kengaytma moduli) topilsa → **oddiy modul** yaratiladi, qidiruv to'xtaydi.
3. Agar hech biri topilmasa, lekin mos nomli papka (hatto `__init__.py`siz) topilsa → bu papka **"portion"** sifatida qayd etiladi, va qidiruv **davom etadi** — `sys.path`dagi keyingi yo'llar ham tekshiriladi.
4. Qidiruv butunlay tugagach, agar kamida bitta portion qayd etilgan bo'lsa (lekin oddiy paket yoki modul topilmagan bo'lsa) → **namespace paket** yaratiladi, uning `__path__`i barcha topilgan portionlarni birlashtiradi.

Natijada:

```
# 1-joy (masalan, bitta pip paketi o'rnatgan):
/usr/lib/python3.12/site-packages/kompaniya_namespace/servis_a/__init__.py

# 2-joy (boshqa pip paketi o'rnatgan, sys.path'da boshqa manzil):
/opt/local-paketlar/kompaniya_namespace/servis_b/__init__.py
```

Bu holatda `import kompaniya_namespace.servis_a` va `import kompaniya_namespace.servis_b` ikkalasi ham ishlaydi — garchi `kompaniya_namespace` papkasining o'zida hech qanday `__init__.py` bo'lmasa ham, va u ikki turli joyda jismonan mavjud bo'lsa ham!

### Namespace paketning texnik farqlari

| Xususiyat | Oddiy paket | Namespace paket |
|---|---|---|
| `__init__.py` talabi | Majburiy | Yo'q |
| `__file__` atributi | Bor (`__init__.py` yo'li) | **Yo'q** (namespace paketning o'zi bitta faylga bog'liq emas) |
| `__path__` turi | Oddiy `list` | `_NamespacePath` — dinamik obyekt |
| `__path__` xatti-harakati | Import vaqtida bir marta hisoblanadi | `sys.path` o'zgarganda **qayta hisoblanadi** |
| Ishga tushirish kodi | Bo'lishi mumkin (`__init__.py` ichida) | Yo'q — namespace paketning o'zida bajariladigan kod bo'lmaydi |
| Tezlik | Tezroq (birinchi mos joy topilganda darhol yaratiladi) | Sekinroq (`sys.path`dagi HAMMA joy tekshirilishi kerak) |

`_NamespacePath`ning dinamikligi qiziq oqibatga olib keladi: agar dastur ishga tushgandan keyin `sys.path`ga yangi manzil qo'shilsa va u manzilda mos nomli yana bir portion papka bo'lsa, keyingi safar namespace paketning `__path__`iga murojaat qilinganda (masalan, ichidagi quyi-modul import qilinganda) yangi portion ham avtomatik hisobga olinadi — bu oddiy paketda mumkin emas.

### Amaliy oqibat: bo'sh papka namespace paket bo'lib qolishi mumkin

PEP 420'ning kutilmagan (ba'zan tuzoq bo'ladigan) oqibati: agar siz tasodifan bir papkani `__init__.py`siz yaratsangiz-yu, u `sys.path` ichida turgan bo'lsa, Python uni **xatosiz** namespace paket deb qabul qiladi — hatto siz buni mo'ljallamagan bo'lsangiz ham. Bu ba'zan chalkash xatti-harakatga olib kelishi mumkin: masalan, siz `import mening_moduli` deganda, kutilganidek `ModuleNotFoundError` o'rniga, bo'sh (funksiyasiz) namespace paket muvaffaqiyatli import bo'lib ketadi, va faqat keyinroq `mening_moduli.biror_funksiya()` chaqirganda `AttributeError` chiqadi — bu xatoni aniqlashni qiyinlashtiradi.

Shuning uchun ko'plab loyihalar (va linter'lar, masalan Ruff'ning `INP001` qoidasi) hamon amaliy tavsiya sifatida **har doim** `__init__.py`ni (hatto bo'sh bo'lsa ham) qo'shishni tavsiya qiladi — namespace paketlar faqat maxsus, ongli holatlarda (haqiqatan ham ko'p-manbali tarqatish kerak bo'lganda) ishlatilishi kerak.

### Nisbiy importlar (`from . import x`) va paket konteksti

`__init__.py`ning yana bir muhim oqibati — u modulga **paket konteksti** beradi, bu esa nisbiy importlarni ishlatish imkonini beradi:

```python
# mening_paketim/modul_a.py ichida:
from . import modul_b          # bir xil paketdagi qo'shni modul
from .ichki.modul_c import X   # ichki quyi-paketdan
from .. import boshqa_paket    # ota-paketdan (agar mening_paketim o'zi quyi-paket bo'lsa)
```

Nisbiy importlar `__name__` va `__package__` atributlariga tayanadi — shuning uchun ular faqat modul **paket ichida** import qilingandagina ishlaydi, to'g'ridan-to'g'ri skript sifatida ishga tushirilganda (`python modul_a.py`) ishlamaydi, chunki bunday holatda `__package__` bo'sh bo'ladi. Bu — boshlang'ich Python dasturchilarining eng ko'p uchraydigan xatoларidan biri (`ImportError: attempted relative import with no known parent package`).

## Amaliy misol

```python
"""
namespace_demo.py — oddiy paket va namespace paket farqini
jonli tekshiruvchi demo skript.
"""
import importlib
import os
import shutil
import sys
import tempfile


def demo():
    ish_papkasi = tempfile.mkdtemp()
    joy_1 = os.path.join(ish_papkasi, "joy_1")
    joy_2 = os.path.join(ish_papkasi, "joy_2")
    os.makedirs(os.path.join(joy_1, "ns_paket", "servis_a"))
    os.makedirs(os.path.join(joy_2, "ns_paket", "servis_b"))

    # ns_paket papkasining o'zida __init__.py YO'Q — bu qasddan qilinmoqda,
    # shunda u namespace paket sifatida tan olinadi.
    with open(os.path.join(joy_1, "ns_paket", "servis_a", "__init__.py"), "w") as f:
        f.write("def salom():\n    return 'servis_a ishladi'\n")
    with open(os.path.join(joy_2, "ns_paket", "servis_b", "__init__.py"), "w") as f:
        f.write("def salom():\n    return 'servis_b ishladi'\n")

    # Ikkala "joy"ni ham sys.path'ga qo'shamiz — xuddi ular alohida
    # o'rnatilgan pip paketlari kabi.
    sys.path.insert(0, joy_1)
    sys.path.insert(0, joy_2)

    import ns_paket
    print("ns_paket turi:", type(ns_paket))
    print("__file__ bormi?:", hasattr(ns_paket, "__file__"))
    print("__path__ turi:", type(ns_paket.__path__))
    print("__path__ tarkibi:", list(ns_paket.__path__))

    import ns_paket.servis_a as servis_a
    import ns_paket.servis_b as servis_b
    print(servis_a.salom())
    print(servis_b.salom())

    # Endi runtime'da UCHINCHI joyni qo'shamiz va __path__ DINAMIK
    # qayta hisoblanishini ko'rsatamiz.
    joy_3 = os.path.join(ish_papkasi, "joy_3")
    os.makedirs(os.path.join(joy_3, "ns_paket", "servis_c"))
    with open(os.path.join(joy_3, "ns_paket", "servis_c", "__init__.py"), "w") as f:
        f.write("def salom():\n    return 'servis_c ishladi (keyin qoshildi)'\n")
    sys.path.insert(0, joy_3)

    print("Yangi joy qo'shilgandan keyin __path__:", list(ns_paket.__path__))
    import ns_paket.servis_c as servis_c
    print(servis_c.salom())

    # Tozalash
    for m in list(sys.modules):
        if m.startswith("ns_paket"):
            del sys.modules[m]
    for yol in (joy_1, joy_2, joy_3):
        sys.path.remove(yol)
    shutil.rmtree(ish_papkasi)


if __name__ == "__main__":
    demo()
```

Chiqishi taxminan:

```
ns_paket turi: <class 'module'>
__file__ bormi?: False
__path__ turi: <class '_frozen_importlib_external._NamespacePath'>
__path__ tarkibi: ['.../joy_2/ns_paket', '.../joy_1/ns_paket']
servis_a ishladi
servis_b ishladi
Yangi joy qo'shilgandan keyin __path__: ['.../joy_3/ns_paket', '.../joy_2/ns_paket', '.../joy_1/ns_paket']
servis_c ishladi (keyin qoshildi)
```

Bu demo aniq ko'rsatadi: `ns_paket`ning o'zi `__init__.py`ga ega emas, `__file__`i yo'q, va `__path__`i dinamik ravishda `sys.path`dagi barcha mos portionlarni yig'adi — hatto import qilingandan **keyin** qo'shilgan joylarni ham.

## Keng tarqalgan xatolar

1. **Bo'sh papkani import qilib, `ModuleNotFoundError` kutish, lekin xato chiqmaydi.** PEP 420 tufayli `__init__.py`siz, hatto bo'sh papka ham (agar `sys.path` ichida bo'lsa) muvaffaqiyatli namespace paket sifatida import bo'ladi. Xato faqat ichidagi mavjud bo'lmagan atributga murojaat qilinganda chiqadi — bu debugging'ni qiyinlashtiradi. Yechim: haqiqiy paketlar uchun har doim `__init__.py`ni ongli ravishda qo'shing.

2. **Nisbiy importni to'g'ridan-to'g'ri skript sifatida ishga tushirishga urinish.** `python mening_paketim/modul_a.py` deb ishga tushirilganda, `modul_a.py` `__main__` sifatida yuklanadi va uning `__package__`i bo'sh bo'ladi — shuning uchun `from . import modul_b` `ImportError: attempted relative import with no known parent package` xatosini beradi. To'g'ri yo'l: paketni modul sifatida ishga tushirish — `python -m mening_paketim.modul_a`.

3. **Oddiy paket va namespace paketni aralashtirib yuborish natijasida kutilmagan `__path__` ustidan yozilishi.** Agar bitta `sys.path` yo'lida `paket/__init__.py` (oddiy paket) bo'lsa-yu, boshqa yo'lda xuddi shu nomli `paket/` (`__init__.py`siz) bo'lsa, PathFinder algoritmining 1-qadami tufayli **birinchi topilgan oddiy paket g'olib chiqadi** — ikkinchi papka butunlay e'tiborga olinmaydi (namespace birlashtirish faqat hech qanday oddiy paket topilmaganda ishlaydi). Bu ko'pincha "nega mening ikkinchi joyimdagi modul ko'rinmayapti" degan chalkashlikka olib keladi.

## Mashq/topshiriq

1. `namespace_demo.py` misolidagi `joy_1` va `joy_2`dan birida qasddan `ns_paket/__init__.py` (paket darajasida, quyi-papka emas) fayl yarating va demoni qayta ishga tushiring. `type(ns_paket.__path__)` endi nima ko'rsatishini va nima uchun `servis_b` (yoki `servis_a`, qaysi joy oldinroq bo'lsa) endi ko'rinmasligi mumkinligini tushuntiring.

2. Kichik paket yarating: `matematika/` papkasi ichida `__init__.py` va unda `from .qoshish import qosh` qatori bo'lsin, `qoshish.py` ichida `def qosh(a, b): return a + b` bo'lsin. `__init__.py` orqali eksport qilingandan keyin foydalanuvchi `matematika.qosh(2, 3)` deb yoza olishini, lekin `__init__.py`dagi importsiz `matematika.qoshish.qosh(2, 3)` deb yozishga majbur bo'lishini ko'rsating.

3. Nima uchun namespace paketlar (`__path__` har safar dinamik hisoblanishi tufayli) katta `sys.path`ga ega loyihalarda import tezligiga salbiy ta'sir qilishi mumkinligini tushuntiring.

**Javoblar:**

1. Agar bitta joyda `ns_paket/__init__.py` paydo bo'lsa, PathFinder algoritmining 1-bosqichi ("agar `__init__.py`ga ega mos papka topilsa — oddiy paket yaratiladi, qidiruv **shu yerda to'xtaydi**") ishga tushadi. `sys.path`da qaysi yo'l birinchi tekshirilsa (`sys.path.insert(0, ...)` tartibiga qarab), o'sha yo'ldagi `ns_paket` **oddiy paket** sifatida yuklanadi, va `__path__` endi oddiy `list` (bitta elementli) bo'ladi. Boshqa joydagi `ns_paket` (portion sifatida) butunlay e'tiborga olinmaydi, chunki namespace birlashtirish faqat hech qanday oddiy paket topilmagan taqdirdagina ishga tushadi. Natijada o'sha ikkinchi joydagi `servis_*` submoduli import qilinganda `ModuleNotFoundError` chiqadi.

2.
```python
# matematika/qoshish.py
def qosh(a, b):
    return a + b

# matematika/__init__.py
from .qoshish import qosh
```
```python
import matematika
print(matematika.qosh(2, 3))          # 5 — ishlaydi, __init__.py orqali eksport qilingan
print(matematika.qoshish.qosh(2, 3))  # AttributeError, agar matematika.qoshish avval
                                       # boshqa yo'l bilan import qilinmagan bo'lsa —
                                       # chunki __init__.py faqat qosh nomini paket
                                       # darajasiga chiqargan, qoshish submoduli nomi
                                       # __init__.py orqali avtomatik "ochilmaydi".
```
(Eslatma: aslida `from .qoshish import qosh` ijro etilganda Python `qoshish` submodulini `sys.modules`ga ham, `matematika.qoshish` atributi sifatida ham qo'shadi — shuning uchun amalda ikkinchi qator ham ishlaydi, lekin bu `__init__.py`dagi import natijasida "yon ta'sir" (side effect) sifatida yuz beradi, ataylab loyihalashtirilmagan.)

3. Namespace paketning `__path__`i statik emas — `_NamespacePath` obyekti bo'lib, unga har murojaat qilinganda (yoki hech bo'lmaganda `sys.path`ning tegishli qismi o'zgarganini aniqlash uchun) qayta hisoblash mantiqi ishga tushadi. Bundan tashqari, PathFinder algoritmining o'zi ham namespace paketni aniqlash uchun **oddiy paketdan farqli o'laroq, `sys.path`dagi HAR BIR yo'lni охиригача tekshirishi kerak** (chunki portion bir nechta joyda bo'lishi mumkin, birinchi topilganda to'xtab bo'lmaydi). Agar `sys.path` uzun bo'lsa (ko'p `site-packages`, virtual muhitlar, minglab papka), bu qo'shimcha fayl tizimi operatsiyalari (har bir yo'lda `stat()`/`listdir()` chaqiruvlari) yig'ilib, import vaqtini sezilarli darajada sekinlashtirishi mumkin — bu ayniqsa katta monorepo yoki ko'p paketli muhitlarda sezilarli bo'ladi.

## Qisqacha xulosa

`__init__.py` — an'anaviy Python paketining belgisi va ishga tushirish nuqtasi: u paketni bitta joyga bog'laydi, `__file__` beradi va `from paket import X` kabi qulay eksportlarni ta'minlaydi. PEP 420 bilan kiritilgan namespace paketlar bu talabni yumshatadi — `__init__.py`siz papkalar ham, agar `sys.path`da mos nomli boshqa oddiy paket yoki modul topilmasa, avtomatik ravishda bir nechta joydan yig'ilgan **portion**lar sifatida birlashtiriladi, natijada dinamik `_NamespacePath` bilan `__path__`ga ega bo'ladi. Bu qudratli mexanizm (masalan, korporativ namespace kutubxonalari uchun), lekin u ham noaniq xatolarni (kutilmagan `ModuleNotFoundError` o'rniga muvaffaqiyatli, lekin bo'sh import) yashirishi mumkin — shu sababli oddiy loyihalarda hamon `__init__.py`ni ongli ravishda qo'shish yaxshi amaliyot hisoblanadi. Nisbiy importlar (`from . import x`) faqat modul paket konteksti ichida (`__package__` to'g'ri o'rnatilganda) ishlaydi — buning uchun modulni `python -m paket.modul` shaklida ishga tushirish kerak.

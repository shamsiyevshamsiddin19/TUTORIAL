# MRO va C3 linearizatsiya — `super()` haqiqatda qanday ishlaydi

## Bu darsda nimalarni o'rganasiz

- **MRO** (Method Resolution Order — metod aniqlash tartibi) nima ekanini va uni `__mro__` orqali ko'rishni bilib olasiz
- **Ko'p marta meros olish** (multiple inheritance) da qaysi metod chaqirilishini aniqlaydigan **C3 linearizatsiya** algoritmini tushunasiz
- `super()`ning "eng yaqin ota-klass" emas, balki **MRO bo'yicha keyingisi**ni chaqirishini chuqur tushunasiz
- Mashhur **"olmos muammosi"** (diamond problem) Python'da qanday hal qilinishini bilib olasiz

## Nazariy qism

### Oddiy holatda hammasi tushunarli

4.2-darsda oddiy meros olishni (`class Bola(Ota):`) ko'rganingizda, "qaysi metod chaqiriladi" savoli oson edi: agar `Bola`da metod bo'lsa — u ishlatiladi, bo'lmasa — `Ota`nikiga qaraladi. Lekin Python **ko'p marta meros olish**ni (bir klass bir nechta ota-klassdan meros olishini) ham qo'llab-quvvatlaydi, va bu yerda savol ancha murakkablashadi: agar ikkita ota-klassda **bir xil nomli** metod bo'lsa, qaysi biri ishlatiladi?

**Manba:** Ushbu dars Python rasmiy hujjatlari, "Python's super() considered super!" (Raymond Hettinger) maqolasi va C3 linearizatsiya algoritmi haqidagi ilmiy manba (Barrett va boshqalar, 1996) asosida tuzilgan.

### MRO — "kim birinchi navbatda tekshiriladi"

**MRO** (Method Resolution Order) — bu klassning **o'zi va barcha ota-klasslarining**, aniq, qat'iy belgilangan tartibdagi ro'yxati. `obj.metod()` chaqirilganda, Python aynan shu MRO ro'yxati bo'yicha, **birinchi topilgan** metodni ishlatadi. MRO'ni har qanday klass uchun `__mro__` atributi (yoki `mro()` metodi) orqali ko'rish mumkin:

```python
class A:
    def salom(self):
        return "A dan salom"

class B(A):
    pass

class C(A):
    def salom(self):
        return "C dan salom"

class D(B, C):
    pass


print(D.__mro__)
# (<class 'D'>, <class 'B'>, <class 'C'>, <class 'A'>, <class 'object'>)

d = D()
print(d.salom())   # "C dan salom" — nega? Chunki MRO'da C, A'dan OLDIN keladi!
```

Diqqat qiling: `D(B, C)` — `B`ni **birinchi** ko'rsatgan bo'lsa-da, `B`da `salom` metodi yo'q (u faqat `A`dan meros oladi), shuning uchun Python MRO bo'yicha davom etib, `C`da `salom`ni topadi — va `A`gacha yetib bormaydi, garchi `A` ham "aslida" `salom`ga ega bo'lsa ham.

### "Olmos muammosi" (diamond problem)

Yuqoridagi misol — klassik **"olmos"** shakli:

```
        A
       / \
      B   C
       \ /
        D
```

Bu tuzilma ko'plab tillarda (masalan, C++) chinakam muammo tug'diradi: `D` — `A`ga ikki xil yo'l orqali (B orqali va C orqali) meros oladi, va agar `A`ning konstruktori ikki marta chaqirilsa — bu xato natijalarga olib kelishi mumkin. Python bu muammoni **C3 linearizatsiya** algoritmi orqali hal qiladi — bu algoritm MRO'ni shunday quradiki, **har bir klass MRO ro'yxatida faqat bir marta** paydo bo'ladi, va tartib "mantiqiy" (bolalar ota-onalardan oldin, chapdan-o'ngga tartib saqlanadi) bo'ladi.

### C3 linearizatsiya — algoritm mantig'i

C3 algoritmi uchta qoidaga rioya qiladi:

1. **Mahalliylik saqlanishi:** bola klass har doim o'z ota-klasslaridan oldin keladi.
2. **Monotoniklik:** agar `X` biror klassning MRO'sida `Y`dan oldin kelsa, bu tartib barcha "avlod" klasslarning MRO'sida ham saqlanishi kerak.
3. **Deklaratsiya tartibi saqlanishi:** `class D(B, C):` yozilganda, `B` har doim `C`dan oldin ko'rib chiqiladi (chunki dasturchi ularni shu tartibda yozgan).

Formula (soddalashtirilgan): `L[D] = D + merge(L[B], L[C], [B, C])`, ya'ni `D`ning linearizatsiyasi — bu `D`ning o'zi, so'ng `B`ning linearizatsiyasi, `C`ning linearizatsiyasi va `[B, C]` ro'yxatlarining maxsus "merge" (birlashtirish) natijasi.

```python
class O:  # object'ning o'rnini bosuvchi, ko'rish uchun
    pass

class A(O): pass
class B(O): pass
class C(O): pass
class Chap(A, B): pass
class Ong(B, C): pass
class Pastki(Chap, Ong): pass

for klass in Pastki.__mro__:
    print(klass.__name__)
# Pastki, Chap, Ong, A, B, C, O, object
```

Diqqat qiling: `B` faqat **bir marta**, va `Chap`dagi barcha ota-klasslar (`A`, `B`) `Ong`ning ota-klasslaridan (`C`) oldin, lekin `B` ikkalasiga ham umumiy bo'lgani uchun eng oxirida, ikkala "shoxcha" birlashgandan keyin joylashadi.

### Agar C3 algoritmi "mumkin bo'lmagan" tartib bilan duch kelsa

Ba'zan sizning meros ierarxiyangiz **qarama-qarshi talablar** qo'yishi mumkin (masalan, bitta joyda `A` `B`dan oldin, boshqa joyda `B` `A`dan oldin talab qilinsa). Bunday holda C3 algoritmi **mantiqan izchil tartib topa olmaydi**, va Python bu haqda ochiq xato beradi:

```python
class X: pass
class Y: pass
class A(X, Y): pass
class B(Y, X): pass   # X va Y tartibi TESKARI!

try:
    class C(A, B):   # C3 algoritmi mantiqiy tartib topa olmaydi
        pass
except TypeError as e:
    print("Xatolik:", e)
    # TypeError: Cannot create a consistent method resolution order (MRO) for bases X, Y
```

Bu xato — aslida **foydali** himoya: u sizga dizaynda mantiqiy nomuvofiqlik borligini, "sukut bo'yicha noto'g'ri tanlov" o'rniga, aniq aytadi.

### `super()` — "ota-klass" emas, "MRO bo'yicha keyingisi"

Endi eng ko'p tushunmovchilikka sabab bo'ladigan nuqtaga kelamiz: `super()` **"mening bevosita ota-klassim"**ni emas, balki **"joriy klassning MRO ro'yxatida, mendan keyingi klass"**ni anglatadi. Bu farq — ko'p marta meros olishda **hal qiluvchi** ahamiyatga ega:

```python
class A:
    def salom(self):
        print("A.salom")

class B(A):
    def salom(self):
        print("B.salom boshlanishi")
        super().salom()   # "MRO bo'yicha keyingisi" — bu holatda A
        print("B.salom tugashi")

class C(A):
    def salom(self):
        print("C.salom boshlanishi")
        super().salom()   # "MRO bo'yicha keyingisi"
        print("C.salom tugashi")

class D(B, C):
    def salom(self):
        print("D.salom boshlanishi")
        super().salom()   # MRO: D -> B -> C -> A -> object, demak keyingisi B
        print("D.salom tugashi")


d = D()
d.salom()
```

Natija:

```
D.salom boshlanishi
B.salom boshlanishi
C.salom boshlanishi     <- E'TIBOR: B.salom() ichidagi super().salom() C ga o'tdi, A'ga EMAS!
A.salom
C.salom tugashi
B.salom tugashi
D.salom tugashi
```

Bu — ko'pchilikni hayratda qoldiradigan natija: `B.salom()` ichidagi `super().salom()` **`A.salom()`ga emas, balki `C.salom()`ga** o'tadi! Sabab — `super()` "B'ning ota-klassi A" demasdan, "D obyektining MRO ro'yxatida, B'dan **keyin** kim keladi" deydi, va `D`ning MRO'si (`D, B, C, A, object`) bo'yicha `B`dan keyin `C` keladi. Aynan shu mexanizm tufayli, olmos shaklidagi ierarxiyada, **`A.salom()` faqat bir marta** chaqiriladi — garchi u ikkita yo'l (B va C) orqali "yetib bo'lsa" ham.

### Nega bu muhim: kooperativ ko'p marta meros olish

Bu mexanizm — **kooperativ ko'p marta meros olish** (cooperative multiple inheritance) deb ataladi, va u to'g'ri ishlashi uchun **har bir** klass o'z `super().metod()`ini chaqirishi shart (hattoki u "oxirgi" klass ekanini bilmasa ham) — chunki `super()` MRO'dagi **keyingi kimligini** runtime'da, `type(self)`ning haqiqiy MRO'siga qarab aniqlaydi, kod yozilgan paytdagi klass ierarxiyasiga emas.

## Amaliy misol

Ko'p marta meros olishni real hayotiy misolda — turli "aralashma" (mixin) klasslar orqali — ko'rish:

```python
# mro_super_demo.py

class LogMixin:
    """Har qanday metodning chaqirilishini log qiladi."""
    def harakat_bajar(self):
        print(f"[LOG] {type(self).__name__}.harakat_bajar() chaqirilmoqda...")
        super().harakat_bajar()
        print(f"[LOG] {type(self).__name__}.harakat_bajar() tugadi")


class Vaqtni_Olchash_Mixin:
    """Metod bajarilish vaqtini o'lchaydi."""
    def harakat_bajar(self):
        import time
        boshlanish = time.perf_counter()
        super().harakat_bajar()
        print(f"[VAQT] {time.perf_counter() - boshlanish:.6f} soniya")


class Bazaviy:
    def harakat_bajar(self):
        print("Asosiy ish bajarilmoqda...")


class ToliqXizmat(LogMixin, Vaqtni_Olchash_Mixin, Bazaviy):
    """Ikkala mixin'ni HAM birlashtirib, log qilish VA vaqt o'lchashni oladi —
    hech qanday kod nusxalanmasdan!"""
    pass


print("MRO:", [k.__name__ for k in ToliqXizmat.__mro__])
xizmat = ToliqXizmat()
xizmat.harakat_bajar()
```

Bu — **mixin** (aralashma) naqshi deb ataladi: kichik, mustaqil "qo'shimcha imkoniyat" klasslarini (`LogMixin`, `Vaqtni_Olchash_Mixin`) yaratib, ularni istalgan klassga "aralashtirib" (meros orqali qo'shib), funksionallikni takrorlanmasdan qayta ishlatish mumkin. Bu naqsh — Python standart kutubxonasida ham (masalan, `http.server` moduli) keng qo'llaniladi, va u faqat `super()`ning MRO-asosli, "kooperativ" ishlashi tufayli mumkin bo'ladi.

## Keng tarqalgan xatolar

**Xato 1:** `super()` — "mening ota-klassim" degani deb, uni to'g'ridan-to'g'ri ota-klass nomi bilan almashtirib bo'ladi deb o'ylash.
❌
```python
class B(A):
    def salom(self):
        A.salom(self)   # bu ISHLAYDI, lekin ko'p marta merosda XATOLIKKA olib kelishi mumkin!
```
✅ To'g'ri: `super().salom()` ishlating, `A.salom(self)` emas — chunki ko'p marta meros olishda `A.salom(self)` MRO zanjirini "buzadi" va ba'zi klasslar (masalan, yuqoridagi misoldagi `C`) umuman chaqirilmay qolishi mumkin.

**Xato 2:** Ko'p marta merosda `__init__`ni `super()` orqali chaqirishni unutish (yoki argumentlarni noto'g'ri uzatish).
❌
```python
class A:
    def __init__(self, x):
        self.x = x

class B(A):
    def __init__(self, x, y):
        self.x = x   # A.__init__ chaqirilmadi — agar A da murakkabroq mantiq bo'lsa, yo'qoladi!
        self.y = y
```
✅ To'g'ri:
```python
class B(A):
    def __init__(self, x, y):
        super().__init__(x)   # A.__init__ MRO orqali to'g'ri chaqiriladi
        self.y = y
```
Ko'p marta merosda esa `**kwargs` orqali argumentlarni "zanjir bo'ylab" uzatish tavsiya etiladi, chunki har bir klass MRO'dagi keyingisi qanday argument kutishini oldindan bilmasligi mumkin.

**Xato 3:** Ko'p marta merosda mixin klasslarni "asosiy" klassdan **keyin** yozish.
❌
```python
class ToliqXizmat(Bazaviy, LogMixin, Vaqtni_Olchash_Mixin):
    pass
# MRO: ToliqXizmat, Bazaviy, LogMixin, ... — Bazaviy.harakat_bajar() BIRINCHI
# ishlaydi va super() chaqirmasa, LogMixin va Vaqtni_Olchash_Mixin UMUMAN
# ishlamaydi!
```
✅ To'g'ri: mixin klasslarni odatda **"asosiy" (bazaviy) klassdan oldin** yozish kerak (`class ToliqXizmat(LogMixin, Vaqtni_Olchash_Mixin, Bazaviy):` — yuqoridagi amaliy misoldagidek), chunki MRO chapdan o'ngga tekshiriladi, va bazaviy klass odatda zanjirning "oxirgi bosqichi" bo'lishi kerak.

## Mashq/topshiriq

**(Oson)** Uch klasslik oddiy olmos ierarxiya yarating (`A` -> `B`, `A` -> `C`, `D(B, C)`), har birida bir xil nomli metod yozing (ichida qaysi klass ekanini chop etsin), va `D().metod_nomi()` chaqirilganda qaysi versiya ishlashini, `__mro__` bilan solishtirib, tushuntiring.

**(O'rtacha)** Ikkita mixin klass yozing: biri metod chaqirilishini konsolga "boshlandi"/"tugadi" deb log qilsin, ikkinchisi — istisno (exception) yuz bersa, uni ushlab, xabar bilan qayta chop etsin (`super()` orqali). Ularni bitta "ish bajaruvchi" klassga aralashtiring va ikkalasi ham to'g'ri ishlashini tekshiring.

**(Qiyin)** `super()`siz, faqat to'g'ridan-to'g'ri ota-klass nomlarini chaqirish orqali (`A.metod(self)` uslubida) yozilgan olmos ierarxiya yarating, va bazaviy klassning metodi **ikki marta** chaqirilib qolishini ko'rsating (masalan, `__init__`da hisoblagichni oshirib, oxirida uning qiymati kutilganidan ko'proq ekanini ko'rsating). Keyin buni `super()` bilan tuzatib, hisoblagich to'g'ri (bir marta) oshishini isbotlang.

## Qisqacha xulosa

MRO (Method Resolution Order) — klassning o'zi va barcha ota-klasslarining, **C3 linearizatsiya** algoritmi orqali quriladigan, qat'iy tartiblangan ro'yxati bo'lib, u har bir klass MRO'da faqat bir marta paydo bo'lishini va "bolalar ota-onalardan oldin" mantig'ini kafolatlaydi — bu klassik "olmos muammosi"ni hal qiladi. `super()` — bu "mening ota-klassim" emas, balki **"joriy obyektning MRO ro'yxatida, mendan keyingisi"** degani, va aynan shu, runtime'da aniqlanadigan xatti-harakat tufayli, ko'p marta meros olishda har bir bazaviy klass metodi **aynan bir marta**, to'g'ri tartibda chaqiriladi — bu esa mixin naqshi orqali funksionallikni takrorlanmasdan qayta ishlatish imkonini beradi.

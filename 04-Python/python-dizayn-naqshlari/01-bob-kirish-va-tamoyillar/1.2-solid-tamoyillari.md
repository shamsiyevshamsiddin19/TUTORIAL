# SOLID tamoyillari

## Bu darsda nimalarni o'rganasiz

- SOLID qisqartmasidagi har bir tamoyilni (S-O-L-I-D) alohida tushuntira olasiz
- Har bir tamoyilni buzuvchi "yomon" kodni va uni to'g'rilangan versiyasini yoza olasiz
- Interface Segregation tamoyili Python'da duck typing tufayli nega boshqacha ko'rinishini bilasiz
- Dependency Inversion tamoyilining keyingi darslardagi ko'p naqshlar (Strategy, Factory) uchun nega asos bo'lib xizmat qilishini tushunasiz

## Nazariy qism

### SOLID — nima va kimdan kelib chiqqan

**SOLID** — Robert C. Martin (taxallusi "Uncle Bob") tomonidan tizimlashtirilgan, obyektga yo'naltirilgan dasturlashda **moslashuvchan, qo'llab-quvvatlash oson** kod yozish uchun besh tamoyilning qisqartmasi:

| Harf | Tamoyil | Qisqa mazmuni |
|---|---|---|
| **S** | Single Responsibility Principle (SRP) | Har bir klass — faqat BITTA mas'uliyatga ega bo'lsin |
| **O** | Open/Closed Principle (OCP) | Kod kengayishga OCHIQ, o'zgarishga YOPIQ bo'lsin |
| **L** | Liskov Substitution Principle (LSP) | Bola klass ota klassning o'rnini to'liq bosa olishi kerak |
| **I** | Interface Segregation Principle (ISP) | Kerak bo'lmagan metodlarga "majburlanmaslik" |
| **D** | Dependency Inversion Principle (DIP) | Yuqori darajali kod quyi darajali detallarga emas, abstraksiyaga bog'liq bo'lsin |

Bu besh tamoyil — 1.1-darsda ko'rgan naqshlarning **"nega"** savoliga javob beradi: deyarli har bir GoF naqshi, aslida, shu tamoyillardan bir yoki bir nechtasini amalga oshirishning **aniq usuli** hisoblanadi. Shu sababli SOLID'ni tushunib olish — qolgan butun darslikni tushunishning kaliti bo'ladi.

### S — Single Responsibility Principle (Yagona mas'uliyat tamoyili)

**Ta'rif:** har bir klass faqat **bitta** o'zgarish sababiga ega bo'lishi kerak — ya'ni klass faqat **bitta** vazifani bajarishi va shu vazifaga oid sabab bilangina o'zgartirilishi kerak.

```python
# ❌ SRP buzilgan — bitta klass UCH xil mas'uliyatni bajaradi
class Hisobot:
    def __init__(self, malumotlar):
        self.malumotlar = malumotlar

    def hisobla(self):
        return sum(self.malumotlar)

    def pdf_qilib_saqlash(self, fayl_nomi):     # mas'uliyat 2: formatlash/saqlash
        with open(fayl_nomi, "w") as f:
            f.write(f"Jami: {self.hisobla()}")

    def emailga_yuborish(self, manzil):          # mas'uliyat 3: tarmoq bilan ishlash
        print(f"[EMAIL] {manzil}ga hisobot yuborildi")


# ✅ SRP to'g'ri qo'llangan — har bir klass BITTA ishni qiladi
class Hisobot:
    def __init__(self, malumotlar):
        self.malumotlar = malumotlar

    def hisobla(self):
        return sum(self.malumotlar)


class HisobotSaqlovchi:
    def pdf_qilib_saqlash(self, hisobot: Hisobot, fayl_nomi: str):
        with open(fayl_nomi, "w") as f:
            f.write(f"Jami: {hisobot.hisobla()}")


class HisobotYuboruvchi:
    def emailga_yuborish(self, hisobot: Hisobot, manzil: str):
        print(f"[EMAIL] {manzil}ga hisobot yuborildi: {hisobot.hisobla()}")
```

Nega bu muhim? Chunki agar saqlash formatini (PDF → Excel) o'zgartirish kerak bo'lsa, siz **faqat** `HisobotSaqlovchi`ni o'zgartirasiz, `Hisobot` yoki `HisobotYuboruvchi`ga tegmaysiz. Har bir klassning **o'zgarish sababi** mustaqil bo'lib qoladi — bu esa testlashni ham osonlashtiradi (har bir klassni alohida, kichik unit-test bilan tekshirish mumkin).

### O — Open/Closed Principle (Ochiq/Yopiq tamoyili)

**Ta'rif:** dastur bo'laklari (klasslar, funksiyalar) **kengayishga ochiq**, lekin **o'zgarishga yopiq** bo'lishi kerak — ya'ni yangi funksionallik qo'shish uchun **mavjud, ishlab turgan kodni o'zgartirmasdan**, faqat **yangi kod qo'shish** orqali erishish kerak.

Bu — aynan 1.1-darsdagi "Amaliy misol"da ko'rgan `bildirishnoma_yubor_yomon` (yomon, elif zanjiri) va `bildirishnoma_yubor_yaxshi` (polimorfizm orqali) farqining o'zi:

```python
from abc import ABC, abstractmethod

# ✅ OCP to'g'ri qo'llangan: yangi shakl qo'shish uchun MAVJUD kodga tegilmaydi
class Shakl(ABC):
    @abstractmethod
    def yuza(self) -> float: ...


class Tortburchak(Shakl):
    def __init__(self, en, boy):
        self.en, self.boy = en, boy

    def yuza(self) -> float:
        return self.en * self.boy


class Doira(Shakl):
    def __init__(self, radius):
        self.radius = radius

    def yuza(self) -> float:
        return 3.14159 * self.radius ** 2


def jami_yuza(shakllar: list[Shakl]) -> float:
    return sum(shakl.yuza() for shakl in shakllar)   # YANGI shakl qo'shilsa ham, bu funksiya O'ZGARMAYDI


# Yangi shakl — Uchburchak — qo'shish uchun faqat YANGI klass yoziladi:
class Uchburchak(Shakl):
    def __init__(self, asos, balandlik):
        self.asos, self.balandlik = asos, balandlik

    def yuza(self) -> float:
        return 0.5 * self.asos * self.balandlik


print(jami_yuza([Tortburchak(4, 5), Doira(3), Uchburchak(6, 4)]))   # 52.27431
```

`jami_yuza` funksiyasi — `Shakl` abstraksiyasiga bog'liq, aniq klasslarga emas. Shu sababli qancha yangi shakl qo'shilsa ham, bu funksiya **hech qachon** o'zgartirilmaydi — bu OCP'ning aynan mohiyati.

### L — Liskov Substitution Principle (Liskov o'rnini bosish tamoyili)

**Ta'rif:** (Barbara Liskov, 1987) — agar `B` klassi `A` klassidan meros olgan bo'lsa, dasturning har qanday joyida `A` o'rniga `B`ni qo'yish mumkin bo'lishi kerak, dastur **noto'g'ri ishlamasligi** kerak.

Klassik, mashhur misol — "To'g'ri to'rtburchak va kvadrat" muammosi:

```python
# ❌ LSP buzilgan — Kvadrat matematik jihatdan ToGriToRTburchakning "turi" bo'lsa ham,
# dasturiy jihatdan uning o'rnini bosa olmaydi
class ToGriToRTburchak:
    def __init__(self, en, boy):
        self.en = en
        self.boy = boy

    def enini_ozgartir(self, yangi_en):
        self.en = yangi_en

    def boyini_ozgartir(self, yangi_boy):
        self.boy = yangi_boy

    def yuza(self):
        return self.en * self.boy


class Kvadrat(ToGriToRTburchak):
    def enini_ozgartir(self, yangi_en):
        self.en = yangi_en
        self.boy = yangi_en          # kvadratda en=boy bo'lishi SHART — lekin bu kutilmagan "yon ta'sir"

    def boyini_ozgartir(self, yangi_boy):
        self.en = yangi_boy
        self.boy = yangi_boy


def test_tortburchak(shakl: ToGriToRTburchak):
    shakl.enini_ozgartir(5)
    shakl.boyini_ozgartir(4)
    # ToGriToRTburchak uchun kutilgan natija: 5 * 4 = 20
    assert shakl.yuza() == 20, f"Kutilmagan natija: {shakl.yuza()}"


test_tortburchak(ToGriToRTburchak(2, 2))   # OK, 20
test_tortburchak(Kvadrat(2, 2))             # AssertionError! Natija 16 (chunki boyini_ozgartir ENNI ham o'zgartirdi)
```

Bu yerda `Kvadrat` — `ToGriToRTburchak`ning **o'rnini bosa olmaydi**, chunki u kutilmagan tarzda ikkinchi atributni ham o'zgartiradi — bu dasturning boshqa qismlarini (masalan, yuqoridagi test) buzadi.

**To'g'ri yechim** — meros olish o'rniga, ikkisini mustaqil, umumiy interfeysdan (`Shakl`) meros oluvchi klasslar qilib yozish (OCP misolidagi kabi), **meros munosabatini faqat haqiqatan "IS-A" (u — bu) munosabat to'liq saqlanganda** ishlatish.

### I — Interface Segregation Principle (Interfeyslarni ajratish tamoyili)

**Ta'rif:** klass **ishlatmaydigan** metodlarni amalga oshirishga "majburlanmasligi" kerak — kattaroq, "semiz" interfeys o'rniga bir nechta kichik, aniq maqsadli interfeys yaxshiroq.

Klassik (Java/C#'ga xos) misol — bitta katta `Ishchi` interfeysi:

```python
from abc import ABC, abstractmethod

# ❌ ISP buzilgan — "semiz" interfeys, har bir klass BARCHA metodlarni amalga oshirishga majbur
class IshchiInterfeysi(ABC):
    @abstractmethod
    def ishla(self): ...
    @abstractmethod
    def ovqatlan(self): ...


class Robot(IshchiInterfeysi):
    def ishla(self):
        print("Robot ishlayapti")

    def ovqatlan(self):
        # Robot ovqatlanmaydi! Lekin interfeys shu metodni MAJBUR qiladi.
        raise NotImplementedError("Robotlar ovqatlanmaydi")


# ✅ ISP to'g'ri qo'llangan — kichik, aniq interfeyslarga bo'lingan
class Ishlovchi(ABC):
    @abstractmethod
    def ishla(self): ...


class Ovqatlanuvchi(ABC):
    @abstractmethod
    def ovqatlan(self): ...


class Inson(Ishlovchi, Ovqatlanuvchi):
    def ishla(self):
        print("Inson ishlayapti")

    def ovqatlan(self):
        print("Inson ovqatlanyapti")


class Robot(Ishlovchi):          # faqat kerakli interfeysni meros oladi
    def ishla(self):
        print("Robot ishlayapti")
```

**Python'da ISP qanday boshqacha ko'rinadi?** Python'ning **duck typing** tabiati (4.3-darsda ko'rgan "agar u o'rdakdek yursa va o'rdakdek g'ag'illasa — bu o'rdak" tamoyili) tufayli, ko'p hollarda Python'da **rasmiy interfeys klassi umuman kerak bo'lmaydi**. Siz shunchaki klassingizda qaysi metod kerak bo'lsa, shuni yozasiz, va Python runtime vaqtida (hech qanday formal `implements` deklaratsiyasiz) "mos kelsa — ishlaydi" tamoyili bilan ishlaydi. Zamonaviy Python'da esa `typing.Protocol` (5.5-darsda ko'rilgan type hints'ning davomi) — statik tekshiruv (`mypy`) uchun **majburiy meros olmasdan**, "structural typing" orqali ISP'ni tabiiy ravishda ta'minlaydi:

```python
from typing import Protocol

class Ishlovchi(Protocol):
    def ishla(self) -> None: ...

# Robot klassi Ishlovchi'dan MEROS OLMAYDI, lekin ishla() metodi bo'lgani uchun
# mypy uni "Ishlovchi mos keladi" deb hisoblaydi — bu klassik OOP'dagi interfeys
# majburiyatidan ANCHA yengilroq, "majburlashsiz" yondashuv.
class Robot:
    def ishla(self) -> None:
        print("Robot ishlayapti")
```

### D — Dependency Inversion Principle (Bog'liqlikni teskari aylantirish tamoyili)

**Ta'rif:** yuqori darajali modullar (biznes mantiq) quyi darajali modullarga (aniq implementatsiya detallariga) **to'g'ridan-to'g'ri bog'liq bo'lmasligi** kerak — ikkisi ham **abstraksiyaga** bog'liq bo'lishi kerak.

```python
# ❌ DIP buzilgan — yuqori darajali BuyurtmaXizmati to'g'ridan-to'g'ri aniq MySqlOmbor klassiga bog'liq
class MySqlOmbor:
    def saqla(self, malumot):
        print(f"[MySQL] saqlandi: {malumot}")


class BuyurtmaXizmati:
    def __init__(self):
        self.ombor = MySqlOmbor()      # QATTIQ bog'lanish — boshqa ombor turiga o'tish uchun bu klass o'zgartiriladi

    def buyurtma_bераr(self, malumot):
        self.ombor.saqla(malumot)


# ✅ DIP to'g'ri qo'llangan — ikkisi ham abstraksiyaga (OmborInterfeysi) bog'liq
from abc import ABC, abstractmethod

class OmborInterfeysi(ABC):
    @abstractmethod
    def saqla(self, malumot): ...


class MySqlOmbor(OmborInterfeysi):
    def saqla(self, malumot):
        print(f"[MySQL] saqlandi: {malumot}")


class PostgresOmbor(OmborInterfeysi):
    def saqla(self, malumot):
        print(f"[PostgreSQL] saqlandi: {malumot}")


class BuyurtmaXizmati:
    def __init__(self, ombor: OmborInterfeysi):     # abstraksiya INJEKSIYA qilinadi (bu — Dependency Injection,
        self.ombor = ombor                           # 5.3-darsda alohida ko'ramiz)

    def buyurtma_bераr(self, malumot):
        self.ombor.saqla(malumot)


BuyurtmaXizmati(MySqlOmbor()).buyurtma_bераr("buyurtma#1")        # [MySQL] saqlandi: buyurtma#1
BuyurtmaXizmati(PostgresOmbor()).buyurtma_bераr("buyurtma#2")     # [PostgreSQL] saqlandi: buyurtma#2
```

Bu yerda "teskari aylantirish" (inversion) so'zi — oddiy holatda `BuyurtmaXizmati` **o'zi** o'ziga kerakli ombor turini (`MySqlOmbor`) yaratishi "to'g'ri" tuyuladi, lekin DIP buni **teskari aylantiradi**: endi ombor obyekti **tashqaridan beriladi** (parametr sifatida), klass esa faqat **abstraksiyani** biladi. Bu — keyingi darslarda ko'radigan Strategy (4.1), Factory Method (2.2) va Dependency Injection (5.3) naqshlarining barchasining **tub asosi** hisoblanadi.

## Amaliy misol

Quyida — barcha besh tamoyilni birlashtirgan, kichik "bildirishnoma tizimi" misoli (1.1-darsdagi misolning rivojlantirilgan, SOLID'ga to'liq mos versiyasi):

```python
# solid_bildirishnoma.py
from abc import ABC, abstractmethod
from dataclasses import dataclass


# S — har bir klass bitta ishni qiladi: Xabar — faqat ma'lumotni saqlaydi
@dataclass
class Xabar:
    matn: str
    manzil: str


# I — kichik, aniq interfeys (faqat bitta metod)
class Yetkazuvchi(ABC):
    @abstractmethod
    def yetkaz(self, xabar: Xabar) -> bool: ...


# O — yangi yetkazuvchi qo'shish uchun MAVJUD kodga tegmaymiz
class EmailYetkazuvchi(Yetkazuvchi):
    def yetkaz(self, xabar: Xabar) -> bool:
        print(f"[EMAIL] {xabar.manzil}ga: {xabar.matn}")
        return True


class SmsYetkazuvchi(Yetkazuvchi):
    def yetkaz(self, xabar: Xabar) -> bool:
        print(f"[SMS] {xabar.manzil}ga: {xabar.matn}")
        return True


# L — har qanday Yetkazuvchi bola klassi, ota klass o'rnida muammosiz ishlashi kerak
# (ikkisi ham bool qaytaradi, ikkisi ham yetkaz(xabar) signaturasiga amal qiladi)


# D — BildirishnomaXizmati aniq EmailYetkazuvchi/SmsYetkazuvchiga emas, Yetkazuvchi abstraksiyasiga bog'liq
class BildirishnomaXizmati:
    def __init__(self, yetkazuvchilar: list[Yetkazuvchi]):
        self._yetkazuvchilar = yetkazuvchilar

    def hammaga_yubor(self, xabar: Xabar) -> int:
        muvaffaqiyatli = 0
        for yetkazuvchi in self._yetkazuvchilar:
            if yetkazuvchi.yetkaz(xabar):
                muvaffaqiyatli += 1
        return muvaffaqiyatli


xizmat = BildirishnomaXizmati([EmailYetkazuvchi(), SmsYetkazuvchi()])
soni = xizmat.hammaga_yubor(Xabar("Buyurtmangiz yetib bordi!", "+998901234567"))
print(f"Jami {soni} ta kanal orqali yuborildi")
# [EMAIL] +998901234567ga: Buyurtmangiz yetib bordi!
# [SMS] +998901234567ga: Buyurtmangiz yetib bordi!
# Jami 2 ta kanal orqali yuborildi
```

Bu misolda: `Xabar` — faqat ma'lumot saqlaydi (**S**); yangi `TelegramYetkazuvchi` qo'shish `BildirishnomaXizmati`ga tegmaydi (**O**); barcha yetkazuvchilar bir xil signaturaga amal qilgani uchun bir-birining o'rnini bosa oladi (**L**); `Yetkazuvchi` interfeysi faqat bitta, aniq metoddan iborat (**I**); `BildirishnomaXizmati` konkret klasslarga emas, abstraksiyaga bog'liq va ro'yxat **tashqaridan beriladi** (**D**).

## Keng tarqalgan xatolar

**Xato 1:** SRP'ni "klass faqat bitta metodga ega bo'lishi kerak" deb noto'g'ri tushunish.
❌ Har bir metodni alohida mikro-klassga ajratib, 10 ta klassdan iborat ortiqcha murakkab tuzilma yaratish.
✅ To'g'ri: SRP — "bitta **o'zgarish sababi**" haqida, "bitta metod" haqida emas. Klassda bir nechta bir-biriga mantiqan bog'liq metod bo'lishi mumkin, muhimi — ularning barchasi **bitta mas'uliyat** doirasida bo'lishi.

**Xato 2:** OCP'ni "hamma narsani oldindan abstraksiya qilib qo'yish" deb tushunish.
❌
```python
# Faqat BITTA implementatsiya bo'lsa ham, "kelajakda kerak bo'lar" deb abstrakt klass yaratish
class OmborInterfeysi(ABC):
    @abstractmethod
    def saqla(self, m): ...

class YagonaOmbor(OmborInterfeysi):     # boshqa implementatsiya HECH QACHON bo'lmaydi
    def saqla(self, m): ...
```
✅ To'g'ri: OCP — 1.1-darsdagi YAGNI tamoyiliga mos holda, **real ehtiyoj** (ikkinchi implementatsiya haqiqatan paydo bo'lganda yoki paydo bo'lishi **aniq** bilinganda) paydo bo'lgandagina qo'llaniladi. Bitta implementatsiya uchun abstraksiya — ortiqcha murakkablik.

**Xato 3:** LSP'ni faqat "metod signaturasi mos kelishi" bilan cheklab tushunish, **xulq-atvor**ni unutish.
❌ Bola klass ota klassning metodini override qilib, signaturasi bir xil bo'lsa-da, **mutlaqo boshqa, kutilmagan natija** qaytaradi (yuqoridagi `Kvadrat` misoli kabi).
✅ To'g'ri: LSP — bola klass ota klassning **"shartnomasi"ni** (nima qaytarishi, qanday yon ta'sirlar borligi) ham to'liq saqlashini talab qiladi, shunchaki metod nomi va argumentlari emas.

## Mashq/topshiriq

**(Oson)** Quyidagi klassni SRP'ga mos ravishda ikkiga ajrating: `Foydalanuvchi` klassi ham foydalanuvchi ma'lumotini saqlaydi, ham parolni validatsiya qiladi (`parol_togrimi(parol)` — kamida 8 belgi bo'lishini tekshiradi).

**(O'rtacha)** Quyidagi kodda qaysi SOLID tamoyili buzilganini aniqlang va to'g'rilang:
```python
class Chop_etuvchi:
    def chop_et(self, matn, formatda="konsol"):
        if formatda == "konsol":
            print(matn)
        elif formatda == "fayl":
            with open("chiqish.txt", "w") as f:
                f.write(matn)
        elif formatda == "json":
            import json
            print(json.dumps({"matn": matn}))
```

**(Qiyin)** `OmborInterfeysi`/`MySqlOmbor`/`PostgresOmbor` misoliga asoslanib, DIP'ga to'liq mos holda, konstruktorga beriladigan `tolov_usuli` (`KartaToTolov` yoki `NaqdToTolov`, ikkisi ham umumiy `TolovUsuli` abstraksiyasidan meros oluvchi) orqali ishlaydigan `Kassa` klassini yozing — `Kassa.hisoblash(summa)` metodi tanlangan usul orqali to'lovni amalga oshirsin.

## Qisqacha xulosa

SOLID — Robert C. Martin tomonidan tizimlashtirilgan besh tamoyil bo'lib, har bir klass bitta mas'uliyatga ega bo'lishi (**S**), kod kengayishga ochiq lekin o'zgarishga yopiq bo'lishi (**O**), bola klass ota klassning o'rnini to'liq bosa olishi (**L**), interfeyslar kichik va aniq bo'lishi (**I**, Python'da ko'pincha `Protocol` orqali majburlashsiz ta'minlanadi) va yuqori darajali kod konkret implementatsiyalarga emas, abstraksiyaga bog'liq bo'lishi (**D**) kerakligini belgilaydi; bu besh tamoyil — keyingi boblarda ko'riladigan deyarli barcha yaratuvchi, tuzilma va xatti-harakat naqshlarining nazariy asosini tashkil etadi, va ularni tushunish naqshlarni **mexanik yodlash** emas, balki **nega aynan shu tuzilma tanlangani**ni tushunishga yordam beradi.

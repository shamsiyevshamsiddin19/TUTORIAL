# Dependency Injection naqshi

## Bu darsda nimalarni o'rganasiz

- Dependency Injection (bog'liqlikni kiritish) naqshi nima ekanini va u qaysi muammoni hal qilishini tushuntira olasiz
- Constructor injection, method injection va ularning farqini bilasiz
- Python'da nega ko'pincha alohida "DI konteyner" kerak bo'lmasligini (Java/C#'dan farqli) tushunasiz
- Duck typing bilan Dependency Injection'ning qanday bog'langanini bilasiz
- Testlarda mock obyektlarni "inject" qilish orqali testlarni qanday soddalashtirishni qo'llay olasiz

## Nazariy qism

### Muammo — "qattiq bog'lanish" (tight coupling)

Klasslar ko'pincha ishlash uchun boshqa obyektlarga muhtoj bo'ladi — bu obyektlar o'zining **bog'liqliklari (dependencies)** deb ataladi. Eng sodda, lekin muammoli yondashuv — bog'liqlikni klassning o'z ichida, to'g'ridan-to'g'ri yaratish:

```python
class EmailYuboruvchi:
    def yubor(self, manzil, xabar):
        print(f"[EMAIL] {manzil}ga yuborildi: {xabar}")


class RoyxatdanOtish:
    def __init__(self):
        self.yuboruvchi = EmailYuboruvchi()     # QATTIQ BOG'LANISH — o'zi yaratadi

    def royxatdan_otkaz(self, email):
        # ... ro'yxatdan o'tkazish mantiqi ...
        self.yuboruvchi.yubor(email, "Xush kelibsiz!")


r = RoyxatdanOtish()
r.royxatdan_otkaz("ali@mail.uz")
```

Bu kod ishlaydi, lekin ikkita jiddiy muammoga ega:

1. **Moslashuvchanlik yo'q:** agar ertaga SMS orqali ham xabar yuborish kerak bo'lsa (yoki test paytida haqiqiy email yubormasdan tekshirish kerak bo'lsa), `RoyxatdanOtish` klassining **ichini** o'zgartirish kerak bo'ladi.
2. **Test qilish qiyin:** `royxatdan_otkaz()`ni test qilganda, **haqiqatan** email yuborilib ketadi (yoki yuborishga urinadi, tarmoq xatosi bersa test ham ishlamaydi) — chunki `EmailYuboruvchi` klass ichida qattiq "qotirilgan" (hardcoded).

### Yechim — bog'liqlikni "tashqaridan kiritish"

**Dependency Injection (DI)** — oddiy g'oya: klass o'ziga kerakli bog'liqlikni **o'zi yaratmaydi**, balki uni **tashqaridan, argument sifatida qabul qiladi**:

```python
class EmailYuboruvchi:
    def yubor(self, manzil, xabar):
        print(f"[EMAIL] {manzil}ga yuborildi: {xabar}")


class SMSYuboruvchi:
    def yubor(self, manzil, xabar):
        print(f"[SMS] {manzil}ga yuborildi: {xabar}")


class RoyxatdanOtish:
    def __init__(self, yuboruvchi):          # bog'liqlik TASHQARIDAN "inject" qilinadi
        self.yuboruvchi = yuboruvchi

    def royxatdan_otkaz(self, manzil):
        self.yuboruvchi.yubor(manzil, "Xush kelibsiz!")


r1 = RoyxatdanOtish(EmailYuboruvchi())       # email orqali
r1.royxatdan_otkaz("ali@mail.uz")

r2 = RoyxatdanOtish(SMSYuboruvchi())          # SMS orqali — RoyxatdanOtish klassi O'ZGARMADI!
r2.royxatdan_otkaz("+998901234567")
```

Bu — **constructor injection**: bog'liqlik `__init__` orqali, obyekt yaratilayotganda kiritiladi. Natijada `RoyxatdanOtish` klassi **qaysi aniq yuborish usuli ishlatilayotganini bilmaydi** — u faqat "yuboruvchi" deb nomlangan, `yubor(manzil, xabar)` metodiga ega **istalgan** obyekt bilan ishlaydi. Bu — 4.3-darsda ko'rgan **polimorfizm va duck typing**ning to'g'ridan-to'g'ri qo'llanilishi.

### Constructor injection va method injection

Bog'liqlikni kiritishning ikki asosiy yo'li bor:

```python
class Hisoblagich:
    # 1) CONSTRUCTOR INJECTION — bog'liqlik butun obyekt umri davomida kerak bo'lsa
    def __init__(self, loglovchi):
        self.loglovchi = loglovchi

    def qosh(self, a, b):
        natija = a + b
        self.loglovchi.yoz(f"{a} + {b} = {natija}")
        return natija


class HisobOperatsiyasi:
    # 2) METHOD INJECTION — bog'liqlik faqat BITTA metod uchun kerak bo'lsa
    def bajar(self, amal, a, b, loglovchi=None):
        natija = amal(a, b)
        if loglovchi:
            loglovchi.yoz(f"Amal bajarildi: {natija}")
        return natija
```

**Constructor injection** — bog'liqlik obyektning "umri" davomida bir necha marta kerak bo'ladigan holatlar uchun tabiiy tanlov (yuqoridagi `RoyxatdanOtish` misoli). **Method injection** — bog'liqlik faqat bitta aniq chaqiruv uchun, vaqtinchalik kerak bo'lganda qulay.

### Python'da nega alohida "DI konteyner" kam kerak bo'ladi

Java yoki C# kabi statik tipizatsiyali tillarda Dependency Injection ko'pincha **DI konteyner** (Spring, .NET DI kabi maxsus kutubxonalar) orqali amalga oshiriladi — chunki bu tillarda interfeyslar (interface) qat'iy e'lon qilinishi, va "qaysi konkret klass qaysi interfeysni amalga oshirishi" aniq belgilanishi kerak bo'ladi.

Python'da vaziyat boshqacha — **duck typing** tufayli (4.3-darsda ko'rgan "agar o'rdak kabi suzsa va g'oz-g'oz deb qichqirsa — u o'rdak" tamoyili):

```python
# Python'da "interfeys" kerak emas — faqat kerakli METOD mavjud bo'lishi kifoya
class KonsolgaYozuvchi:
    def yoz(self, xabar):
        print(f"[KONSOL] {xabar}")


class FaylgaYozuvchi:
    def yoz(self, xabar):
        with open("log.txt", "a") as f:
            f.write(xabar + "\n")


# Hisoblagich klassi YUQORIDA e'lon qilingan — u ikkisidan QAYSI BIRI bilan ham ishlaydi,
# chunki unga faqat ".yoz(xabar)" metodiga ega obyekt kerak, aniq TUR emas
h1 = Hisoblagich(KonsolgaYozuvchi())
h1.qosh(5, 3)

h2 = Hisoblagich(FaylgaYozuvchi())
h2.qosh(10, 20)
```

Bu — Python'da Dependency Injection naqshini qo'llash uchun **maxsus freymvork, interfeys e'loni yoki annotatsiya kerak emasligi** degani: oddiy funksiya argumenti darajasidagi kiritish (yuqoridagi barcha misollar) **to'liq yetarli**. Katta loyihalarda (ko'plab bog'liqliklar, murakkab "qaysi obyekt qaysi obyektga bog'liq" grafigi bo'lganda) `dependency-injector` kabi uchinchi tomon kutubxonalar ham mavjud, lekin ular **shart emas** — ko'pchilik Python loyihalari (shu jumladan Django, FastAPI'ning ba'zi qismlari) oddiy constructor injection bilan to'liq yetarlicha ishlaydi.

### Type hints bilan "bog'liqlik shartnomasi"ni ko'rsatish

Garchi Python'da qat'iy interfeys talab qilinmasa ham, 5.5-darsda ko'rgan **type hints** va `typing.Protocol` orqali "bu obyekt qanday ko'rinishda bo'lishi kerak"ligini **hujjatlashtirish** mumkin (bu — ixtiyoriy, lekin katta loyihalarda juda foydali):

```python
from typing import Protocol


class Yuboruvchi(Protocol):          # "Protocol" — rasmiy interfeys emas, lekin SHAKLNI belgilaydi
    def yubor(self, manzil: str, xabar: str) -> None: ...


class RoyxatdanOtish:
    def __init__(self, yuboruvchi: Yuboruvchi) -> None:    # IDE/mypy endi tekshira oladi
        self.yuboruvchi = yuboruvchi
```

`Protocol` — "structural typing" (strukturaviy tiplash) imkonini beradi: `EmailYuboruvchi` klassi `Yuboruvchi`dan **meros olmasa ham**, agar unda mos `yubor(manzil, xabar)` metodi bo'lsa, mypy (statik tur tekshiruvchisi) uni "`Yuboruvchi` protokoliga mos" deb hisoblaydi. Bu — duck typing'ning **statik tekshirish bilan birlashtirilgan** shakli.

### Testlashda eng katta foyda — mock obyektlarni "inject" qilish

Dependency Injection'ning amaliyotdagi eng katta foydasi — **test yozish osonlashadi**. 6.2-darsda ko'rgan `pytest` bilan:

```python
class SoxtaYuboruvchi:
    """Test uchun — haqiqiy email/SMS yubormaydi, faqat ESLAB QOLADI."""

    def __init__(self):
        self.yuborilgan_xabarlar = []

    def yubor(self, manzil, xabar):
        self.yuborilgan_xabarlar.append((manzil, xabar))     # haqiqiy tarmoq SO'ROVI YO'Q


def test_royxatdan_otish_xabar_yuboradi():
    soxta = SoxtaYuboruvchi()
    r = RoyxatdanOtish(soxta)             # HAQIQIY EmailYuboruvchi o'rniga SOXTASINI "inject" qilamiz

    r.royxatdan_otkaz("test@mail.uz")

    assert len(soxta.yuborilgan_xabarlar) == 1
    assert soxta.yuborilgan_xabarlar[0][0] == "test@mail.uz"
```

Agar `RoyxatdanOtish` o'zining `EmailYuboruvchi`sini **o'zi yaratgan** bo'lsa (birinchi, "qattiq bog'langan" misoldagidek), bu testni yozishning iloji **yo'q** edi — har safar test ishga tushganda haqiqiy email yuborishga urinardi. Dependency Injection — kodni **testga mos (testable)** qiladi, chunki haqiqiy bog'liqlikni soxta (fake/mock/stub) bilan almashtirish — oddiy argument almashtirishdan boshqa narsa emas.

## Amaliy misol

To'lov tizimini (payment processing) turli "to'lov provayder"lari bilan ishlaydigan qilib, Dependency Injection orqali loyihalaymiz:

```python
# dependency_injection_amaliy.py
from typing import Protocol


class TolovProvayderi(Protocol):
    """Har qanday to'lov provayderi shu "shaklga" mos bo'lishi kerak."""
    def tolovni_amalga_oshir(self, summa: float) -> bool: ...


class StripeProvayder:
    def tolovni_amalga_oshir(self, summa: float) -> bool:
        print(f"[Stripe] {summa} so'm uchun so'rov yuborildi")
        return True       # soddalashtirish uchun har doim muvaffaqiyatli


class PayPalProvayder:
    def tolovni_amalga_oshir(self, summa: float) -> bool:
        print(f"[PayPal] {summa} so'm uchun so'rov yuborildi")
        return True


class SoxtaProvayder:
    """Faqat testlar uchun — haqiqiy tarmoq so'rovi yubormaydi."""
    def __init__(self, muvaffaqiyatli=True):
        self.muvaffaqiyatli = muvaffaqiyatli
        self.chaqiruvlar = []

    def tolovni_amalga_oshir(self, summa: float) -> bool:
        self.chaqiruvlar.append(summa)
        return self.muvaffaqiyatli


class BuyurtmaServisi:
    """Qaysi to'lov provayderi ishlatilishini BILMAYDI — faqat protokolga ishonadi."""

    def __init__(self, tolov_provayderi: TolovProvayderi):
        self.tolov_provayderi = tolov_provayderi           # CONSTRUCTOR INJECTION

    def buyurtma_bering(self, mahsulot: str, summa: float) -> str:
        muvaffaqiyatli = self.tolov_provayderi.tolovni_amalga_oshir(summa)
        if muvaffaqiyatli:
            return f"Buyurtma qabul qilindi: {mahsulot}"
        return "To'lov amalga oshmadi"


# ISHLAB CHIQARISHDA (production) — haqiqiy provayder bilan
servis_stripe = BuyurtmaServisi(StripeProvayder())
print(servis_stripe.buyurtma_bering("Noutbuk", 5000000))
# [Stripe] 5000000 so'm uchun so'rov yuborildi
# Buyurtma qabul qilindi: Noutbuk

servis_paypal = BuyurtmaServisi(PayPalProvayder())
print(servis_paypal.buyurtma_bering("Sichqoncha", 150000))
# [PayPal] 150000 so'm uchun so'rov yuborildi
# Buyurtma qabul qilindi: Sichqoncha

# TESTDA — soxta provayder bilan, tarmoqqa HECH QANDAY so'rov YO'Q
soxta = SoxtaProvayder(muvaffaqiyatli=False)
servis_test = BuyurtmaServisi(soxta)
natija = servis_test.buyurtma_bering("Klaviatura", 200000)
print(natija)                      # "To'lov amalga oshmadi"
print(soxta.chaqiruvlar)           # [200000] — chaqiruv ESLAB QOLINDI, tekshirish mumkin
```

`BuyurtmaServisi` — `StripeProvayder`, `PayPalProvayder` yoki `SoxtaProvayder`dan **birortasi haqida ham bilmaydi**: u faqat `tolovni_amalga_oshir(summa)` metodiga ega **istalgan** obyekt bilan ishlaydi. Bu — Dependency Injection naqshining to'liq kuchi: **nima bilan ishlashni tashqaridan belgilash, ichki mantiqni o'zgartirmasdan**.

## Keng tarqalgan xatolar

**Xato 1:** bog'liqlikni klass ichida to'g'ridan-to'g'ri yaratish (eng tez-tez uchraydigan muammo).

❌
```python
class Servis:
    def __init__(self):
        self.mb = PostgreSQLUlanish()    # QATTIQ BOG'LANISH — hech qachon almashtirib bo'lmaydi
```
✅ To'g'ri: `def __init__(self, mb): self.mb = mb` — bog'liqlikni tashqaridan qabul qiling, hatto hozircha faqat bitta turdagi obyekt ishlatilsa ham (kelajakda almashtirish, yoki test yozish osonlashadi).

**Xato 2:** Dependency Injection'ni "har doim, har bir argument uchun" qo'llashga urinish — ortiqcha murakkablashtirish.

❌
```python
class Hisoblagich:
    def __init__(self, qoshuvchi, ayiruvchi, kopaytiruvchi, boluvchi, logchi, formatlagich):
        # 6 TA bog'liqlik — oddiy arifmetika uchun BUNDAY MURAKKABLIK ORTIQCHA!
        ...
```
Dependency Injection — **tashqi resurslarga** (ma'lumotlar bazasi, tarmoq xizmati, fayl tizimi, vaqt/tasodifiy son generatori kabi — ya'ni testda almashtirish kerak bo'lishi **mumkin bo'lgan** narsalar) bog'liqlik uchun ishlatiladi, oddiy arifmetik yoki sof (pure) funksiyalar uchun **shart emas**.

✅ To'g'ri: faqat **haqiqatan tashqi, almashtirilishi mumkin bo'lgan** bog'liqliklarni (tarmoq, baza, fayl, vaqt) inject qiling; oddiy hisob-kitob mantiqini to'g'ridan-to'g'ri yozing.

**Xato 3:** "default" qiymat sifatida mutable obyekt yaratib qo'yish (3.1-darsda ko'rgan umumiy Python xatosi bilan bog'liq).

❌
```python
class Servis:
    def __init__(self, logchi=KonsolgaYozuvchi()):   # DEFAULT ARGUMENT — bitta marta yaratiladi!
        self.logchi = logchi
```
Agar `KonsolgaYozuvchi()` mutable holatga ega bo'lsa (masalan, ichida ro'yxat saqlasa), bu **barcha** `Servis` obyektlari uchun **bitta umumiy** `logchi` obyektini ulashtirib yuborishi mumkin — chunki default qiymat klass ta'rif qilinganda **bir marta** hisoblanadi, har safar yangi obyekt yaratilmaydi.

✅ To'g'ri: `def __init__(self, logchi=None): self.logchi = logchi or KonsolgaYozuvchi()` — har safar `None` kelganda, **yangi** obyekt yarating.

## Mashq/topshiriq

**(Oson)** `Kalkulyator` klassini yozing — `__init__` orqali `tarix_saqlagich` (history logger) obyektini qabul qilsin, har bir amal bajarilganda (`qosh`, `ayir` metodlari) `tarix_saqlagich.yoz(matn)` chaqirilsin. Ikki xil `tarix_saqlagich` (biri konsolga, biri ro'yxatga yozadigan) yarating va ikkisi bilan ham ishlab ko'ring.

**(O'rtacha)** `ObunaXizmati` klassini yozing — `__init__` orqali `vaqt_provayderi` nomli bog'liqlikni (standart holda `datetime.now`ni ishlatadigan, lekin test uchun istalgan funksiyani qabul qila oladigan) oladi; `obuna_muddati_tugaganmi(boshlanish_sanasi, kun_soni)` metodi `vaqt_provayderi()`dan foydalanib hisoblasin. Testda soxta vaqt provayderini (doim bitta aniq sanani qaytaradigan funksiya) "inject" qilib, natijani tekshirib ko'ring.

**(Qiyin)** Oldingi darsdagi (5.1, Context Manager) `Tranzaksiya` klassiga Dependency Injection qo'shing — `SoxtaMB` o'rniga **istalgan** "ma'lumotlar bazasi"ga mos obyekt (`yoz`, `commit`, `rollback` metodlariga ega) ishlatila olishini ta'minlang, va buni `typing.Protocol` bilan rasmiylashtiring.

from typing import Protocol

class MBProtokoli(Protocol):
    def yoz(self, kalit: str, qiymat) -> None: ...
    def commit(self) -> None: ...
    def rollback(self) -> None: ...

class Tranzaksiya:

        return self.mb

        else:

## Qisqacha xulosa

Dependency Injection — klass o'ziga kerakli bog'liqliklarni (ma'lumotlar bazasi, tarmoq xizmati, loglovchi kabi tashqi resurslar) **o'zi yaratmasdan**, tashqaridan (odatda `__init__` orqali — constructor injection, yoki alohida metod orqali — method injection) qabul qilish naqshi bo'lib, bu kodni moslashuvchan (bog'liqlikni almashtirish — klass ichini o'zgartirmasdan mumkin) va testga mos (haqiqiy bog'liqlikni soxta/mock obyekt bilan almashtirib, tarmoq/baza so'rovlarisiz test yozish mumkin) qiladi; Python'ning duck typing tabiati tufayli bu naqshni qo'llash uchun Java/C#dagi kabi alohida DI konteyner **shart emas** — oddiy funksiya argumenti darajasidagi kiritish, ixtiyoriy ravishda `typing.Protocol` bilan "shartnoma"ni hujjatlashtirib, to'liq yetarli bo'ladi.

# 18.2. GIN, GiST, BRIN va Hash — maxsus indeks turlari (ICH-ICHIGA)

## Bu darsda nimalarni o'rganasiz

- B-tree yetarli bo'lmaydigan holatlarni tushunasiz
- **GIN** — `JSONB`, massiv va to'liq matnli qidiruv uchun indeksni jonli sinaysiz
- **BRIN** — juda katta, "tabiiy tartiblangan" jadvallar uchun ixcham indeksni o'rganasiz
- **Hash** — faqat tenglik uchun mo'ljallangan indeksni bilasiz
- **GiST**ning geometrik va murakkab ma'lumot turlari uchun rolini tushunasiz
- Qaysi vazifa uchun qaysi indeks turini tanlashni biladigan bo'lasiz

## Nazariy qism

### Nega bitta B-tree yetarli emas

18.1-darsda ko'rganimizdek, B-tree — oddiy son/matn ustunlar uchun ajoyib ishlaydi. Lekin 14-bobda o'rgangan `JSONB` yoki `ARRAY` kabi turlar uchun B-tree **mos kelmaydi** — chunki "bu JSON ob'ekt boshqasini o'z ichiga oladimi" (`@>`) kabi savolga, oddiy "kichikroq/kattaroq" tartib asosida javob berib bo'lmaydi. Aynan shu kabi holatlar uchun, PostgreSQL bir nechta **muqobil indeks turi**ni taqdim etadi.

### GIN — `JSONB`, massiv va ko'p qiymatli ustunlar uchun

**GIN** (Generalized Inverted Index — "umumlashtirilgan teskari indeks") — bitta ustunda **bir nechta "qidirilishi mumkin bo'lgan qism"** bo'lgan ma'lumotlar uchun mo'ljallangan (masalan, `JSONB` ob'ektining har bir kaliti, yoki massivning har bir elementi).

```sql
CREATE TABLE mahsulot_xususiyatlari (id SERIAL PRIMARY KEY, xususiyatlar JSONB);
INSERT INTO mahsulot_xususiyatlari (xususiyatlar)
SELECT jsonb_build_object('rang', (ARRAY['qora','oq','kulrang'])[1+(random()*2)::int], 'razmer', (random()*50)::int)
FROM generate_series(1, 20000);

CREATE INDEX idx_gin_xususiyat ON mahsulot_xususiyatlari USING GIN (xususiyatlar);
ANALYZE mahsulot_xususiyatlari;

EXPLAIN ANALYZE SELECT * FROM mahsulot_xususiyatlari WHERE xususiyatlar @> '{"rang": "qora"}';
```

```
                                                           QUERY PLAN                                                            
-----------------------------------------------------------------------------------------------------------------------------------
 Bitmap Heap Scan on mahsulot_xususiyatlari  (cost=36.27..279.01 rows=3659 width=47) (actual time=0.654..2.489 rows=4878 loops=1)
   Recheck Cond: (xususiyatlar @> '{"rang": "qora"}'::jsonb)
   Heap Blocks: exact=197
   ->  Bitmap Index Scan on idx_gin_xususiyat  (cost=0.00..35.36 rows=3659 width=0) (actual time=0.654..2.489 rows=4878 loops=1)
         Index Cond: (xususiyatlar @> '{"rang": "qora"}'::jsonb)
 Planning Time: 0.373 ms
 Execution Time: 2.650 ms
```

20 000 qatorli jadvalda, `@>` (containment, 14.1-dars) operatori orqali qidiruv **GIN indeksini** muvaffaqiyatli ishlatdi. GIN'siz, bu so'rov har bir qatorning JSON tarkibini "qo'lda" tekshirishga majbur bo'lar edi (`Seq Scan`).

> **GIN qachon ishlatiladi:** `JSONB`dagi `@>`/`?`/`?&`/`?|` operatorlari (14.1-dars), `ARRAY`dagi `@>`/`&&`/`= ANY()` (14.2-dars), va to'liq matnli qidiruv (`tsvector`/`tsquery`, bu darslikning doirasidan tashqarida, lekin GIN aynan shu vazifa uchun ham eng ko'p ishlatiladi).

### BRIN — juda katta, "tabiiy tartiblangan" jadvallar uchun

**BRIN** (Block Range Index — "blok-diapazon indeksi") — B-tree'dan farqli, **har bir qator** uchun emas, balki jadvalning **har bir sahifalar blokiga** (odatda 128 sahifa) faqat bitta yozuv — o'sha blokdagi qiymatlarning **min/max** diapazonini — saqlaydi. Bu, indeksni **o'ta ixcham** qiladi:

```sql
CREATE INDEX idx_brin_vaqt ON test_index_katta USING BRIN (yaratilgan_vaqti);

SELECT pg_size_pretty(pg_relation_size('idx_brin_vaqt')) AS brin_hajmi,
       pg_size_pretty(pg_relation_size('idx_test_qiymat')) AS btree_hajmi;
```

```
 brin_hajmi | btree_hajmi 
-------------+-------------
 24 kB       | 1048 kB
```

Bir xil, 50 000 qatorli jadvalda, BRIN indeksi B-tree'dan **~43 marta kichikroq**! Buning siri — BRIN har bir qator uchun alohida yozuv saqlamaydi, faqat "128-sahifalik blokda qiymatlar X dan Y gacha" kabi **umumlashtirilgan** ma'lumotni saqlaydi.

BRIN'ning samaradorligi, ma'lumot **jismonan qanchalik tartiblangan** (`ustun qiymati` bilan `jadvaldagi jismoniy joylashuv` orasidagi korrelyatsiya) ekaniga **qat'iy bog'liq**. Bu — vaqt bo'yicha o'sib boruvchi ustunlar (`yaratilgan_vaqti`, avtomatik o'suvchi `id`) uchun ayniqsa mos keladi, chunki ular tabiiy ravishda, yozilish tartibida, jismonan ham tartiblangan bo'ladi.

| | B-tree | BRIN |
|---|---|---|
| **Hajmi** | Katta (har bir qator uchun yozuv) | Juda kichik (har bir blok uchun bitta yozuv) |
| **Aniqligi** | Aniq — to'g'ridan-to'g'ri qatorga ishora qiladi | Taxminiy — "shu blokni tekshirib chiq" deydi, keyin PostgreSQL o'sha blokni haqiqatan skanerlaydi |
| **Eng mos holat** | Kichik-o'rta jadvallar, tasodifiy tartiblangan ma'lumot | Juda katta (yuz millionlab qatorli) jadvallar, jismonan tartiblangan ustunlar (masalan, log jadvallaridagi vaqt tamg'asi) |
| **Yozish narxi** | Nisbatan yuqori | Juda past (yangilanishi kam kerak bo'ladi) |

> **Amaliy qo'llanish:** BRIN — odatda **juda katta** (yuzlab GB/TB) jadvallarda, masalan sensor ma'lumotlari, log yozuvlari yoki tarixiy tranzaksiyalar kabi, doimiy ravishda vaqt bo'yicha o'sib boradigan jadvallarda ishlatiladi. Bizning 50 000 qatorli test jadvalimiz uchun bu farq unchalik sezilmasa-da, million-milliard qatorli jadvallarda BRIN'ning kichik hajmi (butunlay operativ xotirada joylasha olishi) hal qiluvchi ahamiyat kasb etadi.

### Hash — faqat tenglik uchun

**Hash** indeksi — faqat `=` (tenglik) operatori uchun mo'ljallangan, ichki jihatdan xesh-jadvalga o'xshash tuzilma:

```sql
CREATE INDEX idx_hash_kategoriya ON test_index_katta USING HASH (kategoriya);

EXPLAIN ANALYZE SELECT * FROM test_index_katta WHERE kategoriya = 'A';
```

```
                                                             QUERY PLAN                                                             
--------------------------------------------------------------------------------------------------------------------------------------
 Bitmap Heap Scan on test_index_katta  (cost=325.70..750.66 rows=8477 width=18) (actual time=0.296..1.929 rows=8403 loops=1)
   Recheck Cond: (kategoriya = 'A'::text)
   Heap Blocks: exact=319
   ->  Bitmap Index Scan on idx_hash_kategoriya  (cost=0.00..323.58 rows=8477 width=0) (actual time=0.256..0.256 rows=8403 loops=1)
         Index Cond: (kategoriya = 'A'::text)
```

Hash indeksi ishlatildi va to'g'ri natija berdi. Lekin diqqat qiling — Hash indeksi `WHERE qiymat > 100` yoki `ORDER BY` kabi **diapazon**/**saralash** so'rovlarida umuman ishlatib bo'lmaydi (chunki xesh funksiyasi tartibni saqlamaydi). Amaliyotda, zamonaviy PostgreSQL versiyalarida (10+), B-tree'ning tenglik so'rovlari uchun ishlashi Hash'dan deyarli farq qilmaydi, va B-tree qo'shimcha ravishda diapazon/saralashni ham qo'llab-quvvatlagani uchun, **ko'pchilik amaliy holatlarda oddiy B-tree afzalroq** — Hash indeksi kamdan-kam, faqat juda maxsus holatlarda tanlanadi.

### GiST — geometrik va murakkab, "moslashuvchan" qidiruv uchun

**GiST** (Generalized Search Tree — "umumlashtirilgan qidiruv daraxti") — bu, aslida, bitta qat'iy algoritm emas, balki **freymvork**: turli ma'lumot turlari (geometrik shakllar, diapazonlar, hatto to'liq matnli qidiruv) uchun **moslashtirilgan** qidiruv strukturasini qurish imkonini beradi. Eng ko'p uchraydigan qo'llanilishi:

- **Geometrik ma'lumotlar** (`point`, `polygon`, PostGIS kengaytmasi bilan geografik koordinatalar) — "bu nuqta shu ko'pburchak ichidami" kabi so'rovlar
- **Diapazon turlari** (`int4range`, `tsrange` — sana/vaqt oralig'i) — "bu ikki diapazon kesishadimi" kabi so'rovlar
- **Yaqin qo'shni qidiruv** (nearest-neighbor, `<->` operatori bilan "eng yaqin N ta nuqtani top")

Bu darslikning asosiy `dokon_bazasi` sxemasida geometrik ma'lumot yo'qligi sababli, GiST'ni chuqur amaliy misolsiz, faqat kontseptual darajada tanishtiramiz — lekin uni "GIN va BRIN yetarli bo'lmagan, murakkab, ko'p o'lchamli ma'lumotlar uchun universal freymvork" sifatida eslab qolish kifoya.

### Qaysi indeks turini qachon tanlash — xulosa jadvali

| Indeks turi | Eng mos holat |
|---|---|
| **B-tree** (standart) | Oddiy son/matn/sana ustunlar, tenglik, diapazon, saralash — **90% holatda shu yetarli** |
| **GIN** | `JSONB`, `ARRAY`, to'liq matnli qidiruv — "ichida bormi" turidagi savollar |
| **BRIN** | Juda katta (yuz millionlab qatorli), jismonan tartiblangan ustunlar (vaqt, avtomatik ID) |
| **Hash** | Faqat tenglik, kamdan-kam ishlatiladi (B-tree odatda yetarli) |
| **GiST** | Geometrik, diapazon, yaqin-qo'shni qidiruv turlari |

## Amaliy misol

**Vazifa:** `buyurtma_elementlari`ga o'xshash, tez-tez `IN`/tenglik bo'yicha qidiriladigan katta jadval uchun mos indeks tanlang va yarating.

```sql
-- Agar ustun faqat tenglik uchun ishlatilsa va juda katta bo'lsa, B-tree odatda yetarli:
CREATE INDEX idx_buyurtma_elementlari_mahsulot ON buyurtma_elementlari (mahsulot_id);

EXPLAIN SELECT * FROM buyurtma_elementlari WHERE mahsulot_id = 3;
```

## Keng tarqalgan xatolar

**Xato 1:** `JSONB` ustuniga oddiy B-tree indeks qo'shib, `@>` operatori tezlashishini kutish.
❌ B-tree, `JSONB`ning "ichki tarkibi" bo'yicha qidiruvni qo'llab-quvvatlamaydi — u faqat butun JSON qiymatlarni **tenglik** bo'yicha solishtira oladi.
✅ `JSONB`dagi `@>`/`?` operatorlari uchun har doim `USING GIN` bilan indeks yarating.

**Xato 2:** BRIN'ni har qanday katta jadvalga, ma'lumot tartiblanganligidan qat'i nazar, qo'llash.
❌ Agar ustun qiymatlari jadval bo'ylab **tasodifiy tartibda** joylashgan bo'lsa (masalan, `UPDATE`lar orqali qayta-qayta aralashtirilgan), BRIN deyarli foydasiz bo'lib qoladi — har bir "blok" juda keng diapazonni qamrab oladi.
✅ BRIN'ni faqat, ustun bilan jismoniy joylashuv orasida **kuchli korrelyatsiya** borligiga ishonch hosil qilgandan keyin ishlating.

**Xato 3:** Hash indeksni "tezroq" deb, hamma joyda B-tree o'rniga ishlatish.
❌ Zamonaviy PostgreSQL'da Hash, tenglik so'rovlarida B-tree'dan sezilarli tezroq emas, lekin diapazon/saralashni umuman qo'llab-quvvatlamaydi — bu uni ancha kam moslashuvchan qiladi.
✅ Standart holatda har doim B-tree'dan boshlang; Hash'ni faqat, aniq, o'lchangan sabab bo'lgandagina ko'rib chiqing.

## Mashq/topshiriq

**(Oson)** `mahsulot_xususiyatlari` jadvalida, `razmer > 30` bo'lgan mahsulotlarni GIN indeksi yordamida (yoki uning yordamisiz, solishtirish uchun) qidiring va natijani tushuntiring (GIN diapazon so'rovlarini qo'llab-quvvatlamasligini payqang).

**(O'rtacha)** `test_index_katta` jadvalida `id` ustuniga BRIN indeks yarating va uning hajmini mavjud B-tree (`PRIMARY KEY`) indeksi hajmi bilan solishtiring.

**(Qiyin)** `xususiyatlar -> 'rang'` bo'yicha (faqat `rang` kaliti uchun) qidiruvni tezlashtiradigan, GIN'dan farqli, maxsus **expression** B-tree indeks yarating (keyingi darsda chuqur o'rganiladigan mavzu bilan bog'lang) va uni to'liq GIN indeksi bilan hajm jihatidan solishtiring.

```sql
EXPLAIN SELECT * FROM mahsulot_xususiyatlari WHERE (xususiyatlar ->> 'razmer')::int > 30;
```


3.

## Qisqacha xulosa

B-tree — universal standart, lekin `JSONB`/`ARRAY` kabi "ko'p qiymatli" ustunlar uchun **GIN**, juda katta va jismonan tartiblangan jadvallar uchun **BRIN** (o'ta ixcham, bizning testimizda B-tree'dan ~43 marta kichik), faqat tenglik uchun **Hash**, va geometrik/diapazon ma'lumotlar uchun **GiST** — har biri o'z maxsus vazifasi uchun optimallashtirilgan. To'g'ri indeks turini tanlash — nafaqat tezlik, balki disk joyi va yozish unumdorligiga ham sezilarli ta'sir qiladi. Keyingi darsda indeksning **qanday qurilishini** emas, balki uni **qanday moslashtirishni** — qisman (`partial`), ifoda (`expression`) va qamrovchi (`covering`/`INCLUDE`) indekslarni — chuqur o'rganamiz.

# 22.2. Replication slot va failover (ICH-ICHIGA)

## Bu darsda nimalarni o'rganasiz

- **Replication slot** nima ekanini va u nima uchun kerakligini tushunasiz
- Slot'siz replikatsiyada yuzaga kelishi mumkin bo'lgan muammoni bilasiz
- **Failover** — standby'ni primary'ga aylantirish (`promote`) jarayonini jonli bajarasiz
- **Timeline** tushunchasini, real, kuzatiladigan misolda tushunasiz
- Sinxron va asinxron replikatsiya orasidagi farqni bilasiz

## Nazariy qism

### Muammo: standby vaqtincha uzilib qolsa-chi

22.1-darsda standby, primary'dan WAL oqimini doimiy qabul qilishini ko'rdik. Lekin savol: agar standby, tarmoq muammosi yoki texnik xizmat tufayli, **vaqtincha o'chib qolsa** — primary bu orada davom etib, eski WAL fayllarini (20.1-darsda ko'rganimizdek, ular avtomatik "qayta ishlatiladi" yoki o'chiriladi) tozalab yuborsa-chi? Standby qayta ulanganda, unga kerakli WAL fayllari **allaqachon yo'q bo'lib ketgan** bo'lishi mumkin — bu holda, standby **hech qachon** "quvib yeta olmaydi", va uni noldan (`pg_basebackup` bilan) qayta sozlash kerak bo'ladi.

### Replication slot — "meni kutmasdan tozalama"

**Replication slot** — bu muammoni yechadi: u, primary serverga, "menga ulangan standby hali qaysi WAL yozuviga muhtoj ekanini kuzatib bor, va **shu yozuvgacha bo'lgan** WAL fayllarini hech qachon o'chirma" deb "va'da" beradi.

```sql
SELECT pg_create_physical_replication_slot('standby_slot');
```

```
 pg_create_physical_replication_slot 
----------------------------------------
 (standby_slot,)
```

```sql
SELECT slot_name, slot_type, active, restart_lsn FROM pg_replication_slots;
```

```
   slot_name    | slot_type | active | restart_lsn 
------------------+------------+----------+---------------
 standby_slot    | physical  | f        |
```

`active = false` — bu, slot yaratilgan, lekin unga hali **hech qanday standby ulanmagan**ligini bildiradi (haqiqiy foydalanishda, standby `primary_conninfo`da `primary_slot_name = 'standby_slot'` deb ko'rsatib ulanadi). `restart_lsn` — standby ulanganidan keyin, "bu LSN'dan pastdagi WAL'ni o'chirma" degan **haqiqiy chegarani** ko'rsatadi.

> **Muhim, amaliy xavf:** agar slot yaratilgan bo'lsa-yu, lekin unga bog'langan standby **uzoq vaqt** ulanmasa (masalan, standby butunlay o'chib qolgan bo'lsa), primary — slot "va'dasi"ga rioya qilib, WAL fayllarini **cheksiz to'plab boraveradi**, chunki u standby qachon qaytib kelishini bilmaydi. Bu, diskni **to'liq to'ldirib**, butun serverni to'xtatib qo'yishi mumkin! Shu sababli, `max_slot_wal_keep_size` sozlamasi bilan, slot uchun saqlanadigan WAL hajmiga **yuqori chegara** qo'yish tavsiya etiladi — agar bu chegaradan oshsa, PostgreSQL slot'ning "va'dasini" buzib, baribir eski WAL'ni tozalaydi (standby, bu holda, qayta `pg_basebackup` bilan sozlanishi kerak bo'ladi — lekin hech bo'lmasa, server ishlashda davom etadi).

### Failover — standby'ni primary'ga aylantirish

Endi eng muhim, amaliy stsenariy: primary server **ishdan chiqdi** (yoki rejalashtirilgan texnik xizmat uchun o'chirilishi kerak). Standby'ni, **darhol**, yangi primary sifatida ishga tushirish kerak — bu jarayon **failover** deb ataladi, va u `pg_promote` (yoki `pg_ctl promote`) buyrug'i bilan amalga oshiriladi:

```bash
pg_ctl -D /tmp/pg_standby promote
```

```
waiting for server to promote.... done
server promoted
```

Tekshiramiz:

```sql
SELECT pg_is_in_recovery();
```

```
 pg_is_in_recovery 
---------------------
 f
```

**`false`** — endi bu server, avvalgi standby, **to'liq huquqli primary**ga aylandi! Yozishga urinamiz:

```sql
INSERT INTO mahsulotlar (nomi, narxi, kategoriya, ombordagi_soni) VALUES ('Promote sinovi', 1, 'Test', 1);
```

```
INSERT 0 1
```

Muvaffaqiyatli — endi bu server yozishni qabul qiladi, xuddi u har doim primary bo'lgandek.

### Timeline — nega u muhim

Promote qilingandan keyin, juda muhim, kutilmagan o'zgarish sodir bo'ladi:

```sql
-- Yangi primary'da (avvalgi standby):
SELECT pg_walfile_name(pg_current_wal_lsn());
```

```
 pg_walfile_name      
------------------------
 000000020000000000000009
```

```sql
-- Asl primary'da:
SELECT pg_walfile_name(pg_current_wal_lsn());
```

```
 pg_walfile_name      
------------------------
 000000010000000000000009
```

Diqqat qiling — fayl nomining **birinchi** qismi farqli: yangi primary (promote qilingan standby) — `00000002` (timeline **2**), asl primary esa hali ham `00000001` (timeline **1**) bilan davom etmoqda! Bu — 20.1-darsda qisqacha eslatib o'tilgan **timeline** tushunchasining amaliy ma'nosi: har safar bir server "yangi tarix yo'nalishi"ni boshlaganda (masalan, promote orqali, yoki PITR orqali — 20.2-dars), PostgreSQL uning WAL tarixini **yangi timeline raqami** bilan belgilaydi. Bu, ikkita server — asl primary va yangi (promote qilingan) primary — endi **ikkita mustaqil, bir-biridan farqli tarix chizig'ida** ekanligini aniq ko'rsatadi, va ularni **hech qachon** qayta, avtomatik ravishda birlashtirib bo'lmaydi (agar ikkalasi ham parallel yozishda davom etsa, ma'lumotlar **taqsimlanib ketadi** — "split-brain" deb ataladigan, oldini olish zarur bo'lgan xavfli holat).

### Sinxron vs asinxron replikatsiya

22.1-darsda ko'rgan `pg_stat_replication`dagi `sync_state = async` ustuniga e'tibor bering — bu, standart holat: **asinxron replikatsiya**. Bunda, primary, `COMMIT`ni standby WAL'ni qabul qilishini **kutmasdan**, darhol qaytaradi — bu tezroq, lekin agar primary aynan `COMMIT`dan keyin, standby ulgurmasdan yiqilib tushsa, **eng so'nggi bir necha tranzaksiya** yo'qolishi (standby'ga yetib bormaganligi sababli) mumkin.

**Sinxron replikatsiya** (`synchronous_commit` va `synchronous_standby_names` sozlamalari orqali) — bunda, primary, `COMMIT`ni faqat, standby (yoki standby'lar) o'zgarishni **qabul qilib bo'lgandan keyingina** qaytaradi. Bu — ma'lumot yo'qotilishi xavfini yo'qotadi, lekin har bir `COMMIT`, tarmoq orqali standby bilan "gaplashish"ni talab qilgani uchun, **sekinroq** ishlaydi.

| | Asinxron (standart) | Sinxron |
|---|---|---|
| **Tezlik** | Tezroq | Sekinroq (tarmoq kechikishiga bog'liq) |
| **Ma'lumot yo'qotish xavfi** | Bor (oxirgi bir necha tranzaksiya) | Yo'q (agar sinxron standby ishlasa) |
| **Standart holat** | ✅ | Qo'lda yoqilishi kerak |

## Amaliy misol

**Vazifa:** Replication slot yarating va uning `restart_lsn`sini, WAL yozuvlari qo'shilgan sari, kuzating.

```sql
SELECT pg_create_physical_replication_slot('kuzatuv_slot');

-- Bir nechta o'zgarish kiritamiz:
INSERT INTO mahsulotlar (nomi, narxi, kategoriya, ombordagi_soni) VALUES ('Slot sinovi', 1000, 'Test', 5);

SELECT slot_name, restart_lsn FROM pg_replication_slots WHERE slot_name = 'kuzatuv_slot';

-- Tozalash:
SELECT pg_drop_replication_slot('kuzatuv_slot');
```

## Keng tarqalgan xatolar

**Xato 1:** Replication slot yaratib, keyin unga hech qachon standby ulamaslik yoki uni o'chirib qo'yishni unutish.
❌ Bu, yuqorida ta'kidlanganidek, disk to'lib ketishiga olib kelishi mumkin — bu, real production'da eng ko'p uchraydigan replikatsiyaga bog'liq falokatlardan biri.
✅ Ishlatilmayotgan slot'larni doim `pg_drop_replication_slot()` bilan o'chiring, va `max_slot_wal_keep_size`ni har doim cheklangan qiymatga o'rnating.

**Xato 2:** Failoverdan keyin, eski primary'ni, "hech narsa bo'lmagandek", qayta yoqib, ikkalasini ham primary sifatida ishlatishda davom ettirish.
❌ Bu — yuqorida tasvirlangan **split-brain** holatiga olib keladi: ikkala server ham mustaqil yozishni qabul qiladi, ma'lumotlar taqsimlanib, ularni keyinchalik birlashtirish **deyarli imkonsiz** bo'lib qoladi.
✅ Failoverdan keyin, eski primary'ni albatta **yangi standby** sifatida (yangi primary'ga qarab) qayta sozlang, yoki uni butunlay o'chiring — hech qachon ikkalasini ham mustaqil primary sifatida qoldirmang.

**Xato 3:** Har doim sinxron replikatsiyani "eng xavfsiz, shuning uchun eng yaxshi" deb, standart asinxrondan afzal ko'rish.
❌ Sinxron replikatsiya, standby bilan aloqa uzilsa (yoki sekinlashsa), **primary'ning o'zini ham** sekinlashtiradi (chunki u standby javobini kutadi) — bu, ba'zi yuklamali tizimlar uchun qabul qilib bo'lmaydigan narx.
✅ Sinxron replikatsiyani faqat, ma'lumot yo'qotilishi **mutlaqo** yo'l qo'yilmaydigan (masalan, moliyaviy tranzaksiyalar) muhim tizim qismlari uchun, ongli ravishda tanlang.

## Mashq/topshiriq

**(Oson)** `pg_replication_slots` katalog ko'rinishidan foydalanib, hozirda serveringizda nechta replication slot borligini va ularning holatini (`active`) aniqlang.

**(O'rtacha)** `wal_keep_size` va `max_slot_wal_keep_size` sozlamalarining joriy qiymatlarini `SHOW` bilan tekshirib, ular orasidagi farqni (biri slot'siz, ikkinchisi slot uchun chegara) tushuntirib bering.

**(Qiyin)** `pg_control_checkpoint()`dan `timeline_id`ni olib, agar sizning serveringiz hech qachon promote qilinmagan bo'lsa, bu qiymat nega hali ham `1` bo'lib qolishini, va u qachon `2`ga o'zgarishini (aynan qaysi amaldan keyin) tushuntiring.

## Qisqacha xulosa

Replication slot — primary serverga, hali standby tomonidan o'qilmagan WAL fayllarini saqlab turishni "va'da qildiradi", lekin bu, ehtiyotsiz ishlatilsa, disk to'lib ketishiga olib kelishi mumkin. Failover (`pg_promote`) — standby'ni, bir necha soniyada, to'liq huquqli, yozish qabul qiluvchi primary'ga aylantiradi, va bu jarayon, biz jonli ko'rganimizdek, yangi **timeline**ni boshlaydi — bu, eski va yangi primary'larni bir-biridan mustaqil "tarix chiziqlari" sifatida ajratib turadi, va **split-brain**ning oldini olish uchun juda muhim. Sinxron replikatsiya — ma'lumot yo'qotilishi xavfini yo'qotadi, lekin tezlik hisobiga. Bu — 22-bobni yakunlaydi: replikatsiyaning to'liq, amaliy rasmini — WAL asosidagi streaming replikatsiyadan tortib, failover va timeline'gacha — o'zingiz sozlab, jonli ko'rdingiz. Keyingi, 23-bobda **partitioning va performance tuning**ni — juda katta jadvallarni qanday bo'laklarga bo'lish va butun serverni qanday moslashtirishni — chuqur o'rganamiz, bu esa darslikning **yakuniy** ICH-ICHIGA bobi bo'ladi.

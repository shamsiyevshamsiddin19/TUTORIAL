# 8.3. `FOREIGN KEY` va `ON DELETE` strategiyalari

## Bu darsda nimalarni o'rganasiz

- `FOREIGN KEY` (tashqi kalit) qanday yaratilishini va uning nimani ta'minlashini mustahkam tushunasiz
- Standart xatti-harakat (`NO ACTION`)ni chuqur bilasiz — bosh yozuvni o'chirishga to'sqinlik qilishini
- `ON DELETE CASCADE` — bog'liq yozuvlarni avtomatik o'chirishni bilasiz
- `ON DELETE SET NULL` — bog'liq yozuvlardagi tashqi kalitni `NULL`ga o'rnatishni bilasiz
- Har bir strategiyani qachon tanlash kerakligini amaliy nuqtai nazardan baholaysiz

## Nazariy qism

### `FOREIGN KEY` — jadvallar orasidagi bog'lanishni rasmiylashtirish

3.1-darsdan boshlab `xodimlar.bolim_id`, `buyurtmalar.mijoz_id` kabi tashqi kalit ustunlarini faol ishlatib keldik. `FOREIGN KEY` cheklovi bu bog'lanishni **rasmiy** qiladi va PostgreSQL'ga ikkita muhim qoidani majburlashni buyuradi: (1) tashqi kalit ustunidagi qiymat **albatta** bosh (referenced) jadvalda haqiqatan mavjud bo'lishi kerak (yoki `NULL` bo'lishi mumkin, agar ustun `NOT NULL` bo'lmasa); (2) bosh jadvaldagi yozuvni, unga hali ishora qiluvchi bog'liq yozuvlar borligida, oddiy `DELETE` bilan o'chirib bo'lmaydi (agar maxsus strategiya ko'rsatilmagan bo'lsa).

```sql
CREATE TABLE bola_jadval (
    id SERIAL PRIMARY KEY,
    ota_id INTEGER REFERENCES ota_jadval(id)
);
```

Bu — `REFERENCES ota_jadval(id)` — ustun darajasidagi qisqa yozuv. Jadval darajasidagi, ko'proq boshqaruv imkonini beruvchi (masalan, nomlash, yoki bir nechta ustun) shakli:

```sql
CREATE TABLE bola_jadval (
    id SERIAL PRIMARY KEY,
    ota_id INTEGER,
    CONSTRAINT fk_ota FOREIGN KEY (ota_id) REFERENCES ota_jadval(id)
);
```

### Standart xatti-harakat: `NO ACTION` (bosh yozuvni o'chirishga to'sqinlik)

Agar `ON DELETE` aniq ko'rsatilmasa, PostgreSQL standart ravishda `NO ACTION` (7.3-darsda amalda ko'rgan xatti-harakat) qo'llaydi — bosh yozuv o'chirilishiga **umuman yo'l qo'ymaydi**, agar unga ishora qiluvchi bog'liq yozuv mavjud bo'lsa:

```sql
CREATE TABLE test_fk_default (id SERIAL PRIMARY KEY, parent_id INTEGER REFERENCES test_fk_parent(id));
-- ... ma'lumot kiritilgach:
DELETE FROM test_fk_parent WHERE id = 1;
```

```
ERROR:  update or delete on table "test_fk_parent" violates foreign key constraint "test_fk_default_parent_id_fkey" on table "test_fk_default"
DETAIL:  Key (id)=(1) is still referenced from table "test_fk_default".
```

Bu — eng **xavfsiz** standart tanlov: hech qanday ma'lumot sizning bilmasdan yo'qolmaydi yoki o'zgarmaydi, siz har doim aniq qaror qabul qilishga majbursiz.

### `ON DELETE CASCADE` — bog'liq yozuvlarni avtomatik o'chirish

```sql
CREATE TABLE test_fk_cascade (
    id SERIAL PRIMARY KEY,
    parent_id INTEGER REFERENCES test_fk_parent(id) ON DELETE CASCADE
);
```

```sql
DELETE FROM test_fk_parent WHERE id = 1;
SELECT * FROM test_fk_cascade;
```

```
 id | parent_id 
----+-----------
(0 rows)
```

Bosh yozuv o'chirilganda, `ON DELETE CASCADE` bilan bog'langan **barcha** bog'liq yozuvlar ham **avtomatik** o'chib ketadi. Bu — masalan, "buyurtma o'chirilsa, uning barcha `buyurtma_elementlari`si ham avtomatik o'chirilsin" kabi holatlarda mantiqiy: alohida buyurtma qatorlari, o'z buyurtmasisiz, hech qanday mustaqil ma'noga ega emas — ular buyurtmaning **ajralmas qismi**.

> **Katta ehtiyot chorasi:** `CASCADE` — 6.4-darsdagi `DROP TABLE ... CASCADE`ga o'xshab, kuchli va **xavfli** vosita. Agar `CASCADE` zanjiri bir necha bosqichli bo'lsa (A o'chirilsa B ham CASCADE bilan o'chadi, B o'chirilsa esa C ham CASCADE bilan o'chadi), bitta `DELETE` kutilmaganda katta miqdordagi ma'lumotni "zanjir bo'ylab" o'chirib yuborishi mumkin. `CASCADE`ni faqat "bog'liq yozuv, ota yozuvsiz, mantiqan mavjud bo'la olmaydi" degan holatlarda (masalan, buyurtma va uning qatorlari) ishlatish tavsiya etiladi.

### `ON DELETE SET NULL` — bog'liq yozuvni "yetim" qilib qoldirish, lekin buzilmasdan

```sql
CREATE TABLE test_fk_setnull (
    id SERIAL PRIMARY KEY,
    parent_id INTEGER REFERENCES test_fk_parent(id) ON DELETE SET NULL
);
```

```sql
DELETE FROM test_fk_parent WHERE id = 1;
SELECT * FROM test_fk_setnull;
```

```
 id | parent_id 
----+-----------
  1 |          
(1 row)
```

Bu holatda bog'liq yozuv **o'chirilmaydi** — u qoladi, faqat uning tashqi kalit ustuni `NULL`ga o'rnatiladi. Bu — masalan, "xodim ma'lumotlar bazasidan o'chirilsa (ishdan bo'shatilsa), lekin uning avvalgi buyurtmalar tarixi (`sotuvchi_id`) yo'qolmasin, faqat 'sotuvchi noma'lum/o'chirilgan' holatiga o'tsin" kabi vaziyatlarda mantiqiy — bog'liq ma'lumot (buyurtma) o'z-o'zidan mustaqil ahamiyatga ega, faqat unga bog'liq bo'lgan ma'lumot (kim sotgani) endi noma'lum bo'lib qoladi.

> **Muhim shart:** `ON DELETE SET NULL` faqat tashqi kalit ustuni `NOT NULL` **bo'lmagan** holdagina ishlaydi — agar ustun `NOT NULL` bo'lsa, `SET NULL` ham `NOT NULL` cheklovini buzishga urinadi va xato beradi.

### Uch strategiyani solishtirish

| Strategiya | Bosh yozuv o'chirilganda | Qachon mos |
|---|---|---|
| `NO ACTION` (standart) | O'chirish **taqiqlanadi** (agar bog'liq yozuv bo'lsa) | Eng xavfsiz standart; ma'lumot yaxlitligi ustuvor bo'lganda |
| `ON DELETE CASCADE` | Bog'liq yozuvlar ham **avtomatik o'chiriladi** | Bog'liq yozuv ota-yozuvsiz mantiqan mavjud bo'la olmaganda (masalan, buyurtma qatorlari) |
| `ON DELETE SET NULL` | Bog'liq yozuv qoladi, tashqi kalit `NULL`ga o'rnatiladi | Bog'liq yozuv mustaqil ahamiyatga ega, faqat bog'lanish ixtiyoriy bo'lganda |

Yana ikkita kamdan-kam ishlatiladigan variant ham bor: `ON DELETE RESTRICT` (`NO ACTION`ga juda o'xshash, faqat tekshiruv vaqti bo'yicha texnik farq bor — amaliyotda deyarli bir xil natija beradi) va `ON DELETE SET DEFAULT` (tashqi kalitni `NULL` o'rniga ustunning `DEFAULT` qiymatiga o'rnatadi).

### `ON UPDATE` — xuddi shunday, lekin `UPDATE` uchun

`ON DELETE`ga o'xshab, `ON UPDATE CASCADE`/`SET NULL` ham mavjud — bular bosh jadvaldagi asosiy kalit qiymati **o'zgartirilganda** (bu kamdan-kam uchraydi, chunki asosiy kalitlar odatda o'zgarmas deb hisoblanadi) qanday xatti-harakat qilinishini belgilaydi. Amaliyotda `ON UPDATE`dan `ON DELETE`ga qaraganda ancha kamroq foydalaniladi, chunki `SERIAL`/`IDENTITY` asosiy kalitlar deyarli hech qachon o'zgartirilmaydi.

## Amaliy misol

**Vazifa:** `dokon_bazasi`imizda `buyurtma_elementlari.buyurtma_id` uchun `ON DELETE CASCADE`ni qo'shish orqali, "buyurtma o'chirilsa, uning elementlari ham avtomatik o'chsin" degan mantiqiy qoidani rasmiylashtiramiz (hozircha bu cheklov `CASCADE`siz o'rnatilgan edi).

```sql
ALTER TABLE buyurtma_elementlari
DROP CONSTRAINT buyurtma_elementlari_buyurtma_id_fkey;

ALTER TABLE buyurtma_elementlari
ADD CONSTRAINT buyurtma_elementlari_buyurtma_id_fkey
FOREIGN KEY (buyurtma_id) REFERENCES buyurtmalar(id) ON DELETE CASCADE;
```

Bu ikki qadam — avval eski (CASCADE'siz) cheklovni o'chirish, keyin yangi (CASCADE'li) versiyasini qo'shish — mavjud cheklovni **o'zgartirish**ning standart usuli, chunki PostgreSQL'da cheklovni to'g'ridan-to'g'ri "tahrirlash" imkoni yo'q, faqat o'chirib qayta yaratish mumkin.

## Keng tarqalgan xatolar

**Xato 1:** `CASCADE`ni "har doim qulay" deb, oqibatlarini o'ylamasdan hamma joyda ishlatish.
✅ Har bir bog'lanish uchun alohida o'ylab, "bu ma'lumot ota-yozuvsiz mantiqan mavjud bo'la oladimi" degan savolga javob bering.

**Xato 2:** `ON DELETE SET NULL`ni `NOT NULL` ustunga qo'llashga urinish.
❌ Agar `parent_id INTEGER NOT NULL REFERENCES ... ON DELETE SET NULL` bo'lsa, ota yozuv o'chirilganda ikkita cheklov (FK va NOT NULL) o'rtasida to'qnashuv yuzaga keladi, va `DELETE` xato bilan tugaydi.
✅ `SET NULL` ishlatmoqchi bo'lsangiz, ustun `NULL`ga ruxsat berishi kerak.

**Xato 3:** Standart `NO ACTION`ni "xato" deb hisoblab, tekshirmasdan hamma joyda `CASCADE`ga o'zgartirish.
✅ `NO ACTION` — ko'p hollarda eng xavfsiz va to'g'ri tanlov; uni faqat ongli, aniq sabab bilan `CASCADE`/`SET NULL`ga almashtiring.

## Mashq/topshiriq

**(Oson)** Ikkita test jadvali (`ota_test`, `bola_test`, oddiy `FOREIGN KEY`, hech qanday `ON DELETE` ko'rsatilmagan) yarating, ularga ma'lumot kiriting, so'ng `ota_test`dan yozuvni o'chirishga urinib, standart `NO ACTION` xatosini his qiling.

**(O'rtacha)** Xuddi shunday jadvallarni, endi `ON DELETE CASCADE` bilan qayta yarating, va ota yozuv o'chirilganda bola yozuv ham avtomatik o'chib ketishini tasdiqlang.

**(Qiyin)** `xodimlar.boshliq_id` (3.4-darsdagi self-join uchun ishlatilgan tashqi kalit)ni ko'rib chiqing va nima uchun bu ustun uchun `ON DELETE CASCADE` **noto'g'ri** tanlov bo'lishini (bosh direktor o'chirilsa, butun tashkilot ierarxiyasi "zanjir bo'ylab" o'chib ketishi xavfi) va nega `ON DELETE SET NULL` (yoki oddiy `NO ACTION`, avval xodimlarni qayta tayinlab keyin o'chirish) ancha xavfsizroq ekanini tushuntiring.

## Qisqacha xulosa

`FOREIGN KEY` — jadvallar orasidagi bog'lanishni rasmiylashtiradi va yaxlitlikni ta'minlaydi. Standart `NO ACTION` xatti-harakati bosh yozuvni bog'liq yozuv mavjud bo'lganda o'chirishga yo'l qo'ymaydi — bu eng xavfsiz tanlov. `ON DELETE CASCADE` bog'liq yozuvlarni avtomatik o'chiradi (faqat bog'liq yozuv ota-yozuvsiz mantiqan mavjud bo'la olmaganda ishlatilishi kerak), `ON DELETE SET NULL` esa bog'liq yozuvni saqlab, faqat bog'lanishni uzadi. Har bir strategiyani tanlashda "bu ma'lumot o'z ota-yozuvisiz nima ma'noni anglatadi" degan savolga javob berish — to'g'ri qarorga olib keladi. Bu bilan 08-bob (Constraints) yakunlanadi — keyingi, 09-bobda esa Subquery va CTE (WITH bandi)ni chuqur o'rganamiz.

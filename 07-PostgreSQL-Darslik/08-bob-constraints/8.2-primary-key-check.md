# 8.2. `PRIMARY KEY` va `CHECK`

## Bu darsda nimalarni o'rganasiz

- `PRIMARY KEY`ning aslida `NOT NULL` + `UNIQUE`ning birikmasi ekanini tushunasiz
- Kompozit (bir nechta ustundan iborat) asosiy kalitlarni yaratishni bilasiz
- `CHECK` cheklovi bilan o'zboshimcha mantiqiy shartlarni majburlashni o'rganasiz
- Bir nechta ustun ishtirok etadigan `CHECK` shartlarini yaratishni bilasiz

## Nazariy qism

### `PRIMARY KEY` — `NOT NULL` + `UNIQUE`ning birikmasi

6.1-darsdan boshlab har bir jadvalimizda `id SERIAL PRIMARY KEY` ko'rib keldik. Endi buni rasman tushuntiramiz: **`PRIMARY KEY` — texnik jihatdan `NOT NULL` va `UNIQUE`ning birlashmasidan boshqa narsa emas**, qo'shimcha ravishda "bu ustun — jadvalning **asosiy identifikatori**" degan semantik ma'noni bildiradi. Har bir jadvalda (odatda) faqat **bitta** asosiy kalit bo'lishi mumkin (bir nechta `UNIQUE` cheklovi bo'lishi mumkin bo'lsa-da).

```sql
CREATE TABLE mijoz_murojaatlari (
    id SERIAL PRIMARY KEY,   -- bir vaqtning o'zida: NOT NULL + UNIQUE + "bu - asosiy identifikator"
    ...
);
```

`PRIMARY KEY`ning `UNIQUE`dan farqi shundaki, u **hech qachon `NULL`ga ruxsat bermaydi** (`UNIQUE` esa, 8.1-darsda ko'rganimizdek, bir nechta `NULL`ga ruxsat beradi) — bu mantiqan to'g'ri, chunki "identifikatori noma'lum" bo'lgan qator tushunchasi ma'nosiz.

### Kompozit (bir nechta ustundan) asosiy kalit

Ba'zan tabiiy identifikator bitta ustunda emas, balki **ustunlar kombinatsiyasida** bo'ladi. Masalan, "bog'lovchi jadval" (3.1-darsdagi `buyurtma_elementlari` kabi)da ba'zan alohida `id SERIAL` o'rniga, to'g'ridan-to'g'ri `(buyurtma_id, mahsulot_id)` juftligining o'zini asosiy kalit qilib belgilash mumkin:

```sql
CREATE TABLE test_composite_pk (
    buyurtma_id INTEGER,
    mahsulot_id INTEGER,
    soni INTEGER,
    PRIMARY KEY (buyurtma_id, mahsulot_id)
);
```

```sql
INSERT INTO test_composite_pk VALUES (1, 1, 5);
INSERT INTO test_composite_pk VALUES (1, 1, 3);
```

```
INSERT 0 1
ERROR:  duplicate key value violates unique constraint "test_composite_pk_pkey"
DETAIL:  Key (buyurtma_id, mahsulot_id)=(1, 1) already exists.
```

Bu — 8.1-darsdagi kompozit `UNIQUE` bilan juda o'xshash (chunki, aytganimizdek, `PRIMARY KEY` = `UNIQUE` + `NOT NULL`), lekin qo'shimcha ravishda ikkala ustun ham avtomatik `NOT NULL` bo'lib qoladi, va bu — jadvalning **rasmiy, birlamchi** identifikatori sifatida belgilanadi.

**Qachon oddiy `id SERIAL`, qachon kompozit asosiy kalit?** Amaliyotda ko'pchilik zamonaviy loyihalar, hattoki bog'lovchi jadvallar uchun ham, sodda va universal bo'lgani uchun alohida `id SERIAL PRIMARY KEY` ishlatishni afzal ko'radi (bizning `dokon_bazasi`imiz ham shu yo'ldan borgan), kompozit kalitni esa aynan "ustunlar juftligi tabiiy ravishda noyob bo'lishi **shart**" degan holatlarda (masalan, "bitta buyurtmada bitta mahsulot faqat bir marta") qo'shimcha `UNIQUE (buyurtma_id, mahsulot_id)` cheklovi sifatida (asosiy kalit emas, oddiy `id` asosiy kalit bo'lib qolgan holda) qo'llash — 8.1-darsda aynan shu yondashuvni ko'rgan edik.

### `CHECK` — o'zboshimcha mantiqiy shartni majburlash

`NOT NULL`, `UNIQUE` va `PRIMARY KEY` — barchasi oldindan belgilangan, tayyor tekshiruv turlari. `CHECK` esa sizga **istalgan** mantiqiy ifodani cheklov sifatida yozish imkonini beradi:

```sql
CREATE TABLE test_check (
    id SERIAL PRIMARY KEY,
    narxi NUMERIC CHECK (narxi > 0),
    yosh INTEGER CHECK (yosh BETWEEN 0 AND 120)
);
```

```sql
INSERT INTO test_check (narxi, yosh) VALUES (-5, 30);
```

```
ERROR:  new row for relation "test_check" violates check constraint "test_check_narxi_check"
DETAIL:  Failing row contains (1, -5, 30).
```

```sql
INSERT INTO test_check (narxi, yosh) VALUES (100, 200);
```

```
ERROR:  new row for relation "test_check" violates check constraint "test_check_yosh_check"
DETAIL:  Failing row contains (2, 100, 200).
```

To'g'ri qiymatlar bilan esa muvaffaqiyatli o'tadi:

```sql
INSERT INTO test_check (narxi, yosh) VALUES (100, 30) RETURNING *;
```

```
 id | narxi | yosh 
----+-------+------
  3 |   100 |   30
```

`CHECK` ichida `>`, `<`, `BETWEEN`, `LIKE`, va hattoki funksiyalar (masalan, `LENGTH(ustun) > 3`) — deyarli har qanday mantiqiy ifodadan foydalanish mumkin, bu uni juda ko'p qirrali qiladi.

### Bir nechta ustun ishtirok etadigan `CHECK`

`CHECK` faqat bitta ustunga emas, jadval darajasida, **bir nechta ustun orasidagi munosabat**ga ham qo'llanilishi mumkin — masalan, "tugash sanasi boshlanish sanasidan keyin bo'lishi kerak":

```sql
CREATE TABLE test_check2 (
    id SERIAL PRIMARY KEY,
    boshlanish DATE,
    tugash DATE,
    CONSTRAINT tugash_keyinroq CHECK (tugash > boshlanish)
);
```

```sql
INSERT INTO test_check2 (boshlanish, tugash) VALUES ('2024-01-10', '2024-01-01');
```

```
ERROR:  new row for relation "test_check2" violates check constraint "tugash_keyinroq"
DETAIL:  Failing row contains (1, 2024-01-10, 2024-01-01).
```

Bu — "tugash sanasi boshlanishdan oldin bo'lishi mumkin emas" degan biznes qoidasini, ilova kodida emas, bazaning o'zida majburlaydigan juda foydali naqsh.

### `CHECK` va `NOT NULL` orasidagi bog'liqlik

Diqqatli o'quvchi payqagan bo'lishi mumkin: `CHECK (narxi > 0)` — agar `narxi` ustuniga `NULL` qiymat berilsa nima bo'ladi? Javob: **`CHECK` shartlari `NULL` uchun avtomatik ravishda "o'tkaziladi" (o'tadi deb hisoblanadi)**, chunki `NULL > 0` natijasi (2.3-darsda o'rganganimizdek) `TRUE` emas, `FALSE` ham emas, balki `NULL` — va PostgreSQL `CHECK` shartlarini faqat ular aniq `FALSE` bo'lgandagina rad etadi (`NULL` — "noma'lum, demak, taqiqlanmagan" deb talqin qilinadi). Agar sizga `narxi` **ham** majburiy (`NOT NULL`), **ham** musbat (`CHECK (narxi > 0)`) bo'lishi kerak bo'lsa, ikkalasini ham alohida-alohida qo'shish kerak — biri ikkinchisini avtomatik ta'minlamaydi.

## Amaliy misol

**Vazifa:** `xodimlar` jadvaliga, oylik maosh har doim musbat bo'lishini ta'minlovchi `CHECK` cheklovini, va xodim yoshi (agar `tugilgan_sana` ustuni bo'lganida edi, hozircha shartli misol sifatida) 18 dan katta bo'lishini ta'minlovchi mantiqni ko'rib chiqamiz:

```sql
ALTER TABLE xodimlar ADD CONSTRAINT ish_haqi_musbat CHECK (ish_haqi > 0);
```

Endi hech kim (hattoki tasodifiy xato bilan ham) xodimga manfiy yoki nolga teng maosh belgilay olmaydi — bu qoida butun tizim darajasida, doimiy ravishda kuchda bo'ladi.

## Keng tarqalgan xatolar

**Xato 1:** `PRIMARY KEY` va `UNIQUE`ni farqlay olmaslik — ularning `NULL`ga munosabati boshqacha ekanini unutish.
✅ `PRIMARY KEY` — hech qachon `NULL`ga ruxsat bermaydi; `UNIQUE` — bir nechta `NULL`ga ruxsat beradi (8.1-darsda ko'rganimizdek).

**Xato 2:** `CHECK`ning `NULL` qiymatlarni avtomatik "o'tkazishini" bilmasdan, "nega `NULL` qiymatli qator kirib ketdi" deb hayron bo'lish.
✅ Agar `NULL`ga yo'l qo'ymaslik ham kerak bo'lsa, alohida `NOT NULL`ni qo'shing.

**Xato 3:** Murakkab, ko'p shartli biznes mantiqni (masalan, "agar holat = 'yetkazildi' bo'lsa, yetkazish sanasi bo'sh bo'lmasligi kerak") oddiy bitta ustunli `CHECK`ga sig'dirishga urinish.
✅ Ko'p ustunli `CHECK` (yuqorida `tugash_keyinroq` misolida ko'rganimizdek) buni yechishi mumkin, lekin juda murakkab shartli mantiq uchun ko'pincha trigger (12-bobda) yanada mos vosita hisoblanadi.

## Mashq/topshiriq

**(Oson)** `mahsulotlar` jadvaliga, `ombordagi_soni` hech qachon manfiy bo'lmasligini ta'minlovchi `CHECK (ombordagi_soni >= 0)` cheklovini qo'shing.

**(O'rtacha)** Yangi `chegirmalar` jadvalini yarating: `id`, `mahsulot_id`, `chegirma_foizi` (0 dan 100 gacha bo'lishi kerak, `CHECK` bilan). Chegirma foizini `150` qilib kiritishga urinib, xatoni ko'ring.

**(Qiyin)** `buyurtma_elementlari`ga o'xshash yangi `test_narx_tekshiruv` jadvalini yarating: `soni INTEGER`, `narx NUMERIC`, va ularning ko'paytmasi (`soni * narx`) hech qachon `100,000,000`dan oshmasligini ta'minlovchi ko'p ustunli `CHECK` cheklovini qo'shing (bu — "bitta buyurtma qatorining umumiy qiymati cheklangan" degan shartli biznes qoidasi).

## Qisqacha xulosa

`PRIMARY KEY` — `NOT NULL` va `UNIQUE`ning birikmasi bo'lib, jadvalning asosiy identifikatorini belgilaydi va bir nechta ustundan (kompozit) iborat bo'lishi ham mumkin. `CHECK` esa istalgan mantiqiy shartni (bitta yoki bir nechta ustun bo'yicha) bazaning o'zida majburlash imkonini beradi — lekin `NULL` qiymatlar uchun avtomatik "o'tkaziladi", shuning uchun to'liq himoya uchun ko'pincha `NOT NULL` bilan birga ishlatiladi. Keyingi darsda eng muhim va murakkab cheklov turini — jadvallar orasidagi bog'lanishni ta'minlovchi `FOREIGN KEY`ni, va `ON DELETE` strategiyalarini chuqur o'rganamiz.

# 16.2. TOAST, `fillfactor` va HOT update — ICH-ICHIGA

## Bu darsda nimalarni o'rganasiz

- Nega katta qiymatlar 8 KB sahifaga sig'masligini va **TOAST** buni qanday yechishini tushunasiz
- TOAST'ning ikki bosqichini — siqish (compression) va tashqariga chiqarish (out-of-line storage) — jonli ko'rasiz
- `fillfactor` sozlamasini va u nima uchun kerakligini bilasiz
- **HOT (Heap-Only Tuple) update** — indeksni yangilamasdan tezroq `UPDATE` qilish mexanizmini — real o'lchov bilan ko'rasiz

## Nazariy qism

### Muammo: katta qiymat 8 KB sahifaga sig'maydi

16.1-darsda sahifa qat'iy 8 KB ekanini ko'rdik. Lekin PostgreSQL'da `TEXT` yoki `JSONB` ustuniga **istalgan uzunlikdagi** matn yozish mumkin — hatto bir necha megabaytlik. Bu ziddiyatni PostgreSQL **TOAST** (The Oversized-Attribute Storage Technique) mexanizmi orqali hal qiladi.

### TOAST'ning birinchi qadami — siqish (compression)

```sql
CREATE TABLE hujjatlar (
    id SERIAL PRIMARY KEY,
    qisqa_matn TEXT,
    uzun_matn TEXT
);

INSERT INTO hujjatlar (qisqa_matn, uzun_matn)
VALUES ('Kichik', repeat('Bu juda uzun matn boʻlagi. ', 1000));

SELECT id, length(uzun_matn) AS asl_uzunlik,
       pg_column_size(uzun_matn) AS saqlangan_hajm
FROM hujjatlar;
```

```
 id | asl_uzunlik | saqlangan_hajm 
----+-------------+-----------------
  1 |       27000 |             362
```

27 000 belgili matn — atigi **362 baytga** siqilgan! Bu — TOAST'ning birinchi strategiyasi: agar qiymat katta bo'lsa, PostgreSQL avval uni **PGLZ** (yoki `lz4`, sozlamaga qarab) algoritmi bilan siqishga harakat qiladi. Bizning misolimizda matn juda **takrorlanuvchan** (`repeat()` bilan yaratilgan) bo'lgani uchun, siqish g'oyat samarali bo'ldi va natija hatto sahifaga **osongina** sig'adigan hajmda qoldi.

### TOAST'ning ikkinchi qadami — tashqariga chiqarish (out-of-line storage)

Lekin siqish har doim ham yetarli bo'lavermaydi — masalan, **tasodifiy**, siqib bo'lmaydigan ma'lumot bilan sinaymiz:

```sql
INSERT INTO hujjatlar (qisqa_matn, uzun_matn)
SELECT 'Tasodifiy', string_agg(substr(md5(random()::text), 1, 32), '')
FROM generate_series(1, 200);

SELECT id, length(uzun_matn) AS asl_uzunlik, pg_column_size(uzun_matn) AS saqlangan_hajm
FROM hujjatlar WHERE qisqa_matn = 'Tasodifiy';
```

```
 id | asl_uzunlik | saqlangan_hajm 
----+-------------+-----------------
  2 |        6400 |            6400
```

Bu safar `pg_column_size` — `6400`, ya'ni asl uzunlik bilan **bir xil** — siqish deyarli hech qanday foyda bermadi (chunki MD5 xesh qiymatlari tasodifiy, takrorlanuvchan naqshsiz). Bunday holatda PostgreSQL qiymatni **bo'laklarga** (chunks, har biri ~2000 bayt) bo'lib, alohida, maxsus **TOAST jadvali**ga "chiqarib qo'yadi":

```sql
SELECT reltoastrelid::regclass AS toast_jadvali
FROM pg_class WHERE relname = 'hujjatlar';
```

```
 toast_jadvali 
-----------------------
 pg_toast.pg_toast_XXXXX
```

```sql
SELECT count(*) FROM pg_toast.pg_toast_XXXXX;
```

```
 count 
-------
     4
```

6400 baytlik qiymat, ~2000 baytlik bo'laklarga bo'linib, **4 ta** alohida qatorga (chunk) joylashtirildi. Asosiy jadvaldagi qatorda esa, haqiqiy ma'lumot o'rniga, faqat bu bo'laklarga ishora qiluvchi **kichik ko'rsatkich** (pointer) qoladi. Shu tufayli, asosiy jadval fayli kompakt qolaveradi, katta ma'lumotlar esa alohida, "quyi qatlamda" saqlanadi va faqat kerak bo'lganda o'qiladi.

> **Nega bu muhim:** agar sizga faqat `SELECT id, qisqa_matn FROM hujjatlar` kerak bo'lsa (uzun_matn`siz), PostgreSQL TOAST jadvaliga umuman **tegmaydi** — bu, ustunlar ro'yxatini ehtiyotkorlik bilan tanlashning (2.3-dars, `SELECT *`dan saqlanish tavsiyasi) yana bir amaliy sababi: keraksiz ustunlarni so'rashdan saqlanish, katta TOAST ma'lumotlarini keraksiz o'qishning oldini oladi.

### `fillfactor` — sahifada ataylab bo'sh joy qoldirish

16.1-darsda sahifalar, qatorlar to'lguncha "to'lib boradi" deb ko'rgan edik. Standart holatda, PostgreSQL sahifani **100%** to'ldirishga harakat qiladi. Lekin bu, tez-tez `UPDATE` qilinadigan jadvallar uchun — muammoli: agar sahifada bo'sh joy bo'lmasa, yangilangan qator **majburan boshqa sahifaga** ko'chib o'tishi kerak bo'ladi. `fillfactor` — bu muammoni oldindan hal qiladi:

```sql
CREATE TABLE hisoblagichlar (
    id SERIAL PRIMARY KEY,
    qiymat INTEGER
) WITH (fillfactor = 70);
```

`fillfactor = 70` — "har bir sahifani faqat 70% gacha to'ldir, qolgan 30%ni **ataylab bo'sh** qoldir" degani. Bu bo'sh joy, keyinchalik shu sahifadagi qatorlar yangilanganda ishlatiladi.

### HOT (Heap-Only Tuple) update — nega bo'sh joy muhim

Bu yerda **HOT update** deb ataladigan muhim optimizatsiya o'yinga kiradi. Odatda, `UPDATE` MVCC (17-bobda chuqur o'rganiladi) tufayli **yangi tuple versiyasi** yaratadi — eski qator "o'lik" (dead) deb belgilanadi, yangisi yoziladi. Agar jadvalda indeks bo'lsa, standart holatda **indeksni ham** yangilash kerak (yangi tuple manziliga ishora qilishi uchun) — bu qo'shimcha ish.

Lekin agar: (1) yangilanayotgan ustun(lar) **hech qanday indeksda ishlatilmagan** bo'lsa, va (2) yangi tuple **xuddi o'sha sahifada** sig'adigan bo'sh joy bo'lsa — PostgreSQL **HOT update** qila oladi: yangi tuple xuddi o'sha sahifada yaratiladi, va indeks **umuman yangilanmaydi** (eski tuple yangisiga "ichki" ishora qiladi). Buni jonli o'lchab ko'ramiz:

```sql
CREATE TABLE hisoblagichlar (
    id SERIAL PRIMARY KEY,
    qiymat INTEGER
) WITH (fillfactor = 70);

INSERT INTO hisoblagichlar (qiymat) SELECT 0 FROM generate_series(1, 100);

UPDATE hisoblagichlar SET qiymat = qiymat + 1;
UPDATE hisoblagichlar SET qiymat = qiymat + 1;

SELECT n_tup_upd, n_tup_hot_upd, n_live_tup, n_dead_tup
FROM pg_stat_user_tables WHERE relname = 'hisoblagichlar';
```

```
 n_tup_upd | n_tup_hot_upd | n_live_tup | n_dead_tup 
-----------+---------------+------------+------------
       200 |           191 |        100 |        100
```

Jami 200 ta `UPDATE` amalidan **191 tasi (95.5%) HOT update** bo'ldi! `fillfactor = 70` bilan ataylab qoldirilgan bo'sh joy, deyarli barcha yangilanishlarni "arzon" — indeksga tegmasdan — bajarish imkonini berdi. Agar `id` ustuni bo'yicha `PRIMARY KEY` indeksi mavjud bo'lsa-da, biz `qiymat` ustunini (indekslanmagan) yangilaganimiz uchun, HOT sharti (1) ham bajarildi.

### Qachon `fillfactor`ni pasaytirish kerak

| Vaziyat | Tavsiya |
|---|---|
| Jadval asosan `INSERT` qilinadi, kam `UPDATE` | Standart `fillfactor = 100` yetarli |
| Jadval tez-tez `UPDATE` qilinadi, indekslanmagan ustunlar bo'yicha | Pastroq `fillfactor` (70-90) — HOT update imkoniyatini oshiradi |
| Jadval faqat `SELECT` uchun (deyarli statik ma'lumot) | Standart `fillfactor = 100` — bo'sh joy behuda ketmasin |

Pastroq `fillfactor`ning "narxi" bor — jadval, bo'sh joy tufayli, diskda **ko'proq joy** egallaydi va to'liq skanerlash (full scan) biroz sekinroq bo'ladi. Shuning uchun bu — har doim, "tez-tez yangilanadimi" savoliga qarab qabul qilinadigan **savdolashuv** (trade-off).

## Amaliy misol

**Vazifa:** `mahsulotlar`ga o'xshash, tez-tez narx yangilanadigan jadval yarating va `fillfactor`ning HOT update foizi ustidagi ta'sirini kuzating.

```sql
CREATE TABLE narxlar_tez_ozgaruvchi (
    id SERIAL PRIMARY KEY,
    mahsulot_nomi TEXT,
    narxi NUMERIC(10,2)
) WITH (fillfactor = 80);

INSERT INTO narxlar_tez_ozgaruvchi (mahsulot_nomi, narxi)
SELECT 'Mahsulot ' || i, 10000 FROM generate_series(1, 50) AS i;

UPDATE narxlar_tez_ozgaruvchi SET narxi = narxi * 1.05;

SELECT n_tup_hot_upd, n_tup_upd FROM pg_stat_user_tables
WHERE relname = 'narxlar_tez_ozgaruvchi';
```

## Keng tarqalgan xatolar

**Xato 1:** Har bir `TEXT`/`JSONB` ustunni "TOAST bo'lishi kerak" deb, ularni har doim alohida, kichik jadvalga chiqarish.
❌ TOAST — avtomatik, shaffof mexanizm; kichik qiymatlar (2 KB gacha) hech qachon TOAST'ga chiqmaydi, va buni qo'lda boshqarishga hojat yo'q.
✅ TOAST'ni faqat tushunish va diagnostika uchun bilish kifoya — kundalik ishda uni "qo'lda optimallashtirish" shart emas.

**Xato 2:** Barcha jadvallarga "ehtiyot shart" deb, past `fillfactor` qo'yish.
❌ Kam yangilanadigan yoki faqat `INSERT` qilinadigan jadvallarda, past `fillfactor` shunchaki bo'sh joyni behuda sarflaydi.
✅ `fillfactor`ni faqat, `pg_stat_user_tables`da haqiqatan ko'p `UPDATE` ko'rgan jadvallar uchun pasaytiring.

**Xato 3:** HOT update sharti bajarilishi uchun, indeksdagi ustunni **hech qachon** yangilamaslik kerak deb, umuman yangilamaslikdan qochish.
❌ Bu — amaliy emas: ba'zan indekslangan ustunni yangilash zarurat bo'ladi, va bu holda HOT ishlamaydi — bu **normal**, faqat biroz sekinroq.
✅ HOT — bu qo'shimcha optimizatsiya, majburiy talab emas. Uni "iloji bo'lsa" ishlatish kifoya, har doim uning shartini qat'iy saqlashga urinish shart emas.

## Qisqacha xulosa

TOAST — katta qiymatlarni avval **siqish**, agar bu yetarli bo'lmasa — **bo'laklarga bo'lib, alohida jadvalga chiqarish** orqali, 8 KB sahifa chegarasini shaffof tarzda yechadi. `fillfactor` — sahifada ataylab bo'sh joy qoldirib, kelajakdagi yangilanishlarga tayyorgarlik ko'rish imkonini beradi, bu esa **HOT update** — indeksni yangilamasdan, tezroq `UPDATE`ni — ko'proq sodir bo'lishiga olib keladi (bizning testimizda 95.5% gacha). Bu — 16-bobni yakunlaydi: PostgreSQL'ning fizik saqlash arxitekturasini — sahifalar, TOAST, fillfactor — o'rgandingiz. Keyingi, 17-bobda **MVCC va VACUUM**ni — nima uchun "o'lik" tuplelar yig'ilib qolishini va ular qanday tozalanishini — chuqur o'rganamiz.

# 12.2. Trigger amaliy naqshlari — audit jurnali va avtomatik hisoblagichlar

## Bu darsda nimalarni o'rganasiz

- Real hayotiy "audit trail" (o'zgarishlar tarixi) naqshini triggerlar bilan qanday qurishni bilasiz
- `WHEN` sharti bilan triggerni faqat kerakli holatlarda ishga tushirishni o'rganasiz
- Denormallashtirilgan (hisoblangan) ustunni ikkinchi jadvaldagi o'zgarish asosida avtomatik yangilashni bilasiz
- Bu naqshning qachon foydali, qachon ortiqcha murakkablik ekanini baholay olasiz

## Nazariy qism

### Naqsh 1: audit jurnali (audit trail) — `WHEN` sharti bilan

12.1-darsda ko'rgan `AFTER` trigger g'oyasini davom ettirib, eng ko'p ishlatiladigan amaliy naqshlardan birini quramiz: **muhim ustun o'zgarganda, buni alohida tarix jadvaliga yozib borish**. Bu — moliyaviy, kadrlar yoki har qanday "kim, qachon, nimani o'zgartirdi" savoliga javob berish kerak bo'lgan tizimlarda deyarli majburiy talab.

```sql
CREATE TABLE xodimlar_audit (
    id SERIAL PRIMARY KEY,
    xodim_id INTEGER,
    eski_maosh NUMERIC(12,2),
    yangi_maosh NUMERIC(12,2),
    ozgartirilgan_vaqti TIMESTAMP DEFAULT NOW()
);

CREATE OR REPLACE FUNCTION log_maosh_ozgarishi() RETURNS TRIGGER AS $$
BEGIN
    INSERT INTO xodimlar_audit (xodim_id, eski_maosh, yangi_maosh)
    VALUES (OLD.id, OLD.ish_haqi, NEW.ish_haqi);
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_maosh_audit
AFTER UPDATE ON xodimlar
FOR EACH ROW
WHEN (OLD.ish_haqi IS DISTINCT FROM NEW.ish_haqi)
EXECUTE FUNCTION log_maosh_ozgarishi();
```

Bu yerdagi eng muhim yangi element — `WHEN (OLD.ish_haqi IS DISTINCT FROM NEW.ish_haqi)`. `xodimlar` jadvali ustida ko'plab turli `UPDATE`lar bo'lishi mumkin (lavozimni o'zgartirish, bo'limni o'zgartirish va h.k.), lekin bizga faqat **maosh o'zgargan** hollar kerak. `WHEN` sharti — bu aynan shu: trigger funksiyasi faqat shart **rost** bo'lgandagina chaqiriladi (2.3-darsda ko'rgan `IS DISTINCT FROM` bu yerda ham foydali — u `NULL`larni ham to'g'ri, "xavfsiz" solishtiradi).

Sinab ko'ramiz — bitta xodimning maoshini oshiramiz, ikkinchisining faqat lavozimini o'zgartiramiz:

```sql
UPDATE xodimlar SET ish_haqi = ish_haqi * 1.10 WHERE id = 4;
UPDATE xodimlar SET lavozim = lavozim WHERE id = 5;
SELECT * FROM xodimlar_audit;
```

```
 id | xodim_id | eski_maosh | yangi_maosh |    ozgartirilgan_vaqti     
----+----------+------------+-------------+----------------------------
  1 |        4 | 8000000.00 |  8800000.00 | 2026-08-30 03:10:41.390746
```

Natijada faqat **bitta** yozuv bor — 4-xodimning maosh o'zgarishi. 5-xodim uchun `UPDATE` bajarilgan bo'lsa-da (`lavozim = lavozim` — texnik jihatdan `UPDATE`, garchi qiymat aslida o'zgarmagan bo'lsa ham), `WHEN` sharti uni filtrlab tashladi, chunki `ish_haqi` o'zgarmagan edi. Bu — `WHEN`ning kuchi: trigger funksiyasini har safar chaqirib, uning **ichida** `IF`bilan tekshirishdan ko'ra samaraliroq (chunki `WHEN` sharti yolg'on bo'lsa, funksiya umuman chaqirilmaydi).

> **Nega audit jadvali alohida?** Diqqat qiling — `xodimlar_audit` jadvali `xodimlar`ning **hozirgi holatini** emas, balki **tarixini** saqlaydi. Bu — 6.2-darsdagi `CREATE TABLE AS` bilan yaratilgan statik nusxadan farqli: u yerda bitta "suratga olish" (snapshot) bor edi, bu yerda esa **har bir o'zgarish** alohida qator sifatida to'planib boradi — vaqt o'tishi bilan o'sib boradigan, to'liq tarixiy jurnal.

### Naqsh 2: denormallashtirilgan hisoblagichni avtomatik saqlash

Ikkinchi keng tarqalgan naqsh — bir jadvaldagi voqea, boshqa jadvaldagi **hisoblangan** (denormallashtirilgan) qiymatni avtomatik yangilashi kerak bo'lgan holatlar. Klassik misol — sotuv bo'lganda, ombordagi mahsulot sonini avtomatik kamaytirish:

```sql
CREATE TABLE test_mahsulot (
    id SERIAL PRIMARY KEY,
    nomi TEXT,
    ombordagi_soni INTEGER
);
CREATE TABLE test_sotuv (
    id SERIAL PRIMARY KEY,
    mahsulot_id INTEGER REFERENCES test_mahsulot(id),
    soni INTEGER
);

INSERT INTO test_mahsulot (nomi, ombordagi_soni) VALUES ('Test mahsulot', 50);

CREATE OR REPLACE FUNCTION ombordan_ayirish() RETURNS TRIGGER AS $$
BEGIN
    UPDATE test_mahsulot
    SET ombordagi_soni = ombordagi_soni - NEW.soni
    WHERE id = NEW.mahsulot_id;

    IF (SELECT ombordagi_soni FROM test_mahsulot WHERE id = NEW.mahsulot_id) < 0 THEN
        RAISE EXCEPTION 'Omborda yetarli mahsulot yo''q (mahsulot_id=%)', NEW.mahsulot_id;
    END IF;

    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_ombordan_ayirish
AFTER INSERT ON test_sotuv
FOR EACH ROW
EXECUTE FUNCTION ombordan_ayirish();
```

Sinab ko'ramiz:

```sql
INSERT INTO test_sotuv (mahsulot_id, soni) VALUES (1, 12);
SELECT * FROM test_mahsulot;
```

```
 id |     nomi      | ombordagi_soni 
----+---------------+-----------------
  1 | Test mahsulot |             38
```

50 dona bor edi, 12 dona sotildi — trigger avtomatik ravishda `ombordagi_soni`ni 38ga tushirdi, buni hech kim qo'lda `UPDATE test_mahsulot SET ...` yozmasdan. Endi omborda yo'q miqdorni sotishga urinib ko'ramiz:

```sql
INSERT INTO test_sotuv (mahsulot_id, soni) VALUES (1, 1000);
```

```
ERROR:  Omborda yetarli mahsulot yo'q (mahsulot_id=1)
CONTEXT:  PL/pgSQL function ombordan_ayirish() line 8 at RAISE
```

Bu — bitta trigger ikkita vazifani bajarayotganiga misol: (1) denormallashtirilgan qiymatni yangilash, va (2) biznes qoidasini (manfiy songa tushib ketmaslik) ta'minlash. Diqqat qiling — `AFTER INSERT` ichida trigger o'zi yana bir `UPDATE` bajarmoqda (boshqa jadvalga); bu — PL/pgSQL trigger funksiyalari ichida to'liq erkin SQL yozish mumkinligining namunasi.

### Qachon trigger ishlatish, qachon ishlatmaslik kerak

Triggerlar kuchli, lekin ular "ko'rinmas" mantiq yaratadi — kod bazasini o'qiyotgan dasturchi, agar bilmasa, nega `INSERT`dan keyin boshqa jadval ham o'zgarganini tushunmasligi mumkin. Shuning uchun amaliyotda quyidagi tamoyilga rioya qilinadi:

| Vaziyat | Tavsiya |
|---|---|
| Audit/tarix yozish, ma'lumot yaxlitligini ta'minlash (masalan, "manfiy songa tushmasin") | ✅ Trigger juda mos — bu qoida **har doim**, qanday qilib yozilishidan qat'i nazar, amal qilishi kerak |
| Oddiy hisob-kitob, faqat bitta ilova tomonidan qilinadigan | ⚠️ Ko'pincha ilova kodida (backend) qilingani ma'qulroq — kodni o'qish osonroq bo'ladi |
| Murakkab biznes jarayoni (masalan, email yuborish, tashqi API chaqirish) | ❌ Trigger emas — buning uchun navbat (queue) yoki alohida servis kerak, chunki trigger tranzaksiya ichida, sinxron ishlaydi |

Umumiy qoida: **triggerni ma'lumotlar bazasi darajasidagi "hech qachon buzilmasligi kerak bo'lgan qoidalar" uchun**, murakkab biznes jarayonlarni esa ilova darajasida ishlatish — ko'pchilik tajribali muhandislar tavsiya qiladigan yondashuv.

## Amaliy misol

**Vazifa:** `mijozlar` jadvalidagi `shahar` ustuni o'zgarganda, buni kuzatuvchi audit jadvali yarating (yuqoridagi maosh audit naqshini takrorlang, boshqa ustun bilan).

```sql
CREATE TABLE mijozlar_shahar_audit (
    id SERIAL PRIMARY KEY,
    mijoz_id INTEGER,
    eski_shahar TEXT,
    yangi_shahar TEXT,
    ozgartirilgan_vaqti TIMESTAMP DEFAULT NOW()
);

CREATE OR REPLACE FUNCTION log_shahar_ozgarishi() RETURNS TRIGGER AS $$
BEGIN
    INSERT INTO mijozlar_shahar_audit (mijoz_id, eski_shahar, yangi_shahar)
    VALUES (OLD.id, OLD.shahar, NEW.shahar);
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_shahar_audit
AFTER UPDATE ON mijozlar
FOR EACH ROW
WHEN (OLD.shahar IS DISTINCT FROM NEW.shahar)
EXECUTE FUNCTION log_shahar_ozgarishi();
```

## Keng tarqalgan xatolar

**Xato 1:** `WHEN` shartisiz, har bir `UPDATE`da (hatto tegishli ustun o'zgarmagan bo'lsa ham) audit yozuvi yaratish.
❌ Bu — audit jadvalini keraksiz yozuvlar bilan "iflos" qiladi va haqiqiy o'zgarishlarni topishni qiyinlashtiradi.
✅ Har doim `WHEN (OLD.ustun IS DISTINCT FROM NEW.ustun)` bilan aniq shart qo'ying.

**Xato 2:** Denormallashtirilgan hisoblagich triggerida, birinchi `UPDATE`dan keyingi yangi qiymatni tekshirmasdan qoldirish (masalan, yuqoridagi misolda `RAISE EXCEPTION` tekshiruvini o'tkazib yuborish).
❌ Bunday holda, ombordagi son manfiy bo'lib qolishi mumkin — bu jismonan mumkin bo'lmagan holat, lekin baza buni ushlab qolmaydi.
✅ Har doim, denormallashtirilgan qiymatni yangilagandan keyin, uning haligacha mantiqiy chegaralarda ekanini tekshiring.

**Xato 3:** Triggerlar zanjirini (bitta trigger boshqa jadvalni o'zgartiradi, u yerdagi trigger яна boshqasini o'zgartiradi...) nazoratsiz qurish.
❌ Bunday zanjirlar disk tuzilishini tushunish va debug qilishni juda qiyinlashtiradi, ba'zan cheksiz tsiklga ham olib kelishi mumkin.
✅ Trigger zanjirlarini iloji boricha qisqa saqlang, va murakkab ko'p bosqichli mantiqni ilova kodiga yoki saqlangan protseduraga (procedure) ko'chiring.

## Mashq/topshiriq

**(Oson)** `buyurtmalar` jadvalidagi `holati` ustuni o'zgarganda, buni kuzatuvchi `buyurtma_holati_audit(id, buyurtma_id, eski_holat, yangi_holat, vaqt)` jadvali va triggerini yarating.

**(O'rtacha)** `test_mahsulot`/`test_sotuv` naqshini kengaytiring: endi `test_sotuv`dan qator **o'chirilganda** (`DELETE`), ombordagi sonni orqaga qaytaring (ya'ni `ombordagi_soni`ni oshiring).

**(Qiyin)** `bolimlar` jadvaliga `xodimlar_soni INTEGER DEFAULT 0` ustuni qo'shing va `xodimlar` jadvalida `INSERT`/`DELETE`/`UPDATE` (bo'lim o'zgarganda) sodir bo'lganda, `bolimlar.xodimlar_soni`ni avtomatik to'g'ri hisoblab turadigan trigger(lar) yarating.

3.
```sql
ALTER TABLE bolimlar ADD COLUMN xodimlar_soni INTEGER DEFAULT 0;

CREATE OR REPLACE FUNCTION bolim_xodimlar_sonini_yangilash() RETURNS TRIGGER AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        UPDATE bolimlar SET xodimlar_soni = xodimlar_soni + 1 WHERE id = NEW.bolim_id;
        RETURN NEW;
    ELSIF TG_OP = 'DELETE' THEN
        UPDATE bolimlar SET xodimlar_soni = xodimlar_soni - 1 WHERE id = OLD.bolim_id;
        RETURN OLD;
    ELSIF TG_OP = 'UPDATE' AND OLD.bolim_id IS DISTINCT FROM NEW.bolim_id THEN
        UPDATE bolimlar SET xodimlar_soni = xodimlar_soni - 1 WHERE id = OLD.bolim_id;
        UPDATE bolimlar SET xodimlar_soni = xodimlar_soni + 1 WHERE id = NEW.bolim_id;
        RETURN NEW;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_bolim_xodimlar_soni
AFTER INSERT OR UPDATE OR DELETE ON xodimlar
FOR EACH ROW
EXECUTE FUNCTION bolim_xodimlar_sonini_yangilash();
```

(3-mashqda `UPDATE` holatida faqat `bolim_id` **haqiqatan o'zgargan** hollarda ikkala bo'lim hisoblagichini yangilash kerakligiga e'tibor bering — aks holda, masalan, faqat `lavozim`ni o'zgartirganda ham hisoblagich noto'g'ri o'zgarib ketadi.)

## Qisqacha xulosa

Bu darsda triggerlarning ikkita eng ko'p ishlatiladigan amaliy naqshini ko'rdik: **audit jurnali** (`WHEN` sharti bilan, faqat kerakli ustun o'zgarganda tarixni yozib borish) va **denormallashtirilgan hisoblagichni avtomatik saqlash** (bir jadvaldagi voqea, boshqa jadvaldagi hisoblangan qiymatni yangilaydi). Ikkala naqsh ham — ma'lumotlar bazasi darajasida "hech qachon buzilmasligi kerak bo'lgan qoidalar"ni ta'minlashning kuchli usuli, lekin ularni ehtiyotkorlik bilan, faqat haqiqatan kerak bo'lgan joyda ishlatish tavsiya etiladi. Bu — 12-bobni yakunlaydi. Keyingi, 13-bobda **tranzaksiyalar**ni — `BEGIN`/`COMMIT`/`ROLLBACK` va ACID xususiyatlarini — chuqur o'rganamiz (bu darslarda bir necha marta ko'rgan `BEGIN ... ROLLBACK` texnikasining nazariy asosi).

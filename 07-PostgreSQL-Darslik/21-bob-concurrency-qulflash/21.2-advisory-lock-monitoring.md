# 21.2. Advisory lock'lar va qulflarni monitoring qilish (ICH-ICHIGA)

## Bu darsda nimalarni o'rganasiz

- **Advisory lock** — ma'lumotlarga bog'liq bo'lmagan, ilova darajasidagi qulflarni o'rganasiz
- `pg_blocking_pids()` bilan "kim kimni bloklayapti"ni bir zumda aniqlashni bilasiz
- Qulflarni to'liq diagnostika qiladigan so'rovni tuzishni o'rganasiz
- Jadval darajasidagi qulf rejimlarini (`ACCESS EXCLUSIVE` va boshqalar) tushunasiz

## Nazariy qism

### Advisory lock — "o'z qo'lingiz bilan" boshqariladigan qulf

21.1-darsda ko'rgan qulflarning barchasi — PostgreSQL tomonidan, **avtomatik**, qatorlar/jadvallarga bog'liq holda boshqariladi. Lekin ba'zan sizga **ma'lumotga umuman bog'liq bo'lmagan** qulf kerak bo'ladi — masalan, "faqat bitta nusxada ishlashi kerak bo'lgan fon vazifasi (background job)ni, bir vaqtning o'zida ikkita nusxada ishga tushirilmasligini ta'minlash". Buning uchun **advisory lock** (maslahat beruvchi qulf) mo'ljallangan — bu, siz o'zingiz, ixtiyoriy son (kalit) bilan boshqaradigan qulf turi:

```sql
SELECT pg_try_advisory_lock(12345) AS birinchi_urinish;
```

```
 birinchi_urinish 
--------------------
 t
```

`pg_try_advisory_lock(kalit)` — berilgan `kalit` (istalgan `bigint`) bo'yicha qulfni **olishga urinadi**: agar muvaffaqiyatli bo'lsa `true`, band bo'lsa (boshqa sessiya allaqachon ushlab turgan bo'lsa) `false` qaytaradi — **kutmasdan**, darhol.

Muhim xususiyat — bir xil sessiya, bir xil kalitni **qayta-qayta** so'rasa, har safar muvaffaqiyatli bo'ladi (bu — "reentrant" xatti-harakat):

```sql
SELECT pg_try_advisory_lock(12345) AS ikkinchi_urinish_shu_sessiyada;
```

```
 ikkinchi_urinish_shu_sessiyada 
----------------------------------
 t
```

Lekin **boshqa** sessiyadan, xuddi shu kalit bilan urinsak:

```sql
-- 1-sessiyada:
SELECT pg_advisory_lock(99999);  -- qulfni oladi va KUTADI (agar band bo'lsa)

-- 2-sessiyada (mustaqil):
SELECT pg_try_advisory_lock(99999) AS boshqa_sessiyada;
```

```
 boshqa_sessiyada 
--------------------
 f
```

**`false`** — chunki 1-sessiya bu qulfni allaqachon ushlab turibdi. `pg_advisory_unlock(kalit)` bilan uni bo'shatish mumkin, yoki sessiya tugaganda (ulanish uzilganda) u **avtomatik** bo'shaydi.

| Funksiya | Xatti-harakati |
|---|---|
| `pg_advisory_lock(kalit)` | Qulfni oladi, agar band bo'lsa — **bo'shagunicha kutadi** |
| `pg_try_advisory_lock(kalit)` | Qulfni olishga urinadi, band bo'lsa **darhol `false` qaytaradi** (kutmaydi) |
| `pg_advisory_unlock(kalit)` | Qulfni bo'shatadi |

**Amaliy qo'llanish:** kunlik hisobot generatsiya qiluvchi cron vazifasi, "men allaqachon ishga tushganmi" tekshiruvi uchun `pg_try_advisory_lock`dan foydalanishi mumkin — agar `false` qaytsa, demak boshqa nusxa allaqachon ishlamoqda, va bu nusxa oddiygina chiqib ketishi kerak. Bu — ma'lumotlar bazasi darajasida, alohida "qulflash serveri" (masalan, Redis) o'rnatmasdan, oddiy va ishonchli **"faqat bitta nusxa"** (mutual exclusion) mexanizmini beradi.

### `pg_blocking_pids()` — kim kimni bloklayotganini bir zumda aniqlash

21.1-darsda `pg_stat_activity`dan `wait_event_type = Lock`ni qo'lda qidirdik. PostgreSQL buning uchun ancha qulayroq, tayyor funksiya taqdim etadi:

```sql
SELECT pid, pg_blocking_pids(pid) AS meni_bloklayotganlar
FROM pg_stat_activity WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

```
 pid  | meni_bloklayotganlar 
-------+------------------------
 3642 | {3637}
```

Bu natija — bir zumda, aniq javob beradi: `pid=3642` jarayoni, hozir `pid=3637` tomonidan bloklanmoqda. `pg_blocking_pids()` — massiv qaytaradi, chunki nazariy jihatdan bitta jarayon, bir vaqtning o'zida, **bir nechta** boshqa jarayon tomonidan bloklanishi mumkin.

### To'liq diagnostika so'rovi — "kim kimni, qaysi so'rov bilan" bloklamoqda

Amaliy diagnostikada, odatda sizga faqat `pid` raqamlari emas, balki **haqiqiy so'rov matni** ham kerak bo'ladi:

```sql
SELECT blocked.pid AS bloklangan_pid, blocked.query AS bloklangan_sorov,
       blocking.pid AS bloklovchi_pid, blocking.query AS bloklovchi_sorov
FROM pg_stat_activity blocked
JOIN pg_locks bl ON bl.pid = blocked.pid AND NOT bl.granted
JOIN pg_locks kl ON kl.locktype = bl.locktype AND kl.database IS NOT DISTINCT FROM bl.database
    AND kl.relation IS NOT DISTINCT FROM bl.relation AND kl.pid != bl.pid AND kl.granted
JOIN pg_stat_activity blocking ON blocking.pid = kl.pid;
```

```
 bloklangan_pid |                     bloklangan_sorov                       | bloklovchi_pid |                     bloklovchi_sorov                       
------------------+--------------------------------------------------------------+-------------------+--------------------------------------------------------------
             3622 | UPDATE test_lock_demo SET balans = balans - 1 WHERE id = 1; |            3617 | UPDATE test_lock_demo SET balans = balans - 1 WHERE id = 1;
```

Bu so'rov — 9-bobdagi `JOIN`/subquery bilimlarimizni, endi tizim katalog jadvallariga (`pg_locks`, `pg_stat_activity`) qo'llash namunasi: `pg_locks`ni **o'zi bilan** (self-join, 3.4-dars) birlashtirib, "berilmagan" (`NOT bl.granted`) qulf bilan "berilgan" (`kl.granted`) qulfni, bir xil resurs (`locktype`, `relation`) bo'yicha moslashtiramiz. Real production muhitida, bu so'rov — "hozir nima uchun so'rovlar sekinlashib qolgan" degan savolga tezkor javob beradigan, eng ko'p ishlatiladigan diagnostika vositalaridan biri.

### Jadval darajasidagi qulf rejimlari

15.2-darsda `VACUUM FULL`ning `ACCESS EXCLUSIVE` qulfini eslatib o'tgan edik. PostgreSQL'da, aslida, jadval darajasida **sakkizta** turli qulf rejimi bor, har biri **turli darajada** cheklovchi:

| Rejim | Qachon olinadi | Nimani bloklaydi |
|---|---|---|
| `ACCESS SHARE` | Oddiy `SELECT` | Faqat `ACCESS EXCLUSIVE`ni bloklaydi |
| `ROW SHARE` | `SELECT ... FOR UPDATE`/`FOR SHARE` | `EXCLUSIVE`, `ACCESS EXCLUSIVE`ni bloklaydi |
| `ROW EXCLUSIVE` | `INSERT`, `UPDATE`, `DELETE` | `SHARE` va undan yuqorilarni bloklaydi |
| ... | (oraliq rejimlar) | |
| `ACCESS EXCLUSIVE` | `DROP TABLE`, `ALTER TABLE` (ko'p turlari), `VACUUM FULL`, `TRUNCATE` | **Hammasini** bloklaydi — hatto oddiy `SELECT`ni ham |

Muhim, amaliy xulosa: **oddiy `SELECT` va oddiy `UPDATE`/`INSERT`** bir-birini deyarli hech qachon bloklamaydi (turli, bir-biriga mos keluvchi rejimlar) — bu, MVCC (17-bob) bilan birgalikda, PostgreSQL'ning yuqori parallellik ko'rsatkichining sababi. Lekin **struktura o'zgartiruvchi** amallar (`ALTER TABLE`, `DROP TABLE`, `VACUUM FULL`) — `ACCESS EXCLUSIVE` talab qiladi va **hamma narsani**, hatto oddiy `SELECT`larni ham, vaqtincha to'xtatadi. Bu — 15.2-darsda `VACUUM FULL`ni "faqat texnik xizmat oynasida" ishlatish tavsiyasining, va umuman, `ALTER TABLE`ni ishlab turgan, yuklamali tizimda ehtiyotkorlik bilan rejalashtirish zarurligining sababi.

## Amaliy misol

**Vazifa:** Fon vazifasining faqat bitta nusxada ishlashini ta'minlovchi oddiy naqshni yozing.

```sql
DO $$
BEGIN
    IF pg_try_advisory_lock(555555) THEN
        RAISE NOTICE 'Qulf olindi - vazifa boshlanmoqda...';
        -- (bu yerda haqiqiy ish bajarilardi)
        PERFORM pg_advisory_unlock(555555);
        RAISE NOTICE 'Vazifa tugadi, qulf bo''shatildi.';
    ELSE
        RAISE NOTICE 'Boshqa nusxa allaqachon ishlamoqda - chiqib ketilmoqda.';
    END IF;
END $$;
```

## Keng tarqalgan xatolar

**Xato 1:** Advisory lock'ni bo'shatishni (`pg_advisory_unlock`) unutib, uni "abadiy band" holatda qoldirish.
❌ Agar sessiya tugamasa (masalan, connection pool orqali qayta ishlatilsa), unutilgan qulf, boshqa barcha keyingi urinishlarni **abadiy** bloklab qo'yishi mumkin.
✅ Har doim `pg_advisory_unlock`ni, ish tugagach (yoki xato yuz bersa ham, `EXCEPTION` blokida) chaqirishni unutmang, yoki sessiya darajasidagi emas, **tranzaksiya darajasidagi** variantlardan (`pg_advisory_xact_lock` — tranzaksiya tugashi bilan avtomatik bo'shaydi) foydalaning.

**Xato 2:** `ALTER TABLE`ni, ishlab turgan, yuqori yuklamali jadvalda, "tez amal" deb, ogohlantirishsiz bajarish.
❌ `ACCESS EXCLUSIVE` qulfi, hatto tezkor `ALTER TABLE`ning o'zi ham, agar u jadvalda **band bo'lgan** boshqa uzoq tranzaksiya bo'lsa, o'sha tranzaksiya tugashini kutib, navbatda uzoq turishi mumkin — va bu orada, **undan keyin** kelgan barcha oddiy `SELECT`lar ham, ushbu `ALTER TABLE`ning orqasida "navbatga tizilib" qoladi.
✅ Ishlab turgan tizimlarda struktura o'zgartirishlarni, past yuklama vaqtida yoki maxsus texnikalar (masalan, `CREATE INDEX CONCURRENTLY`) bilan rejalashtiring.

**Xato 3:** `pg_locks`ni tekshirmasdan, "so'rov nega sekin ishlayapti" degan savolga faqat `EXPLAIN` (19-bob) orqali javob izlash.
❌ Ba'zida so'rovning o'zi mukammal optimallashtirilgan, lekin u shunchaki **boshqa tranzaksiya tugashini kutmoqda** — bu holatda `EXPLAIN` hech narsani ko'rsatmaydi.
✅ "Sekin so'rov" muammosini diagnostika qilishda, avval `pg_blocking_pids()`/`pg_stat_activity` bilan **qulflanish** sababmi yoki yo'qmi, tekshiring, keyingina `EXPLAIN`ga o'ting.

## Mashq/topshiriq

**(Oson)** `pg_try_advisory_lock`dan foydalanib, ikkita turli kalit (masalan, `111` va `222`) bilan mustaqil ravishda qulf olib-qo'yib ko'ring, ular bir-biriga ta'sir qilmasligini tasdiqlang.

**(O'rtacha)** Ikkita mustaqil sessiyada, 21.1-darsdagi blokirovka ssenariysini takrorlang, lekin bu safar `pg_blocking_pids()` funksiyasidan foydalanib, bloklanish holatini aniqlang.

**(Qiyin)** `pg_advisory_xact_lock` (tranzaksiya darajasidagi variant) bilan `pg_advisory_lock` (sessiya darajasidagi) orasidagi farqni, `COMMIT`dan keyin qulf avtomatik bo'shaydimi yoki yo'qmi tekshirib, amaliy tasdiqlang.

3.
```sql
BEGIN;
SELECT pg_advisory_xact_lock(777);
COMMIT;
-- COMMIT'dan keyin, qulf AVTOMATIK bo'shaydi (chunki u tranzaksiya darajasida edi)

SELECT pg_advisory_lock(888);
-- Bu sessiya darajasida - COMMIT/ROLLBACK unga ta'sir qilmaydi,
-- faqat pg_advisory_unlock(888) yoki sessiya tugashi uni bo'shatadi
```

## Qisqacha xulosa

Advisory lock'lar — ma'lumotlarga bog'liq bo'lmagan, ilova darajasidagi muvofiqlashtirish (masalan, "faqat bitta nusxa" mexanizmi) uchun ishlatiladi, `pg_try_advisory_lock`/`pg_advisory_unlock` orqali boshqariladi. `pg_blocking_pids()` va `pg_locks`+`pg_stat_activity` self-join so'rovi — real vaqtda "kim kimni bloklamoqda" degan savolga tezkor javob beradigan, amaliy diagnostika vositalari. Jadval darajasidagi qulf rejimlari (`ACCESS SHARE`dan `ACCESS EXCLUSIVE`gacha) — turli amallarning bir-biriga qanchalik "xalaqit berishini" belgilaydi, va struktura o'zgartiruvchi amallar (`ALTER TABLE`, `VACUUM FULL`) eng qattiq, hamma narsani to'xtatuvchi qulfni talab qilishini bilish muhim. Bu — 21-bobni yakunlaydi: concurrency va qulflashning to'liq rasmini oldingiz. Keyingi, 22-bobda **replikatsiya**ni — bir nechta server orasida ma'lumotni qanday nusxalashni — chuqur o'rganamiz.

# 21.1. Qator va jadval qulflari, blokirovka va deadlock (ICH-ICHIGA)

## Bu darsda nimalarni o'rganasiz

- `SELECT ... FOR UPDATE` bilan qator darajasidagi qulfni jonli sinaysiz
- `pg_locks` va `pg_stat_activity` bilan qulflarni **real vaqtda kuzatishni** o'rganasiz
- Bitta tranzaksiya, boshqasi tugaguncha, qanday "kutib turishini" ko'rasiz
- **Deadlock**ni — ikkita tranzaksiya bir-birini abadiy kutib qolishini — real, jonli holatda hosil qilasiz va PostgreSQL uni qanday hal qilishini ko'rasiz

## Nazariy qism

### Nega qulflash kerak

17-bobda MVCC — o'qish va yozishning bir-biriga xalaqit bermasligini ta'minlashini ko'rgan edik. Lekin MVCC **hamma narsani** hal qilmaydi: agar **ikkita** tranzaksiya, **bir vaqtning o'zida, bir xil qatorni yangilamoqchi** bo'lsa-chi? Bu yerda MVCC'ning "versiyalash" g'oyasi yetarli emas — chunki ikkala yozish ham, oxir-oqibat, **ketma-ket**, biri-biridan keyin amalga oshishi kerak. Aynan shu vazifani **qulflar** (locks) hal qiladi.

### `FOR UPDATE` — qatorni "band qilib qo'yish"

```sql
CREATE TABLE test_lock_demo (id SERIAL PRIMARY KEY, egasi TEXT, balans NUMERIC(12,2));
INSERT INTO test_lock_demo (egasi, balans) VALUES ('Ali', 1000), ('Vali', 500);
```

`SELECT ... FOR UPDATE` — bu, oddiy `SELECT`dan farqli, o'qigan qatorni **shu tranzaksiya tugaguncha, boshqalar o'zgartira olmasin** deb "band qiladi":

```sql
BEGIN;
SELECT * FROM test_lock_demo WHERE id = 1 FOR UPDATE;
```

```
BEGIN
 id | egasi | balans  
----+-------+---------
  1 | Ali   | 1000.00
```

Bu tranzaksiya hali `COMMIT`/`ROLLBACK` qilinmagan holda, boshqa (mustaqil) sessiyadan `pg_locks`ni tekshiramiz:

```sql
SELECT pid, locktype, mode, granted, relation::regclass
FROM pg_locks WHERE relation = 'test_lock_demo'::regclass;
```

```
 pid  | locktype |     mode     | granted |    relation    
------+----------+---------------+---------+------------------
 3498 | relation | RowShareLock | t       | test_lock_demo
```

`pg_locks` — PostgreSQL'ning **barcha faol qulflarini** ko'rsatadigan tizim ko'rinishi (view). `RowShareLock` — `FOR UPDATE`ning jadval darajasidagi "yon ta'siri" (o'zi esa, aynan qatorning ichida, tuple darajasida qo'shimcha, alohida belgi bilan qulflanadi — bu, `pg_locks`da alohida qator sifatida har doim ko'rinavermaydi, lekin uning ta'siri quyida ko'rinadi).

### Blokirovka — ikkinchi tranzaksiya "kutadi"

Endi, birinchi tranzaksiya hali ochiq turgan holda (u `id=1`ni `UPDATE` qilib, hali `COMMIT` qilmagan), **ikkinchi**, mustaqil tranzaksiya xuddi shu qatorni yangilashga urinadi:

```sql
-- 1-sessiya:
BEGIN;
UPDATE test_lock_demo SET balans = balans - 100 WHERE id = 1;
-- (hali COMMIT qilinmagan)

-- 2-sessiya (mustaqil ulanish):
UPDATE test_lock_demo SET balans = balans - 50 WHERE id = 1;
-- Bu buyruq DARHOL natija bermaydi - u "osilib qoladi" (kutadi)!
```

1-sessiya hali ochiq turgan paytda, 2-sessiyani kuzatib turgan uchinchi, tashqi sessiyadan holatni tekshiramiz:

```sql
SELECT pid, wait_event_type, wait_event, state, query
FROM pg_stat_activity
WHERE datname = 'dokon_bazasi' AND query LIKE 'UPDATE%';
```

```
 pid  | wait_event_type |  wait_event   |        state         |                             query                              
------+------------------+---------------+----------------------+------------------------------------------------------------------
 3516 | Client           | ClientRead    | idle in transaction  | UPDATE test_lock_demo SET balans = balans - 100 WHERE id = 1;
 3522 | Lock             | transactionid | active               | UPDATE test_lock_demo SET balans = balans - 50 WHERE id = 1;
```

Bu — juda ma'rifiy: 2-sessiya (`pid=3522`)ning holati `wait_event_type = Lock`, `wait_event = transactionid` — ya'ni u **faol ravishda kutmoqda**, chunki 1-sessiya (`pid=3516`, holati `idle in transaction` — "tranzaksiya ichida, hozircha hech narsa qilmayapti") hali `id=1`ni band qilib turibdi. Endi 1-sessiyada `COMMIT;` chaqirsak:

```sql
-- 1-sessiyada:
COMMIT;
```

Aynan shu daqiqada, 2-sessiyaning "osilib qolgan" `UPDATE`i **darhol** davom etadi va muvaffaqiyatli yakunlanadi (`UPDATE 1`). Bu — qulflashning aynan shu maqsadi: ikkita bir vaqtdagi yozishni, **xavfsiz, ketma-ket** tartibga solish, hech qanday ma'lumot yo'qolmasdan yoki buzilmasdan (agar qulflash bo'lmaganida, "yo'qolgan yangilanish" — lost update — muammosi yuzaga kelishi mumkin edi: ikkala `UPDATE` ham eski qiymatni o'qib, biri ikkinchisining natijasini "bosib" yuborgan bo'lardi).

### Deadlock — ikkita tranzaksiya bir-birini abadiy kutib qolishi

Endi eng qiziq holat — **deadlock** ("o'lik qulflanish"): ikkita tranzaksiya, **teskari tartibda**, bir-birining resurslarini kutib qolsa nima bo'ladi? Buni jonli hosil qilamiz:

**A tranzaksiyasi**, avval `id=1`ni qulflaydi:
```sql
BEGIN;
UPDATE test_lock_demo SET balans = balans - 10 WHERE id = 1;
```

**B tranzaksiyasi**, avval `id=2`ni qulflaydi:
```sql
BEGIN;
UPDATE test_lock_demo SET balans = balans - 10 WHERE id = 2;
```

Endi **A**, `id=2`ga (B tomonidan band qilingan) urinadi — A kutadi:
```sql
-- A da:
UPDATE test_lock_demo SET balans = balans + 10 WHERE id = 2;
-- (kutmoqda, chunki B id=2ni band qilgan)
```

Va **B**, `id=1`ga (A tomonidan band qilingan) urinadi — mana shu daqiqada, **doiraviy kutish** (circular wait) yuzaga keladi: A — B'ni kutmoqda, B — A'ni kutmoqda:

```sql
-- B da:
UPDATE test_lock_demo SET balans = balans + 10 WHERE id = 1;
```

PostgreSQL, bu doiraviy holatni **avtomatik aniqlaydi** (maxsus, muntazam ishlaydigan "deadlock detector" orqali) va, ikkita tranzaksiyadan **birini**, majburan xato bilan to'xtatadi:

```
ERROR:  deadlock detected
DETAIL:  Process 3543 waits for ShareLock on transaction 1170; blocked by process 3544.
Process 3544 waits for ShareLock on transaction 1169; blocked by process 3543.
HINT:  See server log for query details.
CONTEXT:  while updating tuple (0,2) in relation "test_lock_demo"
```

A tranzaksiyasi (`3543`) — **"qurbon"** sifatida tanlanib, xato bilan bekor qilindi (uning barcha o'zgarishlari avtomatik `ROLLBACK` qilindi). B tranzaksiyasi esa, endi A ortga chekingani uchun, o'z ishini **muvaffaqiyatli davom ettirdi va yakunladi**.

> **Muhim tushuncha:** deadlock — bu, dasturchi tomonidan yozilgan **noto'g'ri kod natijasi**, PostgreSQL'ning nosozligi emas. U, agar ikkita (yoki undan ko'p) tranzaksiya, **turli tartibda** bir nechta qatorni yangilasa, har doim yuzaga kelishi **mumkin**. Yechim — ilova darajasida: (1) barcha tranzaksiyalarda, resurslarni **doim bir xil tartibda** (masalan, har doim kichikroq `id`dan boshlab) qulflash, yoki (2) deadlock xatosini ilova kodida **ushlab**, tranzaksiyani avtomatik qayta urinish (retry).

## Amaliy misol

**Vazifa:** Ikkita mustaqil sessiyada, `xodimlar` jadvalidagi bitta xodimning maoshini bir vaqtning o'zida yangilashga urinib, blokirovkani kuzating.

```sql
-- 1-sessiya:
BEGIN;
UPDATE xodimlar SET ish_haqi = ish_haqi * 1.05 WHERE id = 1;
-- COMMIT qilmasdan kuting

-- 2-sessiya (boshqa oynada):
UPDATE xodimlar SET ish_haqi = ish_haqi * 1.03 WHERE id = 1;
-- Bu "osilib qoladi", 1-sessiya COMMIT/ROLLBACK qilguncha

-- 3-sessiyada, blokirovkani kuzating:
SELECT pid, wait_event_type, state, query FROM pg_stat_activity
WHERE query LIKE '%xodimlar%' AND query LIKE 'UPDATE%';
```

## Keng tarqalgan xatolar

**Xato 1:** `FOR UPDATE`ni "har doim, ehtiyot shart" barcha `SELECT`larga qo'shish.
❌ Bu — keraksiz qulflashga, va natijada, boshqa tranzaksiyalarni behuda "kutish"ga majburlaydi, umumiy parallellikni pasaytiradi.
✅ `FOR UPDATE`ni faqat, o'qilgan qatorni **haqiqatan keyinroq, shu tranzaksiya ichida yangilash** niyatida bo'lganda ishlating (masalan, "o'qib, tekshirib, keyin yangilash" naqshida).

**Xato 2:** Deadlock xatosini "kutilmagan, jiddiy tizim xatosi" deb, uni ilova kodida hech qanday qayta ishlashsiz qoldirish.
❌ Ishlab turgan, yuklamali tizimda deadlock'lar **vaqti-vaqti bilan** sodir bo'lishi — kutilgan holat, va ularni e'tiborsiz qoldirish, ba'zi foydalanuvchi amallarining "sababsiz" muvaffaqiyatsiz bo'lishiga olib keladi.
✅ Ilova kodida, `deadlock detected` xatosini maxsus ushlab, tranzaksiyani (odatda muvaffaqiyatli, chunki deadlock kamdan-kam qayta takrorlanadi) avtomatik qayta urinish mantig'ini yozing.

**Xato 3:** Ikkita jadvalni turli tartibda yangilaydigan kodni, "bu holat kamdan-kam sodir bo'ladi" deb, tuzatmasdan qoldirish.
❌ Yuklama ortishi bilan, "kamdan-kam" holatlar ham tez-tez sodir bo'la boshlaydi.
✅ Agar bir nechta joyda bir xil ikkita (yoki undan ko'p) resursni yangilaydigan kod bo'lsa, ularning barchasida **bir xil tartibni** (masalan, har doim `id`si kichikroq qatordan boshlab) qat'iy saqlang — bu, deadlock imkoniyatini tubdan yo'qotadi.

## Mashq/topshiriq

**(Oson)** `pg_locks`ni, hech qanday ochiq tranzaksiyasiz holda so'rab, natija bo'sh qaytishini tasdiqlang, so'ng `BEGIN; SELECT ... FOR UPDATE;` bilan qulf oling va qayta tekshiring.

**(O'rtacha)** Ikkita mustaqil sessiyada, `mahsulotlar` jadvalidagi bitta mahsulotning `ombordagi_soni`sini bir vaqtda kamaytirishga (turli miqdorda) urinib, ikkinchi sessiya birinchisi tugaguncha kutishini kuzating.

**(Qiyin)** Yuqoridagi deadlock ssenariysini o'zingiz, ikkita alohida `psql` sessiyasida qo'lda takrorlang, va xato xabaridagi `DETAIL` qismini o'qib, qaysi jarayon (process) qaysi tranzaksiyani kutayotganini aniqlang.

## Qisqacha xulosa

Qulflash — MVCC (17-bob) yetarli bo'lmagan holatlarda, ikkita tranzaksiyaning **bir xil qatorni bir vaqtda yozishini** xavfsiz tartibga soladi: `FOR UPDATE` qatorni "band qiladi", boshqa tranzaksiyalar esa, `pg_stat_activity`da `wait_event_type = Lock` bilan ko'ringan holda, birinchisi tugashini **kutadi**. Agar ikkita tranzaksiya, resurslarni **teskari tartibda** qulflasa, **deadlock** yuzaga kelishi mumkin — PostgreSQL buni avtomatik aniqlab, bittasini "qurbon" sifatida bekor qiladi. Bu — dasturchi tomonidan, resurslarni izchil tartibda qulflash orqali, oldindan oldini olinishi kerak bo'lgan holat. Keyingi darsda **advisory lock**larni va qulflarni monitoring qilishning amaliy usullarini chuqur o'rganamiz.

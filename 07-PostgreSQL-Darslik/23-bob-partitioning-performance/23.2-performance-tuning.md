# 23.2. Performance Tuning — serverni sozlash va monitoring (ICH-ICHIGA)

## Bu darsda nimalarni o'rganasiz

- `postgresql.conf`dagi eng muhim xotira parametrlarini (`shared_buffers`, `work_mem`, `maintenance_work_mem`) tushunasiz va ularning ta'sirini jonli o'lchaysiz
- `pg_stat_statements` kengaytmasini **haqiqiy** serverga o'rnatib, eng sekin so'rovlarni topishni o'rganasiz
- `random_page_cost` planner qarorlariga qanday ta'sir qilishini ko'rasiz
- Checkpoint statistikasi orqali `max_wal_size`ni qachon oshirish kerakligini aniqlaysiz
- **Connection pooling** (`pgbouncer`) ni o'zingiz o'rnatib, u qanday qilib ko'p mijozni kam server-ulanishga "siqishini" jonli kuzatasiz

## Nazariy qism

### Sozlash parametrlari uchta darajaga bo'linadi

PostgreSQL parametrlarini o'zgartirish uchun, avvalo, har bir parametr **qanday qo'llanishini** bilish kerak — chunki bu, sozlashdan keyin nima qilish kerakligini belgilaydi:

```sql
SELECT name, setting, unit, context
FROM pg_settings
WHERE name IN ('shared_buffers','work_mem','maintenance_work_mem',
               'max_connections','checkpoint_timeout','shared_preload_libraries')
ORDER BY context, name;
```

```
          name          | setting |  context   
-------------------------+---------+------------
 max_connections         | 100     | postmaster
 shared_buffers          | 16384   | postmaster
 shared_preload_libraries| ...     | postmaster
 checkpoint_timeout      | 300     | sighup
 maintenance_work_mem    | 65536   | user
 work_mem                | 4096    | user
```

`context` ustuni — parametrni **qayerda va qanday** o'zgartirish mumkinligini ko'rsatadi: **`postmaster`** — faqat `postgresql.conf`da o'zgartirib, serverni **to'liq qayta ishga tushirish** kerak (`shared_buffers`, `max_connections`, `shared_preload_libraries`); **`sighup`** — `postgresql.conf`ni o'zgartirib, `pg_ctl reload` yoki `SELECT pg_reload_conf()` bilan, **qayta ishga tushirmasdan** qo'llash mumkin (`checkpoint_timeout`, `max_wal_size`, `autovacuum`); **`user`** — hatto bitta sessiya ichida `SET` buyrug'i bilan o'zgartirish mumkin (`work_mem`, `random_page_cost`, `maintenance_work_mem`).

### `work_mem` — saralash va hash operatsiyalari uchun xotira

`work_mem` — har bir so'rov operatsiyasi (saralash, hash join, hash agregatsiya) uchun **bitta ijrochiga** ajratiladigan xotira miqdori. Agar operatsiya bu hajmga sig'masa, PostgreSQL diskka "to'kib" ishlaydi — bu sezilarli sekinlashuvga olib keladi. Buni jonli ko'ramiz — avval juda kichik `work_mem` bilan:

```sql
SET work_mem = '64kB';
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)
SELECT * FROM test_buyurtmalar_katta ORDER BY summa;
```

```
 Gather Merge  (cost=26592.47..55761.17 rows=250000 width=33) (actual rows=300001 loops=1)
   ->  Sort  (cost=25592.44..25904.94 rows=125000 width=33) (actual rows=100000 loops=3)
         Sort Method: external merge  Disk: 3840kB
         Worker 0:  Sort Method: external merge  Disk: 2936kB
         Worker 1:  Sort Method: external merge  Disk: 6624kB
 Execution Time: 378.448 ms
```

`Sort Method: external merge  Disk: ...` — bu, saralash **diskda** (vaqtinchalik fayllar orqali) bajarilganini bildiradi, chunki 300,001 qatorni saralash uchun kerakli xotira, 64kB'ga sig'madi. Endi `work_mem`ni oshiramiz:

```sql
SET work_mem = '64MB';
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)
SELECT * FROM test_buyurtmalar_katta ORDER BY summa;
```

```
 Sort  (cost=34154.02..34904.02 rows=300001 width=33) (actual rows=300001 loops=1)
   Sort Method: quicksort  Memory: 29868kB
 Execution Time: 157.778 ms
```

`Sort Method: quicksort  Memory: 29868kB` — endi saralash **to'liq xotirada** bajarildi, va bajarilish vaqti `378ms`dan `158ms`ga, ya'ni **2.4 barobar** tezlashdi (bundan tashqari, diskdan kichikroq bo'lgani uchun, bu safar parallel workerlar hatto kerak ham bo'lmadi).

**Muhim ogohlantirish:** `work_mem` — har bir **operatsiya** uchun, va bitta murakkab so'rovda bir nechta marta (masalan, bir nechta `JOIN` + `ORDER BY`) ishlatilishi mumkin, va bu **har bir parallel** ulanish uchun **alohida-alohida** ajratiladi. Shuning uchun uni "server umumiy xotirasi / max_connections" kabi oddiy formula bilan emas, balki ehtiyotkorlik bilan, real yuklama asosida sozlash kerak — juda katta qiymat, ko'p parallel so'rovlar bilan, serverni xotiradan chiqarib yuborishi mumkin.

### `maintenance_work_mem` — VACUUM va indeks yaratish uchun

`maintenance_work_mem` — `VACUUM`, `CREATE INDEX`, `ALTER TABLE` kabi "xizmat" operatsiyalari uchun ishlatiladi. Farqini `CREATE INDEX` vaqtini o'lchab ko'ramiz:

```sql
SET maintenance_work_mem = '4MB';
\timing on
CREATE INDEX idx_test_low_mem ON test_buyurtmalar_flat (summa);
```

```
Time: 382.593 ms
```

```sql
SET maintenance_work_mem = '256MB';
CREATE INDEX idx_test_high_mem ON test_buyurtmalar_flat (summa);
```

```
Time: 228.757 ms
```

Bir xil indeksni yaratish, `4MB`dan `256MB`ga o'tganda, `382ms`dan `229ms`ga tezlashdi (~40% tezroq) — chunki indeksni qurish uchun kerakli saralash, ko'proq xotirada, diskka kamroq murojaat qilib bajarildi. Katta jadvallarda (millionlab qator), bu farq soatlab vaqtga teng bo'lishi mumkin — shuning uchun katta `CREATE INDEX`/`VACUUM FULL` oldidan, faqat shu sessiya uchun `maintenance_work_mem`ni vaqtincha oshirish keng tarqalgan amaliyot.

### `random_page_cost` — disk turi haqida planner'ga "ma'lumot berish"

19-bobda o'rgangan cost formulasida, tasodifiy sahifa o'qish narxi (`random_page_cost`, standart qiymat — `4`) muhim rol o'ynaydi. Bu qiymat, aslida, **mexanik HDD** davridan qolgan taxmin (ketma-ket o'qish tasodifiy o'qishdan 4 marta arzon). Zamonaviy SSD/NVMe disklarda bu farq deyarli yo'q, shuning uchun ko'plab production sozlamalarda `random_page_cost = 1.1` qilib qo'yiladi. Ta'sirini ko'ramiz:

```sql
SET random_page_cost = 4;  -- standart, HDD uchun mo'ljallangan
EXPLAIN SELECT id FROM test_buyurtmalar_flat WHERE summa BETWEEN 2000000 AND 2600000;
```

```
 Bitmap Heap Scan on test_buyurtmalar_flat  (cost=912.16..3812.47 rows=35487 width=8)
   ->  Bitmap Index Scan on idx_flat_summa  (cost=0.00..903.29 rows=35487 width=0)
```

```sql
SET random_page_cost = 1.1;  -- SSD uchun realroq
EXPLAIN SELECT id FROM test_buyurtmalar_flat WHERE summa BETWEEN 2000000 AND 2600000;
```

```
 Bitmap Heap Scan on test_buyurtmalar_flat  (cost=514.86..3415.17 rows=35487 width=8)
   ->  Bitmap Index Scan on idx_flat_summa  (cost=0.00..505.99 rows=35487 width=0)
```

Bir xil so'rov, bir xil reja tanlandi, lekin baholangan **cost** `912.16`dan `514.86`ga tushdi — chunki planner endi indeks orqali tasodifiy o'qishni **arzonroq** deb hisoblaydi. Ba'zi (bordervoy) so'rovlarda, bu o'zgarish hatto planner'ni `Seq Scan`dan `Index Scan`ga (yoki aksincha) **to'liq o'tishga** majbur qilishi mumkin — shuning uchun disk turingizga mos `random_page_cost`ni to'g'ri sozlash, ayniqsa indekslardan foydalanish kerak bo'lgan so'rovlar uchun, muhim.

### `pg_stat_statements` — qaysi so'rov eng ko'p vaqt yeydi

Amaliyotda eng foydali vosita — **qaysi so'rov** eng sekin yoki eng ko'p chaqirilayotganini bilish. `pg_stat_statements` kengaytmasi buni kuzatadi, lekin u **shunchaki** `CREATE EXTENSION` bilan ishlamaydi:

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
SELECT * FROM pg_stat_statements LIMIT 1;
```

```
ERROR:  pg_stat_statements must be loaded via shared_preload_libraries
```

Bu — `context = postmaster` parametrlarga tegishli haqiqiy xato: `pg_stat_statements`, so'rov statistikasini saqlash uchun, serverning **umumiy xotira segmentida** joy band qiladi, shuning uchun u faqat server ishga tushishi **paytida** yuklanishi mumkin. `postgresql.conf`ga qo'shib, serverni qayta ishga tushiramiz:

```bash
# postgresql.conf:
shared_preload_libraries = 'pg_stat_statements'
```

```bash
pg_ctl restart
```

```sql
SHOW shared_preload_libraries;
```

```
 shared_preload_libraries 
--------------------------
 pg_stat_statements
```

Endi ishlaydi. Bir nechta so'rov bajarib, statistikani tekshiramiz:

```sql
SELECT pg_stat_statements_reset();

SELECT count(*) FROM mahsulotlar;
SELECT * FROM xodimlar WHERE bolim_id = 1;
SELECT * FROM xodimlar WHERE bolim_id = 2;

SELECT query, calls, round(mean_exec_time::numeric, 3) AS ortacha_ms
FROM pg_stat_statements
WHERE query NOT ILIKE '%pg_stat_statements%'
ORDER BY total_exec_time DESC LIMIT 5;
```

```
                        query                        | calls | ortacha_ms 
-------------------------------------------------------+-------+------------
 SELECT m.nomi, count(*) FROM buyurtma_elementlari ... |     1 |      0.055
 SELECT * FROM xodimlar WHERE bolim_id = $1            |     2 |      0.024
 SELECT count(*) FROM mahsulotlar                      |     1 |      0.021
```

E'tibor bering: `WHERE bolim_id = 1` va `WHERE bolim_id = 2` — ikkita **turli** so'rov edi, lekin `pg_stat_statements`da ular **bitta** yozuvga (`bolim_id = $1`, parametr sifatida normallashtirilgan) birlashtirilib, `calls = 2` ko'rsatilmoqda. Bu — real production muhitida, "eng ko'p resurs yeydigan so'rov turlari"ni (aniq qiymatlardan qat'iy nazar) topish uchun juda muhim xususiyat.

### Checkpoint statistikasi — `max_wal_size` yetarlimi

20.2-darsda checkpoint nima ekanini o'rgandik. `pg_stat_bgwriter` orqali, checkpointlar **qanday sababdan** sodir bo'layotganini kuzatish mumkin:

```sql
SELECT checkpoints_timed, checkpoints_req FROM pg_stat_bgwriter;
```

```
 checkpoints_timed | checkpoints_req 
--------------------+-----------------
                 16 |               7
```

`checkpoints_timed` — rejalashtirilgan (`checkpoint_timeout` bo'yicha, vaqt asosida) checkpointlar soni; `checkpoints_req` — **majburiy** (WAL hajmi `max_wal_size`ga yetganda, vaqtdan oldin) checkpointlar soni. Agar `checkpoints_req`, `checkpoints_timed`ga nisbatan **yuqori** bo'lsa (bu misolda nisbat unchalik yomon emas, lekin ogohlantiruvchi), bu — yozish yuklamasi juda katta va checkpointlar juda tez-tez, "kutilmagan" tarzda sodir bo'layotganini bildiradi; yechim — `max_wal_size`ni oshirish (checkpointlar orasidagi masofani kengaytirish), bu esa checkpoint yozish yukini vaqt bo'ylab yanada tekisroq taqsimlaydi.

### Connection pooling — `pgbouncer` bilan ulanishlarni "siqish"

Har bir PostgreSQL ulanishi — alohida OS jarayoni (process), va bu jarayonni yaratish/saqlash — arzon emas (xotira, CPU). Agar ilova minglab qisqa ulanish ochsa-yopsa (masalan, veb-server har so'rov uchun yangi ulanish), server tezda **`max_connections`** chegarasiga (yoki xotira tanqisligiga) yetib boradi. **Connection pooling** — mijozlar bilan PostgreSQL orasiga "vositachi" qo'yib, ko'p mijoz ulanishini **kam sonli, qayta ishlatiladigan** haqiqiy serverga ulanishga "siqish" g'oyasi. `pgbouncer` — buning uchun eng keng tarqalgan vosita.

O'rnatib, sinab ko'ramiz:

```ini
; /etc/pgbouncer/pgbouncer.ini
[databases]
dokon_bazasi = host=127.0.0.1 port=5432 dbname=dokon_bazasi

[pgbouncer]
listen_port = 6432
auth_type = scram-sha-256
pool_mode = transaction
default_pool_size = 5
```

`pool_mode = transaction` — bitta backend ulanish, mijoz bitta **tranzaksiya**ni tugatgach, darhol boshqa mijozga "qayta ishlatiladi" (eng samarali va keng tarqalgan rejim); `default_pool_size = 5` — har bir baza uchun, ko'pi bilan **5 ta** haqiqiy PostgreSQL ulanishi saqlanadi, mijozlar sonidan qat'iy nazar.

8 ta mijozni **bir vaqtda**, `pgbouncer` orqali ulaymiz (har biri 1.5 soniya "band" bo'lib turadi) va pool holatini o'rtada tekshiramiz:

```sql
-- pgbouncer admin konsolidan:
SHOW POOLS;
```

```
   database   |   user    | cl_active | cl_waiting | sv_active | pool_mode   
--------------+-----------+-----------+------------+-----------+-------------
 dokon_bazasi | postgres  |         5 |          3 |         5 | transaction
```

Bu — connection pooling'ning mohiyatini aniq ko'rsatadi: **8 ta** mijoz ulangan bo'lsa-da (`cl_active=5` faol xizmat ko'rsatilayotgan + `cl_waiting=3` navbatda kutayotgan = 8), haqiqiy PostgreSQL serveriga esa faqat **5 ta** ulanish (`sv_active=5`) ochilgan — aynan `default_pool_size` bo'yicha belgilangan chegara. Qolgan 3 ta mijoz, birinchi 5 tadan biri "bo'shashi" (tranzaksiyasini tugatishi) bilan, navbat bilan xizmat oladi. Shu tarzda, `pgbouncer`, yuzlab-minglab mijoz ulanishini, PostgreSQL serverining o'ziga esa atigi bir necha o'nlab haqiqiy ulanish sifatida ko'rsatadi.

**Muhim eslatma:** `pool_mode = transaction` rejimida, sessiya darajasidagi holat (masalan, `SET` buyrug'i bilan o'zgartirilgan parametrlar, tayyorlangan operatorlar) tranzaksiyalar orasida **saqlanmaydi**, chunki keyingi tranzaksiya butunlay boshqa haqiqiy ulanishga tushishi mumkin — bu, ilova kodini yozishda hisobga olinishi kerak bo'lgan muhim cheklov.

## Amaliy misol

**Vazifa:** `dokon_bazasi`dagi joriy xotira parametrlarini (`shared_buffers`, `work_mem`, `effective_cache_size`) ko'rib chiqing va ularning `context` qiymatiga qarab, qaysilarini serverni qayta ishga tushirmasdan o'zgartirish mumkinligini aniqlang.

```sql
SELECT name, setting, unit, context
FROM pg_settings
WHERE name IN ('shared_buffers', 'work_mem', 'effective_cache_size');
```

## Keng tarqalgan xatolar

**Xato 1:** `work_mem`ni global (`postgresql.conf`da) juda katta qilib qo'yish.
❌ `work_mem = 1GB` va `max_connections = 100` bilan, nazariy jihatdan, bir vaqtning o'zida yuzlab operatsiyalar (har bir ulanishda bir nechtadan) bu xotirani talab qilib, serverni xotiradan chiqarib yuborishi mumkin.
✅ Global qiymatni ehtiyotkorlik bilan (kichikroq) belgilang; og'ir, bitta martalik so'rovlar uchun esa, faqat o'sha sessiyada `SET work_mem = '...'` bilan vaqtincha oshiring.

**Xato 2:** `pg_stat_statements`ni o'rnatib, lekin `shared_preload_libraries`ga qo'shishni unutib, "ishlamayapti" deb hisoblash.
❌ `CREATE EXTENSION pg_stat_statements` — funksiyalar va view'larni yaratadi, lekin haqiqiy statistika yig'ish uchun, server ishga tushishida **preload** qilinishi shart.
✅ `shared_preload_libraries`ga qo'shib, serverni **qayta ishga tushirgandan** keyin qayta tekshiring (`SHOW shared_preload_libraries`).

**Xato 3:** `pool_mode = transaction` bilan ishlayotganda, sessiya darajasidagi funksiyalarga (masalan, `SET`, `LISTEN/NOTIFY`, vaqtinchalik jadvallar) tayanish.
❌ Bu funksiyalar, `pgbouncer` transaction rejimida, kutilmagan tarzda ishlamasligi yoki noto'g'ri ulanishga "tushib qolishi" mumkin.
✅ Bunday funksionallik zarur bo'lsa, `pool_mode = session` ishlatilsin (garchi bu, pooling samaradorligini pasaytirsa ham) yoki to'g'ridan-to'g'ri (pooling'siz) ulanishdan foydalaning.

## Mashq/topshiriq

**(Oson)** `pg_settings`dan, `context = 'user'` bo'lgan (ya'ni, sessiya ichida `SET` bilan o'zgartirish mumkin bo'lgan) barcha parametrlar sonini hisoblang.

**(O'rtacha)** `work_mem`ni `'1MB'` ga o'rnatib, `test_buyurtmalar_katta`ni `summa` bo'yicha saralang va `Sort Method` qanday ekanini (`quicksort` yoki `external merge`) `EXPLAIN ANALYZE` orqali aniqlang.

**(Qiyin)** `pg_stat_statements`da, `dokon_bazasi`dagi eng ko'p **umumiy vaqt** (`total_exec_time`) sarflagan 3 ta so'rov turini toping va nima uchun ular boshqalardan ko'proq vaqt yeyayotganini (chaqirilish soni ko'pligimi, yoki har bir chaqiruv sekinligimi) tushuntiring.

## Qisqacha xulosa

Performance tuning — bitta "sehrli tugma" emas, balki bir nechta o'lchamli jarayon: xotira parametrlarini (`work_mem` — saralash/hash uchun, `maintenance_work_mem` — `VACUUM`/`CREATE INDEX` uchun, `shared_buffers` — umumiy kesh uchun) ishchi yuklamaga mos sozlash; `random_page_cost`ni jismoniy disk turiga (SSD/NVMe uchun pastroq) moslashtirish; `pg_stat_statements` orqali **aniq qaysi** so'rov muammoli ekanini (taxmin emas, **o'lchov** asosida) topish; checkpoint statistikasi orqali WAL yozish yukini muvozanatlash; va nihoyat, `pgbouncer` kabi connection pooling vositasi orqali — biz jonli ko'rganimizdek, 8 ta mijoz ulanishini atigi 5 ta haqiqiy server-ulanishga "siqib" — server resurslarini himoya qilish. Ushbu darslikning amaliy asosi (1-15 bob) va ichki mexanizmlari (16-23 bob) — SQL yozishdan tortib, sahifa darajasidagi saqlashgacha, tranzaksiyalar va replikatsiyagacha — endi to'liq. Keyingi (yakuniy) hujjatda — to'liq mundarija va darslikning umumiy xulosasi keltiriladi.

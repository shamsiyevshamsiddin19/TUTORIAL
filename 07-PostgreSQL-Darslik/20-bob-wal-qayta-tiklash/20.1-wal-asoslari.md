# 20.1. WAL — Write-Ahead Log (ICH-ICHIGA)

## Bu darsda nimalarni o'rganasiz

- **WAL** (Write-Ahead Log) nima ekanini va u 13.1-darsdagi Durability xususiyatini qanday ta'minlashini tushunasiz
- `pg_wal/` katalogidagi fayllarni va **LSN** (Log Sequence Number) tushunchasini bilasiz
- `pg_waldump` bilan WAL yozuvlarining **ichki tarkibini** jonli ko'rasiz
- Bitta oddiy `INSERT` nechta WAL yozuvi yaratishini aniqlaysiz

## Nazariy qism

### Muammo: `COMMIT`dan keyin server o'chib qolsa-chi

13.1-darsda ACID'ning "D" harfi — Durability — `COMMIT` qilingan ma'lumot, server yiqilib tushsa ham, yo'qolmasligini talab qilishini ko'rgan edik. Lekin buni **qanday** ta'minlash mumkin? Agar PostgreSQL o'zgarishlarni faqat jadval fayliga (16-bob) yozsa, va aynan shu yozish jarayonida server elektr uzilishi tufayli o'chib qolsa — fayl **yarim yozilgan, buzuq** holatda qolishi mumkin edi.

Yechim — **WAL** (Write-Ahead Log, "oldindan yozish jurnali"): PostgreSQL, jadval faylining o'ziga o'zgarish kiritishdan **oldin**, bu o'zgarish haqidagi **yozuvni** alohida, maxsus jurnal faylga yozadi va uni diskka **majburan** (`fsync`) yuboradi. Faqat shundan keyingina, `COMMIT` "muvaffaqiyatli" deb qaytariladi. Agar server aynan shu vaqtda o'chib qolsa, keyingi ishga tushishda PostgreSQL WAL jurnalini "o'qib chiqib", tugallanmagan o'zgarishlarni **qayta bajaradi** (redo) — bu jarayon **crash recovery** (avariyadan tiklanish) deb ataladi, va u 20.2-darsda chuqurroq o'rganiladi.

### `pg_wal/` katalogi va WAL fayllari

16.1-darsda ko'rgan klaster katalogida, `pg_wal/` — aynan shu jurnal fayllari saqlanadigan joy:

```bash
ls -la /var/lib/postgresql/16/main/pg_wal/
```

```
-rw------- 1 postgres postgres 16777216 ... 000000010000000000000004
-rw------- 1 postgres postgres 16777216 ... 000000010000000000000005
-rw------- 1 postgres postgres 16777216 ... 000000010000000000000006
```

Har bir WAL fayli — qat'iy **16 MB** (standart holatda). Fayl nomi uch qismdan iborat: **timeline** raqami (`00000001` — server necha marta "qayta tiklangan tarix chizig'i"da ekanini bildiradi, 22-bobda replikatsiya kontekstida chuqurroq ko'riladi) va ketma-ket **segment** raqami. PostgreSQL yozishni davom ettirar ekan, eski fayllar (endi kerak bo'lmasa) qayta ishlatiladi yoki o'chiriladi, yangi fayllar esa yaratiladi.

### LSN — Log Sequence Number

Har bir WAL yozuvi, jurnal ichidagi **aniq, noyob manzil**ga — **LSN**ga — ega:

```sql
SELECT pg_current_wal_lsn();
SELECT pg_walfile_name(pg_current_wal_lsn());
```

```
 pg_current_wal_lsn 
---------------------
 0/53B47C8

 pg_walfile_name      
------------------------
 000000010000000000000005
```

LSN (`0/53B47C8` formatida) — "hozirgi jurnal qanchalik uzoqqa yozilgan" degan **aniq ko'rsatkich**. Bu — 16.1-darsda `page_header`da ko'rgan `lsn` maydoniga to'g'ridan-to'g'ri bog'liq: har bir sahifa, "men oxirgi marta qaysi WAL yozuvi bilan o'zgartirilganman" ma'lumotini o'zida saqlaydi — bu, qayta tiklashda, "bu sahifa allaqachon yangilanganmi yoki yo'qmi"ni aniqlash uchun ishlatiladi.

### Bitta `INSERT` — nechta WAL yozuvi yaratadi

Buni jonli o'lchaymiz. Avval joriy LSN'ni yozib olamiz, so'ng bitta oddiy `INSERT` bajaramiz:

```sql
-- LSN_OLDIN ni saqlab qo'yamiz
INSERT INTO test_wal_demo (qiymat) VALUES ('Uchinchi yozuv');
-- LSN_KEYIN bilan farqni hisoblaymiz
SELECT pg_size_pretty(pg_wal_lsn_diff('LSN_KEYIN', 'LSN_OLDIN')) AS bitta_insert_hajmi;
```

```
 bitta_insert_hajmi 
---------------------
 248 bytes
```

Bitta oddiy `INSERT` — atigi **248 bayt** WAL yozdi. Endi `pg_waldump` yordamchi dasturi bilan, bu yozuvning **aniq tarkibini** ko'ramiz:

```bash
pg_waldump -p /var/lib/postgresql/16/main/pg_wal --start=<LSN_OLDIN>
```

```
rmgr: Heap        len (rec/tot):     89/    89, tx:  1162, lsn: 0/053CBDB8, desc: INSERT off: 3, blkref #0: rel 1663/16384/25437 blk 0
rmgr: Btree       len (rec/tot):     64/    64, tx:  1162, lsn: 0/053CBE18, desc: INSERT_LEAF off: 3, blkref #0: rel 1663/16384/25443 blk 1
rmgr: Transaction len (rec/tot):     34/    34, tx:  1162, lsn: 0/053CBE58, desc: COMMIT 2026-08-30 03:51:56.481752 UTC
```

Bu — juda ma'rifiy natija: bitta `INSERT` amali, aslida **uchta** alohida WAL yozuvi yaratdi:

1. **`rmgr: Heap ... desc: INSERT`** — asosiy jadvalga (16-bobdagi heap fayliga) yangi tuple qo'shilishi.
2. **`rmgr: Btree ... desc: INSERT_LEAF`** — jadvalning `PRIMARY KEY` indeksiga (18-bob) mos yozuv qo'shilishi (18.1-darsda ko'rganimizdek, har bir `INSERT` tegishli indekslarni ham yangilashi kerak).
3. **`rmgr: Transaction ... desc: COMMIT`** — 13.1-darsdagi `COMMIT`ning o'zi, WAL jurnalida **rasmiy ravishda qayd etilishi**.

Bu — 18.1-darsda aytilgan "har bir indeks — yozish narxini oshiradi" fikrining, endi WAL darajasida ham **jismonan ko'rinishi**: bitta `INSERT`, ikkita alohida joy (heap + indeks)ni o'zgartirgani uchun, ikkita alohida WAL yozuvi talab qildi.

### `wal_level` — qancha ma'lumot yoziladi

```sql
SHOW wal_level;
```

```
 wal_level 
------------
 replica
```

`wal_level` — WAL jurnaliga **qancha tafsilot** yozilishini boshqaradi:

| Daraja | Vazifasi |
|---|---|
| `minimal` | Faqat crash recovery uchun yetarli minimal ma'lumot (replikatsiya ishlamaydi) |
| `replica` (standart) | `minimal`ga qo'shimcha, replika serverlar (22-bob) uchun yetarli ma'lumot |
| `logical` | `replica`ga qo'shimcha, "logical replication" (faqat o'zgargan qatorlarni, mantiqiy darajada, boshqa formatlarga uzatish) uchun kerakli ma'lumot |

Standart `replica` darajasi — aksariyat amaliy loyihalar uchun to'g'ri tanlov, chunki u backup/replikatsiya imkoniyatlarini saqlaydi, ortiqcha yozish "og'irligi"ni qo'shmasdan.

## Amaliy misol

**Vazifa:** Bir nechta qatorni bitta tranzaksiyada qo'shib, WAL hajmini bitta-bitta qo'shishga solishtiring.

```sql
-- 1-holat: 100 ta alohida INSERT (100 ta alohida tranzaksiya, avtomatik commit)
-- 2-holat: 100 ta qatorni BITTA INSERT ... SELECT bilan (bitta tranzaksiya)

SELECT pg_current_wal_lsn() AS boshlangich;
INSERT INTO test_wal_demo (qiymat) SELECT 'qator_' || i FROM generate_series(1, 100) AS i;
SELECT pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), 'BOSHLANGICH_LSN')) AS jami_hajm;
```

Kutilgan xulosa: 100 ta qatorni **bitta** `INSERT`da qo'shish, 100 ta alohida `INSERT`ga qaraganda, umumiy WAL hajmini kamroq "qo'shimcha xarajat" (har bir alohida `COMMIT` yozuvi) bilan yaratadi — bu, 13.1-darsdagi "avtomatik commit" tushunchasining amaliy narxini ko'rsatadi.

## Keng tarqalgan xatolar

**Xato 1:** WAL faylini "faqat replikatsiya uchun kerak" deb, `wal_level = minimal`ga tushirib qo'yish.
❌ `minimal` darajada, `pg_basebackup` yoki streaming replikatsiya (22-bob) ishlay olmaydi — bu, kelajakda zaxira nusxa yoki replika sozlashni **imkonsiz** qiladi.
✅ Standart `replica` (yoki, logical replikatsiya kerak bo'lsa, `logical`) darajasida qoldiring, hatto hozircha replikatsiya ishlatmasangiz ham.

**Xato 2:** WAL fayllarini `pg_wal/` katalogidan qo'lda, to'g'ridan-to'g'ri o'chirishga urinish (masalan, disk joyini bo'shatish uchun).
❌ Bu — ma'lumotlar bazasini **jiddiy buzilish** xavfiga qo'yadi, chunki PostgreSQL hali kerak bo'lgan WAL fayllarini o'chirib yuborishi mumkin (masalan, checkpoint hali bajarilmagan, yoki replika ular kutayotgan bo'lsa).
✅ WAL fayllarini hech qachon qo'lda boshqarmang — PostgreSQL ularni o'zi, checkpoint (20.2-dars) va `wal_keep_size`/replikatsiya sozlamalariga qarab, avtomatik boshqaradi.

**Xato 3:** Har bir kichik `UPDATE`/`INSERT`ni alohida tranzaksiya sifatida yuborib, "WAL yozuvi kam bo'ladi" deb o'ylash.
❌ Aksincha — har bir alohida tranzaksiya, o'zining `COMMIT` WAL yozuvini talab qiladi, bu esa ko'p sonli kichik amallarda, umumiy WAL hajmini oshiradi.
✅ Agar bir nechta bog'liq amal bo'lsa, ularni 13.1-darsdagi `BEGIN`/`COMMIT` bilan **birlashtirib**, WAL yozish "qo'shimcha xarajati"ni kamaytiring.

## Mashq/topshiriq

**(Oson)** `pg_current_wal_lsn()`ni ikki marta, orasida biror `INSERT` bajarib chaqiring, va `pg_wal_lsn_diff()` bilan orada qancha WAL yozilganini hisoblang.

**(O'rtacha)** `pg_wal/` katalogidagi fayllar sonini va ularning umumiy hajmini (`du -sh` yoki `pg_ls_waldir()` funksiyasi bilan) aniqlang.

**(Qiyin)** Bitta `UPDATE` (indekslangan ustunni o'zgartiradigan) va bitta HOT update (16.2-darsdagi, indekslanmagan ustunni o'zgartiradigan) o'rtasida, WAL hajmini solishtiring va farqni HOT update mexanizmi orqali tushuntiring.

<details>
<summary>Javoblarni ko'rish</summary>

1.
```sql
SELECT pg_current_wal_lsn() AS lsn1 \gset
INSERT INTO test_wal_demo (qiymat) VALUES ('test');
SELECT pg_current_wal_lsn() AS lsn2 \gset
SELECT pg_size_pretty(pg_wal_lsn_diff(:'lsn2', :'lsn1'));
```

2.
```sql
SELECT pg_size_pretty(sum(size)) AS jami_hajm, count(*) AS fayllar_soni
FROM pg_ls_waldir();
```

3.
```sql
-- Indekslangan ustunni yangilash:
SELECT pg_current_wal_lsn() AS a \gset
UPDATE test_wal_demo SET id = id WHERE id = 1; -- (misol uchun, PK'ga tegib ko'rish odatda son o'zgarmasa ham WAL yaratadi)
SELECT pg_wal_lsn_diff(pg_current_wal_lsn(), :'a');

-- Indekslanmagan ustunni yangilash (agar fillfactor bo'sh joy qoldirgan bo'lsa, HOT update bo'ladi):
SELECT pg_current_wal_lsn() AS b \gset
UPDATE test_wal_demo SET qiymat = qiymat || '!' WHERE id = 1;
SELECT pg_wal_lsn_diff(pg_current_wal_lsn(), :'b');
-- HOT update odatda ozroq WAL yozadi, chunki indeksni yangilash shart emas
```

## Qisqacha xulosa

WAL — PostgreSQL'ning har bir o'zgarishni, jadval faylining o'ziga yozishdan **oldin**, alohida jurnalga yozib, diskka majburan yuborish orqali Durability'ni ta'minlaydigan mexanizm. `pg_wal/` katalogidagi 16 MB'lik fayllar, LSN bilan raqamlangan, ketma-ket yozuvlardan iborat. `pg_waldump` bilan ko'rganimizdek, hatto bitta oddiy `INSERT` ham, agar indekslangan bo'lsa, bir nechta alohida WAL yozuvini (heap + indeks + commit) yaratadi — bu, indekslarning "yozish narxi" (18-bob) haqidagi tushunchani, WAL darajasida yana bir bor tasdiqlaydi. Keyingi darsda, WAL asosida qanday **checkpoint** va **avariyadan tiklanish** (crash recovery) sodir bo'lishini chuqur o'rganamiz.

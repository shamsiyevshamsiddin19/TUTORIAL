# 20.2. Checkpoint va avariyadan tiklanish (ICH-ICHIGA)

## Bu darsda nimalarni o'rganasiz

- **Checkpoint** nima ekanini va u WAL bilan qanday bog'liqligini tushunasiz
- `pg_control_checkpoint()` bilan oxirgi checkpoint ma'lumotlarini jonli ko'rasiz
- Avariyadan tiklanish (crash recovery) jarayonini, qadamma-qadam, tushunasiz
- Point-in-Time Recovery (PITR) tushunchasi va uning amaliy ahamiyatini bilasiz

## Nazariy qism

### Muammo: WAL cheksiz o'sib boraveradi, uni "o'qib chiqish" abadiy davom etmasligi kerak

20.1-darsda WAL — har bir o'zgarishni jurnalga yozishini ko'rdik. Lekin savol tug'iladi: agar server yiqilib tushsa, PostgreSQL WAL jurnalini **qayerdan boshlab** qayta o'qishi kerak? Agar u har doim **butun tarix boshidan** boshlasa — bu, server uzoq vaqt ishlagan bo'lsa, **soatlab** davom etadigan tiklanish jarayoniga olib kelar edi. Aynan shu muammoni **checkpoint** yechadi.

### Checkpoint nima

**Checkpoint** — bu, PostgreSQL muntazam ravishda bajaradigan "nazorat nuqtasi": bu vaqtda, xotiradagi barcha **"iflos" (dirty)** sahifalar — ya'ni o'zgargan, lekin hali diskka yozilmagan sahifalar — **majburan diskka yoziladi**. Checkpoint tugagach, PostgreSQL "bu nuqtadan oldingi barcha o'zgarishlar, endi jadval fayllarining o'zida ham mavjud" deb **kafolatlay oladi**.

```sql
SELECT checkpoint_lsn, redo_lsn, timeline_id, checkpoint_time FROM pg_control_checkpoint();
```

```
 checkpoint_lsn | redo_lsn  | timeline_id |    checkpoint_time     
-----------------+------------+--------------+-------------------------
 0/53CBEB8      | 0/53CBE80 |            1 | 2026-08-30 03:52:03+00
```

`redo_lsn` — bu, agar hozir server yiqilib tushsa, qayta tiklanish **aynan shu LSN'dan boshlab** WAL'ni qayta o'qishi kerakligini bildiradi. Bu — checkpoint'ning butun ma'nosi: `redo_lsn`dan **oldingi** hech qanday WAL yozuvini qayta bajarish shart emas, chunki ular allaqachon jadval fayllarida "jismonan" mavjud.

`CHECKPOINT;` buyrug'i bilan uni qo'lda ham chaqirish mumkin (odatda buni qo'lda chaqirish shart emas — PostgreSQL buni avtomatik, quyidagi sozlamalarga qarab bajaradi):

```sql
SHOW checkpoint_timeout;
SHOW max_wal_size;
```

```
 checkpoint_timeout 
--------------------
 5min

 max_wal_size 
--------------
 1GB
```

PostgreSQL checkpoint'ni ikki holatdan **qaysi biri birinchi** yuz bersa, o'shanda avtomatik bajaradi: (1) `checkpoint_timeout` vaqti (standart — 5 daqiqa) o'tganda, yoki (2) yozilgan WAL hajmi `max_wal_size`ga (standart — 1 GB) yetganda.

### Avariyadan tiklanish (crash recovery) — qadamma-qadam

Endi, checkpoint tushunchasi asosida, PostgreSQL kutilmagan o'chishdan (elektr uzilishi, `kill -9`, apparat nosozligi) keyin qanday "o'ziga keladi"gan jarayonni tushuntiramiz:

1. **Server qayta ishga tushadi.** PostgreSQL, avval, `pg_control` faylidan **oxirgi muvaffaqiyatli checkpoint**ning `redo_lsn`sini o'qiydi.
2. **WAL qayta o'qiladi (`redo` bosqichi).** PostgreSQL, `redo_lsn`dan boshlab, WAL jurnalidagi **barcha** yozuvlarni, ketma-ket, qayta bajaradi — xuddi ular endigina sodir bo'layotgandek. Har bir yozuv uchun, tegishli sahifaning `lsn`si (16.1-darsdagi `page_header`dagi maydon) tekshiriladi: agar sahifa allaqachon shu yozuvdan **keyingi** LSN'ga ega bo'lsa, yozuv **e'tiborsiz qoldiriladi** (chunki bu o'zgarish allaqachon jismonan mavjud) — bu, redo jarayonini **xavfsiz takrorlanadigan** (idempotent) qiladi.
3. **Tugallanmagan tranzaksiyalar aniqlanadi.** Agar biror tranzaksiya, o'chish paytida, `COMMIT` yozuvigacha yetib bormagan bo'lsa — u **tugallanmagan** deb hisoblanadi, va uning barcha o'zgarishlari (garchi ular WAL'da qisman mavjud bo'lsa ham) **e'tiborsiz qoldiriladi** — bu, 13.1-darsdagi Atomicity xususiyatining, server yiqilishi sharoitida ham saqlanishini ta'minlaydi.
4. **Server "sog'lom" holatga qaytadi.** Redo tugagach, server oddiy ishlashni davom ettiradi — barcha `COMMIT` qilingan tranzaksiyalar (garchi ularning o'zgarishlari checkpoint vaqtida jadval fayliga hali yozilmagan bo'lsa ham) saqlanib qolgan, tugallanmaganlari esa yo'q.

Bu jarayon — nega WAL "Write-**Ahead**" (oldindan yozish) deb atalishining sababi: o'zgarish **avval** jurnalga, keyin (checkpoint orqali, kechiktirilgan holda) jadvalning o'ziga yoziladi — va aynan shu tartib, yiqilish paytida hech narsa yo'qolmasligini kafolatlaydi.

### Point-in-Time Recovery (PITR) — "vaqt mashinasi"

Checkpoint va WAL redo mexanizmi — faqat **"eng so'nggi holatga"** tiklash uchun ishlatiladi. Lekin ba'zida sizga **muayyan, o'tmishdagi bir vaqt nuqtasi**ga qaytish kerak bo'ladi — masalan, kimdir bir soat oldin, xato bilan, `DELETE FROM xodimlar;` (WHERE'siz!) yuborgan bo'lsa, va siz "aynan shu xatodan **oldingi**" holatga qaytmoqchi bo'lsangiz.

**PITR** (Point-in-Time Recovery) — aynan shu vazifani yechadi, va u ikkita komponentga tayanadi: (1) 15.2-darsdagi `pg_dump`/`pg_basebackup` orqali olingan **bazaviy zaxira nusxa** (baza qaysidir vaqtdagi holati), va (2) o'sha vaqtdan buyon **arxivlangan barcha WAL fayllari** (`archive_command` sozlamasi orqali, WAL fayllari alohida, xavfsiz joyga nusxalanib boriladi).

Tiklash jarayoni: (1) bazaviy zaxiradan boshlanadi, (2) so'ng arxivlangan WAL fayllari, checkpoint'dagi kabi, **ketma-ket qayta bajariladi** — lekin bu safar, cheksiz emas, balki siz ko'rsatgan **aniq vaqt yoki LSN**gacha (`recovery_target_time` sozlamasi orqali). Natijada, baza aynan o'sha, siz tanlagan tarixiy nuqtadagi holatga "qaytariladi".

| | Oddiy crash recovery | PITR |
|---|---|---|
| **Qachon ishlatiladi** | Har bir oddiy server qayta ishga tushishida, avtomatik | Faqat aniq, qo'lda so'ralganda (masalan, xato ma'lumot kiritilgandan keyin) |
| **Qayergacha tiklaydi** | Eng so'nggi mavjud holatgacha | Siz ko'rsatgan **aniq** vaqt/LSN'gacha |
| **Talab qiladigan narsa** | Faqat mavjud WAL fayllari | Bazaviy zaxira + **arxivlangan** WAL fayllari |

> **Amaliy eslatma:** PITR'ni sozlash — ishlab turgan, jiddiy loyihalarda muhim, lekin murakkab jarayon (`archive_command`, `restore_command`, `recovery_target_*` sozlamalari), va u ushbu darslikning amaliy doirasidan tashqarida. Bu yerda muhimi — **kontseptual jihatdan** WAL, nafaqat avariyadan tiklanish, balki "vaqt bo'yicha" tiklanish uchun ham asos bo'la olishini tushunish.

## Amaliy misol

**Vazifa:** Joriy checkpoint holatini tekshiring va `checkpoint_timeout` muddatini vaqtincha qisqartirib, avtomatik checkpoint qachon ishga tushishini kuzating.

```sql
SELECT checkpoint_lsn, checkpoint_time FROM pg_control_checkpoint();

-- Faqat shu sessiya uchun (diagnostika maqsadida):
SET checkpoint_timeout = '30s';

-- Biroz kutib, qayta tekshiring:
SELECT checkpoint_lsn, checkpoint_time FROM pg_control_checkpoint();
```

## Keng tarqalgan xatolar

**Xato 1:** `CHECKPOINT;`ni qo'lda, tez-tez chaqirishni "xavfsizlik" chorasi deb hisoblash.
❌ Har bir checkpoint — barcha "iflos" sahifalarni diskka yozishni talab qiladi, bu esa **qimmat** amal; uni tez-tez, keraksiz chaqirish, serverning umumiy unumdorligini pasaytiradi.
✅ Avtomatik checkpoint mexanizmiga ishoning; qo'lda `CHECKPOINT;`ni faqat aniq, maxsus holatlarda (masalan, rejalashtirilgan server o'chirishdan oldin) ishlating.

**Xato 2:** Crash recovery'ni "ma'lumot yo'qotilishi mumkin" degan ma'noda tushunish.
❌ Aksincha — crash recovery, aynan **ma'lumot yo'qotilmasligini** ta'minlash uchun mo'ljallangan (WAL orqali `COMMIT` qilingan barcha o'zgarishlarni tiklaydi).
✅ Yo'qoladigan narsa — faqat, yiqilish paytida hali `COMMIT` qilinmagan (tugallanmagan) tranzaksiyalar, va bu — kutilgan, to'g'ri xatti-harakat (Atomicity).

**Xato 3:** PITR'ni faqat `pg_dump`ning o'zi bilan amalga oshirish mumkin deb o'ylash.
❌ 15.2-darsdagi `pg_dump`/`pg_restore` — faqat **bitta, aniq vaqtdagi** to'liq nusxa; ular orasidagi **istalgan** vaqt nuqtasiga qaytish uchun, WAL arxivlash shart.
✅ Agar loyihangizga "istalgan daqiqaga qaytish" imkoniyati kerak bo'lsa, oddiy `pg_dump`dan tashqari, WAL arxivlashni ham sozlashni rejalashtiring.

## Mashq/topshiriq

**(Oson)** `pg_control_checkpoint()` funksiyasidan foydalanib, oxirgi checkpoint qachon bo'lganini (`checkpoint_time`) aniqlang va joriy vaqt bilan solishtirib, undan necha daqiqa o'tganini hisoblang.

**(O'rtacha)** `CHECKPOINT;`ni qo'lda chaqirib, undan oldin va keyin `pg_control_checkpoint()`dagi `redo_lsn` qanday o'zgarishini kuzating.

**(Qiyin)** 20.1-darsdagi `pg_waldump` chiqishini yana bir bor ko'rib chiqing va, agar server aynan `Btree ... INSERT_LEAF` yozuvidan keyin, lekin `Transaction ... COMMIT` yozuvidan **oldin** yiqilib tushganida, crash recovery bu tranzaksiyaga qanday munosabatda bo'lishini (uni saqlab qolish yoki bekor qilish) tushuntirib bering.

<summary>Javoblarni ko'rish</summary>

1.
```sql
SELECT checkpoint_time, NOW() - checkpoint_time AS otgan_vaqt
FROM pg_control_checkpoint();
```

2.
```sql
SELECT redo_lsn AS oldin FROM pg_control_checkpoint();
CHECKPOINT;

-- "keyin" LSN'i "oldin"dan katta bo'ladi - checkpoint yangi nazorat nuqtasini o'rnatdi
```

3. Agar server aynan `COMMIT` yozuvidan oldin yiqilsa, bu tranzaksiya **tugallanmagan** hisoblanadi. Crash recovery, `Heap INSERT` va `Btree INSERT_LEAF` yozuvlarini WAL'da ko'rgan bo'lsa-da, `Transaction COMMIT` yozuvi **yo'qligi** sababli, bu tranzaksiyaning barcha o'zgarishlarini **bekor qiladi** (amalda, tegishli tuple'lar "hech qachon commit qilinmagan" deb belgilanadi va keyinchalik VACUUM tomonidan tozalanadi) — bu, Atomicity xususiyatining, hatto server yiqilishi holatida ham, to'liq saqlanishini ta'minlaydi.

## Qisqacha xulosa

Checkpoint — barcha "iflos" sahifalarni diskka majburan yozib, "bu nuqtadan oldingi hamma narsa jismonan saqlangan" degan nazorat nuqtasini o'rnatadi, va bu, avariyadan tiklanishda WAL'ni **butun tarix boshidan emas**, faqat oxirgi checkpoint'ning `redo_lsn`sidan qayta o'qish imkonini beradi. Crash recovery — bu jarayonni avtomatik bajaradi: WAL'ni qayta ijro etib (redo), faqat **`COMMIT` qilingan** tranzaksiyalarni saqlab qoladi. Point-in-Time Recovery (PITR) — bazaviy zaxira va arxivlangan WAL fayllarini birlashtirib, bazani **istalgan o'tmishdagi** vaqt nuqtasiga qaytarish imkonini beradi. Bu — 20-bobni yakunlaydi: WAL, checkpoint va qayta tiklanish mexanizmlarini chuqur o'rgandingiz. Keyingi, 21-bobda **concurrency va qulflash**ni — bir nechta tranzaksiya bir xil ma'lumot ustida ishlaganda PostgreSQL ularni qanday muvofiqlashtirishini — chuqur o'rganamiz.

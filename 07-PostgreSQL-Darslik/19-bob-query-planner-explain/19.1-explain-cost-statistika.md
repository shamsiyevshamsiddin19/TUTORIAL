# 19.1. Query Planner, `EXPLAIN` va statistika (ICH-ICHIGA)

## Bu darsda nimalarni o'rganasiz

- Query planner (so'rov rejalashtiruvchisi) nima ekanini va u nima uchun kerakligini tushunasiz
- `EXPLAIN`dagi `cost` sonini **qanday hisoblanishini**, formula bo'yicha, o'zingiz tasdiqlaysiz
- `ANALYZE` va `pg_stats` — planner qaror qabul qilish uchun tayangan statistikani — o'rganasiz
- Eskirgan statistika so'rov rejasini qanday **yomonlashtirishi** mumkinligini jonli ko'rasiz

## Nazariy qism

### Query planner nima

Har safar siz `SELECT` yozganingizda, PostgreSQL uni **darhol** bajarmaydi. Avval, maxsus komponent — **query planner** (so'rov rejalashtiruvchisi) — sizning so'rovingizni bajarishning **bir nechta mumkin bo'lgan usulini** ko'rib chiqadi (masalan: `Seq Scan` yoki `Index Scan` — 18-bob; qaysi `JOIN` strategiyasi — bu darsning ikkinchi qismida), har birining taxminiy "narxi"ni hisoblaydi, va **eng arzon** deb topilgan rejani tanlab, aynan shuni bajaradi. Bu jarayonni ko'rish uchun `EXPLAIN` buyrug'i ishlatiladi — biz uni darslik davomida ko'p marta ishlatdik, endi uning **ichiga** chuqurroq kiramiz.

### `cost` — qayerdan kelib chiqadi

```sql
CREATE TABLE test_planner_katta (
    id SERIAL PRIMARY KEY,
    tashqi_id INTEGER,
    qiymat INTEGER,
    matn TEXT
);
INSERT INTO test_planner_katta (tashqi_id, qiymat, matn)
SELECT i, (random()*1000)::int, 'matn_' || i
FROM generate_series(1, 100000) AS i;

ANALYZE test_planner_katta;

EXPLAIN SELECT * FROM test_planner_katta WHERE qiymat = 500;
```

```
                              QUERY PLAN                               
-------------------------------------------------------------------------
 Seq Scan on test_planner_katta  (cost=0.00..1887.00 rows=99 width=22)
   Filter: (qiymat = 500)
```

`cost=0.00..1887.00` — ikkita son: **boshlang'ich** narx (birinchi qatorni qaytarishgacha bo'lgan xarajat — `Seq Scan` uchun bu deyarli `0`) va **umumiy** narx (barcha mos qatorlarni qaytarishgacha bo'lgan xarajat). Bu sonlar — **millisekund emas**, balki shartli, nisbiy birlik: ular faqat turli rejalarni **bir-biri bilan solishtirish** uchun ishlatiladi.

`1887.00` qayerdan kelib chiqqanini **aniq formula bilan** tasdiqlaymiz:

```sql
SHOW seq_page_cost;
SHOW cpu_tuple_cost;
SELECT relpages, reltuples FROM pg_class WHERE relname = 'test_planner_katta';
```

```
 seq_page_cost 
----------------
 1

 cpu_tuple_cost 
-----------------
 0.01

 relpages | reltuples 
-----------+------------
      637 |     100000
```

`Seq Scan`ning narxi — ikki komponentdan iborat: (1) **har bir sahifani** diskdan o'qish narxi (`seq_page_cost × relpages`), va (2) **har bir qatorni** tekshirish (CPU) narxi (`cpu_tuple_cost × reltuples`):

```
narx = seq_page_cost × relpages + cpu_tuple_cost × reltuples
     = 1 × 637 + 0.01 × 100000
     = 637 + 1000
     = 1637
```

Lekin `EXPLAIN` `1887.00` ko'rsatdi, `1637` emas — farq qayerdan? Chunki bizning so'rovimizda `WHERE qiymat = 500` — **filtr** ham bor, va har bir qatorni filtrlash uchun qo'shimcha **`cpu_operator_cost`** sarflanadi:

```sql
SHOW cpu_operator_cost;
```

```
 cpu_operator_cost 
---------------------
 0.0025
```

```
qoshimcha = cpu_operator_cost × reltuples = 0.0025 × 100000 = 250

yakuniy narx = 1637 + 250 = 1887
```

Bu — aynan `EXPLAIN`da ko'rsatilgan `1887.00`! Bu — planner "sehr" emasligini, balki **aniq, hisoblanadigan formulalar** asosida ishlashini isbotlaydi. `postgresql.conf`dagi bu sozlamalar (`seq_page_cost`, `cpu_tuple_cost`, `cpu_operator_cost`, va indeks uchun `random_page_cost`) — serveringizning apparat xususiyatlariga (masalan, SSD vs HDD) moslashtirilishi mumkin, garchi amaliyotda standart qiymatlar aksariyat holatlar uchun yetarli.

### Statistika — planner "ko'rlik bilan" ishlamaydi

Yuqoridagi formulada `rows=99` qayerdan kelib chiqdi? Planner buni **haqiqatan hisoblab chiqmaydi** (bu — butun jadvalni skanerlashni talab qilar edi, ya'ni so'rovning o'zi kabi qimmat bo'lardi!). Buning o'rniga, u oldindan **yig'ilgan statistika**dan foydalanadi — bu statistika `pg_stats` katalog ko'rinishida (view) saqlanadi:

```sql
SELECT attname, n_distinct, most_common_vals, most_common_freqs
FROM pg_stats WHERE tablename = 'test_planner_katta' AND attname = 'qiymat';
```

```
 attname | n_distinct |                    most_common_vals (qisqartirilgan)                     
----------+-------------+---------------------------------------------------------------------------
 qiymat  |        1001 | {8,712,604,150,383,602,...}
```

`n_distinct = 1001` — planner, `qiymat` ustunida taxminan 1001 xil noyob qiymat borligini "biladi" (chunki biz `0-1000` oralig'ida tasodifiy son generatsiya qilgan edik). Shundan kelib chiqib: `100000 qator / 1001 noyob qiymat ≈ 99.9 qator har bir qiymat uchun` — bu, aynan `rows=99` bashoratining manbai!

`most_common_vals`/`most_common_freqs` — eng tez-tez uchraydigan qiymatlar va ularning **aniq chastotasi** (agar ma'lumot notekis taqsimlangan bo'lsa, bu oddiy `n_distinct`ga asoslangan taxmindan ancha **aniqroq** bashorat beradi).

### `ANALYZE` — statistikani yangilash

Bu statistika **avtomatik ravishda o'z-o'zidan** paydo bo'lmaydi — uni `ANALYZE` buyrug'i yig'adi (va standart holatda, `autovacuum` buni fon rejimida, jadval sezilarli o'zgarganda, avtomatik ham bajaradi). Agar statistika **eskirgan** (yoki umuman yig'ilmagan) bo'lsa, planner **noto'g'ri** taxminlar qilishi va natijada **yomon** reja tanlashi mumkin. Buni jonli ko'ramiz:

```sql
CREATE TABLE test_stale_stats (id SERIAL PRIMARY KEY, qiymat INTEGER);
INSERT INTO test_stale_stats (qiymat) SELECT (random()*10)::int FROM generate_series(1, 50000);

-- ANALIZ qilishdan OLDIN:
EXPLAIN SELECT * FROM test_stale_stats WHERE qiymat = 5;
```

```
                             QUERY PLAN                             
----------------------------------------------------------------------
 Seq Scan on test_stale_stats  (cost=0.00..849.15 rows=251 width=8)
   Filter: (qiymat = 5)
```

`rows=251` — bu, PostgreSQL'ning **umumiy, hech qanday real statistikaga asoslanmagan taxminiy** bashorati (yangi jadvalda hali `ANALYZE` ishlamagan). Haqiqiy son esa (`SELECT count(*) ... WHERE qiymat = 5` bilan tekshirilganda) — **5030**! Endi `ANALYZE` bajaramiz:

```sql
ANALYZE test_stale_stats;
EXPLAIN SELECT * FROM test_stale_stats WHERE qiymat = 5;
```

```
                             QUERY PLAN                              
-----------------------------------------------------------------------
 Seq Scan on test_stale_stats  (cost=0.00..847.00 rows=5075 width=8)
   Filter: (qiymat = 5)
```

`rows=5075` — haqiqiy qiymat (`5030`)ga **juda yaqin**! `ANALYZE`dan keyin, planner endi aniq statistikaga ega, va uning bashorati sezilarli darajada to'g'rilandi.

> **Nega bu muhim:** kichik jadvalda, noto'g'ri bashorat (251 vs 5030) hech qanday amaliy farq qilmadi — ikkala holatda ham `Seq Scan` eng arzon reja bo'lib qoldi. Lekin **katta, murakkab** so'rovlarda (ayniqsa bir nechta `JOIN` bilan), noto'g'ri qator-soni bashorati planner'ni **butunlay noto'g'ri strategiya** (masalan, kichik natija kutib `Nested Loop`ni tanlash, aslida natija million qator bo'lsa) tanlashga olib kelishi mumkin — bu, real loyihalarda "so'rov sekin ishlayapti" muammolarining eng keng tarqalgan sabablaridan biri.

## Amaliy misol

**Vazifa:** `mahsulotlar` jadvali uchun statistikani qo'lda yangilang va `kategoriya` ustuni bo'yicha planner bashoratini tekshiring.

```sql
ANALYZE mahsulotlar;

SELECT attname, n_distinct, most_common_vals
FROM pg_stats WHERE tablename = 'mahsulotlar' AND attname = 'kategoriya';

EXPLAIN SELECT * FROM mahsulotlar WHERE kategoriya = 'Elektronika';
```

## Keng tarqalgan xatolar

**Xato 1:** `cost`ni "millisekund" yoki boshqa real vaqt birligi deb tushunish.
❌ `cost` — faqat **nisbiy, shartli** birlik, turli rejalarni solishtirish uchun; haqiqiy vaqtni bilish uchun `EXPLAIN ANALYZE` (`actual time=...`) kerak.
✅ `cost`ni faqat "qaysi reja arzonroq" degan **taqqoslash** uchun ishlating, uni bevosita millisekundga aylantirmang.

**Xato 2:** Katta hajmda ma'lumot yuklab (`bulk INSERT`, `COPY`), `ANALYZE`ni chaqirishni unutish.
❌ `autovacuum` statistikani yangilashi vaqt talab qiladi — agar siz darhol, katta o'zgarishdan keyin murakkab so'rov yuborsangiz, planner hali **eski** statistika bilan ishlayotgan bo'lishi mumkin.
✅ Katta hajmdagi `INSERT`/`COPY`/`UPDATE`dan so'ng, agar darhol murakkab so'rovlar kutilsa, qo'lda `ANALYZE jadval_nomi;` chaqiring.

**Xato 3:** Statistikani "bir marta yig'ilib, abadiy to'g'ri qoladi" deb o'ylash.
❌ Ma'lumot vaqt o'tishi bilan o'zgaradi (yangi qatorlar, o'chirilganlar, taqsimotning o'zgarishi) — eski statistika, vaqt o'tishi bilan, tobora noaniqroq bo'lib boradi.
✅ `autovacuum_analyze_scale_factor` sozlamasiga ishoning (standart holatda yoqilgan), lekin katta, kutilmagan o'zgarishlardan keyin qo'lda `ANALYZE`ni ham unutmang.

## Mashq/topshiriq

**(Oson)** `xodimlar` jadvali uchun `ANALYZE` bajarib, `bolim_id` ustunining `n_distinct` qiymatini `pg_stats`dan aniqlang.

**(O'rtacha)** `test_planner_katta` jadvalida, `EXPLAIN`dagi `rows` bashoratini haqiqiy `SELECT count(*)` natijasi bilan solishtirib, farq necha foiz ekanini hisoblang.

**(Qiyin)** `test_stale_stats` jadvaliga yana 50 000 qator qo'shing (`qiymat` endi boshqacha taqsimotda, masalan `(random()*100)::int`), lekin `ANALYZE` chaqirmasdan turib `EXPLAIN` bilan `rows` bashoratini tekshiring — u hali ham eski taqsimotga asoslanganini kuzating, so'ng `ANALYZE`dan keyin qanday tuzatilishini ko'ring.

## Qisqacha xulosa

Query planner — har bir so'rov uchun bir nechta mumkin bo'lgan bajarish rejasini "narxlab", eng arzonini tanlaydi; `cost` — bu narxning shartli o'lchovi, aniq formulalar (`seq_page_cost`, `cpu_tuple_cost`, `cpu_operator_cost` va jadval hajmi/qator soni) asosida hisoblanadi. Planner'ning aniq ishlashi, `ANALYZE` orqali yig'iladigan **statistika**ga (`pg_stats`: `n_distinct`, `most_common_vals`) bevosita bog'liq — eskirgan yoki yo'q statistika, bizning testimizda ko'rganimizdek (`251` vs haqiqiy `5030`), noto'g'ri bashoratlarga va, murakkab so'rovlarda, yomon rejalarga olib kelishi mumkin. Keyingi darsda planner'ning eng muhim qarorlaridan birini — **`JOIN` strategiyasini** (Nested Loop, Hash Join, Merge Join) qanday tanlashini — chuqur o'rganamiz.

# 2.2. Import grafi — "kim kimni chaqiradi" va qaysi kod qayerga

## Bu darsda nimalarni o'rganasiz

- App darajasidagi `urls.py`ni yaratib, uni `config/urls.py`ga `include()` orqali ulaysiz
- Django fayllari orasidagi **"to'g'ri" chaqiruv yo'nalishini** (import grafi) tushunasiz
- Nega `models.py` **hech qachon** `views.py`ni import qilmasligi kerakligini, haqiqiy xato orqali ko'rasiz
- To'liq "qaysi kod qayerga yoziladi" qoidalar jadvalini olasiz — bu, darslik davomida qayta-qayta murojaat qiladigan asosiy qurolingiz bo'ladi

## Nazariy qism

### Ikki darajali `urls.py` — nega kerak

1-bobda `config/urls.py`ni ko'rgan edik — bu, **loyiha darajasidagi** marshrutizator. Lekin har bir app, odatda, **o'zining** `urls.py`siga ega bo'ladi. Buni yaratamiz:

```python
# apps/dokon/urls.py
from django.urls import path
from . import views

app_name = "dokon"

urlpatterns = [
    path("", views.bosh_sahifa, name="bosh-sahifa"),
]
```

Diqqat qiling: `from . import views` — bu, **nisbiy import** (relative import): nuqta (`.`) "shu paketning o'zidan" degani, ya'ni `apps.dokon.views`ni to'liq yozish shart emas. `app_name = "dokon"` — bu, keyinchalik (5-bobda) shablonlarda `{% url 'dokon:bosh-sahifa' %}` kabi, app nomini ko'rsatib manzil yasashda ishlatiladi.

Endi buni **loyiha darajasidagi** `urls.py`ga ulaymiz:

```python
# config/urls.py
from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path("admin/", admin.site.urls),
    path("", include("apps.dokon.urls")),
]
```

`include("apps.dokon.urls")` — Django'ga: "bu yo'ldan boshlangan har qanday manzilni, `apps/dokon/urls.py`dagi ro'yxatga **topshir**" deydi. Tekshiramiz:

```bash
python manage.py runserver
curl http://127.0.0.1:8000/
```

```
Onlayn do'kon — bosh sahifa
```

Ishladi! Bu — **ikki qavatli marshrutlash**: `config/urls.py` — "qaysi app ishga tushishi kerak"ni hal qiladi, `apps/dokon/urls.py` — "shu app ichida qaysi aniq sahifa"ni hal qiladi. Loyiha kattalashganda (ko'plab app bilan), `config/urls.py` juda qisqa qolaveradi — u faqat `include()` qatorlaridan iborat bo'ladi, haqiqiy marshrutlar esa har bir app'ning o'zida.

### Import grafi — "kim kimni chaqirishi mumkin"

Django loyihasida, fayllar orasidagi import yo'nalishi **tasodifiy emas** — u, aslida, MTV (Model-Template-View) arxitekturasining o'zidan kelib chiqadi:

```
urls.py  →  views.py  →  models.py
              ↓
           templates/ (shablon fayllar, Python emas)

admin.py  →  models.py
```

O'qiymiz: `urls.py` — `views.py`dagi funksiyalarga ishora qiladi (import qiladi); `views.py` — kerak bo'lsa, `models.py`dagi modellarni import qiladi (ma'lumot olish/saqlash uchun); `admin.py` — ham `models.py`ni import qiladi (modelni admin panelda ko'rsatish uchun). **O'q har doim bitta yo'nalishda** — pastdan yuqoriga (`models.py`dan `views.py`ga yoki `urls.py`ga) **hech qachon** import bo'lmasligi kerak.

### Nega bu qoida buzilsa, kod "yiqiladi" — haqiqiy misolda

Tasavvur qiling, kimdir (bilmasdan) `models.py` ichiga, `views.py`dagi funksiyaga ishora qo'shib qo'ydi:

```python
# apps/dokon/models.py — NOTO'G'RI
from django.db import models
from apps.dokon.views import bosh_sahifa  # ❌ teskari yo'nalish!

MAHSULOT_NOMI_UZUNLIGI = 100
```

```python
# apps/dokon/views.py — o'zi, odatdagidek, models.py'ni import qiladi
from django.http import HttpResponse
from apps.dokon.models import MAHSULOT_NOMI_UZUNLIGI


def bosh_sahifa(request):
    return HttpResponse("Onlayn do'kon — bosh sahifa")
```

Bu ikkalasini birga ishga tushirsak:

```
ImportError: cannot import name 'MAHSULOT_NOMI_UZUNLIGI' from partially
initialized module 'apps.dokon.models' (most likely due to a circular import)
(.../apps/dokon/models.py)
```

Bu xatoni **satrma-satr** tushunamiz: Python, `models.py`ni yuklashni boshlaydi → 2-qatorga yetganda, `views.py`ni yuklashga o'tadi → `views.py`ning 2-qatorida, o'z navbatida, `models.py`dan `MAHSULOT_NOMI_UZUNLIGI`ni so'raydi → lekin `models.py` hali **to'liq yuklanmagan** (u hali 2-qatorda "muzlab" turibdi, 4-qatordagi `MAHSULOT_NOMI_UZUNLIGI` hali e'lon qilinmagan) → Python bunga "yo'q" deydi, va aniq, foydali xabar bilan xato tashlaydi: **"aylanma import (circular import) sababli bo'lishi mumkin"**.

Bu — **aylanma import (circular import)** deb ataladigan klassik muammo, va u aynan, import yo'nalishi qoidasi (`models.py → views.py` emas, faqat `views.py → models.py`) buzilganda yuzaga keladi. Xatoni tuzatish — oddiy: `models.py`dan noto'g'ri import qatorini olib tashlash, chunki **model'ga umuman view kerak emas**.

### Boshqa, standart bo'lmagan, lekin tez-tez uchraydigan fayllar

Loyiha kattalashgani sayin, app ichida quyidagi fayllar ham (avtomatik yaratilmasa-da) qo'shilishi mumkin — ularning har biri, xuddi standart fayllar kabi, **aniq o'z o'rniga** ega:

| Fayl | Vazifasi | Qachon paydo bo'ladi |
|---|---|---|
| `forms.py` | Foydalanuvchi kiritadigan ma'lumotni tekshirish/qayta ishlash | 8-bobda (bu darslikda: forms bo'limi) |
| `serializers.py` | API uchun, Python ob'ektini JSON'ga (va aksincha) o'giruvchi kod | REST API loyihalarida |
| `signals.py` | "Voqea sodir bo'lganda avtomatik ishga tushuvchi" kod (masalan, "model saqlangandan keyin") | Murakkabroq, avtomatlashtirilgan mantiq kerak bo'lganda |
| `management/commands/` | `python manage.py <buyruq_nomi>` orqali chaqiriladigan, o'zingiz yozgan buyruqlar | Muntazam vazifalar (masalan, kunlik hisobot) uchun |
| `static/<app_nomi>/` | Shu app'ga tegishli CSS/JS/rasm fayllar | Har doim, agar app o'z dizayniga ega bo'lsa |
| `templates/<app_nomi>/` | Shu app'ga tegishli HTML shablonlar | Har doim, agar app sahifa ko'rsatsa |

**Muhim naqsh:** `static/` va `templates/` ichida, papka nomi **yana bir marta app nomi bilan takrorlanadi** (`templates/dokon/bosh_sahifa.html`, shunchaki `templates/bosh_sahifa.html` emas). Bu — ataylab qilingan: agar ikkita turli app'da bir xil nomli shablon (`sahifa.html`) bo'lsa, bu "ichki" takrorlash, ular bir-biriga aralashib ketishining oldini oladi (buni 7-bobda amalda ko'ramiz).

## Kodni o'qish mashqi

Quyida — (xayoliy) yangi hamkasbingiz yozgan kod. U sizdan so'raydi: "Men mahsulot narxini chegirma bilan hisoblovchi funksiyani qayerga yozishim kerak — `models.py`gami yoki `views.py`gami?" U sizga ikki variantni ko'rsatadi:

**A variant** (`models.py` ichida, model metodi sifatida):
```python
class Mahsulot(models.Model):
    narxi = models.DecimalField(max_digits=10, decimal_places=2)

    def chegirmali_narx(self, foiz):
        return self.narxi * (1 - foiz / 100)
```

**B variant** (`views.py` ichida, alohida funksiya sifatida):
```python
def chegirmali_narx_hisobla(mahsulot, foiz):
    return mahsulot.narxi * (1 - foiz / 100)
```

**Savol:** Import grafi qoidasiga ko'ra, ikkalasi ham **texnik jihatdan** ishlaydi (chunki ikkalasi ham, faqat "to'g'ri yo'nalish"da — `views.py`dan `models.py`ga qarab — ishlaydi). Lekin qaysi biri **kodni o'qish** nuqtai nazaridan afzalroq, va nega?

<details>
<summary>Javobni ko'rish</summary>

**A variant afzalroq.** Sabab — bu logika, aynan **shu modelning o'ziga tegishli xususiyat** (mahsulotning narxi bilan chambarchas bog'liq hisob-kitob), shuning uchun uni **modelning o'zida** saqlash, kodni o'qiyotgan har qanday kishi uchun uni topishni osonlashtiradi: "Mahsulot bilan bog'liq barcha narsa — `models.py`da" degan aniq, bashorat qilinadigan qoida ishlaydi. Agar bu B variantdagidek `views.py`da bo'lsa, va ertaga boshqa bir view yoki hatto boshqa app ham xuddi shu hisob-kitobga muhtoj bo'lsa, uni har safar qayta yozish yoki noqulay import qilish kerak bo'ladi. **Umumiy qoida:** agar mantiq faqat **bitta model haqidagi ma'lumotga** tayansa (boshqa hech narsaga bog'liq bo'lmasa) — uni shu modelning metodi qiling; agar u so'rov (`request`) ma'lumotiga, yoki bir nechta turli modelga birdek tayansa — `views.py`da qoldiring.

</details>

## Keng tarqalgan xatolar

**Xato 1:** `models.py`dan `views.py`ni (yoki `urls.py`ni) import qilish.
❌ Yuqorida ko'rganimizdek, `ImportError: cannot import name '...' from partially initialized module` — aylanma import xatosi.
✅ Import oqimi har doim **faqat bitta yo'nalishda**: `urls.py → views.py → models.py`. Agar `models.py`ga biror narsa kerak bo'lib qolsa-yu, u `views.py`da bo'lsa — bu, aslida, o'sha kodni **noto'g'ri faylga** yozganingizning belgisi; uni `models.py`ga ko'chiring.

**Xato 2:** Barcha mantiqni `views.py`ga to'plash ("hamma narsa view'da bo'laversin" degan dangasalik).
❌ `views.py` tobora "shishib" ketadi, yuzlab qatorli, turli mas'uliyatlarni aralashtirib yuborgan funksiyalarga aylanadi — bunday kodni o'qish, olti oydan keyin, hatto o'zingiz uchun ham qiyinlashadi.
✅ Har bir mantiqni "u nimaga tegishli" degan savol bilan tekshiring: modelga tegishli hisob-kitob — `models.py`ga; forma tekshiruvi — `forms.py`ga; view esa faqat "so'rovni qabul qil, kerakli narsalarni chaqir, javob qaytar" — "yo'l ko'rsatuvchi" vazifasida qolsin.

**Xato 3:** `include()`ni ishlatganda, app'ning `urls.py`sida `app_name`ni unutish.
❌ Keyinchalik (5-bobda) shablonda `{% url 'dokon:bosh-sahifa' %}` yozganingizda, "`dokon` nomli namespace topilmadi" kabi xatoga uchraysiz.
✅ Har bir app darajasidagi `urls.py`da, odat sifatida, **darhol** `app_name = "<app_nomi>"`ni qo'shing.

## Mashq/topshiriq

**(Oson)** `apps/dokon/urls.py`ga yangi yo'nalish qo'shing: `path("haqida/", views.haqida_sahifasi, name="haqida")`. `views.py`ga mos `haqida_sahifasi` funksiyasini yozing (`HttpResponse("Bu — onlayn do'kon haqida")` qaytaruvchi). Serverni qayta ishga tushirib, `/haqida/` manzilini tekshiring.

**(O'rtacha)** Yuqoridagi "Kodni o'qish mashqi"dagi A va B variantlarni **ikkalasini ham** amalda, `python manage.py shell` orqali (soxta klass bilan) sinab ko'ring, va ikkalasi ham **bir xil natija** berishini, lekin kod **o'qilishi** jihatidan farq qilishini o'zingiz his qiling.

**(Qiyin)** Ataylab, `apps/dokon/views.py`ga quyidagi qatorni qo'shing: `from apps.dokon.models import Mahsulot` (hali `models.py`da `Mahsulot` degan model yo'q). Xatoni o'qib, u aylanma import xatosidan **qanday farq qilishini** aniqlang (ikkalasi ham `ImportError`ga o'xshaydimi, yoki turlichami?).

A variant (model metodi) — `mahsulot.chegirmali_narx(20)` kabi, tabiiy, "ob'ektga savol berayotgandek" o'qiladi; B variant — `chegirmali_narx_hisobla(mahsulot, 20)` kabi, "tashqi funksiyaga ob'ektni berib yuborayotgandek" o'qiladi. Katta loyihada, birinchi uslub odatda afzal ko'riladi.

3. Xato turi **boshqacha**: bu safar `ImportError: cannot import name 'Mahsulot' from 'apps.dokon.models'` (aylanma import haqida hech qanday eslatmasiz) — chunki bu holda `models.py` **to'liq yuklangan**, lekin unda haqiqatan ham `Mahsulot` degan nom **umuman mavjud emas** (oddiy "yo'q narsani so'rash" xatosi). Aylanma import xatosida esa, Python aniq "**partially initialized module**... **circular import**" deb ogohlantiradi — bu, ikki xato turini bir-biridan ajratishning kalitidir: agar xato xabarida "circular import" so'zi bo'lsa — muammo import **yo'nalishida**; bo'lmasa — muammo shunchaki **yo'q nomni so'rashda** (masalan, hali yozilmagan model/funksiya nomida xato qilish).

## Qisqacha xulosa

App darajasidagi `urls.py` (`include()` orqali loyiha darajasidagi `urls.py`ga ulanadi) — katta loyihalarda marshrutlashni tartibli saqlashning kaliti. Django fayllari orasidagi import yo'nalishi qat'iy bir tomonlama: `urls.py → views.py → models.py` (va `admin.py → models.py`) — **hech qachon teskari emas**; bu qoida buzilsa, Python aniq, "circular import" haqida ogohlantiruvchi xato beradi (biz buni jonli ko'rdik va tuzatdik). Qo'shimcha fayllar (`forms.py`, `signals.py`, `management/commands/`, `static/<app>/`, `templates/<app>/`) — har biri, xuddi asosiy fayllar kabi, o'zining aniq, boshqa fayl bilan aralashmaydigan vazifasiga ega. Keyingi (3-)bobda — bu barcha fayllar, bitta haqiqiy foydalanuvchi so'rovi kelganda, **qanday tartibda, birin-ketin** ishga tushishini (URL'dan Response'gacha to'liq yo'l) jonli kuzatamiz — bu, ehtimol, butun darslikning eng markaziy darsi bo'ladi.

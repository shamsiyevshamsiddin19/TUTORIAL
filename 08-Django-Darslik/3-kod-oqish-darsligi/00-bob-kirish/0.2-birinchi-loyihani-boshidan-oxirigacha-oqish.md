# 0.2. Birinchi loyihani yaratib, boshidan-oxirigacha o'qish

## Bu darsda nimalarni o'rganasiz

- `django-admin startproject` buyrug'i **aynan nechta va qaysi** fayl yaratishini bilib olasiz
- Har bir yaratilgan faylni ochib, ichidagi kodni **satrma-satr** o'qiysiz (hali hech narsani o'zgartirmasdan)
- "Loyiha xaritasi" — har bir faylning bir jumlalik vazifasini yodda saqlash usulini o'rganasiz
- Loyihani ishga tushirib, natijani **kod bilan bog'lab** tushunasiz (nega aynan shu sahifa chiqadi)

## Nazariy qism

### Bitta buyruq — beshta fayl

O'tgan darsda tayyorlagan muhitda, yangi Django loyihasi yaratamiz:

```bash
mkdir onlayn_dokon && cd onlayn_dokon
django-admin startproject config .
```

**Muhim tafsilot:** buyruq oxiridagi **nuqta (`.`)** — "loyihani joriy papkaning ichida yarat, yana bitta qo'shimcha ichki papka ochma" degani. Agar nuqtani tushirib qoldirsangiz, Django `config/config/` kabi ikki qavatli, keraksiz ichma-ich tuzilma yaratadi.

Bajarilgandan so'ng, quyidagi fayllar paydo bo'ladi — buni o'zingiz `find . -type f` bilan tekshiring:

```
./manage.py
./config/__init__.py
./config/settings.py
./config/urls.py
./config/wsgi.py
./config/asgi.py
```

Diqqat qiling: **bitta** buyruq, **beshta** fayl yaratdi, va ular ikkita joyga taqsimlangan — loyiha ildizidagi `manage.py`, va `config/` papkasi ichidagi qolgan to'rttasi. Bu tasodifiy emas — Django, ataylab, "loyiha bilan **ishlash uchun vosita**" (`manage.py`) va "loyihaning **o'zi, uning miyasi**" (`config/`)ni jismonan ajratib qo'ygan. Keling, har birini navbat bilan ochib, o'qiymiz.

### 1-fayl: `manage.py` — "boshqaruv paneli"

```python
#!/usr/bin/env python
"""Django's command-line utility for administrative tasks."""

import os
import sys


def main():
    """Run administrative tasks."""
    os.environ.setdefault("DJANGO_SETTINGS_MODULE", "config.settings")
    try:
        from django.core.management import execute_from_command_line
    except ImportError as exc:
        raise ImportError(
            "Couldn't import Django. Are you sure it's installed and "
            "available on your PYTHONPATH environment variable? Did you "
            "forget to activate a virtual environment?"
        ) from exc
    execute_from_command_line(sys.argv)


if __name__ == "__main__":
    main()
```

Buni **satrma-satr** o'qiymiz:

- `os.environ.setdefault("DJANGO_SETTINGS_MODULE", "config.settings")` — bu qator, Python muhitiga "sozlamalar (settings) qayerda ekanini" aytadi: `config` papkasidagi `settings.py` fayli. Bu — juda muhim: Django o'zi hech qachon "settings.py qayerda" deb taxmin qilmaydi, u har doim shu muhit o'zgaruvchisidan o'qiydi.
- `from django.core.management import execute_from_command_line` — bu, Django kutubxonasining o'zidan, "buyruqlarni bajaruvchi" funksiyani import qiladi. Bu qator `try/except` ichiga olingan — agar Django o'rnatilmagan bo'lsa (yoki `venv` faollashtirilmagan bo'lsa), foydalanuvchiga **tushunarli** xato xabari ko'rsatiladi (`"Did you forget to activate a virtual environment?"`), umumiy `ModuleNotFoundError` o'rniga.
- `execute_from_command_line(sys.argv)` — terminaldan kiritilgan buyruqni (`sys.argv`, masalan `["manage.py", "runserver"]`) haqiqiy bajarishga yuboradi.

**Xulosa:** `manage.py` — o'zi **hech qanday biznes-mantiq** saqlamaydi. U shunchaki — "terminal buyrug'ini Django'ning ichki mexanizmiga uzatuvchi ko'prik". Shuning uchun, deyarli hech qachon, `manage.py`ning o'zini o'zgartirish kerak bo'lmaydi.

### 2-fayl: `config/__init__.py` — bo'sh, lekin muhim

```python
# (bo'sh fayl, 0 bayt)
```

Bu fayl **butunlay bo'sh**. Uning yagona vazifasi — Python'ga "`config` — bu oddiy papka emas, bu **paket** (import qilса bo'ladigan modul)" deb bildirish. Agar bu fayl bo'lmasa, boshqa fayllardagi `from config.settings import ...` kabi import'lar ishlamay qoladi.

### 3-fayl: `config/settings.py` — loyihaning "miyasi"

Bu — eng katta va eng muhim fayl (keyingi darsda, 1-bobda, uni to'liq, chuqur o'qiymiz). Hozircha faqat eng yuqori qismini ko'ramiz:

```python
from pathlib import Path

BASE_DIR = Path(__file__).resolve().parent.parent

SECRET_KEY = "django-insecure-xzg^g34+vm)q#d9jh_kk6jd_djg+5l6yinefmrzbx@se^6p&5z"
DEBUG = True
ALLOWED_HOSTS = []
```

`BASE_DIR = Path(__file__).resolve().parent.parent` — bu qatorni diqqat bilan o'qiymiz, chunki u ko'p yangi boshlovchini chalg'itadi: `__file__` — joriy faylning (`settings.py`) o'zining to'liq yo'li (`.../onlayn_dokon/config/settings.py`); `.resolve()` — bu yo'lni **mutlaq** (absolute) qiladi; birinchi `.parent` — `config/` papkasiga chiqadi; ikkinchi `.parent` — undan yana bir qavat yuqoriga, loyiha **ildiz** papkasiga (`onlayn_dokon/`) chiqadi. Ya'ni, `BASE_DIR` — bu, qayerdan ishga tushirilishidan qat'iy nazar, loyiha ildizini **doim to'g'ri** topib beradigan o'zgaruvchi.

### 4-fayl va 5-fayl: `wsgi.py` va `asgi.py` — "eshiklar"

```python
# config/wsgi.py
import os
from django.core.wsgi import get_wsgi_application
os.environ.setdefault("DJANGO_SETTINGS_MODULE", "config.settings")
application = get_wsgi_application()
```

```python
# config/asgi.py
import os
from django.core.asgi import get_asgi_application
os.environ.setdefault("DJANGO_SETTINGS_MODULE", "config.settings")
application = get_asgi_application()
```

Bu ikki fayl bir-biriga juda o'xshaydi, lekin **ikki xil "til"**da gaplashadi: `wsgi.py` — an'anaviy, **sinxron** production serverlar (masalan, Gunicorn) uchun kirish nuqtasi; `asgi.py` — **asinxron** (`async`/`await`, WebSocket kabi) imkoniyatlarni qo'llab-quvvatlaydigan serverlar uchun. `python manage.py runserver` (biz rivojlanish paytida ishlatadigan buyruq) — bu ikkalasini ham ishlatmaydi, u o'zining **soddalashtirilgan, faqat rivojlantirish uchun** serverini ishga tushiradi. `wsgi.py`/`asgi.py` — faqat **production**ga chiqarilganda kerak bo'ladi (16-bobda ko'ramiz — hozircha faqat ularning **borligini va vazifasini** bilib qo'yamiz, ichiga tegmaymiz).

### 6-fayl: `config/urls.py` — "yo'l ko'rsatkich"

```python
from django.contrib import admin
from django.urls import path

urlpatterns = [
    path("admin/", admin.site.urls),
]
```

`urlpatterns` — bu, Django'ning **eng markaziy** ro'yxati: "qaysi URL manzil, qaysi kodga olib boradi". Hozircha bu yerda faqat bitta yo'nalish bor: `/admin/` manzili, Django'ning tayyor admin panellik kodiga (`admin.site.urls`) ulanadi. Bu ro'yxat, biz app qo'shgan sari, o'sib boradi — 2-bobda buni chuqur o'rganamiz.

## Kodni o'qish mashqi

Loyihani hali ishga tushirmasdan, faqat yuqoridagi olti faylni o'qib chiqqan holda, quyidagi savolga javob bering: **agar men `http://127.0.0.1:8000/admin/` manziliga kirsam, nima bo'ladi? Agar `http://127.0.0.1:8000/` (bo'sh, ildiz manzil)ga kirsam-chi?**

<details>
<summary>Javobni ko'rish</summary>

`urls.py`ni qayta o'qiymiz: `urlpatterns` ro'yxatida faqat **bitta** yo'nalish bor — `"admin/"`. Shuning uchun `/admin/`ga kirsangiz, Django buni topadi va admin panelining login sahifasiga yo'naltiradi (garchi hali `migrate` bajarilmagani uchun, bazada jadvallar yo'q, u xato berishi mumkin — buni keyingi bo'limda tekshiramiz).

Bo'sh, ildiz manzil (`/`) uchun esa — `urlpatterns`da unga mos **hech qanday** yozuv yo'q. Oddiy holatda bu `Page not found (404)` xatosiga olib kelishi kerak edi. **Lekin** — Django'ning maxsus xususiyati bor: agar `DEBUG = True` bo'lsa (bu, `settings.py`da biz yuqorida o'qigan qatorimiz!) VA `urlpatterns`da hech qanday mos yo'nalish topilmasa, Django, oddiy 404 o'rniga, **maxsus "o'rnatish muvaffaqiyatli" (raketa) sahifasini** ko'rsatadi — bu, yangi loyiha to'g'ri sozlanganini tasdiqlash uchun qulaylik.

</details>

## Keng tarqalgan xatolar

**Xato 1:** `startproject config .` o'rniga `startproject config` (nuqtasiz) ishlatish.
❌ Natijada `config/config/settings.py`, `config/manage.py` kabi ikki qavatli tuzilma hosil bo'ladi — bu, `BASE_DIR` hisoblanishini ham, keyingi barcha buyruqlarni ham chalkashtiradi.
✅ Har doim, loyiha ildizida turib, oxiriga nuqta qo'shib `django-admin startproject config .` ishlating.

**Xato 2:** `migrate`ni bajarmasdan, to'g'ridan-to'g'ri `/admin/`ga kirishga urinish.
❌ Django'ning ichki jadvallari (foydalanuvchi, sessiya) hali bazada yo'q bo'lgani uchun, `OperationalError: no such table` kabi xatoga uchraysiz.
✅ Yangi loyihada, birinchi ishga tushirishdan **oldin**, har doim `python manage.py migrate`ni bajaring — bu, deyarli har doim birinchi qadam.

**Xato 3:** "Raketa sahifasi" chiqqanini "loyiha to'liq tayyor" deb tushunish.
❌ Bu sahifa faqat "Django to'g'ri o'rnatilgan va ishga tushdi" degan ma'noni bildiradi — hali hech qanday sizning kodingiz (app, model, view) yozilmagan.
✅ Bu sahifani ko'rgach, `urlpatterns`ga o'z yo'nalishingizni qo'shgan zahoti, u avtomatik ravishda **yo'qoladi** (chunki endi mos yozuv topiladi) — buni 2-3-bobda ko'ramiz.

## Mashq/topshiriq

**(Oson)** `config/settings.py` faylini oching va `DEBUG = True` qatorini `DEBUG = False`ga o'zgartiring. `python manage.py runserver`ni qayta ishga tushirishga urinib ko'ring — natijada nima bo'lishini kuzating va nega bunday bo'lganini, shu darsda o'qiganlaringizga (xususan, `ALLOWED_HOSTS = []` qatoriga) tayanib tushuntiring.

**(O'rtacha)** `config/urls.py` faylining eng yuqorisiga `from django.http import HttpResponse` qatorini qo'shing, va `urlpatterns` ro'yxatiga yangi qator qo'shing: `path("salom/", lambda request: HttpResponse("Salom, Django!"))`. Serverni qayta ishga tushirib, `http://127.0.0.1:8000/salom/` manziliga kirib, natijani tekshiring. (Bu — hali "to'g'ri" usul emas, keyingi bo'limlarda buni qanday tozaroq yozishni ko'rasiz — lekin `urlpatterns`ning ishlash mexanizmini his qilish uchun foydali mashq.)

**(Qiyin)** `manage.py`dagi `os.environ.setdefault("DJANGO_SETTINGS_MODULE", "config.settings")` qatorini vaqtincha `"config.notogri_nom"`ga o'zgartiring va `python manage.py runserver`ni ishga tushirishga urinib ko'ring. Chiqqan xato xabarini to'liq o'qing va tushuntiring: bu xato Python darajasidami yoki Django darajasidami, va nega aynan shu xabar chiqmoqda?

<details>
<summary>Javoblarni ko'rish</summary>

1. Server hatto **ishga tushmaydi** — terminalda darhol quyidagi xato chiqadi: `CommandError: You must set settings.ALLOWED_HOSTS if DEBUG is False.` Sabab: `DEBUG = True`da Django, xavfsizlik nuqtai nazaridan, `ALLOWED_HOSTS`ni tekshirmaydi (rivojlantirish qulay bo'lishi uchun). Lekin `DEBUG = False`ga o'tilgan zahoti — bu, "endi biz production'dagidek jiddiy muhitdamiz" degani — Django darhol qattiqroq talab qo'yadi: qaysi domen/host nomlari orqali saytga murojaat qilish mumkinligini (`ALLOWED_HOSTS`) aniq ko'rsatishni **majburiy** qiladi, aks holda hatto serverni ishga tushirishga yo'l qo'ymaydi. Bu — production muhitida `DEBUG=True` qoldirish nega xavfli ekanini (va Django buni qanday oldini olishga harakat qilishini) ko'rsatuvchi aniq, kod orqali tasdiqlangan misol.

2. `http://127.0.0.1:8000/salom/` manziliga kirganda, "Salom, Django!" matni ko'rinadi — bu, `urlpatterns`ning har bir yozuvi, aslida, "manzil → chaqiriladigan funksiya" juftligi ekanini isbotlaydi (funksiya `lambda` bilan ham, alohida `views.py`da ham yozilishi mumkin — buni 2-bobda ko'ramiz).

3. Xato — Python darajasida, aniqrog'i **Django'ning ichida**: `ModuleNotFoundError: No module named 'config.notogri_nom'`. Sabab: `DJANGO_SETTINGS_MODULE` — Django'ga qaysi Python modulini (`import` yo'li sifatida) sozlamalar deb hisoblashni aytadi; `config.notogri_nom` degan modul jismonan mavjud emas, shuning uchun Django uni import qilishga urinib, standart Python xatosiga uchraydi. Bu — "sozlamalar fayli topilmasa nima bo'ladi" degan savolga aniq, kod orqali tasdiqlangan javob.

</details>

## Qisqacha xulosa

`django-admin startproject config .` — bitta buyruq bilan oltita fayl yaratadi, va ularning har biri o'ziga xos, aniq vazifaga ega: `manage.py` — terminal buyruqlarini Django'ga uzatuvchi ko'prik; `config/__init__.py` — papkani Python paketi qiladi; `config/settings.py` — loyihaning barcha global sozlamalari (`BASE_DIR`, `DEBUG`, va h.k.); `config/urls.py` — "qaysi manzil qaysi kodga olib boradi" ro'yxati; `config/wsgi.py`/`asgi.py` — production serverlar uchun kirish eshiklari. "Raketa sahifasi" — `DEBUG = True` va `urlpatterns`da mos yo'q bo'lganda ko'rinadigan, "hammasi to'g'ri o'rnatilgan" belgisi, lekin hali sizning kodingiz yo'qligini ham bildiradi. Keyingi (1-)bobda, `settings.py`ni to'liq, satrma-satr o'qib chiqamiz, va uni **o'zgartirib** — bazani SQLite'dan, PostgreSQL darsligidan tanish `dokon_bazasi`ga o'xshash real PostgreSQL bazasiga ulaymiz.

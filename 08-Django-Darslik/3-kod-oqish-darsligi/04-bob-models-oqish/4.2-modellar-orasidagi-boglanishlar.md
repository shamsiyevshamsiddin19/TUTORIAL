# 4.2. Modellar orasidagi bog'lanishlar — ForeignKey, OneToOne va "M2M nega yo'q"

## Bu darsda nimalarni o'rganasiz

- `ForeignKey` — bitta modelni ikkinchisiga "bog'lash", va `on_delete` parametri **aslida qayerda** ishlayotganini (bazadami, Python'dami?) real so'rovlar orqali ko'rasiz
- `on_delete=CASCADE`, `SET_NULL`, `PROTECT` — uchtasi orasidagi farqni, real xatolar va real SQL orqali his qilasiz
- `related_name` — "orqaga qarab" so'rov yozish (`bolim.xodimlar.all()`) qanday ishlashini
- `OneToOneField` — bu, aslida, `ForeignKey(unique=True)` ekanini, bazaviy sathda tasdiqlaysiz
- To'liq `onlayn_dokon` sxemasini yakunlaysiz: `Xodim`, `Mijoz`, `Mahsulot`, `Buyurtma`, `BuyurtmaElementi`

## Nazariy qism

### `ForeignKey` — "bitta jadval, ikkinchisiga ishora qiladi"

4.1'da faqat bitta model — `Bolim` — bor edi. Endi, PostgreSQL darsligidagi `dokon_bazasi`ga mos, qolgan modellarni qo'shamiz. Avval — `Xodim`:

```python
class Xodim(models.Model):
    bolim = models.ForeignKey(Bolim, on_delete=models.CASCADE, related_name="xodimlar")
    ism = models.CharField(max_length=50)
    familiya = models.CharField(max_length=50)
    lavozim = models.CharField(max_length=50)
    ish_haqi = models.DecimalField(max_digits=10, decimal_places=2)

    def __str__(self):
        return f"{self.ism} {self.familiya}"
```

Buni satrma-satr o'qiymiz: `bolim = models.ForeignKey(Bolim, ...)` — bu qatorni **PostgreSQL darsligidagi** `bolim_id INTEGER REFERENCES bolimlar(id)` bilan solishtiring — aynan bir xil narsa, faqat Python sintaksisida yozilgan. `ForeignKey`ning **birinchi argumenti** — qaysi modelga bog'lanayotgani (`Bolim`), bu — "har bir `Xodim`, aynan bitta `Bolim`ga tegishli" degani. Diqqat qiling: klassda maydon nomi — `bolim` (`bolim_id` emas!) — Django, avtomatik ravishda, bazada `bolim_id` nomli ustun yaratadi, lekin Python kodida siz doim `xodim.bolim` (to'liq `Bolim` ob'ekti) bilan ishlaysiz, `xodim.bolim_id` (faqat raqam) ham mavjud, lekin kamdan-kam ishlatiladi.

`on_delete=models.CASCADE` — bu, "agar bog'langan `Bolim` o'chirilsa, bu `Xodim` bilan nima qilamiz" degan savolga javob. `related_name="xodimlar"` — bu, **"orqaga qarab" so'rov nomi**: uni belgilamasangiz, Django avtomatik `xodim_set` nomini beradi (masalan, `bolim.xodim_set.all()`), lekin `related_name` bilan, o'qishga qulayroq `bolim.xodimlar.all()` yozish mumkin bo'ladi — buni pastda, jonli sinaymiz.

### To'liq sxemani yozamiz

Qolgan to'rtta modelni ham qo'shamiz — bularning barchasi, PostgreSQL darsligidagi `dokon_bazasi` jadvallariga to'g'ridan-to'g'ri mos:

```python
class Mijoz(models.Model):
    ism = models.CharField(max_length=50)
    familiya = models.CharField(max_length=50)
    email = models.EmailField(unique=True)
    telefon = models.CharField(max_length=20, blank=True)

    def __str__(self):
        return f"{self.ism} {self.familiya}"


class Mahsulot(models.Model):
    bolim = models.ForeignKey(Bolim, on_delete=models.CASCADE, related_name="mahsulotlar")
    nomi = models.CharField(max_length=100)
    narxi = models.DecimalField(max_digits=10, decimal_places=2)
    ombordagi_soni = models.IntegerField(default=0)

    def __str__(self):
        return self.nomi


class Buyurtma(models.Model):
    mijoz = models.ForeignKey(Mijoz, on_delete=models.CASCADE, related_name="buyurtmalar")
    xodim = models.ForeignKey(
        Xodim, on_delete=models.SET_NULL, null=True, related_name="qabul_qilgan_buyurtmalar"
    )
    sana = models.DateTimeField(auto_now_add=True)

    def __str__(self):
        return f"Buyurtma #{self.id} — {self.mijoz}"


class BuyurtmaElementi(models.Model):
    buyurtma = models.ForeignKey(Buyurtma, on_delete=models.CASCADE, related_name="elementlar")
    mahsulot = models.ForeignKey(Mahsulot, on_delete=models.PROTECT)
    soni = models.IntegerField(default=1)
    narxi_buyurtma_vaqtida = models.DecimalField(max_digits=10, decimal_places=2)

    def __str__(self):
        return f"{self.mahsulot} x{self.soni}"
```

Bu yerda uchta muhim, o'qishga arziydigan qaror bor:

**1) `Buyurtma.xodim` — nega `SET_NULL`, `Mahsulot.bolim` kabi `CASCADE` emas?** Chunki mantiqiy jihatdan farq bor: agar bir `Bolim` (masalan, "Elektronika") butunlay yopilsa, u yerdagi `Mahsulot`lar ham ma'nosiz qoladi — `CASCADE` mantiqan to'g'ri. Lekin agar bir `Xodim` ishdan bo'shasa, uning oldin qabul qilgan `Buyurtma`lari **haqiqiy tarixiy yozuv** — ular o'chirilmasligi kerak, faqat "kim qabul qilgani" ma'lumoti yo'qolishi mumkin — shuning uchun `SET_NULL` (va shuning uchun ham `null=True` qo'shilgan — `SET_NULL` ishlashi uchun, ustun **majburiy ravishda** `nullable` bo'lishi kerak, aks holda Django, loyihani ishga tushirishda xato beradi).

**2) `BuyurtmaElementi.mahsulot` — nega `PROTECT`?** Bu — "sotilgan mahsulotni o'chirib bo'lmaydi" qoidasi: agar kimdir `Mahsulot`ni bazadan o'chirmoqchi bo'lsa-yu, u mahsulot allaqachon biror `BuyurtmaElementi`da "sotilgan" bo'lsa — bu, moliyaviy tarixni buzadi. `PROTECT`, bunday o'chirishni **butunlay taqiqlaydi** — quyida buni real xato bilan ko'ramiz.

**3) `BuyurtmaElementi` — nega alohida model, nega to'g'ridan-to'g'ri `Buyurtma.mahsulotlar = ManyToManyField(Mahsulot)` emas?** Bu — keyingi bo'limning markaziy savoli.

### `ManyToManyField` — va nega bu yerda ishlatilmagan

Bir qarashda, "bitta buyurtmada bir nechta mahsulot, bitta mahsulot bir nechta buyurtmada bo'lishi mumkin" — bu, klassik **many-to-many** munosabat, va uni bitta qatorda yozish mumkin edi:

```python
class Buyurtma(models.Model):
    mahsulotlar = models.ManyToManyField(Mahsulot)  # oddiy, lekin YETARLI EMAS
```

Bu, "ichkarida" avtomatik, uchinchi (oraliq) jadval yaratadi — PostgreSQL darsligining 4-bobida ko'rgan "bog'lovchi jadval" g'oyasi aynan shu. Lekin muammo: bunday oddiy `ManyToManyField`, faqat "qaysi mahsulot qaysi buyurtmada bor" degan **bog'lanishni** saqlaydi — u yerda **qo'shimcha ma'lumot** uchun joy yo'q: nechta dona sotilgani (`soni`) qayerda? Sotuv vaqtidagi narx (`narxi_buyurtma_vaqtida`) qayerda — axir mahsulotning "hozirgi" narxi, olti oy oldin sotilganida qanday bo'lganidan farq qilishi mumkin-ku?

Aynan shuning uchun, `BuyurtmaElementi` — qo'lda yozilgan, **ikkita `ForeignKey`li oddiy model** sifatida quriladi (Django buni "through model" — oraliq model, deb ataydi): u, `ManyToManyField` avtomatik yaratgan oraliq jadvalning **aynan o'zi**, lekin endi unga o'zimiz xohlagancha qo'shimcha ustun (`soni`, `narxi_buyurtma_vaqtida`) qo'sha olamiz. Xulosa qoidasi: agar ikki model orasidagi bog'lanishning **o'zi haqida** qo'shimcha ma'lumot saqlash kerak bo'lsa (qachon, nechta, qanday narxda) — `ManyToManyField` emas, ikkita `ForeignKey`li alohida model kerak.

Nega — migratsiya tizimi, `models.py`dagi yozuv tartibiga emas, balki **boshqa narsaga** qarab reja tuzadi, deb o'ylaysiz?

<details>
<summary>Javobni ko'rish</summary>

Migratsiya tizimi, `models.py`dagi **yozuv tartibiga umuman e'tibor bermaydi** — u, modellar orasidagi **bog'liqlik grafi** (dependency graph)ga qarab ishlaydi: `Buyurtma`, `Mijoz`ga `ForeignKey` orqali bog'liq, shuning uchun `Mijoz` jadvali, `Buyurtma`dan **oldin** yaratilishi SHART (aks holda, `Buyurtma`ning `mijoz_id REFERENCES dokon_mijoz(id)` cheklovi, mavjud bo'lmagan jadvalga ishora qilgan bo'lardi). Xuddi shunday, `Xodim`, `Bolim`ga bog'liq — lekin `Buyurtma` ham `Xodim`ga bog'liq, shuning uchun avval `Buyurtma` model **o'zi** (`xodim` maydonisiz, keyin alohida "Add field xodim to buyurtma" qadamida) yaratiladi, so'ng `Xodim` yaratiladi, so'ng `Buyurtma`ga `xodim` ustuni **qo'shiladi**. Bu — 2-bobda ko'rgan import-graf qoidasining, migratsiyalar darajasidagi ko'rinishi: **kod tartibi emas, bog'liqlik tartibi hal qiluvchi**.

## Amaliy misol

To'liq zanjirni yaratamiz va `on_delete`larni **jonli** sinaymiz:

```python
b = Bolim.objects.create(nomi="Elektronika")
x = Xodim.objects.create(bolim=b, ism="Aziz", familiya="Vali", lavozim="Sotuvchi", ish_haqi="4500000")
m = Mijoz.objects.create(ism="Olim", familiya="Karim", email="olim@example.com")
mah = Mahsulot.objects.create(bolim=b, nomi="Noutbuk", narxi="5000000", ombordagi_soni=10)
buy = Buyurtma.objects.create(mijoz=m, xodim=x)
elem = BuyurtmaElementi.objects.create(buyurtma=buy, mahsulot=mah, soni=1, narxi_buyurtma_vaqtida="5000000")
```

`related_name`lar orqali, "orqaga qarab" so'rov yozamiz:

```python
>>> b.xodimlar.all()
<QuerySet [<Xodim: Aziz Vali>]>
>>> b.mahsulotlar.all()
<QuerySet [<Mahsulot: Noutbuk>]>
>>> x.qabul_qilgan_buyurtmalar.all()
<QuerySet [<Buyurtma: Buyurtma #1 — Olim Karim>]>
```

Endi **`PROTECT`**ni sinaymiz — sotilgan mahsulotni o'chirishga urinamiz:

```python
>>> mah.delete()
```

```
ProtectedError: ("Cannot delete some instances of model 'Mahsulot' because they are referenced through
protected foreign keys: 'BuyurtmaElementi.mahsulot'.", {<BuyurtmaElementi: Noutbuk x1>})
```

Django, o'chirishga **umuman yo'l qo'ymadi** — `mah` bazada hamon mavjud. Endi **`SET_NULL`**ni sinaymiz — `Xodim`ni o'chiramiz:

```python
>>> x.delete()
>>> buy = Buyurtma.objects.get(id=1)
>>> buy.xodim
None
```

`Buyurtma` **o'chirilmadi** — faqat `xodim_id` ustuni `NULL`ga aylandi. Endi eng qiziqarli qismi — **`CASCADE`ning zanjir bo'ylab qanday to'xtashi**: `Bolim`ni o'chirishga urinamiz. Kutilishicha, `CASCADE` — bog'liq `Mahsulot`larni ham o'chirishi kerak, lekin `mah` — hamon `BuyurtmaElementi` orqali **himoyalangan** (`PROTECT`):

```python
>>> b.delete()
```

```
ProtectedError: ("Cannot delete some instances of model 'Bolim' because they are referenced through
protected foreign keys: 'Mahsulot.bolim'.", {<BuyurtmaElementi: Noutbuk x1>})
```

**Muhim xulosa:** `CASCADE`, o'z yo'lidagi modellarni o'chirishga "harakat qiladi", lekin agar zanjirning **istalgan bosqichida** `PROTECT`ga duch kelsa — butun operatsiya (`Bolim`ni o'chirish ham!) bekor qilinadi. `PROTECT` — zanjirning istalgan chuqurligida, yuqoriroqdagi `CASCADE`ni ham "to'xtatishi" mumkin.

### `on_delete` — bazada emas, Python'da ishlaydi!

Bu — ko'p odamni chalg'itadigan, muhim haqiqat. PostgreSQL darsligida siz `ON DELETE CASCADE`ni **bazaning o'zida**, SQL darajasida yozgan edingiz. Django'da esa — boshqacha. Real jadval tuzilishini tekshiramiz:

```bash
sudo -u postgres psql -d onlayn_dokon -c "\d dokon_xodim"
```

```
Foreign-key constraints:
    "dokon_xodim_bolim_id_2e4b4b03_fk_dokon_bolim_id" FOREIGN KEY (bolim_id) REFERENCES dokon_bolim(id) DEFERRABLE INITIALLY DEFERRED
```

Diqqat qiling: bu yerda **`ON DELETE CASCADE` degan so'z umuman yo'q**! `models.py`da `on_delete=models.CASCADE` deb yozgan bo'lsak ham, PostgreSQL'ning o'zi, bu cheklovni "CASCADE" deb bilmaydi. Buning sababini, real SQL so'rovlarni "tinglab" ko'ramiz:

```python
from django.test.utils import CaptureQueriesContext
from django.db import connection

b2 = Bolim.objects.create(nomi="Kiyim-kechak")
x2 = Xodim.objects.create(bolim=b2, ism="Nodira", familiya="Yusupova", lavozim="Menejer", ish_haqi="3000000")

with CaptureQueriesContext(connection) as ctx:
    b2.delete()

for q in ctx.captured_queries:
    print(q["sql"])
```

```
SELECT "dokon_xodim"."id" FROM "dokon_xodim" WHERE "dokon_xodim"."bolim_id" IN (2)
SELECT "dokon_mahsulot"."id" FROM "dokon_mahsulot" WHERE "dokon_mahsulot"."bolim_id" IN (2)
BEGIN
UPDATE "dokon_buyurtma" SET "xodim_id" = NULL WHERE "dokon_buyurtma"."xodim_id" IN (2)
DELETE FROM "dokon_xodim" WHERE "dokon_xodim"."id" IN (2)
DELETE FROM "dokon_bolim" WHERE "dokon_bolim"."id" IN (2)
COMMIT
```

Endi tushunarli: `b2.delete()` chaqirilganda, Django **avval** (SELECT orqali) qaysi `Xodim`/`Mahsulot` yozuvlari bog'liqligini **o'zi Python darajasida hisoblab chiqadi**, so'ng, bitta tranzaksiya (`BEGIN`...`COMMIT`) ichida, kerakli `UPDATE`/`DELETE` buyruqlarini **birma-bir, qo'lda** yuboradi. `on_delete=CASCADE`/`SET_NULL`/`PROTECT` — bu, **PostgreSQL'ning emas, Django ORM'ning o'z mantiqi**: `models.py`dagi shu bitta so'z, aslida, yuqoridagi butun SQL zanjirini "orqasida" yaratadi. Bu — nega katta jadvallarda, ko'plab bog'liq yozuvlar bo'lsa, `.delete()` sekin ishlashi mumkinligining ham sababi (bitta `DELETE`, PostgreSQL darajasidagi `ON DELETE CASCADE`dek emas — bir nechta alohida so'rov kerak bo'ladi).

## Keng tarqalgan xatolar

**Xato 1:** `ForeignKey` maydoniga, ob'ekt o'rniga, to'g'ridan-to'g'ri ID sonini yozib, keyin `.save()` chaqirmasdan, uni ob'ekt kabi ishlatishga urinish.
❌
```python
x = Xodim(bolim=1, ism="Test", ...)  # bolim=1 — bu Bolim ob'ekti emas, oddiy son!
print(x.bolim.nomi)  # AttributeError yoki noto'g'ri xulq
```
✅ To'g'ri yo'l — yo haqiqiy ob'ektni uzatish (`bolim=b`), yo `bolim_id=1` (aynan `_id` qo'shimchasi bilan, bu holda Django, uni "xom" ID sifatida qabul qiladi va keyinroq kerak bo'lsa o'zi so'rov yuboradi).

**Xato 2:** `null=True`ni unutib, `on_delete=SET_NULL` yozish.
❌
```python
xodim = models.ForeignKey(Xodim, on_delete=models.SET_NULL, related_name="...")  # null=True yo'q!
```
Bu, `python manage.py check` bosqichida darhol xato beradi: `django.core.exceptions.FieldError`ga o'xshash, aniqrog'i Django'ning system check xatosi — `SET_NULL` mantiqiy jihatdan, ustun `NULL` qabul qila olishini talab qiladi, aks holda "bo'sh qoldirish" jismonan mumkin emas.
✅ `SET_NULL` ishlatilsa — har doim, albatta `null=True` ham qo'shiladi.

**Xato 3:** `related_name`larni bir xil qilib qo'yish (yoki umuman yozmaslik), natijada ikkita FK bitta modelga ishora qilganda to'qnashuv.
❌ Agar `Buyurtma`da ikkita `ForeignKey(Xodim, ...)` bo'lsa-yu (masalan, "qabul qilgan xodim" va "yetkazib bergan xodim"), ikkalasiga ham `related_name` berilmasa — Django, `xodim_set` nomini **ikkalasiga ham** berishga urinadi va `SystemCheckError` chiqaradi ("reverse accessor clashes").
✅ Bir modelga bir nechta `ForeignKey` bog'langanda, **har biriga alohida, tushunarli `related_name`** bering (masalan, `related_name="qabul_qilgan_buyurtmalar"`).

## Mashq/topshiriq

**(Oson)** `Xodim` modeliga bog'liq, yangi `OneToOneField`li model qo'shing:

```python
class XodimHujjati(models.Model):
    xodim = models.OneToOneField(Xodim, on_delete=models.CASCADE, related_name="hujjat")
    passport_raqami = models.CharField(max_length=20, unique=True)
```

`makemigrations`/`migrate`dan so'ng, `\d dokon_xodimhujjati` orqali, `xodim_id` ustunida **oddiy indeks emas, balki `UNIQUE CONSTRAINT`** borligini tasdiqlang. Nega aynan shu, `OneToOneField`ni `ForeignKey`dan farqlaydigan **yagona** narsa ekanini, o'z so'zlaringiz bilan tushuntiring.

**(O'rtacha)** Bitta `Xodim`ga ikkita `XodimHujjati` yaratishga urinib ko'ring (`xodim=` bir xil, `passport_raqami=` boshqa-boshqa). Nima bo'ladi? Xatoni o'qing va u aynan qaysi cheklov tufayli chiqayotganini toping.

**(Qiyin)** `Buyurtma`ga ikkinchi `ForeignKey(Xodim)` qo'shing — `yetkazib_bergan_xodim = models.ForeignKey(Xodim, on_delete=models.SET_NULL, null=True)` (bu safar `related_name`siz, ataylab). `python manage.py check` ishga tushiring. **Bashorat qiling:** xato chiqadimi? (Eslatma: `xodim` maydonida allaqachon `related_name="qabul_qilgan_buyurtmalar"` bor — bu, natijaga ta'sir qiladimi?) So'ng, `xodim`dan ham `related_name`ni **vaqtincha olib tashlab**, `check`ni qayta ishga tushiring va natijani solishtiring.

Endi `xodim`dan ham `related_name`ni olib tashlab (ikkalasi ham standart nomga da'vogar bo'lganda), `check`ni qayta ishga tushirsak:

Endi **ikkalasi ham** standart `buyurtma_set` nomiga da'vogar bo'lgani uchun, Django ikkalasini ham xato deb belgilaydi (bitta emas, ikkita alohida xabar — har bir maydon nuqtai nazaridan bittadan). Tuzatish — ikkala maydonga ham, aniq, bir-biridan farqli `related_name` berish:
```python
xodim = models.ForeignKey(Xodim, on_delete=models.SET_NULL, null=True, related_name="qabul_qilgan_buyurtmalar")
yetkazib_bergan_xodim = models.ForeignKey(Xodim, on_delete=models.SET_NULL, null=True, related_name="yetkazib_bergan_buyurtmalar")
```
**Xulosa (bashoratingiz chippakka chiqqan bo'lsa ham, muhim saboq):** to'qnashuv, "ikkita `ForeignKey` bitta modelga bog'langanda" emas, balki **ikkita maydon aynan bir xil (yoki ikkalasi ham standart) nomga da'vogar bo'lganda** yuzaga keladi. Shuning uchun ham, amaliyotda, bitta modelga bir nechta `ForeignKey` yozilsa — **har biriga darhol, aniq `related_name` berish** — kelajakdagi shunga o'xshash to'qnashuvlarning oldini oladigan yaxshi odat.

</details>

## Qisqacha xulosa

`ForeignKey` — PostgreSQL'dagi `REFERENCES` cheklovining Python ko'rinishi, lekin `on_delete` xulqi (`CASCADE`, `SET_NULL`, `PROTECT`) — bazada emas, **Django ORM darajasida, alohida SQL so'rovlar zanjiri orqali** amalga oshiriladi (buni `\d` chiqishida `ON DELETE` so'zi yo'qligidan va real so'rovlarni "tinglab" ko'rish orqali tasdiqladik). `related_name` — "orqaga qarab" (`bolim.xodimlar.all()`) so'rov yozish imkonini beradi; bitta modelga bir nechta `ForeignKey` bog'langanda, har biriga alohida `related_name` shart. `OneToOneField` — texnik jihatdan, `ForeignKey(unique=True)`dan farq qilmaydi. Ikki model orasidagi bog'lanishning **o'zi haqida** qo'shimcha ma'lumot kerak bo'lganda (`soni`, `narxi_buyurtma_vaqtida` kabi), oddiy `ManyToManyField` emas, ikkita `ForeignKey`li alohida "through" model yoziladi — aynan `BuyurtmaElementi` kabi. Shu bilan, `onlayn_dokon`ning to'liq sxemasi (`Bolim`, `Xodim`, `Mijoz`, `Mahsulot`, `Buyurtma`, `BuyurtmaElementi`) yakunlandi. Keyingi bo'limda — bu modellarga asoslangan **view va template**larni o'qishni, ya'ni ma'lumot bazadan ekranga qanday "oqib" borishini o'rganamiz.

# 4.1. Model maydonlari va migratsiyalar — Python kod PostgreSQL jadvaliga qanday aylanadi

## Bu darsda nimalarni o'rganasiz

- `models.py`da yozilgan bitta oddiy klass, real PostgreSQL jadvaliga qanday aylanishini, boshidan-oxirigacha kuzatasiz
- **Migratsiya fayli** (`0001_initial.py`) — bu, aslida, kim tomonidan yozilgan va nima uchun kerakligini, uni o'qib tushunasiz
- `blank=True` va `null=True` — ikkita **butunlay boshqa** narsa ekanini, real xato orqali isbotlaysiz
- Model maydon turlari (`CharField`, `IntegerField`...) va ularga mos PostgreSQL ustun turlari orasidagi "tarjima jadvali"ni bilib olasiz

## Nazariy qism

### Bitta klass — bitta jadval

`apps/dokon/models.py`ga birinchi modelimizni yozamiz — PostgreSQL darsligidagi `dokon_bazasi`dan tanish `bolimlar` jadvaliga mos:

```python
from django.db import models


class Bolim(models.Model):
    nomi = models.CharField(max_length=50)
    joylashuv = models.CharField(max_length=50, blank=True)

    def __str__(self):
        return self.nomi
```

Buni o'qiymiz: `class Bolim(models.Model)` — `models.Model`dan meros olish, Django'ga "bu klass — oddiy Python klassi emas, bu — **bazadagi jadvalning tavsifi**" deydi. `nomi = models.CharField(max_length=50)` — bu, kelajakdagi jadvalning **bitta ustunini** e'lon qiladi: `CharField` — matn turi (PostgreSQL'dagi `VARCHAR`ga mos), `max_length=50` — uzunlik chegarasi. `__str__` metodi — bu, jadvalning **o'zi emas**, balki qulaylik uchun: Django admin panelida yoki `shell`da, `Bolim` ob'ekti chop etilganda, `<Bolim: object (1)>` o'rniga, tushunarli nom (`<Bolim: Sotuv>`) ko'rsatish uchun.

### `makemigrations` — "reja tuzish", `migrate` — "bajarish"

Django, model o'zgarishini bazaga qo'llashni, **ataylab ikki bosqichga** ajratadi:

```bash
python manage.py makemigrations dokon
```

```
Migrations for 'dokon':
  apps/dokon/migrations/0001_initial.py
    + Create model Bolim
```

`makemigrations` — bazaga **hech qanday** ta'sir qilmaydi! U faqat, `models.py`dagi joriy holatni, oldingi holat bilan solishtirib, farqni **Python fayli sifatida yozib qo'yadi**. Bu faylni ochamiz — bu, sizga hech kim ko'rsatmagan, lekin **doim mavjud bo'lgan** kod:

```python
# apps/dokon/migrations/0001_initial.py
from django.db import migrations, models


class Migration(migrations.Migration):
    initial = True
    dependencies = []

    operations = [
        migrations.CreateModel(
            name="Bolim",
            fields=[
                ("id", models.BigAutoField(auto_created=True, primary_key=True, serialize=False, verbose_name="ID")),
                ("nomi", models.CharField(max_length=50)),
                ("joylashuv", models.CharField(blank=True, max_length=50)),
            ],
        ),
    ]
```

Bu — **avtomatik generatsiya qilingan, lekin oddiy Python kodi** (hech qanday "sehr" yo'q): `operations` — bajarilishi kerak bo'lgan amallar ro'yxati; `migrations.CreateModel(...)` — "yangi jadval yarat" buyrug'i, `models.py`dagi `Bolim` klassidan **avtomatik** o'qib olingan. Diqqat qiling: bizning `models.py`da `id` maydonini umuman yozmagan edik — lekin migratsiyada u **avtomatik qo'shilgan** (`BigAutoField`, `primary_key=True`) — bu, 1-bobda ko'rgan `DEFAULT_AUTO_FIELD` sozlamasining amalda ishlashi.

Endi bu **rejani** haqiqatan bazaga qo'llaymiz:

```bash
python manage.py migrate dokon
```

```
Operations to perform:
  Apply all migrations: dokon
Running migrations:
  Applying dokon.0001_initial... OK
```

### Natijani PostgreSQL'ning o'zidan tekshiramiz

PostgreSQL darsligidan tanish `\d` buyrug'i orqali:

```bash
sudo -u postgres psql -d onlayn_dokon -c "\d dokon_bolim"
```

```
                                 Table "public.dokon_bolim"
  Column   |         Type          | Collation | Nullable |             Default              
-----------+-----------------------+-----------+----------+----------------------------------
 id        | bigint                |           | not null | generated by default as identity
 nomi      | character varying(50) |           | not null | 
 joylashuv | character varying(50) |           | not null | 
Indexes:
    "dokon_bolim_pkey" PRIMARY KEY, btree (id)
```

Bir nechta muhim narsani ko'ramiz: (1) jadval nomi — **`dokon_bolim`**, ya'ni `<app_nomi>_<model_nomi_kichik_harflarda>` — bu, Django'ning **avtomatik** nomlash konvensiyasi (o'zingiz hech qanday nom bermagansiz!); (2) `CharField(max_length=50)` — aynan `character varying(50)`ga aylandi; (3) `id` — `bigint`, `generated by default as identity` (PostgreSQL darsligining 6-bobida ko'rgan `IDENTITY` mexanizmi — aynan shu!).

### `blank=True` — bu, `null=True` EMAS!

Bu — Django'dagi eng ko'p uchraydigan, chalkashtiradigan tafovutlardan biri. Modelimizda `joylashuv = models.CharField(max_length=50, blank=True)` — deb yozgan edik. Buni sinaymiz:

```python
python manage.py shell
```

```python
>>> from apps.dokon.models import Bolim
>>> b1 = Bolim(nomi="Sotuv", joylashuv="")
>>> b1.save()
>>> print("Saqlandi:", b1.id, b1.nomi)
Saqlandi: 1 Sotuv
```

Bo'sh **matn** (`""`) bilan — muammosiz saqlandi. Endi `None` bilan sinaymiz:

```python
>>> b2 = Bolim(nomi="IT", joylashuv=None)
>>> b2.save()
```

```
django.db.utils.IntegrityError: null value in column "joylashuv" of relation "dokon_bolim" violates not-null constraint
DETAIL:  Failing row contains (2, IT, null).
```

**Xato!** Sabab — aynan yuqorida `\d`da ko'rganimiz: `joylashuv` ustuni, PostgreSQL darajasida, **`not null`**. `blank=True` — bu, faqat Django **formalari va admin panelida** (10-11-bobda ko'ramiz) "bu maydonni bo'sh qoldirish mumkin" degan **validatsiya qoidasi** — u bazaga **hech qanday ta'sir qilmaydi**. Baza darajasida `NULL` qiymatga ruxsat berish uchun, alohida, **`null=True`** kerak:

```python
joylashuv = models.CharField(max_length=50, blank=True, null=True)
```

**Muhim qoida (Django'ning o'z tavsiyasi):** matn maydonlari (`CharField`, `TextField`) uchun, odatda, **faqat `blank=True`** ishlatiladi, `null=True` qo'shilMAYdi — chunki Django konvensiyasi bo'yicha, "matn yo'q" holati — `None` emas, balki **bo'sh matn (`""`)** orqali ifodalanadi (aynan biz `b1`da sinaganimizdek). `null=True`ni matn maydonlariga qo'shish — odatda ortiqcha, va ikki xil "bo'shlik" (`None` va `""`) bir vaqtda mavjud bo'lishiga olib kelib, keyinchalik chalkashlik tug'diradi.

## Kodni o'qish mashqi

Quyida — model maydonlari va ularga mos, `\d` orqali ko'rilgan PostgreSQL ustun turlari:

| Model maydoni | PostgreSQL turi |
|---|---|
| `models.CharField(max_length=50)` | `character varying(50)` |
| `models.IntegerField()` | `integer` |
| `models.DecimalField(max_digits=10, decimal_places=2)` | `numeric(10,2)` |
| `models.DateField()` | `date` |
| `models.BooleanField()` | `boolean` |
| `models.TextField()` | `text` |

**Savol:** PostgreSQL darsligining 6-bobida siz `mahsulotlar` jadvalini `narxi NUMERIC(10,2)` turi bilan yaratgan edingiz. Yuqoridagi jadvalga asoslanib, Django modelida bu ustunni qanday e'lon qilasiz?

<details>
<summary>Javobni ko'rish</summary>

```python
narxi = models.DecimalField(max_digits=10, decimal_places=2)
```

`max_digits=10` — jami ruxsat etilgan raqamlar soni (butun va kasr qismi birga), `decimal_places=2` — kasr qismidagi raqamlar soni — bu, aynan PostgreSQL'dagi `NUMERIC(10, 2)`ning ikkita parametriga **to'g'ridan-to'g'ri** mos keladi. Muhim: pul miqdorlari uchun **hech qachon** `FloatField` ishlatilmaydi (aynan PostgreSQL darsligida ham ta'kidlangan, `NUMERIC` — moliyaviy aniqlik uchun, `FLOAT` esa yumaloqlash xatolariga moyil).

</details>

## Amaliy misol

`null=True`ni qo'shib, xatoni tuzatamiz va to'liq tsiklni qayta sinaymiz:

```python
# models.py
class Bolim(models.Model):
    nomi = models.CharField(max_length=50)
    joylashuv = models.CharField(max_length=50, blank=True, null=True)

    def __str__(self):
        return self.nomi
```

```bash
python manage.py makemigrations dokon
```

```
Migrations for 'dokon':
  apps/dokon/migrations/0002_alter_bolim_joylashuv.py
    ~ Alter field joylashuv on bolim
```

Diqqat qiling: bu safar `0002_...` fayli — **`0001`ni o'zgartirmadi**, balki **yangi, qo'shimcha** migratsiya yaratdi. Bu — muhim tamoyil: migratsiyalar, PostgreSQL darsligining 20-bobida o'rgangan **WAL** kabi, o'zgarishlar **tarixi**ni tashkil qiladi — hech qachon eskisi "qayta yozilmaydi", faqat yangi "qadam" qo'shiladi.

```bash
python manage.py migrate dokon
```

```
Applying dokon.0002_alter_bolim_joylashuv... OK
```

Endi `None` bilan qayta sinaymiz:

```python
>>> b2 = Bolim(nomi="IT", joylashuv=None)
>>> b2.save()
>>> print("Muvaffaqiyatli:", b2.id, b2.nomi, b2.joylashuv)
Muvaffaqiyatli: 3 IT None
```

Endi ishladi — chunki `null=True` qo'shilgach, PostgreSQL ustuni ham `nullable`ga aylandi.

**Diqqat qiling: `id` — `2` emas, `3`!** Bu — xato emas, balki PostgreSQL'ning **`IDENTITY`/sequence** mexanizmi haqida muhim, real hayotiy dalil (PostgreSQL darsligining 6-bobida ko'rgan mavzu, endi amalda): yuqorida, `null=True`siz holatda, `IT`ni saqlashga **urinish muvaffaqiyatsiz** tugagan edi (`IntegrityError`) — lekin PostgreSQL, urinishdan oldin, sequence'dan `id=2`ni allaqachon "band qilib qo'ygan" edi. Tranzaksiya bekor bo'lgach ham, **sequence orqaga qaytmaydi** — shuning uchun keyingi muvaffaqiyatli yozuv, `2`ni emas, `3`ni oladi. Xulosa: PostgreSQL'da `id`larda "teshik" (gap) bo'lishi — normal holat, bu xato belgisi emas.

## Keng tarqalgan xatolar

**Xato 1:** `models.py`ni o'zgartirgach, `makemigrations`ni unutib, to'g'ridan-to'g'ri `migrate`ga o'tish.
❌ `migrate` — faqat **mavjud** migratsiya fayllarini qo'llaydi; agar yangi o'zgarish uchun fayl hali yaratilmagan bo'lsa, `migrate` **hech narsa qilmaydi** ("No migrations to apply"), va baza eski holatda qolib ketadi.
✅ Har doim, model o'zgarishidan keyin, ketma-ketlikni saqlang: avval `makemigrations`, keyin `migrate`.

**Xato 2:** Migratsiya faylini qo'lda, to'g'ridan-to'g'ri tahrirlash.
❌ Migratsiya fayllari — `makemigrations` tomonidan **avtomatik** yaratiladi va, ideal holda, qo'lda tahrirlanmasligi kerak (murakkab, maxsus holatlar bundan mustasno) — aks holda, fayl va haqiqiy `models.py` holati orasida **nomuvofiqlik** paydo bo'lishi mumkin.
✅ Model o'zgarishi kerak bo'lsa — `models.py`ni o'zgartiring, so'ng `makemigrations`ni qayta ishga tushiring; u sizning o'zgarishingizni avtomatik "ushlab", yangi migratsiya yaratadi.

**Xato 3:** `null=True`ni har bir maydonga, "xavfsizroq bo'ladi" deb, o'ylab ko'rmasdan qo'shaverish.
❌ Bu, keyinchalik, "qiymat `None`mi yoki bo'sh matnmi?" degan keraksiz tekshiruvlarni ko'paytiradi va kodni murakkablashtiradi.
✅ `null=True`ni faqat, maydon **haqiqatan** "qiymat umuman yo'q" holatini ifodalashi kerak bo'lganda qo'shing (masalan, `DateField` — "hali sana belgilanmagan"); matn maydonlari uchun, odatda, faqat `blank=True` yetarli.

## Mashq/topshiriq

> **Eslatma:** quyidagi uchta mashq — mustaqil sinov maydonchasi. Ularni bajarib bo'lgach, keyingi darsda (4.2) `Bolim` modeli yana **toza holatda** (faqat `nomi` va `joylashuv`) davom etadi — chunki 4.2'ning maqsadi, `tavsif`/`manager_soni` emas, balki modellar orasidagi **bog'lanishlar**ni o'qishdir. Shuning uchun, mashqlardan keyin, o'zingiz ham xohlasangiz, qo'shgan maydonlaringizni `models.py`dan olib tashlab, yangi `makemigrations`/`migrate` bilan loyihani "tozalab qo'yishingiz" mumkin — bu ham, real loyihalarda tez-tez uchraydigan, oddiy amaliyot.

**(Oson)** `Bolim` modeliga yangi maydon qo'shing: `tavsif = models.TextField(blank=True)`. `makemigrations` va `migrate`ni ishga tushiring, so'ng `\d dokon_bolim` orqali yangi ustun `text` turida qo'shilganini tasdiqlang.

**(O'rtacha)** `python manage.py shell` orqali, `Bolim.objects.create(nomi="Moliya")` (bu safar `joylashuv`siz, umuman ko'rsatmasdan) qatorini bajaring. Bu ishlaydimi? Natijada `joylashuv`ning qiymati — `''` (bo'sh matn) bo'ladimi yoki `None`mi? Nega (maslahat: bir oz yuqorida, aynan shu maydonga `null=True` qo'shgan edik — bu, `CharField`ning **standart qiymatini o'zi ham o'zgartiradi**)?

**(Qiyin)** `Bolim` modeliga yangi, **majburiy** (`blank=False`, ya'ni standart) maydon qo'shing: `manager_soni = models.IntegerField()`. `makemigrations`ni ishga tushirishga urinib ko'ring — Django sizdan **qo'shimcha savol** so'raydi (chunki jadvalda allaqachon qatorlar bor, va yangi majburiy ustun uchun standart qiymat kerak). Django taklif qilgan variantlardan birini tanlab, jarayonni yakunlang.

Sabab — Django'ning "standart qiymatni tanlash" qoidasi, `default` aniq ko'rsatilmaganda, **maydonning `null` holatiga qarab o'zgaradi**: agar maydon `null=True` bo'lsa (bizning holatimizda — aynan shunday, chunki bir oz yuqorida, "Amaliy misol"da, `joylashuv`ga `null=True` qo'shgan edik), Django standart qiymat sifatida `None`ni tanlaydi. Agar maydon `null=False` bo'lganida (darsning boshida, `null=True` qo'shishdan OLDIN bo'lgani kabi), standart qiymat `''` (bo'sh matn) bo'lar edi. Buni to'g'ridan-to'g'ri tekshirish mumkin:

```python
>>> from django.db import models
>>> f1 = models.CharField(max_length=50, blank=True, null=True)
>>> f2 = models.CharField(max_length=50, blank=True)
>>> f1.set_attributes_from_name("x"); f2.set_attributes_from_name("y")
>>> f1.get_default(), f2.get_default()
(None, '')
```

**Xulosa:** `null=True` qo'shish — nafaqat bazada `NULL`ga ruxsat beradi, balki Django'ning o'zi ham, "qiymat ko'rsatilmasa nima qilaman" degan savolga, **boshqacha javob** beradi. Bu — 3-mashqdagi kabi, "kichik" o'zgarish (`null=True` qo'shish) aslida ko'proq narsaga ta'sir qilishi mumkinligining yana bir misoli.

## Qisqacha xulosa

`models.py`dagi har bir klass — bitta PostgreSQL jadvaliga, har bir maydon — bitta ustunga aylanadi; bu jarayon ikki bosqichli: `makemigrations` (Python kodidan **reja** — migratsiya fayli — yaratish) va `migrate` (rejani haqiqatan bazaga **qo'llash**). Migratsiya fayllari — avtomatik yaratiladigan, lekin **oddiy, o'qish mumkin** bo'lgan Python kodi, va ular hech qachon "qayta yozilmaydi" — faqat yangi fayllar sifatida, tarix ko'rinishida to'planadi. `blank=True` (forma/validatsiya darajasi) va `null=True` (baza darajasi) — ikki **butunlay boshqa** narsa, va buni farqlamaslik, `IntegrityError` kabi real xatolarga olib keladi. Keyingi darsda — modellar orasidagi **bog'lanishlar** (`ForeignKey`, `ManyToManyField`) ni yozib, ulardan real ER-diagram "o'qib chiqarish"ni o'rganamiz — va butun `onlayn_dokon` sxemasini yakunlaymiz.

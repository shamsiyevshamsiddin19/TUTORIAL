# 1.1. `settings.py`ni chuqur o'qish — loyihaning "miyasi"

## Bu darsda nimalarni o'rganasiz

- `INSTALLED_APPS`, `MIDDLEWARE`, `TEMPLATES` — uchta eng muhim ro'yxatni satrma-satr o'qiysiz
- `MIDDLEWARE` ro'yxatidagi **tartib nega muhimligini** amalda ko'rasiz
- `settings.py`dagi qolgan sozlamalarni (parol tekshiruvi, til, statik fayllar) tushunasiz
- Yangi sozlamani qo'shish uchun **qayerga** yozish kerakligini bilib olasiz

## Nazariy qism

### `INSTALLED_APPS` — "kim ishtirok etadi"

```python
INSTALLED_APPS = [
    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
    "django.contrib.sessions",
    "django.contrib.messages",
    "django.contrib.staticfiles",
]
```

Bu — Django'ga "loyihada qaysi ilovalar (app'lar) ishtirok etishi"ni aytadigan ro'yxat. Har bir yozuv — bu, aslida, Python **paketining yo'li** (import path). Standart olti app — Django'ning o'zi bilan birga keladigan, tayyor funksionallik: `admin` (boshqaruv paneli), `auth` (foydalanuvchi/parol tizimi), `contenttypes` (Django'ning ichki "qaysi model qaysi turga tegishli" mexanizmi), `sessions` (foydalanuvchi sessiyalari — masalan, kim tizimga kirgani), `messages` (bir martalik xabarlar — "muvaffaqiyatli saqlandi" kabi), `staticfiles` (CSS/JS/rasm fayllarni boshqarish).

**Muhim qoida:** agar biror app shu ro'yxatda **bo'lmasa**, Django uning `models.py`sini "ko'rmaydi" — ya'ni, u app ichida qancha to'g'ri kod yozilmasin, Django uni butunlay e'tiborsiz qoldiradi. Bu — 2-bobda o'zimiz app yaratganimizda, birinchi navbatda duch keladigan qoida.

### `MIDDLEWARE` — "nazoratchilar zanjiri", va nega TARTIB muhim

```python
MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",
    "django.contrib.sessions.middleware.SessionMiddleware",
    "django.middleware.common.CommonMiddleware",
    "django.middleware.csrf.CsrfViewMiddleware",
    "django.contrib.auth.middleware.AuthenticationMiddleware",
    "django.contrib.messages.middleware.MessageMiddleware",
    "django.middleware.clickjacking.XFrameOptionsMiddleware",
]
```

Middleware — bu, **har bir** so'rov (request) va javob (response) ustidan, ketma-ket o'tadigan "nazoratchilar zanjiri" (bu haqda 3-bobda, so'rov hayot yo'lini kuzatganda, amalda ko'ramiz). Hozircha eng muhim narsani tushunib olamiz: **bu ro'yxatning tartibi tasodifiy emas**.

So'rov kelganda, u ro'yxat bo'ylab **yuqoridan pastga** o'tadi; javob esa — **pastdan yuqoriga**, teskari tartibda. Masalan, `SessionMiddleware` — `AuthenticationMiddleware`dan **oldin** turishi shart, chunki "foydalanuvchi kim ekanini aniqlash" (`Authentication`) uchun, avval "sessiya ma'lumotini o'qish" (`Session`) kerak — aks holda, `Authentication` qaysi foydalanuvchi ekanini bilish uchun hech qanday ma'lumotga ega bo'lmaydi.

### Kodni satrma-satr o'qiymiz: nega `CsrfViewMiddleware` — `AuthenticationMiddleware`dan OLDIN?

Bu — chuqurroq savol, lekin javobi oddiy mantiqqa asoslangan: `CsrfViewMiddleware` — forma orqali yuborilgan har bir so'rovda maxsus "xavfsizlik tokeni" borligini tekshiradi (soxta so'rovlardan himoya). Bu tekshiruv, foydalanuvchi **kim ekanidan qat'iy nazar** bajarilishi kerak — ya'ni, `Authentication` hali ishlamagan bo'lsa ham, CSRF himoyasi allaqachon ishlab turishi kerak. Shuning uchun u ro'yxatda yuqoriroqda joylashgan.

### `TEMPLATES` — shablonlarni qanday topish kerakligi

```python
TEMPLATES = [
    {
        "BACKEND": "django.template.backends.django.DjangoTemplates",
        "DIRS": [],
        "APP_DIRS": True,
        "OPTIONS": {
            "context_processors": [
                "django.template.context_processors.request",
                "django.contrib.auth.context_processors.auth",
                "django.contrib.messages.context_processors.messages",
            ],
        },
    },
]
```

- `"DIRS": []` — hozircha bo'sh: bu, "loyiha darajasidagi, umumiy shablonlar qayerda" degan qo'shimcha yo'llar ro'yxati (7-bobda to'ldiramiz).
- `"APP_DIRS": True` — bu **juda muhim**: Django'ga, har bir app ichidagi `templates/` papkasini **avtomatik** qidirishni buyuradi. Shuning uchun, keyinroq, `blog/templates/blog/sahifa.html` kabi fayl yaratsangiz, uni alohida ro'yxatdan o'tkazish shart emas — Django uni o'zi topadi.
- `context_processors` — bu, **har bir** shablonga, so'ralmasdan ham, avtomatik taqdim etiladigan o'zgaruvchilar ro'yxati (masalan, `request` — joriy so'rov ob'ekti; `auth` — joriy foydalanuvchi). Bu, nega shablon ichida hech qanday qo'shimcha kod yozmasdan ham `{{ user }}` yoki `{{ request }}`ni ishlatish mumkinligini tushuntiradi (7-bobda ko'ramiz).

### `ROOT_URLCONF` va `WSGI_APPLICATION` — "ko'rsatkichlar"

```python
ROOT_URLCONF = "config.urls"
WSGI_APPLICATION = "config.wsgi.application"
```

Bu ikki qator — **string** ko'rinishidagi Python yo'llari, boshqa fayllarga ishora qiluvchi "ko'rsatkichlar". `ROOT_URLCONF = "config.urls"` — Django'ga "URL manzillarini `config/urls.py`dan qidir" deydi (agar bu faylni boshqa nomga o'zgartirsangiz — masalan `config/marshrutlar.py` — shu qatorni ham mos ravishda o'zgartirishingiz shart, aks holda Django uni topolmaydi).

### Qolgan sozlamalar — qisqacha

```python
AUTH_PASSWORD_VALIDATORS = [
    {"NAME": "django.contrib.auth.password_validation.UserAttributeSimilarityValidator"},
    {"NAME": "django.contrib.auth.password_validation.MinimumLengthValidator"},
    {"NAME": "django.contrib.auth.password_validation.CommonPasswordValidator"},
    {"NAME": "django.contrib.auth.password_validation.NumericPasswordValidator"},
]

LANGUAGE_CODE = "en-us"
TIME_ZONE = "UTC"
USE_I18N = True
USE_TZ = True

STATIC_URL = "static/"

DEFAULT_AUTO_FIELD = "django.db.models.BigAutoField"
```

`AUTH_PASSWORD_VALIDATORS` — foydalanuvchi ro'yxatdan o'tganda, parolining "kuchli"ligini tekshiruvchi qoidalar ro'yxati (11-bobda amalda ko'ramiz). `TIME_ZONE = "UTC"` — barcha sana/vaqt ma'lumotlari, bazada, **UTC** vaqt zonasida saqlanadi (bu — ko'p mamlakatli loyihalar uchun eng xavfsiz standart). `STATIC_URL = "static/"` — CSS/JS fayllarga qanday **manzil orqali** murojaat qilinishini belgilaydi (masalan, `style.css` fayli, brauzerda `/static/style.css` manzilida ochiladi). `DEFAULT_AUTO_FIELD` — har bir yangi model uchun, agar biz aniq ko'rsatmasak, avtomatik yaratiladigan **ID maydonining turi** (4-bobda modellar bilan ishlaganda muhim bo'ladi).

## Kodni o'qish mashqi

Quyida — o'zgartirilgan `MIDDLEWARE` ro'yxati (`SessionMiddleware`, ataylab, `AuthenticationMiddleware`dan **keyinga** ko'chirilgan):

```python
MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",
    "django.middleware.common.CommonMiddleware",
    "django.middleware.csrf.CsrfViewMiddleware",
    "django.contrib.auth.middleware.AuthenticationMiddleware",
    "django.contrib.sessions.middleware.SessionMiddleware",
    "django.contrib.messages.middleware.MessageMiddleware",
    "django.middleware.clickjacking.XFrameOptionsMiddleware",
]
```

**Savol:** Yuqorida o'qigan mantiqqa asoslanib, bu o'zgartirish qanday muammoga olib kelishi mumkin? Va: `python manage.py check` bu xatoni **darhol** ushlaydimi? (Hali sinamasdan, faqat mantiq bilan bashorat qiling.)

<details>
<summary>Javobni ko'rish</summary>

`AuthenticationMiddleware` — "joriy foydalanuvchi kim" ekanini aniqlash uchun, `request.session`ga (sessiya ma'lumotiga) tayanadi. Agar `SessionMiddleware` undan **keyin** ishga tushsa, `AuthenticationMiddleware` ishlagan paytda, sessiya ma'lumoti hali **mavjud bo'lmaydi**. Ammo bu — `python manage.py check`ning tekshiruv doirasiga **kirmaydi** (`check`, asosan, sozlamalar va app konfiguratsiyasining statik to'g'riligini tekshiradi, middleware **tartibini** emas) — shuning uchun `check` xato bermaydi, xato faqat **haqiqiy so'rov kelganda**, kod haqiqatan bajarilganda paydo bo'ladi. Buni pastdagi "Amaliy misol"da haqiqatan sinab ko'ramiz — bu, "statik tekshiruv" va "runtime (bajarilish paytidagi) xato" orasidagi farqni ko'rsatuvchi muhim misol.

</details>

## Amaliy misol

Yuqoridagi o'zgarishni haqiqatan kiritib, natijani tekshiramiz. Avval `check`:

```bash
python manage.py check
```

```
System check identified no issues (0 silenced).
```

Bashoratimizdek — `check` hech qanday muammo ko'rmadi. Endi serverni ishga tushirib, `/admin/` manziliga haqiqiy so'rov yuboramiz:

```bash
python manage.py runserver
curl http://127.0.0.1:8000/admin/
```

```
Internal Server Error: /admin/
Traceback (most recent call last):
  File ".../django/contrib/auth/middleware.py", line 33, in process_request
    raise ImproperlyConfigured(
django.core.exceptions.ImproperlyConfigured: The Django authentication middleware
requires session middleware to be installed. Edit your MIDDLEWARE setting to insert
'django.contrib.sessions.middleware.SessionMiddleware' before
'django.contrib.auth.middleware.AuthenticationMiddleware'.
```

Bu — juda o'rgatuvchi natija, va bashoratimizdan ham **aniqroq**: server o'zi muammosiz ishga tushdi (`check` xato bermagani uchun), lekin `/admin/`ga birinchi haqiqiy so'rov kelgan zahoti, `AuthenticationMiddleware`ning o'zi (`django/contrib/auth/middleware.py` ichida) sessiyani topolmay, aniq, tushunarli xato (`ImproperlyConfigured`) tashladi — hatto to'g'ri tartib qanday bo'lishi kerakligini ham xato matnida ko'rsatib. **Xulosa:** `python manage.py check` — barcha xatolarni ushlay olmaydi; ba'zi muammolar faqat kod haqiqatan **ishga tushganda** (runtime'da) namoyon bo'ladi — bu, nega "server ishga tushdi" degani "hamma narsa to'g'ri" degani emasligini ko'rsatadi. Middleware'ni asl tartibiga qaytaring va `/admin/` yana xatosiz ochilishini tasdiqlang.

## Keng tarqalgan xatolar

**Xato 1:** Yangi app yaratib, uni `INSTALLED_APPS`ga qo'shishni unutish (2-bobda batafsil, lekin shu yerda ham eslatib o'tamiz).
❌ App'ning `models.py`, `admin.py` fayllari yozilgan, lekin Django ularni "ko'rmaydi" — chunki app ro'yxatda yo'q.
✅ Har doim, yangi app yaratilgach, birinchi navbatda `INSTALLED_APPS`ni tekshiring.

**Xato 2:** `MIDDLEWARE` ro'yxatiga o'zingiznikini qo'shganda, uni ro'yxatning **oxiriga** qo'yaverish (o'ylab ko'rmasdan).
❌ Agar sizning middleware'ingiz `request.user`dan foydalansa, lekin u `AuthenticationMiddleware`dan **oldin** joylashtirilsa — `request.user` hali mavjud bo'lmaydi.
✅ Yangi middleware qo'shishdan oldin, unga nima **kerakligini** (masalan, sessiya, autentifikatsiya) aniqlang, va uni shu bog'liqliklardan **keyin** joylashtiring.

**Xato 3:** `settings.py`dagi biror ro'yxatni (masalan, `INSTALLED_APPS`) qo'lda tahrirlaganda, oxiriga vergul qo'yishni unutish.
❌ `"apps.blog"` dan keyin vergul bo'lmasa, Python bu qatorni oldingi qator bilan **avtomatik birlashtirib** (string concatenation) tushunishi mumkin, bu esa xilma-xil, tushunish qiyin xatolarga olib keladi.
✅ Python ro'yxatlarida, oxirgi elementdan keyin ham vergul qoldirish (`trailing comma`) — xavfsiz odat, chunki bu, keyingi element qo'shilganda, diff'ni ham tozaroq qiladi.

## Mashq/topshiriq

**(Oson)** `settings.py`da `LANGUAGE_CODE = "en-us"`ni `"uz"`ga o'zgartiring va `TIME_ZONE = "UTC"`ni `"Asia/Tashkent"`ga o'zgartiring. `python manage.py check` orqali xatosiz ekanini tasdiqlang.

**(O'rtacha)** `INSTALLED_APPS`dan `"django.contrib.admin"`ni vaqtincha olib tashlang (o'chirib qo'ying yoki `#` bilan izohga oling) va `python manage.py runserver`ni ishga tushirishga urinib ko'ring. Chiqqan xatoni o'qib, nima uchun bunday bo'lganini tushuntiring.

**(Qiyin)** `MIDDLEWARE`dan `"django.middleware.csrf.CsrfViewMiddleware"`ni butunlay olib tashlang. `python manage.py check`ni ishga tushiring — bu safar xato chiqmasligi mumkin (chunki CSRF, admin kabi qattiq talab qilinmaydi). Nega bu middleware'ning yo'qligi **darhol** xato bermasligini, lekin baribir nega uni **hech qachon** olib tashlash tavsiya etilmasligini (xavfsizlik nuqtai nazaridan) tushuntiring.

Shuning uchun Django buni **majburiy tekshirmaydi** (chunki ba'zi maxsus holatlarda ataylab o'chirilishi mumkin), lekin standart amaliyot sifatida **hech qachon** olib tashlanmasligi kerak.

## Qisqacha xulosa

`settings.py` — bir nechta muhim ro'yxatdan iborat: `INSTALLED_APPS` (kim ishtirok etadi), `MIDDLEWARE` (so'rov/javob ustidan qat'iy **tartibda** ishlaydigan nazoratchilar zanjiri — tartib buzilsa, Django buni system check orqali darhol aniqlaydi), `TEMPLATES` (shablonlarni qanday topish va ularga nima avtomatik taqdim etilishi). `ROOT_URLCONF` va `WSGI_APPLICATION` — boshqa fayllarga ishora qiluvchi "ko'rsatkichlar" bo'lib, ularni o'zgartirsangiz, ishora qilingan faylni ham mos ravishda o'zgartirish kerak. Keyingi darsda — bu faylni shunchaki o'qish emas, balki haqiqatan **o'zgartirib**, bazani SQLite'dan real PostgreSQL'ga o'tkazamiz — bu, "kodni o'qib, keyin ongli ravishda o'zgartirish" mahoratining birinchi jiddiy sinovi bo'ladi.

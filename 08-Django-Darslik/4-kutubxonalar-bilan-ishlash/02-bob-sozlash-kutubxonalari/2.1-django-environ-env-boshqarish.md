# 2.1. django-environ bilan .env orqali maxfiy sozlamalarni boshqarish

## Bu darsda nimalarni o'rganasiz

- Nega `SECRET_KEY`, parol kabi maxfiy ma'lumotlarni to'g'ridan-to'g'ri `settings.py`ga yozib qo'ymaslik kerakligini tushunasiz
- `django-environ`ni o'rnatib, `settings.py` bilan integratsiya qilishni o'rganasiz
- `.env` faylidan turli tur (bool, int, ro'yxat, `DATABASE_URL`) o'qishni bilib olasiz
- `.env` faylini Git'dan qanday yashirishni va o'rniga namuna (`.env.example`) qoldirishni o'rganasiz

## Nazariy qism

### Nega maxfiy ma'lumotlarni kodga yozib bo'lmaydi

`django-admin startproject` orqali yaratilgan `settings.py`da, standart holda, `SECRET_KEY` to'g'ridan-to'g'ri kod ichida yozilgan bo'ladi:

```python
# settings.py — YOMON amaliyot
SECRET_KEY = "django-insecure-x7k9m2p4q8..."
DATABASES = {
    "default": {
        "PASSWORD": "juda_maxfiy_parol123",
    }
}
```

Bu — ikkita jiddiy muammo tug'diradi: (1) loyiha Git'ga yuklanganda, bu maxfiy qiymatlar **butun versiyalash tarixida** abadiy qoladi (hatto keyin o'chirilsa ham, eski commit'larda saqlanib qoladi); (2) development va production muhitlarida **turli** qiymatlar (masalan turli baza parollari) kerak bo'lganda, kodni har safar qo'lda o'zgartirish kerak bo'ladi.

Yechim — bu qiymatlarni kod'dan **ajratib**, alohida, Git'ga qo'shilmaydigan `.env` faylida saqlash.

### django-environ o'rnatish va asosiy foydalanish

```bash
pip install django-environ
```

```python
# settings.py
import environ

env = environ.Env()
environ.Env.read_env(BASE_DIR / ".env")

SECRET_KEY = env("SECRET_KEY")
DEBUG = env.bool("DEBUG", default=False)
```

Loyiha ildizida `.env` fayli (oddiy matn, `KALIT=qiymat` formatida):

```
# .env
SECRET_KEY=django-insecure-x7k9m2p4q8...
DEBUG=True
```

`env("SECRET_KEY")` — `.env` faylidan `SECRET_KEY` qiymatini **matn (string)** sifatida o'qiydi. Agar `.env`da bunday kalit bo'lmasa va `default` berilmagan bo'lsa, `environ.ImproperlyConfigured` xatosi chiqadi — bu ataylab shunday: maxfiy qiymat unutilib qolishining oldini oladi.

### Tur konvertatsiyalar

`.env` fayldagi hamma narsa — matn, lekin Python kodida ko'pincha `bool`, `int`, ro'yxat kerak bo'ladi. `django-environ` buni avtomatik bajaradi:

| Metod | .env qatori | Python natijasi |
|---|---|---|
| `env("KEY")` | `KEY=salom` | `"salom"` (str) |
| `env.bool("DEBUG")` | `DEBUG=True` | `True` (bool) |
| `env.int("PORT")` | `PORT=5432` | `5432` (int) |
| `env.list("ALLOWED_HOSTS")` | `ALLOWED_HOSTS=localhost,127.0.0.1` | `["localhost", "127.0.0.1"]` |
| `env.db()` | `DATABASE_URL=postgres://user:parol@localhost:5432/baza` | Django `DATABASES["default"]` uchun to'liq lug'at |

`env.db()` — ayniqsa qulay: bitta `DATABASE_URL` qatoridan, Django ORM'ga kerakli barcha kalitlarni (`ENGINE`, `NAME`, `USER`, `PASSWORD`, `HOST`, `PORT`) avtomatik ajratib beradi.

```python
DATABASES = {
    "default": env.db("DATABASE_URL"),
}
```

### .env faylini himoya qilish

`.env` — **hech qachon** Git'ga qo'shilmasligi kerak:

```
# .gitignore
.env
```

Buning o'rniga, jamoadoshlaringiz (yoki kelajakdagi o'zingiz) qaysi o'zgaruvchilar kerakligini bilishi uchun, **qiymatlarsiz**, faqat kalit nomlari yozilgan `.env.example` faylini Git'ga qo'shib qoldiring:

```
# .env.example
SECRET_KEY=
DEBUG=True
DATABASE_URL=postgres://user:parol@localhost:5432/dbnomi
```

## Amaliy misol

`onlayn_dokon` loyihasi uchun to'liq sozlash:

```bash
pip install django-environ
```

```
# .env
SECRET_KEY=django-insecure-onlayn-dokon-maxfiy-kalit-2026
DEBUG=True
ALLOWED_HOSTS=localhost,127.0.0.1
DATABASE_URL=postgres://dokon_user:xavfsiz_parol@localhost:5432/dokon_bazasi
```

```
# .env.example  (Git'ga qo'shiladi, .env esa qo'shilmaydi)
SECRET_KEY=
DEBUG=True
ALLOWED_HOSTS=localhost,127.0.0.1
DATABASE_URL=postgres://user:parol@localhost:5432/dbnomi
```

```python
# onlayn_dokon/settings.py
from pathlib import Path
import environ

BASE_DIR = Path(__file__).resolve().parent.parent

env = environ.Env()
environ.Env.read_env(BASE_DIR / ".env")

SECRET_KEY = env("SECRET_KEY")
DEBUG = env.bool("DEBUG", default=False)
ALLOWED_HOSTS = env.list("ALLOWED_HOSTS", default=[])

DATABASES = {
    "default": env.db("DATABASE_URL"),
}
```

```
# .gitignore
.env
venv/
```

Endi `git status` bajarilsa, `.env` fayli ko'rinmaydi (e'tiborsiz qoldirilgan), lekin `.env.example` — Git tomonidan kuzatiladi, shunday qilib jamoadoshingiz loyihani klonlab olganda, qaysi o'zgaruvchilarni o'zi to'ldirishi kerakligini darhol biladi.

## Keng tarqalgan xatolar

**Xato 1:** `.env` faylini tasodifan Git'ga qo'shib yuborish.

❌ `.gitignore`ga `.env` qo'shilmagan, va `git add .` bilan u ham commit qilinib ketgan — endi `SECRET_KEY` va baza paroli ochiq repozitoriyda (yoki hatto yopiq repozitoriyda ham, versiyalash tarixida abadiy) qoladi.

✅ `.env` faylini yaratishning birinchi qadami — darhol `.gitignore`ga qo'shish. Agar allaqachon commit qilib yuborilgan bo'lsa, faqat faylni o'chirish yetarli emas — `SECRET_KEY`ni **almashtirish** va (agar mumkin bo'lsa) Git tarixini tozalash kerak.

**Xato 2:** `env()`ga `default` bermasdan, lekin `.env` faylini serverga ko'chirishni unutish.

❌ `SECRET_KEY = env("SECRET_KEY")` — `.env` fayli production serverda mavjud emas (chunki u Git orqali ko'chirilmagan, to'g'ri!) — lekin serverga qo'lda ham qo'yilmagan. Natijada `manage.py runserver` `ImproperlyConfigured` xatosi bilan to'xtaydi.

✅ `.env`ni har bir yangi muhitga (development kompyuter, production server) **qo'lda va xavfsiz** (masalan SSH orqali, Git orqali emas) ko'chirish kerakligini jamoada kelishib oling — bu, "nega .env ishlamayapti" degan tez-tez uchraydigan chalkashlikning oldini oladi.

**Xato 3:** `DEBUG=True`ni production serverning `.env` faylida ham qoldirib qo'yish.

❌ Development uchun qulay bo'lgan `DEBUG=True` production serverga ham xuddi shu holda ko'chirilsa — xato yuz berganda, Django foydalanuvchiga **to'liq traceback** (fayl yo'llari, kod, hatto sozlamalar) ko'rsatadi, bu jiddiy xavfsizlik zaifligi.

✅ Har bir muhit uchun **alohida** `.env` (development uchun `DEBUG=True`, production uchun `DEBUG=False`) yuriting — bu mavzuni keyingi darsda (2.2) chuqurroq ko'ramiz.

## Mashq/topshiriq

**(Oson)** `django-environ`ni o'rnating, `.env` faylida `SAYT_NOMI=Onlayn Do'kon` qatorini yozing, va Django shell orqali `env("SAYT_NOMI")` qiymatini chiqarib ko'ring.

**(O'rtacha)** `.env`ga `MAHSULOT_SAHIFADA=20` qatorini qo'shing va `settings.py`da `env.int("MAHSULOT_SAHIFADA", default=10)` orqali o'qing. `.env`dagi qatorni vaqtincha o'chirib, kodni qayta ishga tushiring — `default=10` ishlaganini tasdiqlang.

**(Qiyin)** `.env`ga `DATABASE_URL=postgres://dokon_user:parol123@localhost:5432/dokon_bazasi` qatorini yozing va `env.db("DATABASE_URL")` natijasini Django shell orqali chiqarib ko'ring — natija lug'atida qanday kalitlar (`ENGINE`, `NAME`, `USER`, `PASSWORD`, `HOST`, `PORT`) borligini va ularning qiymatlarini aniqlang.

## Qisqacha xulosa

`django-environ` — maxfiy va muhitga bog'liq sozlamalarni (`SECRET_KEY`, baza parollari, `DEBUG`) kod'dan ajratib, alohida, Git'ga qo'shilmaydigan `.env` faylida saqlash imkonini beradi; `env.bool()`, `env.int()`, `env.list()`, `env.db()` kabi metodlar matn ko'rinishidagi qiymatlarni to'g'ri Python turiga avtomatik aylantiradi. `.env`ni `.gitignore`ga qo'shish va o'rniga qiymatlarsiz `.env.example` qoldirish — xavfsizlik va jamoaviy ishlashning standart amaliyoti. Keyingi darsda — bitta `.env` fayl bilan cheklanmasdan, development va production uchun **butunlay alohida** sozlamalar strukturasini qanday qurishni ko'ramiz.

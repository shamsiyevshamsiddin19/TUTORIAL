# 9.1. Barcha kutubxonalarni onlayn_dokon'ga birlashtirib integratsiya qilish

## Bu darsda nimalarni o'rganasiz

- Bu darslik davomida qo'shilgan 14 ta kutubxonaning **hammasi birga** qanday ishlashini ko'rasiz
- `INSTALLED_APPS`, `MIDDLEWARE`, `AUTHENTICATION_BACKENDS` ro'yxatlarida **tartib nega muhimligini** yana bir bor, yaxlit holda tasdiqlaysiz
- Kutubxonalar orasidagi **yashirin bog'liqliklarni** (masalan, biri ikkinchisining ishlashiga ta'sir qilishi) aniqlashni o'rganasiz
- Yaxlit, ishlaydigan `settings/` paketini qanday ko'rinishga ega bo'lishini bir joyda ko'rasiz

## Nazariy qism

### Nega alohida "birlashtirish" darsi kerak

Har bir oldingi bobda, biz **bittalab** kutubxona qo'shdik — bu, har birini alohida tushunish uchun to'g'ri yondashuv edi. Lekin real loyihada, hammasi **bir vaqtning o'zida**, bitta `settings.py`da yashaydi, va ular orasida ba'zan **kutilmagan** o'zaro ta'sirlar bo'ladi: ikkita middleware'ning tartibi to'qnashishi, ikkita kutubxonaning bir xil sozlamani talab qilishi, yoki birining ishlashi ikkinchisiga bog'liq bo'lishi mumkin. Shuning uchun, hammasini **bir joyga yig'ib**, yaxlit holda ko'rib chiqish — ularning **birga** to'g'ri ishlashini tasdiqlashning yagona yo'li.

### Tartib nega har doim muhim: uchta ro'yxat

Bu darslik davomida uch marta "tartib muhim" degan ogohlantirish uchradi — keling, ularni **birga** ko'ramiz:

**`AUTHENTICATION_BACKENDS`** (4.2-darsdan): `axes` birinchi, keyin standart, keyin `allauth`:

```python
AUTHENTICATION_BACKENDS = [
    "axes.backends.AxesStandaloneBackend",              # 1. birinchi — bloklashni tekshiradi
    "django.contrib.auth.backends.ModelBackend",         # 2. standart — admin uchun
    "allauth.account.auth_backends.AuthenticationBackend",  # 3. — sayt foydalanuvchilari uchun
]
```

**`MIDDLEWARE`** (3.2, 4.2, 6.2-darslardan): bir nechta kutubxona o'z middleware'ini qo'shadi, va ularning **har biri** o'z qoidasiga ega:

```python
MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",
    "corsheaders.middleware.CorsMiddleware",              # CommonMiddleware'dan OLDIN (6.2)
    "whitenoise.middleware.WhiteNoiseMiddleware",          # SecurityMiddleware'dan DARHOL keyin (3.2)
    "django.contrib.sessions.middleware.SessionMiddleware",
    "django.middleware.common.CommonMiddleware",
    "django.middleware.csrf.CsrfViewMiddleware",
    "django.contrib.auth.middleware.AuthenticationMiddleware",
    "allauth.account.middleware.AccountMiddleware",        # allauth uchun (4.1)
    "django.contrib.messages.middleware.MessageMiddleware",
    "django.middleware.clickjacking.XFrameOptionsMiddleware",
    "axes.middleware.AxesMiddleware",                       # HAR DOIM OXIRIDA (4.2)
]
```

E'tibor bering: `whitenoise` ikkinchi o'rinda turadi (u ham `SecurityMiddleware`dan keyin bo'lishi kerak), `corsheaders` esa undan **oldin** kelishi tavsiya etiladi — ikkalasi ham "boshida" bo'lishni talab qilgani uchun, aniq tartib rasmiy hujjatlarga asoslanib tanlanadi: `CorsMiddleware` → `WhiteNoiseMiddleware`, chunki CORS sarlavhalari barcha javoblarga (shu jumladan statik fayllar javobiga ham) qo'shilishi kerak.

**`INSTALLED_APPS`** — bu yerda qat'iy tartib talab qilinmaydi (ba'zi Django ichki app'lardan tashqari, masalan `django.contrib.sites` allauth'dan oldin bo'lishi shart emas, lekin loyihada izchillik uchun guruhlab yozish tavsiya etiladi):

```python
INSTALLED_APPS = [
    # Django ichki app'lari
    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
    "django.contrib.sessions",
    "django.contrib.messages",
    "django.contrib.staticfiles",
    "django.contrib.sites",              # allauth uchun (4.1)

    # Uchinchi-tomon kutubxonalar
    "crispy_forms",                       # 3.1
    "crispy_bootstrap5",                  # 3.1
    "allauth",                            # 4.1
    "allauth.account",
    "allauth.socialaccount",
    "allauth.socialaccount.providers.google",
    "axes",                               # 4.2
    "rest_framework",                     # 6.1
    "drf_spectacular",                    # 6.1
    "django_filters",                     # 6.2
    "corsheaders",                        # 6.2

    # O'z ilovalarimiz
    "apps.dokon",
]
```

### Yashirin bog'liqliklarga misollar

Bir necha o'rinda, bir kutubxonaning ishlashi ikkinchisiga **bog'liq** bo'lib qoladi:

- `django-storages` (5.2) production'da yoqilganda, `Pillow` (5.1) hamon **kerak** — chunki `ImageField`ning o'zi (fayl qayerda saqlanishidan qat'i nazar) Pillow'ga tayanadi.
- `django-redis` (7.2) va `Celery`ning broker'i (7.1) — **bir xil** Redis serverida, lekin turli baza raqamlarida (`/0` va `/1`) ishlaydi; agar ikkalasi ham `/0`ni ishlatsa, kesh kalitlari va Celery navbati aralashib ketishi mumkin.
- `pytest-django` (8.1) testlari — `django-environ` (2.1) orqali o'qiladigan `.env`ga bog'liq; agar test muhitida `.env` fayli topilmasa (yoki CI serverida mavjud bo'lmasa), testlar sozlama yo'qligi sababli yiqiladi — shuning uchun CI'da muhit o'zgaruvchilari alohida (masalan GitHub Actions "secrets") orqali berilishi kerak.

## Amaliy misol

`onlayn_dokon`ning to'liq, barcha 14 kutubxona bilan boyitilgan `settings/` paketi:

```python
# onlayn_dokon/settings/base.py
from pathlib import Path
import environ

BASE_DIR = Path(__file__).resolve().parent.parent.parent
env = environ.Env()
environ.Env.read_env(BASE_DIR / ".env")

SECRET_KEY = env("SECRET_KEY")

INSTALLED_APPS = [
    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
    "django.contrib.sessions",
    "django.contrib.messages",
    "django.contrib.staticfiles",
    "django.contrib.sites",
    "crispy_forms",
    "crispy_bootstrap5",
    "allauth",
    "allauth.account",
    "allauth.socialaccount",
    "allauth.socialaccount.providers.google",
    "axes",
    "rest_framework",
    "drf_spectacular",
    "django_filters",
    "corsheaders",
    "apps.dokon",
]

MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",
    "corsheaders.middleware.CorsMiddleware",
    "whitenoise.middleware.WhiteNoiseMiddleware",
    "django.contrib.sessions.middleware.SessionMiddleware",
    "django.middleware.common.CommonMiddleware",
    "django.middleware.csrf.CsrfViewMiddleware",
    "django.contrib.auth.middleware.AuthenticationMiddleware",
    "allauth.account.middleware.AccountMiddleware",
    "django.contrib.messages.middleware.MessageMiddleware",
    "django.middleware.clickjacking.XFrameOptionsMiddleware",
    "axes.middleware.AxesMiddleware",
]

AUTHENTICATION_BACKENDS = [
    "axes.backends.AxesStandaloneBackend",
    "django.contrib.auth.backends.ModelBackend",
    "allauth.account.auth_backends.AuthenticationBackend",
]

SITE_ID = 1
CRISPY_ALLOWED_TEMPLATE_PACKS = "bootstrap5"
CRISPY_TEMPLATE_PACK = "bootstrap5"

ACCOUNT_LOGIN_METHODS = {"email"}
ACCOUNT_SIGNUP_FIELDS = ["email*", "password1*", "password2*"]

AXES_FAILURE_LIMIT = 5
AXES_COOLOFF_TIME = 1

REST_FRAMEWORK = {
    "DEFAULT_SCHEMA_CLASS": "drf_spectacular.openapi.AutoSchema",
    "DEFAULT_FILTER_BACKENDS": ["django_filters.rest_framework.DjangoFilterBackend"],
}
SPECTACULAR_SETTINGS = {"TITLE": "Onlayn Do'kon API", "VERSION": "1.0.0"}

CELERY_BROKER_URL = env("CELERY_BROKER_URL", default="redis://localhost:6379/0")
CELERY_RESULT_BACKEND = env("CELERY_BROKER_URL", default="redis://localhost:6379/0")

CACHES = {
    "default": {
        "BACKEND": "django_redis.cache.RedisCache",
        "LOCATION": env("REDIS_CACHE_URL", default="redis://localhost:6379/1"),
        "OPTIONS": {"CLIENT_CLASS": "django_redis.client.DefaultClient"},
    }
}

STATIC_URL = "static/"
STATIC_ROOT = BASE_DIR / "staticfiles"
```

```python
# onlayn_dokon/settings/development.py
from .base import *  # noqa

DEBUG = True
ALLOWED_HOSTS = ["localhost", "127.0.0.1"]

STORAGES = {
    "default": {"BACKEND": "django.core.files.storage.FileSystemStorage"},
    "staticfiles": {"BACKEND": "django.contrib.staticfiles.storage.StaticFilesStorage"},
}

CORS_ALLOWED_ORIGINS = ["http://localhost:3000"]
ACCOUNT_EMAIL_VERIFICATION = "optional"
```

```python
# onlayn_dokon/settings/production.py
from .base import *  # noqa

DEBUG = False
ALLOWED_HOSTS = env.list("ALLOWED_HOSTS")

    "default": {"BACKEND": "storages.backends.s3.S3Storage"},
```

Tekshiruv — barcha app'lar to'g'ri yuklanganini tasdiqlash uchun Django'ning o'z tekshiruv buyrug'i:

```bash
python manage.py check
```

```
System check identified no issues (0 silenced).
```

`python manage.py check` — bu, migratsiya yaratmasdan yoki serverni ishga tushirmasdan, `INSTALLED_APPS`, `MIDDLEWARE`, model'lar orasidagi **umumiy nomuvofiqliklarni** (masalan `ImageField` uchun `Pillow` yo'qligi, yoki noto'g'ri middleware tartibi kabi ba'zi holatlar) tezda topib beradigan, tez-tez unutiladigan, lekin juda foydali buyruq.

## Keng tarqalgan xatolar

**Xato 1:** Har bir kutubxonani alohida qo'shganda ishlagan, lekin hammasi birga bo'lganda middleware to'qnashuvini payqamaslik.

❌ `corsheaders` va `whitenoise` middleware'lari, ikkalasi ham alohida darsda "boshida bo'lishi kerak" deb o'rgatilgan, lekin ular **qaysi tartibda o'zaro** joylashishi kerakligi (`CorsMiddleware` → `WhiteNoiseMiddleware`) alohida darslarda ko'rinmagan edi — ikkalasini birga qo'shganda, dasturchi tasodifiy tartibda yozib qo'yishi mumkin.

✅ Har safar yangi kutubxona qo'shganda, uning middleware'ini **mavjud** ro'yxatga, rasmiy hujjatidagi "boshqa middleware'larga nisbatan qayerda bo'lishi kerak" ko'rsatmasiga qarab, **aniq joyga** joylashtiring — yuqoridagi "Amaliy misol"dagi to'liq ro'yxat, tekshirilgan namuna sifatida xizmat qiladi.

**Xato 2:** `python manage.py check`ni hech qachon ishlatmaslik.

❌ Loyiha to'g'ridan-to'g'ri `runserver` yoki `migrate` bilan sinaladi — agar biror sozlama xato bo'lsa (masalan middleware tartibi), bu ba'zida **sokin** ishlaydi (xato chiqmaydi, lekin funksiya to'liq ishlamaydi), va muammo faqat production'da, kutilmagan holatda (masalan CORS ishlamay qolganda) sezilib qoladi.

✅ Har bir yangi kutubxona qo'shilgandan keyin, **odat qilib**, `python manage.py check`ni ishga tushiring — bu, ko'p (hammasi emas) konfiguratsiya xatolarini erta, arzon bosqichda topadi.

**Xato 3:** development va production sozlamalarini alohida-alohida sinab, ular orasidagi **farqni** hech qachon yaxlit solishtirmaslik.

❌ `development.py` bilan hamma narsa ishlaydi (lokal fayl tizimi, CORS o'chirilgan email tekshiruvi), lekin `production.py`da farq qiluvchi qatorlar (`STORAGES`, `ACCOUNT_EMAIL_VERIFICATION`, `CORS_ALLOWED_ORIGINS`) hech qachon **haqiqiy production-o'xshash muhitda** sinovdan o'tkazilmagan — birinchi haqiqiy deploy paytida kutilmagan xatolar chiqadi.

✅ Deploy qilishdan oldin, imkon qadar, `DJANGO_SETTINGS_MODULE=onlayn_dokon.settings.production` bilan, lokal yoki staging muhitda (haqiqiy S3 bucket, haqiqiy Redis bilan) **kamida bir marta** to'liq sinab ko'ring — 9.2-darsda buni tizimli cheklist shakliga keltiramiz.

## Mashq/topshiriq

**(Oson)** O'zingizning `onlayn_dokon` loyihangizdagi `settings/base.py`, `development.py`, `production.py` fayllarini, yuqoridagi "Amaliy misol"dagi to'liq namuna bilan solishtiring — qaysi kutubxona/sozlama sizda yo'qligini ro'yxat qiling.

**(O'rtacha)** `python manage.py check`ni ishga tushiring. Agar xato yoki ogohlantirish chiqsa, uni tuzating; agar hech narsa chiqmasa, ataylab `MIDDLEWARE`dagi ikkita qatorni joyini almashtirib (masalan `AxesMiddleware`ni boshiga ko'chirib) qayta ishga tushiring va natijani solishtiring.

**(Qiyin)** `DJANGO_SETTINGS_MODULE=onlayn_dokon.settings.production`ni (haqiqiy yoki sinov S3 bucket va `ALLOWED_HOSTS` bilan) mahalliy muhitda ishga tushirishga harakat qiling. Qanday xatolar chiqishini (masalan yetishmayotgan muhit o'zgaruvchisi) hujjatlashtirib, ularni birma-bir tuzating.

## Qisqacha xulosa

Bu darsda biz, alohida-alohida o'rgangan 14 ta kutubxonani **bitta** yaxlit `settings/` paketida birlashtirdik va ularning orasidagi tartib talablari (`AUTHENTICATION_BACKENDS`, `MIDDLEWARE`) va yashirin bog'liqliklarni (Redis baza raqamlari, Pillow'ning har doim kerakligi) ko'rib chiqdik; `python manage.py check` — bunday konfiguratsiya xatolarini erta topishning oddiy, lekin tez-tez unutiladigan vositasi. Darslikning so'nggi darsida — yakuniy `requirements.txt`ni tozalash, to'liq production cheklistini yaratish, va kelajakda versiyalarni xavfsiz yangilab borish strategiyasini ko'ramiz.

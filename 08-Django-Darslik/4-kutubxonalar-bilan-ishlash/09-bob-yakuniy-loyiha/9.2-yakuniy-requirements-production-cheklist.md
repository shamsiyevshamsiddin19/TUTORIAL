# 9.2. Yakuniy requirements.txt, production cheklisti va versiyalarni yangilash strategiyasi

## Bu darsda nimalarni o'rganasiz

- Darslik davomida qo'shilgan barcha kutubxonalarni yakuniy, tartiblangan `requirements.txt`ga jamlashni o'rganasiz
- Loyihani production'ga joylashtirishdan oldin tekshirish kerak bo'lgan to'liq cheklistni olasiz
- Kutubxona versiyalarini **xavfsiz** yangilab borish strategiyasini (qachon, qanday, qanday tartibda) bilib olasiz
- Bu darslikda o'rgangan barcha bilimlarni, **yagona tamoyilga** birlashtirib, xulosalaysiz

## Nazariy qism

### Yakuniy requirements.txt qanday tuzilishi kerak

1.2-darsda `pip-tools`ni o'rgandik — u, `requirements.in` (o'zingiz yozgan, "asosiy" bog'liqliklar) faylidan, to'liq `requirements.txt`ni (barcha tranzitiv bog'liqliklar bilan) avtomatik generatsiya qiladi. Yakuniy bosqichda, `requirements.in`ni **tartibli, izohli** holga keltirish tavsiya etiladi:

```
# requirements.in — onlayn_dokon, yakuniy versiya

# Asosiy freymvork
Django~=4.2

# Sozlash va bog'liqliklar
django-environ~=0.11

# Forma va frontend
django-crispy-forms~=2.1
crispy-bootstrap5~=2023.10
whitenoise~=6.6

# Autentifikatsiya
django-allauth~=0.58
django-axes~=6.3

# Media va fayllar
Pillow~=10.1
django-storages~=1.14
boto3~=1.34

# API
djangorestframework~=3.14
drf-spectacular~=0.27
django-filter~=23.5
django-cors-headers~=4.3

# Fon vazifalar va kesh
celery~=5.3
redis~=5.0
django-redis~=5.4

# Test va sifat (faqat development uchun — quyida alohida faylga ajratamiz)
pytest~=7.4
pytest-django~=4.7
pytest-cov~=4.1
factory_boy~=3.3
coverage~=7.4
pip-audit~=2.6
```

```bash
pip-compile requirements.in
```

### Development va production bog'liqliklarini ajratish

E'tibor bering: yuqoridagi ro'yxatda `pytest`, `factory_boy`, `coverage` kabi kutubxonalar bor — bular **faqat** development/CI muhitida kerak, production serverida ular umuman ishlatilmaydi (va production'da bo'lmasligi ham mumkin — bu, serverdagi keraksiz kodni kamaytiradi). Shuning uchun, real loyihalarda, ko'pincha ikkita alohida fayl ishlatiladi:

```
# requirements/base.in — production'da HAM kerak bo'lgan bog'liqliklar
Django~=4.2
django-environ~=0.11
django-crispy-forms~=2.1
# ... (test kutubxonalaridan tashqari, barchasi)
```

```
# requirements/dev.in — faqat development/CI uchun
-r base.in
pytest~=7.4
pytest-django~=4.7
factory_boy~=3.3
coverage~=7.4
pip-audit~=2.6
```

```bash
pip-compile requirements/base.in -o requirements/base.txt
pip-compile requirements/dev.in -o requirements/dev.txt
```

Production serverida — faqat `pip install -r requirements/base.txt`; development mashinada — `pip install -r requirements/dev.txt` (bu, `base.txt`dagilarni ham avtomatik o'z ichiga oladi, chunki `dev.in` `-r base.in` orqali unga ishora qiladi).

### Production'ga joylashtirish oldidan to'liq cheklist

Bu darslikda ko'rgan har bir kutubxonaning o'z "production'ga tayyorlik" talabi bor edi. Ularni bitta ro'yxatga jamlaymiz:

**Sozlamalar va maxfiylik:**
- [ ] `DEBUG = False` production sozlamasida
- [ ] `SECRET_KEY` `.env` orqali, kodda hardcoded emas (2.1)
- [ ] `.env` fayli `.gitignore`da, hech qachon repozitoriyga commit qilinmagan
- [ ] `ALLOWED_HOSTS` aniq domenlar bilan to'ldirilgan

**Statik va media fayllar:**
- [ ] `collectstatic --noinput` deploy skriptining majburiy qadami (3.2)
- [ ] `STORAGES["staticfiles"]` — `CompressedManifestStaticFilesStorage` (3.2)
- [ ] `STORAGES["default"]` — `S3Storage`, mahalliy diskka emas (5.2)
- [ ] S3 bucket **shaxsiy** (public emas), faqat kerakli fayllar ochiq (5.2)

**Autentifikatsiya va xavfsizlik:**
- [ ] `ACCOUNT_EMAIL_VERIFICATION = "mandatory"` production'da (4.1)
- [ ] `AxesStandaloneBackend` — `AUTHENTICATION_BACKENDS`ning birinchisi (4.2)
- [ ] `AxesMiddleware` — `MIDDLEWARE`ning oxirgisi (4.2)
- [ ] `CORS_ALLOWED_ORIGINS` — aniq ro'yxat, `CORS_ALLOW_ALL_ORIGINS` emas (6.2)

**Fon vazifalar va infratuzilma:**
- [ ] Celery worker — alohida, `systemd`/Docker orqali doimiy ishlab turadigan jarayon (7.1)
- [ ] Redis — Celery (`/0`) va kesh (`/1`) uchun alohida baza raqamlari (7.2)

**Bog'liqliklar va sifat:**
- [ ] `pip-audit -r requirements/base.txt` — zaifliklarsiz (8.2)
- [ ] `pytest --cov=apps --cov-fail-under=70` — CI'da o'tgan (8.1, 8.2)
- [ ] `python manage.py check --deploy` — Django'ning o'z production-tekshiruvi

```bash
python manage.py check --deploy
```

`--deploy` bayrog'i — oddiy `check`dan farqli, **maxsus production-uchun** tekshiruvlarni (masalan `SECRET_KEY` yetarlicha murakkabmi, `SECURE_SSL_REDIRECT` yoqilganmi) qo'shimcha bajaradi.

### Versiyalarni xavfsiz yangilab borish strategiyasi

Loyiha tugagach ham, kutubxonalar hayoti davom etadi — yangi versiyalar, xavfsizlik tuzatishlari chiqib turadi. Xavfsiz yangilash uchun tavsiya etilgan tartib:

1. **Muntazam ravishda** (masalan oyiga bir marta) `pip-audit`ni ishga tushiring — yangi zaifliklarni erta payqash uchun.
2. Yangilashdan oldin, **qaysi turdagi** o'zgarish ekanini ko'ring (1.1-darsdagi semver): patch (`4.2.1`→`4.2.2`) — deyarli har doim xavfsiz; minor (`4.2`→`4.3`) — o'zgarishlar jurnalini (changelog) o'qing; major (`4`→`5`) — alohida, ehtiyotkorlik bilan rejalashtiring.
3. Bittalab yangilang (bir vaqtning o'zida 10 ta kutubxonani emas) — shunda, agar biror narsa buzilsa, **qaysi** yangilanish sabab bo'lganini aniqlash oson.
4. Har bir yangilanishdan keyin **to'liq test to'plamini** (`pytest --cov`) ishga tushiring.
5. Avval **staging** (production'ga o'xshash, lekin alohida) muhitda sinab ko'ring, keyingina haqiqiy production'ga joylashtiring.

## Amaliy misol

`onlayn_dokon` uchun yakuniy fayl tuzilishi va deploy skripti:

```
onlayn_dokon/
├── requirements/
│   ├── base.in
│   ├── base.txt
│   ├── dev.in
│   └── dev.txt
├── .env                    # .gitignore'da
├── .env.example             # namuna, repozitoriyda
├── onlayn_dokon/
│   ├── celery.py
│   ├── settings/
│   │   ├── base.py
│   │   ├── development.py
│   │   └── production.py
│   └── urls.py
└── apps/
    └── dokon/
```

```bash
# scripts/deploy_tekshiruvi.sh — production'ga joylashtirishdan OLDIN ishga tushiriladi
#!/bin/bash
set -e

echo "1. Bog'liqliklar xavfsizligi..."
pip-audit -r requirements/base.txt

echo "2. Testlar va qamrov..."
DJANGO_SETTINGS_MODULE=onlayn_dokon.settings.development pytest --cov=apps --cov-fail-under=70

echo "3. Django deploy-tekshiruvi..."
DJANGO_SETTINGS_MODULE=onlayn_dokon.settings.production python manage.py check --deploy

echo "4. Statik fayllarni yig'ish..."
DJANGO_SETTINGS_MODULE=onlayn_dokon.settings.production python manage.py collectstatic --noinput

echo "Hammasi tayyor — deploy qilish mumkin."
```

```
1. Bog'liqliklar xavfsizligi...
No known vulnerabilities found

2. Testlar va qamrov...
================= 24 passed in 2.1s =================
TOTAL   82% (talab: 70%) — OK

3. Django deploy-tekshiruvi...
System check identified no issues (0 silenced).

4. Statik fayllarni yig'ish...
147 static files copied, 147 post-processed.

Hammasi tayyor — deploy qilish mumkin.
```

Shu skript — bu darslikda o'rganilgan **barcha** kutubxonalarning (pip-audit, pytest-cov, Django'ning o'zi, whitenoise) natijasini, bitta buyruq bilan, deploy oldidan yakuniy "yashil chiroq" sifatida birlashtiradi.

## Keng tarqalgan xatolar

**Xato 1:** Test kutubxonalarini (`pytest`, `factory_boy`) production `requirements.txt`ga ham qo'shib qo'yish.

❌ Bitta umumiy `requirements.txt` ishlatilgan, unda `pytest`, `factory_boy`, `coverage` ham bor — production serveriga bularning **hech biri kerak emas**, lekin ular ham o'rnatiladi, konteyner hajmini kattalashtiradi va (nazariy jihatdan) hujum yuzasini kengaytiradi.

✅ Yuqoridagi "Nazariy qism"dagi kabi, `base.txt` (production) va `dev.txt` (development/CI, `base`ni o'z ichiga oladi) fayllarini **alohida** yuriting.

**Xato 2:** `check --deploy`ni hech qachon ishlatmasdan, faqat oddiy `check` bilan cheklanish.

❌ `python manage.py check` xatosiz o'tdi, dasturchi bunga tayanib, "hammasi tayyor" deb xulosa qildi — lekin oddiy `check` production-ga xos xavfsizlik sozlamalarini (masalan `SECURE_HSTS_SECONDS`, cookie xavfsizligi) tekshirmaydi.

✅ Production'ga joylashtirishdan oldin, har doim `python manage.py check --deploy`ni **ham** ishga tushiring — u, oddiy `check`ka qo'shimcha, maxsus production-xavfsizlik ogohlantirishlarini beradi.

**Xato 3:** Barcha kutubxonalarni bir vaqtning o'zida, "umumiy tozalash" nomi ostida, eng yangi versiyalarga yangilash.

❌ Oylar davomida yangilanmagan loyihada, dasturchi `pip-compile --upgrade`ni ishga tushirib, **14 ta** kutubxonani bir vaqtning o'zida eng yangi versiyaga o'tkazadi — agar shundan keyin biror narsa buzilsa (masalan bitta kutubxonaning API'si o'zgargan bo'lsa), **qaysi** kutubxona sabab bo'lganini aniqlash amalda mumkin emas.

✅ Yuqoridagi "Versiyalarni xavfsiz yangilab borish strategiyasi"dagi kabi, kutubxonalarni **bittalab**, har birini alohida test qilib yangilang — sekinroq, lekin muammoni aniqlash tez va oson.

## Mashq/topshiriq

**(Oson)** O'zingizning `onlayn_dokon` loyihangiz uchun, yuqoridagi namunaga asoslanib, `requirements/base.in` va `requirements/dev.in`ni yozing, `pip-compile` orqali `.txt` fayllarini generatsiya qiling.

**(O'rtacha)** Yuqoridagi production cheklistini o'z loyihangizga nisbatan, birma-bir belgilab chiqing (`[ ]` → `[x]`). Belgilanmagan punktlarni tuzating.

**(Qiyin)** `scripts/deploy_tekshiruvi.sh` skriptini yozing va ishga tushiring. Agar biror qadam muvaffaqiyatsiz bo'lsa (masalan qamrov 70%dan past), muammoni tuzating va skript to'liq, xatosiz o'tguncha qayta ishga tushiring.

3. Skript `set -e` bilan yozilgani uchun, **har qanday** qadam muvaffaqiyatsiz bo'lsa (masalan `pytest` biror test yiqilsa, yoki `pip-audit` zaiflik topsa), skript **darhol to'xtaydi** — bu, "yashil chiroq bo'lmasa, deploy qilinmaydi" tamoyilini avtomatik ta'minlaydi.

## Qisqacha xulosa

Ushbu darslik davomida siz `onlayn_dokon` loyihasiga 14 ta uchinchi-tomon kutubxonani — sozlamadan (`django-environ`) tortib, xavfsizlik tekshiruvigacha (`pip-audit`) — bosqichma-bosqich, har birini **to'g'ri tanlash**, **xavfsiz integratsiya qilish** va **bog'liqliklarni boshqarish** tamoyillari asosida qo'shdingiz. Bu so'nggi darsda ko'rganingizdek, alohida-alohida o'rganilgan bilim — yakunda, bitta yaxlit `requirements/` tuzilmasi, production cheklisti va deploy-tekshiruv skripti sifatida birlashadi. Kelajakda yangi kutubxona bilan tanishganda ham, xuddi shu uchta savolni bering: *bu kutubxona nima uchun kerak, uni qanday xavfsiz integratsiya qilish kerak, va uning bog'liqliklarini qanday nazorat qilaman?* — shu savollarga javob topa olsangiz, istalgan yangi kutubxonani, mustaqil ravishda, ishonchli tarzda loyihangizga qo'sha olasiz.

Darslik shu bilan yakunlanadi. Omad, va yangi loyihalaringizda muvaffaqiyatlar tilaymiz!

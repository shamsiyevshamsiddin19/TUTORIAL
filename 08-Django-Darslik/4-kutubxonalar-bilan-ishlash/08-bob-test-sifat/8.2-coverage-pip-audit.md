# 8.2. coverage.py va pip-audit — sinov qamrovi va xavfsizlik tekshiruvi

## Bu darsda nimalarni o'rganasiz

- Test **qamrovi** (coverage) nima ekanini va u nimani ko'rsatib, nimani ko'rsatmasligini tushunasiz
- `coverage.py`ni `pytest` bilan birga ishlatib, HTML hisobot olishni o'rganasiz
- `pip-audit` orqali `requirements.txt`dagi kutubxonalarda ma'lum xavfsizlik zaifliklarini avtomatik tekshirishni bilib olasiz
- Ikkala vositani ham CI (Continuous Integration) jarayoniga qanday joylashtirish mumkinligini tushunasiz

## Nazariy qism

### Test qamrovi (coverage) nima

8.1-darsda testlar yozdik — lekin loyihaning **qanday qismi** testlar bilan qamrab olingan, qaysi qismi umuman sinovdan o'tmagan? Bu savolga javob berish uchun qo'lda kodni ko'zdan kechirish — katta loyihada amaliy emas. **`coverage.py`** — testlar ishga tushganda, qaysi kod qatorlari **bajarilgani**ni kuzatib boradigan vosita; natijada, foydalanuvchiga "loyihangizning 73% qatorlari test bilan qamrab olingan, 27% hech qachon bajarilmagan" kabi aniq foiz va, muhimi, **aniq qaysi qatorlar** test qilinmaganini ko'rsatadi.

**Muhim ogohlantirish:** 100% qamrov — kodning **xatosiz** ekanini bildirmaydi, faqat har bir qator **kamida bir marta** bajarilganini bildiradi (natija noto'g'ri bo'lsa ham). Qamrov — foydali **signal** (test yozilmagan joylarni topish uchun), lekin o'zi maqsad emas.

### coverage.py o'rnatish va ishlatish

```bash
pip install coverage
```

```bash
coverage run -m pytest
coverage report
```

```
Name                              Stmts   Miss  Cover
-----------------------------------------------------
apps/dokon/models.py                  45      3    93%
apps/dokon/views.py                   78     22    72%
apps/dokon/services.py                18      0   100%
apps/dokon/tasks.py                   15      8    47%
-----------------------------------------------------
TOTAL                                156     33    79%
```

`Stmts` — jami bajariladigan qatorlar soni, `Miss` — testlar bilan **bajarilmagan** qatorlar soni. Bu jadvaldan ko'rinib turibdiki, `tasks.py` (7.1-darsdagi Celery vazifalari) — eng kam sinovdan o'tgan qism (47%) — bu, e'tibor qaratish kerak bo'lgan joyni ko'rsatadi.

### HTML hisobot — aniq qaysi qatorlar qamrab olinmagan

```bash
coverage html
```

Bu, `htmlcov/` papkasida, har bir faylni **rang bilan belgilangan** holda ko'rsatadigan HTML sahifalar yaratadi: yashil — test bilan bajarilgan qatorlar, qizil — bajarilmagan qatorlar. `htmlcov/index.html`ni brauzerda ochib, aniq qaysi `if` shoxobchasi yoki `except` bloki hech qachon sinovdan o'tmaganini ko'rish mumkin.

### pytest bilan integratsiya

```bash
pip install pytest-cov
```

```bash
pytest --cov=apps --cov-report=html --cov-report=term
```

`pytest-cov` — `coverage run -m pytest` + `coverage report`ni **bitta** buyruqqa birlashtiradi, `pytest`ning o'z buyruq qatori argumentlari orqali.

### Xavfsizlik muammosi: eskirgan kutubxonalar

1.1-2.2-darslarda `requirements.txt` orqali kutubxona versiyalarini "muzlatishni" o'rgandik. Lekin vaqt o'tishi bilan, ishlatilayotgan kutubxonaning **ma'lum** versiyalarida xavfsizlik zaifliklari (masalan, SQL-in'ektsiya yoki XSS imkoniyati) topilishi va e'lon qilinishi mumkin (bunday e'lonlar **CVE** — Common Vulnerabilities and Exposures — deb nomlanadi). Loyihangiz o'nlab bog'liqliklarga ega bo'lsa, ularning **har birini** qo'lda kuzatib borish amaliy emas.

### pip-audit yechimi

```bash
pip install pip-audit
```

```bash
pip-audit -r requirements.txt
```


`pip-audit` — [PyPI Advisory Database](https://github.com/pypa/advisory-database)ga murojaat qilib, `requirements.txt`dagi **har bir** kutubxona versiyasini ma'lum zaifliklar bazasi bilan solishtiradi, va agar mos kelsa — zaiflik ID'si (CVE yoki GHSA) va **qaysi versiyada tuzatilganini** ko'rsatadi.

## Amaliy misol

`onlayn_dokon` loyihasida qamrov va xavfsizlik tekshiruvini birlashtirib ishlatish:

```bash
pip install pytest-cov pip-audit
```

```ini
# pytest.ini
[pytest]
DJANGO_SETTINGS_MODULE = onlayn_dokon.settings.development
python_files = tests.py test_*.py *_tests.py

[coverage:run]
source = apps
omit =
    */migrations/*
    */tests/*
    manage.py
```

`[coverage:run]`dagi `omit` — migratsiya fayllari va testlarning o'zini qamrov hisobidan **chiqarib tashlaydi** (ular "sinov qilinishi kerak bo'lgan biznes mantiq" emas, shuning uchun ularning past qamrovi noto'g'ri xavotir tug'diradi).

```bash
pytest --cov=apps --cov-report=term-missing
```

```
Name                              Stmts   Miss  Cover   Missing
----------------------------------------------------------------
apps/dokon/models.py                  45      3    93%   67-69
apps/dokon/services.py                18      0   100%
apps/dokon/views.py                   78     22    72%   102-115, 140-148
----------------------------------------------------------------
TOTAL                                141     25    82%
```

`--cov-report=term-missing` — `Missing` ustunida, **aynan qaysi qator raqamlari** qamrab olinmaganini to'g'ridan-to'g'ri terminalda ko'rsatadi (HTML hisobot ochish shart emas).

```bash
pip-audit -r requirements.txt
```

```
No known vulnerabilities found
```

Bularni birlashtirib, oddiy tekshiruv skripti:

```bash
# scripts/sifat_tekshiruvi.sh
#!/bin/bash
set -e

echo "=== Testlar va qamrov ==="
pytest --cov=apps --cov-report=term-missing --cov-fail-under=70

echo "=== Xavfsizlik tekshiruvi ==="
pip-audit -r requirements.txt
```

`--cov-fail-under=70` — agar umumiy qamrov 70%dan **past** bo'lsa, `pytest` xato kodi bilan tugaydi — bu, CI'da "qamrov pasaysa, build muvaffaqiyatsiz" qoidasini avtomatik qo'llash uchun ishlatiladi.

## Keng tarqalgan xatolar

**Xato 1:** Faqat foizga (masalan "90% qamrov bor") qarab, kod sifatli deb xulosa chiqarish.

❌ Loyiha 95% qamrovga ega, lekin testlar faqat funksiyani **chaqiradi**, natijani hech narsa bilan solishtirmaydi (`assert True` yoki umuman `assert`siz) — qatorlar "bajarilgan" hisoblanadi, lekin xato natija chiqsa ham test **muvaffaqiyatli** ko'rinadi.

✅ Qamrov foizini **faqat** "qaysi qatorlar hali sinovdan o'tmagan"ni topish vositasi sifatida ishlating; har bir testda, albatta, **aniq natijani** tekshiruvchi `assert` bo'lishi shart.

**Xato 2:** `pip-audit` topgan zaiflikni ko'rib, darhol, sinovdan o'tkazmasdan, eng yangi versiyaga yangilash.

❌ `pip-audit` `django==4.2.1`da zaiflik borligini ko'rsatdi, dasturchi darhol `pip install --upgrade django` qildi (masalan `5.0`ga) — bu, katta versiya sakrashi bo'lib, loyihada ishlatilgan, `5.0`da o'chirilgan/o'zgargan funksiyalarni buzishi mumkin.

✅ Zaiflik topilganda, avval **tavsiya etilgan tuzatilgan versiyani** (`pip-audit` chiqishidagi `Fix Versions`) ko'ring — odatda bu, mos **kichik** (patch/minor) versiya, katta (major) emas; yangilagandan keyin, albatta, to'liq test to'plamini (`pytest`) qayta ishga tushiring.

**Xato 3:** `coverage:run`da `omit` sozlamasini qo'shmasdan, migratsiya fayllarining past qamrovidan xavotirlanish.

❌ `python manage.py makemigrations` avtomatik generatsiya qilgan `migrations/0003_...py` fayllari ham qamrov hisobiga kiritilgan — bu fayllar odatda **hech qachon** to'g'ridan-to'g'ri test qilinmaydi (ular Django tomonidan ichki ishlatiladi), shuning uchun umumiy qamrov foizini sun'iy ravishda pasaytiradi.

✅ `pytest.ini`dagi `[coverage:run]` bo'limida, yuqoridagi misoldagi kabi, `migrations/`, `tests/` papkalarini `omit`ga qo'shing — qamrov foizi faqat **haqiqatan sinovdan o'tishi kerak bo'lgan** biznes-mantiq kodini aks ettirsin.

## Mashq/topshiriq

**(Oson)** `coverage` (yoki `pytest-cov`)ni o'rnating, `pytest --cov=apps --cov-report=term`ni ishga tushiring, va umumiy qamrov foizini ko'ring.

**(O'rtacha)** `coverage html`ni ishga tushiring, `htmlcov/index.html`ni brauzerda oching, va eng past qamrovga ega faylni toping. Shu faylga, qizil rangda belgilangan qatorlardan birini qamrab oluvchi, yangi test yozing.

**(Qiyin)** `pip-audit -r requirements.txt`ni ishga tushiring. Agar zaiflik topilmasa, `requirements.txt`ga ataylab eski (masalan `django==3.2.0`) versiyani qo'shib qayta ishga tushiring va zaiflik ro'yxatini ko'ring; keyin uni `pip-audit` tavsiya qilgan versiyaga yangilang va qayta tekshiring.

1-2. Buyruqlar — yuqoridagi "Amaliy misol" bo'limidagi kabi. HTML hisobotda qizil qator — masalan, `if` blokining faqat bitta shoxobchasi (masalan `else`) sinovdan o'tmagani ko'rsatiladi; shu holatni qamrab oluvchi test yozilgach, `coverage html` qayta ishga tushirilganda, o'sha qator **yashil**ga aylanadi.

3. Eski `django==3.2.0` bilan, `pip-audit` bir nechta zaiflikni (masalan eski Django versiyalarida ma'lum bo'lgan CVE'larni) ko'rsatishi kerak. Tavsiya etilgan versiyaga yangilangach (`requirements.txt`da versiyani o'zgartirib, `pip install -r requirements.txt`ni qayta ishga tushirib), `pip-audit` qayta ishga tushirilganda, `No known vulnerabilities found` chiqishi kerak.

## Qisqacha xulosa

`coverage.py` (odatda `pytest-cov` orqali) — testlarning loyihaning qancha qismini qamrab olganini o'lchaydi va **aynan qaysi qatorlar** sinovdan o'tmaganini ko'rsatadi, bu esa keyingi testlarni qayerga yozish kerakligini aniqlashtiradi; `--cov-fail-under` orqali, past qamrov CI'da avtomatik "xato" sifatida belgilanishi mumkin. `pip-audit` — loyihaning bog'liqliklarini, ma'lum xavfsizlik zaifliklari bazasi bilan solishtirib, e'lon qilingan muammolarni va ularning tuzatilgan versiyalarini avtomatik topadi. Ikkalasi ham — **kod sifatini o'lchash** va **xavfsizlikni doimiy nazorat qilish**ning amaliy vositalari. Shu bilan 08-bob (test va sifat kutubxonalari) yakunlandi — so'nggi, 09-bobda, shu paytgacha `onlayn_dokon`ga qo'shilgan **barcha** kutubxonalarni bitta yaxlit loyihada birlashtiramiz va production'ga tayyorlash cheklistini ko'ramiz.

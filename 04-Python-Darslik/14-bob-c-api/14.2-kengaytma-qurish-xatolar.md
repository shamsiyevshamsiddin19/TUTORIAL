# 14.2. C kengaytmalarda xotira boshqaruvi, istisnolar va keng tarqalgan xatolar

## Bu darsda nimalarni o'rganasiz

- C kengaytmalar ichida `Py_INCREF`/`Py_DECREF`ni qo'lda boshqarish
- "Yangi havola" (new reference) va "qarzga olingan havola" (borrowed reference) farqi
- Python istisnolarini C darajasida ko'tarish va tekshirish (`PyErr_*`)
- GIL bilan C kengaytmalar ichida ishlash (`Py_BEGIN_ALLOW_THREADS`)

## Nazariy qism

**Manba:** [Python rasmiy dokumentatsiyasi — Extending Python with C or C++](https://docs.python.org/3/extending/extending.html), [Python rasmiy dokumentatsiyasi — Reference Counting](https://docs.python.org/3/extending/extending.html#reference-counts).

### Qo'lda reference counting — eng xavfli qism

7-bobda ko'rganimizdek, standart (GIL'li) CPython'da har bir `PyObject`ning `ob_refcnt` maydoni bor, va Python darajasida bu avtomatik boshqariladi — dasturchi hech qachon `INCREF`/`DECREF`ni o'zi chaqirmaydi. Lekin **C kengaytma yozganda**, siz aynan CPython'ning o'zi bajaradigan ishni **qo'lda** bajarishga majbursiz: har safar `PyObject*`ni saqlab qolsangiz — `Py_INCREF()`; har safar undan voz kechsangiz (funksiyadan chiqishdan oldin, yoki boshqa obyektga almashtirganda) — `Py_DECREF()`.

Bu — C kengaytma yozishning eng xatoga moyil qismi. Ikki turdagi xato juda tez-tez uchraydi:

- **Xotira sizib chiqishi (memory leak):** `INCREF` qilingan, lekin hech qachon `DECREF` qilinmagan obyekt — reference count hech qachon nolga tushmaydi, obyekt abadiy xotirada qoladi.
- **Use-after-free / dangling pointer:** obyekt kerakli `INCREF` qilinmasdan ishlatiladi, boshqa joyda uning `DECREF`i chaqirilib, reference count nolga tushib ketadi (obyekt yo'q qilinadi), lekin siz hamon o'sha, endi bekor qilingan xotiraga ko'rsatkichni ishlatishda davom etasiz — bu segmentation fault yoki, undan ham yomoni, **tasodifiy noto'g'ri natija** beradi.

### "Yangi havola" va "qarzga olingan havola"

C API hujjatlari har bir funksiya nima qaytarishini ikki toifaga ajratadi:

**Yangi havola (new reference):** funksiya sizga **allaqachon** `INCREF` qilingan `PyObject*` qaytaradi — siz uning "egasisiz" (owner), va ishingiz tugagach uni `Py_DECREF()` qilishga **javobgarsiz**. Masalan, `PyLong_FromLong(42)` — yangi `PyLongObject` yaratadi, reference count'i 1 bilan.

**Qarzga olingan havola (borrowed reference):** funksiya sizga `PyObject*` qaytaradi, lekin uning reference count'ini **oshirmaydi** — siz faqat "qarz" oldingiz, egasi boshqa joyda (masalan, uni saqlagan `list` yoki `dict`). Siz uni `DECREF` qilishga **haqli emassiz** (aks holda ownerdan oldinroq obyekt yo'q qilinishi mumkin) — lekin agar uni **saqlab qolmoqchi** bo'lsangiz (masalan, o'zingizning strukturangizga yozib qo'yish uchun), unga o'zingiz `Py_INCREF()` qilishingiz shart, aks holda asl egasi obyektni yo'q qilib yuborsa, sizning ko'rsatkichingiz "osilib qoladi" (dangling).

```c
// PyList_GetItem — QARZGA OLINGAN havola qaytaradi
PyObject* element = PyList_GetItem(royxat, 0);  // INCREF QILMAGAN

// Agar bu elementni funksiyadan tashqariga, uzoq muddat saqlab qolmoqchi bo'lsangiz:
Py_INCREF(element);  // endi siz ham "egasisiz"
saqlangan_qiymat = element;
// ... keyinroq, kerak bo'lmay qolganda:
Py_DECREF(saqlangan_qiymat);
```

Har bir C API funksiyasi hujjatida aniq "Return value: New reference" yoki "Return value: Borrowed reference" deb yozib qo'yiladi — bu qatorni **har doim tekshirish** kerak, chunki bu ikkisini aralashtirib yuborish C kengaytma xatolarining eng katta manbai hisoblanadi.

### Xatolarni ko'tarish va tekshirish

Python C API'da istisno ko'tarish ikki bosqichli: avval **xato holatini o'rnatish** (`PyErr_SetString` va o'xshashlar), so'ng **`NULL` qaytarish** — bu ikkalasi birga "Python darajasida istisno ko'tarildi" degan ma'noni bildiradi:

```c
if (n < 0) {
    PyErr_SetString(PyExc_ValueError, "n manfiy bo'lmasligi kerak");
    return NULL;  // MAJBURIY — aks holda Python "xato holati bor, lekin funksiya
                   // muvaffaqiyatli qaytdi" degan chalkash holatga tushadi
}
```

Boshqa C API funksiyasini chaqirganda, u xato qaytarganini (odatda `NULL` qaytarish orqali) tekshirish va, agar kerak bo'lsa, o'zingizning funksiyangizni ham to'g'ri to'xtatish muhim:

```c
PyObject* natija = PyObject_CallMethod(obyekt, "metod_nomi", NULL);
if (natija == NULL) {
    // Xato allaqachon PyErr_* orqali o'rnatilgan — shunchaki tarqatib yuborish kifoya
    return NULL;
}
```

### GIL va C kengaytmalar

12.1-darsda ko'rganimizdek, GIL C kengaytma kodi bajarilayotganda ham (standart holatda) **ushlab turiladi** — bu odatda kerak, chunki C kodi Python obyektlari bilan ishlaydi (reference counting xavfsizligi uchun). Lekin agar C kengaytmangiz uzoq davom etadigan, **Python obyektlariga tegmaydigan** hisoblash (masalan, sof C massivda katta tsikl) bajarsa, GIL'ni vaqtincha bo'shatib, boshqa Python oqimlariga ishlash imkonini berish mumkin:

```c
static PyObject* uzoq_c_hisoblash(PyObject* self, PyObject* args) {
    long n;
    if (!PyArg_ParseTuple(args, "l", &n)) return NULL;

    long natija;
    Py_BEGIN_ALLOW_THREADS
    // Bu blok ichida GIL BO'SHATILGAN — Python obyektlariga
    // HECH QANDAY murojaat qilib bo'lmaydi (xavfsiz emas)!
    natija = 0;
    for (long i = 0; i < n; i++) {
        natija += i;
    }
    Py_END_ALLOW_THREADS

    return Py_BuildValue("l", natija);
}
```

`Py_BEGIN_ALLOW_THREADS`/`Py_END_ALLOW_THREADS` orasidagi kodda **hech qanday** Python C API funksiyasini (yoki `PyObject*`ga murojaatni) chaqirish mumkin emas — chunki GIL bo'shatilgan, boshqa oqim shu paytda xuddi shu obyektlarni xavfsiz bo'lmagan tarzda o'zgartirishi mumkin. Bu naqsh, masalan, NumPy'ning ichida katta massivlar ustida amalga oshiriladigan sof-C tsikllarda keng qo'llaniladi — shu orqali NumPy chaqiruvi davomida boshqa Python oqimlari ishlashda davom eta oladi.

### Zamonaviy muqobillar — "xom" C API har doim kerak emas

"Xom" (raw) C API bilan ishlash — quyi darajadagi, xatoga moyil, ko'p boilerplate talab qiladigan jarayon. Amaliyotda ko'plab loyihalar quyidagi yuqori darajadagi muqobillardan foydalanadi:

- **Cython** (13.3-darsda ko'rdik) — reference counting, xato tekshiruvi avtomatik amalga oshiriladi, Python-ga o'xshash sintaksis.
- **pybind11** (C++ uchun) — zamonaviy C++ klasslarini avtomatik Python ob'ektlariga o'rab beradi, reference counting'ni o'zi boshqaradi.
- **CFFI** (13.3-darsda ko'rdik) — mavjud C kutubxonalarini chaqirish uchun, C API'ni to'g'ridan-to'g'ri yozmasdan.

"Xom" C API bilimi baribir foydali — chunki bu vositalarning barchasi, pirovardida, aynan shu C API ustiga qurilgan, va murakkab, o'ta ixtisoslashtirilgan hollarda (masalan, CPython'ning o'ziga eng yaqin darajadagi optimallashtirish kerak bo'lganda) to'g'ridan-to'g'ri C API bilan ishlash hamon zarur bo'lib qoladi.

## Amaliy misol

```c
/* xavfsiz_royxat_modul.c — reference counting'ni to'g'ri va noto'g'ri
   ishlatishni ko'rsatuvchi ta'lim maqsadidagi kengaytma. */
#include <Python.h>

/* TO'G'RI: ro'yxatning har bir elementini xavfsiz yig'indilash. */
static PyObject* royxat_yigindisi(PyObject* self, PyObject* args) {
    PyObject* royxat;
    if (!PyArg_ParseTuple(args, "O", &royxat)) {
        return NULL;
    }
    if (!PyList_Check(royxat)) {
        PyErr_SetString(PyExc_TypeError, "argument list bo'lishi kerak");
        return NULL;
    }

    Py_ssize_t uzunlik = PyList_Size(royxat);
    double yigindi = 0.0;

    for (Py_ssize_t i = 0; i < uzunlik; i++) {
        /* PyList_GetItem — QARZGA OLINGAN havola, INCREF shart emas,
           chunki biz uni faqat vaqtincha o'qiymiz, saqlab qolmaymiz. */
        PyObject* element = PyList_GetItem(royxat, i);

        /* PyFloat_AsDouble xato bo'lsa -1.0 qaytaradi VA xato holatini
           o'rnatadi — shuning uchun PyErr_Occurred() bilan tekshiramiz. */
        double qiymat = PyFloat_AsDouble(element);
        if (qiymat == -1.0 && PyErr_Occurred()) {
            return NULL;  /* xato allaqachon o'rnatilgan (masalan, TypeError) */
        }
        yigindi += qiymat;
    }

    return Py_BuildValue("d", yigindi);
}

/* TO'G'RI: yangi ro'yxat yaratib, unga yangi obyektlar qo'shish
   (yangi havolalarni to'g'ri boshqarish namunasi). */
static PyObject* royxat_ikki_baravar(PyObject* self, PyObject* args) {
    PyObject* royxat;
    if (!PyArg_ParseTuple(args, "O", &royxat)) {
        return NULL;
    }

    Py_ssize_t uzunlik = PyList_Size(royxat);
    PyObject* yangi_royxat = PyList_New(uzunlik);  /* yangi havola, biz egasimiz */
    if (yangi_royxat == NULL) {
        return NULL;
    }

    for (Py_ssize_t i = 0; i < uzunlik; i++) {
        PyObject* element = PyList_GetItem(royxat, i);  /* qarzga olingan */
        double qiymat = PyFloat_AsDouble(element);
        if (qiymat == -1.0 && PyErr_Occurred()) {
            Py_DECREF(yangi_royxat);  /* xato holatida yaratilgan obyektni tozalash */
            return NULL;
        }

        PyObject* yangi_qiymat = PyFloat_FromDouble(qiymat * 2);  /* yangi havola */
        /* PyList_SetItem YANGI havolani "yutib yuboradi" (steals reference) —
           biz bu yerda Py_DECREF chaqirmaymiz, PyList_SetItem buni o'z zimmasiga oladi. */
        PyList_SetItem(yangi_royxat, i, yangi_qiymat);
    }

    return yangi_royxat;  /* egalikni chaqiruvchiga topshiramiz */
}

static PyMethodDef Metodlar[] = {
    {"yigindisi", royxat_yigindisi, METH_VARARGS, "Ro'yxat elementlari yig'indisi."},
    {"ikki_baravar", royxat_ikki_baravar, METH_VARARGS, "Har bir elementni ikki baravar qiladi."},
    {NULL, NULL, 0, NULL}
};

static struct PyModuleDef Modul = {
    PyModuleDef_HEAD_INIT,
    "xavfsiz_royxat_modul",
    "Reference counting namunalari.",
    -1,
    Metodlar
};

PyMODINIT_FUNC PyInit_xavfsiz_royxat_modul(void) {
    return PyModule_Create(&Modul);
}
```

```python
# ishlatish_demo.py
import xavfsiz_royxat_modul as m

royxat = [1.0, 2.5, 3.5, 4.0]
print("Yig'indi:", m.yigindisi(royxat))
print("Ikki baravar:", m.ikki_baravar(royxat))

try:
    m.yigindisi([1.0, "satr", 3.0])  # TypeError kutilmoqda
except TypeError as e:
    print("Kutilgan xato ushlandi:", e)
```

Chiqishi:

```
Yig'indi: 11.0
Ikki baravar: [2.0, 5.0, 7.0, 8.0]
Kutilgan xato ushlandi: must be real number, not str
```

## Keng tarqalgan xatolar

1. **`PyList_SetItem`/`PyTuple_SetItem`ga uzatilgan obyektni qo'shimcha `Py_INCREF` qilish.** Bu ikki funksiya maxsus — ular uzatilgan **yangi havolani "yutib yuboradi" (steal)**, ya'ni ular o'zlari egalikni oladi. Agar siz qo'shimcha `INCREF` qilsangiz, reference count haddan tashqari yuqori bo'lib qoladi — bu xotira sizib chiqishiga olib keladi. (Bu — `PyList_GetItem` kabi "qarzga oluvchi" funksiyalardan farqli, chalkashtirib yuborish oson bo'lgan holat.)

2. **`PyErr_Occurred()`ni tekshirmasdan, funksiya `-1`/`NULL` qaytarganida "bu shunchaki oddiy qiymat" deb hisoblash.** `PyFloat_AsDouble()` kabi funksiyalar xato holatida `-1.0` qaytaradi — lekin `-1.0` ayni paytda **haqiqiy, to'g'ri natija** ham bo'lishi mumkin (masalan, Python `float(-1.0)` uchun). Xato va haqiqiy `-1.0`ni ajratish uchun har doim `PyErr_Occurred()` bilan tekshirish shart.

3. **`Py_BEGIN_ALLOW_THREADS` blokida Python obyektiga murojaat qilish.** Bu blok ichida GIL bo'shatilgan — agar shu yerda `Py_INCREF`, `PyList_GetItem` yoki boshqa har qanday C API funksiyasi chaqirilsa, bu **xavfsiz emas** (boshqa oqim bir vaqtda xuddi shu obyektni o'zgartirishi mumkin) va noaniq, aniqlash qiyin bo'lgan xatolarga olib keladi.

## Mashq/topshiriq

1. `royxat_yigindisi` funksiyasini shunday o'zgartiringki, agar ro'yxat bo'sh bo'lsa, `ValueError("bo'sh ro'yxat")` ko'tarsin (yig'indi hisoblanishidan oldin tekshirish orqali).

2. `PyList_GetItem`ning "qarzga olingan havola" ekanini bilgan holda, agar siz `royxat_ikki_baravar` funksiyasida elementni **darhol ishlatish o'rniga**, uni alohida global (statik) o'zgaruvchiga saqlab, funksiyadan chiqqandan keyin ham ishlatmoqchi bo'lsangiz, nima qilishingiz kerakligini yozing.

3. Nima uchun `PyList_SetItem(yangi_royxat, i, yangi_qiymat)`dan keyin, kodda hech qayerda `yangi_qiymat`ga `Py_DECREF` chaqirilmaganini (yuqoridagi misolda) izohlang — bu xotira sizib chiqishi emasmi?

**Javoblar:**

1.
```c
static PyObject* royxat_yigindisi(PyObject* self, PyObject* args) {
    PyObject* royxat;
    if (!PyArg_ParseTuple(args, "O", &royxat)) {
        return NULL;
    }
    if (!PyList_Check(royxat)) {
        PyErr_SetString(PyExc_TypeError, "argument list bo'lishi kerak");
        return NULL;
    }
    Py_ssize_t uzunlik = PyList_Size(royxat);
    if (uzunlik == 0) {
        PyErr_SetString(PyExc_ValueError, "bo'sh ro'yxat");
        return NULL;
    }
    /* ... qolgan qismi o'zgarmaydi ... */
}
```

2.
```c
PyObject* saqlangan_element = NULL;  /* global/statik o'zgaruvchi */

/* funksiya ichida: */
PyObject* element = PyList_GetItem(royxat, 0);  /* qarzga olingan */
Py_XDECREF(saqlangan_element);   /* eski qiymatdan (agar bor bo'lsa) voz kechish */
Py_INCREF(element);              /* endi biz ham "egamiz" */
saqlangan_element = element;     /* xavfsiz saqlash */
```
Bu yerda `Py_INCREF(element)` **majburiy** — chunki `PyList_GetItem` faqat "qarz" beradi, funksiya qaytgandan keyin ham `royxat` obyekti o'zi (yoki uning shu elementi) hali mavjudligiga kafolat yo'q; agar asl ro'yxat keyinroq o'chirilsa yoki element almashtirilsa, `INCREF` qilinmagan holda `saqlangan_element` osilib qolgan (dangling) ko'rsatkichga aylanadi.

3. Bu xotira sizib chiqishi emas, chunki `PyList_SetItem` maxsus semantikaga ega: u ikkinchi argument sifatida uzatilgan `PyObject*`ning **egaligini o'z zimmasiga oladi (steals the reference)**. Boshqacha aytganda, `PyFloat_FromDouble(qiymat * 2)` chaqirilganda reference count 1 bilan yangi obyekt yaratiladi (biz "egamiz"), va `PyList_SetItem` chaqirilganda bu egalik **ro'yxatning o'ziga o'tkaziladi** — endi ro'yxat ushbu elementning yagona "egasi" hisoblanadi, va bizning tomonimizdan qo'shimcha `DECREF` chaqirish **noto'g'ri** bo'lardi (bu reference count'ni kerakli darajadan pastga tushirib, obyektni muddatidan oldin yo'q qilib yuborardi). Bu — C API'dagi "steals a reference" deb nomlangan, alohida hujjatlashtiriladigan xatti-harakat, va uni "borrows a reference" bilan aralashtirib yubormaslik muhim.

## Qisqacha xulosa

C kengaytmalar yozishda eng muhim va xatoga moyil qism — reference counting'ni qo'lda, to'g'ri boshqarish: har bir "yangi havola" oxir-oqibat `DECREF` qilinishi, har bir "qarzga olingan havola" esa faqat vaqtincha ishlatilishi (yoki saqlab qolinmoqchi bo'lsa, avval `INCREF` qilinishi) kerak. `PyList_SetItem`/`PyTuple_SetItem` kabi ba'zi funksiyalar uzatilgan havolani "yutib yuboradi" — bu alohida eslab qolinishi kerak bo'lgan qoida. Xatolarni ko'tarish ikki bosqichli (`PyErr_SetString` + `NULL` qaytarish), va boshqa funksiyalardan qaytgan xato holatlarini har doim tekshirish shart. `Py_BEGIN_ALLOW_THREADS`/`Py_END_ALLOW_THREADS` GIL'ni vaqtincha bo'shatib, uzoq davom etadigan sof-C hisoblashlarda boshqa Python oqimlariga ishlash imkonini beradi — lekin bu blok ichida Python obyektlariga murojaat qilib bo'lmaydi. Amaliyotda ko'p loyihalar bu murakkablikdan qochish uchun Cython, pybind11 yoki CFFI kabi yuqori darajadagi vositalarni afzal ko'radi, lekin "xom" C API bilimi CPython'ning o'zi qanday ishlashini to'liq tushunish, va zarurat tug'ilganda eng chuqur darajadagi optimallashtirishni amalga oshirish uchun qimmatli poydevor bo'lib qoladi.

# Specializing adaptive interpreter (PEP 659) va LEGB chuqur

## Bu darsda nimalarni o'rganasiz

- Python 3.11'dan boshlab interpretator **o'z-o'zini optimallashtirishi** (specializing adaptive interpreter) qanday ishlashini tushunasiz
- Bu o'zgarish nega Python'ni sezilarli tezlashtirganini bilib olasiz
- **LEGB** (Local → Enclosing → Global → Built-in) skoup zanjirini bytecode darajasida qanday amalga oshirilishini chuqur tushunasiz
- `globals()`, `locals()`, `__builtins__` bilan amaliy ishlashni mustahkamlaysiz

## Nazariy qism

### Muammo: Python dinamik, lekin dinamiklik narxi bor

Python'ning eng katta kuchli tomonlaridan biri — uning **dinamikligi**: bir xil `+` operatori sonlar, satrlar, ro'yxatlar uchun ishlaydi (7.1-darsda ko'rgan `tp_as_number->nb_add` orqali), va bu qaysi turlar ekanligi faqat **runtime**da (dastur ishlayotganda) ma'lum bo'ladi. Lekin bu moslashuvchanlikning narxi bor: har safar `a + b` bajarilganda, CPython avval `a` va `b`ning turlarini tekshirishi, keyin mos operatsiyani topishi kerak — bu C yoki Java kabi statik tipdagi tillarga nisbatan qo'shimcha "overhead" (qo'shimcha ish).

**Manba:** Ushbu dars PEP 659 (peps.python.org/pep-0659) va Python 3.11 rasmiy "What's New" hujjati asosida tuzilgan.

### Kuzatuv: amaliyotda turlar kamdan-kam o'zgaradi

PEP 659 (Specializing Adaptive Interpreter, Python 3.11'da amalga oshirilgan) muhim bir kuzatuvga asoslanadi: garchi Python **nazariy jihatdan** har safar turlar har xil bo'lishiga imkon bersa-da, **amaliyotda** bir xil bytecode joyi (masalan, sikl ichidagi `a + b`) deyarli har doim **bir xil turlar** bilan ishlaydi. Masalan:

```python
def yigindi_hisobla(royxat):
    natija = 0
    for son in royxat:
        natija += son   # agar royxat faqat int'lardan iborat bo'lsa, BU YERDA
                          # har doim int + int bo'ladi, minglab marta takrorlansa ham
    return natija
```

Agar interpretator "bu joyda deyarli har doim `int + int` bo'lyapti" degan naqshni **kuzatib, undan foydalansa**, u umumiy, "har qanday turga tayyor" sekin yo'l o'rniga, **maxsus, tezlashtirilgan** yo'ldan borishi mumkin.

### Qanday ishlaydi: "adaptiv" va "ixtisoslashtirilgan" bytecode

CPython 3.11+ har bir bytecode buyrug'ini boshida **umumiy** (generic) shaklda bajaradi. Lekin bir necha marta bajarilgandan keyin (bir necha o'nlab marta), agar interpretator bir xil turlar takrorlanayotganini payqasa, u o'sha **aynan shu bytecode joyini** ishga tushirilgan dasturning o'zida, "on-the-fly" (ishlash jarayonining o'zida) **ixtisoslashtirilgan** versiyaga almashtiradi:

```
Umumiy (generic) BINARY_OP  →  bir necha marotaba bajariladi, kuzatiladi  →  BINARY_OP_ADD_INT
   (har turga tayyor,             (turlar bir xilligi payqaladi)          (faqat int+int uchun,
    sekinroq)                                                              ancha tezroq yo'l)
```

Agar keyinroq turlar o'zgarsa (masalan, ro'yxatda birdan `float` paydo bo'lsa), interpretator buni payqaydi va **qaytadan umumiy** yo'lga o'tadi (yoki boshqa maxsus versiyaga moslashadi) — shuning uchun bu **"adaptiv"** deb ataladi: u statik emas, doimiy ravishda dastur xatti-harakatiga moslashadi.

Buni `dis` moduli orqali **bilvosita** kuzatish mumkin — `dis.dis(..., adaptive=True)` parametri (Python 3.11+) ixtisoslashtirilgan opcode'larni ko'rsatadi:

```python
import dis

def qoshish(a, b):
    return a + b

# Funksiyani ko'p marta chaqirib, "isitib" olamiz (interpretator ixtisoslashtirishi uchun)
for _ in range(1000):
    qoshish(1, 2)

# adaptive=True bilan, agar interpretator ixtisoslashtirgan bo'lsa,
# BINARY_OP o'rniga ichki ixtisoslashtirilgan variant ko'rinishi mumkin
dis.dis(qoshish, adaptive=True)
```

### Natija: real dasturlarda sezilarli tezlashish

Python 3.11 rasmiy hujjatlariga ko'ra, bu va boshqa optimallashtirishlar tufayli Python 3.11 — Python 3.10'ga nisbatan o'rtacha **10-60%** tezroq (dastur turiga qarab). Bu — sintaksisni **o'zgartirmasdan**, faqat CPython'ning ichki ijro mexanizmini yaxshilash orqali erishilgan yutuq, va bu — nega "Python'ni yangi versiyaga yangilash" ba'zan hech qanday kod o'zgartirishsiz sezilarli tezlashish berishi mumkinligining sababidir.

### LEGB — endi bytecode nazari bilan

1-3-boblarda "LEGB" qoidasini (Local → Enclosing → Global → Built-in — Python o'zgaruvchini qidirganda izlaydigan tartib) ko'rgan bo'lishingiz mumkin. Endi, 8.2-darsdagi bytecode bilimimiz asosida, bu qoidani **haqiqatan qanday amalga oshirilishini** ko'ramiz:

```python
import dis

x = "global x"

def tashqi():
    y = "enclosing y"

    def ichki():
        z = "local z"
        print(z)   # LOCAL — LOAD_FAST (eng tez, massiv indeksi)
        print(y)   # ENCLOSING — LOAD_DEREF (closure katakchasi orqali, 3.2-darsda ko'rgan)
        print(x)   # GLOBAL — LOAD_GLOBAL (modul lug'atida qidiruv)
        print(len)  # BUILT-IN — LOAD_GLOBAL (topilmasa, builtins modulida qidiriladi)

    return ichki

tashqi()()
```

Bytecode darajasida bu farq **aniq ko'rinadi**:

- **Local** (`z`) — `LOAD_FAST`: to'g'ridan-to'g'ri, freymning lokal o'zgaruvchilar massividan, indeks bo'yicha (eng tez).
- **Enclosing** (`y`) — `LOAD_DEREF`: closure "katakcha"sidan (cell obyekt) o'qiladi — bu 3.2-darsda ko'rgan closure mexanizmining bytecode ko'rinishi.
- **Global** (`x`) — `LOAD_GLOBAL`: modulning `__dict__`ida (lug'atida) nom bo'yicha qidiriladi.
- **Built-in** (`len`) — ham `LOAD_GLOBAL` (Python 3.11+da bitta opcode, ichki flag bilan farqlanadi): avval modul lug'atida, topilmasa `builtins` modulida qidiriladi.

Bu — nafaqat nazariy tartib, balki **haqiqiy, ketma-ket bajariladigan qidiruv operatsiyalari**: `Local` eng tez (indeks), `Global`/`Built-in` eng sekin (lug'at qidiruvi, va Built-in uchun ikkita lug'atda ketma-ket qidiruv bo'lishi mumkin).

### `globals()`, `locals()`, `__builtins__` — LEGB'ni qo'lda ko'rish

```python
x = "men globalman"

def funksiya():
    y = "men lokalman"
    print("Lokal nomlar:", locals())      # {'y': 'men lokalman'}
    print("'x' globals() da bormi:", 'x' in globals())   # True
    print("'y' globals() da bormi:", 'y' in globals())   # False — y faqat lokal!

    import builtins
    print("'len' builtins modulida bormi:", hasattr(builtins, 'len'))   # True

funksiya()
```

### `global` va `nonlocal` — LEGB'ni "buzish" (aslida — yo'nalishni o'zgartirish)

3.2-darsda ko'rgan `global` va `nonlocal` kalit so'zlari — bu, aslida, kompilyatorga "bu o'zgaruvchini **yangi lokal** sifatida emas, balki tashqi (mos ravishda global yoki enclosing) skoupdagi mavjud o'zgaruvchi sifatida ishlat" degan **ko'rsatma**. Bu qaror **kompilyatsiya vaqtida** (8.1-darsda ko'rgan bosqichda) qabul qilinadi — CPython kompilyatori har bir funksiyani ko'rib chiqib, unda `global`/`nonlocal` orqali e'lon qilinmagan, lekin ichida tayinlanadigan (`=` orqali qiymat beriladigan) har qanday nomni **avtomatik ravishda lokal** deb belgilaydi:

```python
sanoq = 0

def notogri_oshirish():
    sanoq += 1   # XATOLIK! Bu yerda "sanoq" AVTOMATIK ravishda LOKAL deb belgilanadi
                  # (chunki funksiya ichida "sanoq = ..." ko'rinishidagi tayinlash bor),
                  # lekin += o'ng tomonidagi sanoq hali tayinlanmagan — shuning uchun:
    # UnboundLocalError: local variable 'sanoq' referenced before assignment

def togri_oshirish():
    global sanoq   # kompilyatorga: "sanoq" GLOBAL, yangi lokal EMAS
    sanoq += 1
```

Bu xatolik (`UnboundLocalError`) — LEGB qoidasining **kompilyatsiya vaqtida, statik tahlil orqali** amalga oshirilishining to'g'ridan-to'g'ri natijasi: Python funksiya ichidagi har bir o'zgaruvchi nomi "lokal yoki emas"ligini **kod hali bajarilmasdan turib**, faqat kodning matnini ko'rib aniqlaydi.

## Amaliy misol

LEGB zanjirini va tezlik farqini amalda ko'rish:

```python
# legb_va_tezlik.py
import dis
import timeit


GLOBAL_QIYMAT = 42


def legb_namoyishi():
    enclosing_qiymat = "men enclosing'man"

    def eng_ichki():
        lokal_qiymat = "men lokalman"
        # Har bir qatorni ALOHIDA disassemble qilib ko'ramiz
        print(lokal_qiymat)          # LOAD_FAST
        print(enclosing_qiymat)      # LOAD_DEREF
        print(GLOBAL_QIYMAT)         # LOAD_GLOBAL
        print(abs(-5))                # LOAD_GLOBAL (builtins'dan)

    return eng_ichki


def lokal_orqali_qoshish(n):
    natija = 0
    for i in range(n):
        natija += i
    return natija


global_natija = 0

def global_orqali_qoshish(n):
    global global_natija
    global_natija = 0
    for i in range(n):
        global_natija += i
    return global_natija


if __name__ == "__main__":
    print("=== LEGB zanjiri amalda ===")
    legb_namoyishi()()

    print("\n=== Bytecode: lokal o'zgaruvchi bilan ishlash ===")
    dis.dis(lokal_orqali_qoshish)

    print("\n=== Tezlik taqqoslash: lokal vs global o'zgaruvchi ===")
    n = 100_000
    lokal_vaqt = timeit.timeit(lambda: lokal_orqali_qoshish(n), number=50)
    global_vaqt = timeit.timeit(lambda: global_orqali_qoshish(n), number=50)
    print(f"Lokal o'zgaruvchi bilan: {lokal_vaqt:.4f} soniya")
    print(f"Global o'zgaruvchi bilan: {global_vaqt:.4f} soniya")
    print(f"Farq: {(global_vaqt / lokal_vaqt - 1) * 100:.1f}% sekinroq global bilan")
```

## Keng tarqalgan xatolar

**Xato 1:** "Adaptiv interpretator" tufayli endi turlarga umuman e'tibor bermaslik mumkin deb o'ylash.
❌ "3.11+ endi avtomatik optimallashtiradi, demak men qaysi turlar bilan ishlayotganimga umuman ahamiyat bermasam ham bo'ladi" degan xulosa.
✅ To'g'ri: adaptiv interpretator **mavjud, bir xil kodning ko'p marta takrorlanishini** tezlashtiradi, lekin u algoritmning o'zini (masalan, noto'g'ri tanlangan ma'lumot tuzilmasini, 2.5-darsda ko'rgan) tuzata olmaydi. Turlarni izchil, oldindan bilingan tarzda ishlatish — hali ham yaxshi amaliyot, chunki bu ham o'qilishi, ham interpretator ixtisoslashtirishi uchun foydali.

**Xato 2:** Sikl ichida global o'zgaruvchiga ko'p marta murojaat qilishning "arzon" ekanligini o'ylash.
❌
```python
KOEFFITSIENT = 1.5

def hisobla(royxat):
    return [x * KOEFFITSIENT for x in royxat]   # har elementda GLOBAL qidiruv
```
✅ To'g'ri: agar funksiya juda ko'p marta yoki juda katta ro'yxat bilan chaqirilsa, global qiymatni funksiya boshida lokal o'zgaruvchiga "keshlash" (8.2-darsda ko'rgan `sqrt = math.sqrt` texnikasi) sezilarli tezlik farqini berishi mumkin — garchi bu, albatta, faqat **profiling orqali tasdiqlanganda** qo'llanilishi kerak bo'lgan mikro-optimallashtirish.

**Xato 3:** `UnboundLocalError`ni "Python xato qilyapti" deb o'ylab, `global` kalit so'zisiz muammoni "hal qilishga" urinish (masalan, boshqa nom qo'yib).
❌
```python
sanoq = 0
def oshirish():
    sanoq2 = sanoq + 1   # asl muammoni "aylanib o'tish", lekin global sanoq baribir o'zgarmaydi
```
✅ To'g'ri: agar funksiya ichida global o'zgaruvchini **haqiqatan o'zgartirish** kerak bo'lsa, `global` kalit so'zini ochiq ishlating. Lekin ko'pincha global holatni funksiyalar orqali o'zgartirish — yomon dizayn belgisi; buning o'rniga funksiyaga qiymatni argument sifatida berish va yangi qiymatni `return` qilish (yoki OOP, 4-bob, orqali holatni klass ichida boshqarish) ko'proq tavsiya etiladi.

## Mashq/topshiriq

**(Oson)** Uch darajali ichma-ich funksiyalar yozing (tashqi → o'rta → ichki), har bir darajada bitta o'zgaruvchi e'lon qiling, va eng ichki funksiyada barcha uchta o'zgaruvchini (shu jumladan bitta built-in funksiyani) chop eting. `locals()` va `globals()` natijalarini solishtiring.

**(O'rtacha)** `timeit` yordamida, 1,000,000 marta takrorlanadigan sikl ichida global o'zgaruvchiga murojaat qilish bilan, xuddi shu qiymatni funksiya boshida lokal o'zgaruvchiga saqlab, keyin lokal orqali murojaat qilishni solishtiring. Foizda qancha farq borligini hisoblang.

**(Qiyin)** `UnboundLocalError` yuzaga keladigan kichik dastur yozing, so'ng uni **ikki xil** usulda tuzating: (1) `global` kalit so'zi bilan, (2) global o'zgaruvchiga umuman tegmasdan, funksiyaga qiymatni argument sifatida berib va natijani qaytarib (funksional yondashuv). Ikkala yechimning afzallik/kamchiliklarini 2-3 gapda taqqoslang.

## Qisqacha xulosa

Python 3.11'dan boshlab CPython **specializing adaptive interpreter** (PEP 659) orqali dastur ishlash jarayonining o'zida ko'p marta takrorlanuvchi bytecode joylarini kuzatib, agar turlar barqaror bo'lsa, ularni avtomatik ravishda tezroq, "ixtisoslashtirilgan" versiyalarga almashtiradi — bu sintaksisni o'zgartirmasdan sezilarli tezlashishga olib keldi. LEGB skoup zanjiri (Local → Enclosing → Global → Built-in) esa shunchaki nazariy qoida emas — bu bytecode darajasida turli opcode'lar (`LOAD_FAST`, `LOAD_DEREF`, `LOAD_GLOBAL`) orqali amalga oshiriladigan, tezlik jihatidan **haqiqiy farqli** operatsiyalar zanjiri, va `global`/`nonlocal` kalit so'zlari — bu zanjirning yo'nalishini kompilyatsiya vaqtida o'zgartiruvchi ko'rsatmalar.

# 17.2. `VACUUM` va `autovacuum` — MVCC "qoldig'i"ni tozalash (ICH-ICHIGA)

## Bu darsda nimalarni o'rganasiz

- 17.1-darsda ko'rgan "o'lik" tuple'lar qanday tozalanishini o'rganasiz
- `VACUUM` va `VACUUM FULL` orasidagi farqni **jonli o'lchov bilan** ko'rasiz
- `autovacuum` — avtomatik, fon rejimida ishlaydigan tozalash mexanizmini bilasiz
- Jadval "shishishi" (bloat) nima ekanini va uni qanday kuzatishni o'rganasiz

## Nazariy qism

### Nega tozalash kerak

17.1-darsda ko'rganimizdek, har bir `UPDATE`/`DELETE` — eski tuple versiyasini darhol o'chirmaydi, uni shunchaki "o'lik" (dead) deb belgilaydi. Agar hech narsa bu "o'lik" tuple'larni tozalamasa, jadval fayli **cheksiz o'sib boraveradi** — hatto qatorlar soni o'zgarmasa ham! Aynan shu muammoni **`VACUUM`** yechadi.

### `VACUUM` — asosiy tozalash

```sql
VACUUM test_bloat_demo;
```

`VACUUM` quyidagilarni bajaradi: (1) jadvaldagi barcha "o'lik" tuple'larni (hech qanday faol tranzaksiya endi ularga muhtoj emasligini tekshirib) topadi; (2) ularni **bo'shatadi** — ya'ni ular egallagan joyni "qayta ishlatsa bo'ladigan" deb belgilaydi; (3) tegishli indekslarni ham tozalaydi. Lekin muhim nuance bor — buni sinab ko'ramiz:

```sql
CREATE TABLE test_bloat_demo (id SERIAL PRIMARY KEY, qiymat INTEGER);
INSERT INTO test_bloat_demo (qiymat) SELECT i FROM generate_series(1, 1000) AS i;

SELECT pg_size_pretty(pg_relation_size('test_bloat_demo')) AS boshlangich;
```

```
 boshlangich 
-------------
 40 kB
```

Endi jadvalni besh marta, to'liq yangilaymiz (har bir `UPDATE` — barcha 1000 qatorni yangilaydi):

```sql
UPDATE test_bloat_demo SET qiymat = qiymat + 1;
-- ... (jami 5 marta)

SELECT pg_size_pretty(pg_relation_size('test_bloat_demo')) AS ozgarishlardan_keyin;
```

```
 ozgarishlardan_keyin 
-----------------------
 208 kB
```

40 KB'dan **208 KB**ga o'sdi — bu, 17.1-darsda ko'rganimizdek, har bir `UPDATE` yangi tuple versiyasi yaratgani uchun. Endi oddiy `VACUUM` bajaramiz:

```sql
VACUUM test_bloat_demo;
SELECT pg_size_pretty(pg_relation_size('test_bloat_demo')) AS vacuumdan_keyin;
```

```
 vacuumdan_keyin 
------------------
 208 kB
```

**Hajm o'zgarmadi!** Bu — `VACUUM`ning eng muhim, ko'pincha kutilmagan xususiyati: u "o'lik" joylarni **operatsion tizimga qaytarmaydi** (fayl hajmini kamaytirmaydi), balki ularni PostgreSQL'ning o'z ichida, **kelajakdagi yozishlar uchun qayta ishlatiladigan** deb belgilaydi. Ya'ni, keyingi `INSERT`/`UPDATE`lar, yangi joy diskdan so'rashdan oldin, avval shu "bo'shatilgan" joylarni ishlatadi.

### `VACUUM FULL` — faylni qayta yozib, hajmni haqiqatan kamaytirish

Agar sizga haqiqatan **fayl hajmini kamaytirish** kerak bo'lsa (masalan, disk joyi tugab qolayotgan bo'lsa):

```sql
VACUUM FULL test_bloat_demo;
SELECT pg_size_pretty(pg_relation_size('test_bloat_demo')) AS vacuum_fulldan_keyin;
```

```
 vacuum_fulldan_keyin 
------------------------
 40 kB
```

`VACUUM FULL` — jadvalni **butunlay qayta yozadi**: faqat joriy, jonli tuple'larni yangi, kompakt faylga ko'chiradi, eski faylni esa o'chiradi. Natijada hajm asl `40 KB`ga qaytdi. Lekin bu jarayonning **jiddiy narxi** bor: `VACUUM FULL` jadvalga **eksklyuziv qulf** (`ACCESS EXCLUSIVE LOCK` — 21-bobda chuqur o'rganiladi) qo'yadi, ya'ni bajarilish davomida jadvalga hech qanday boshqa so'rov (hatto `SELECT` ham) kira olmaydi. Katta jadvallarda bu — daqiqalar, hatto soatlab davom etishi va butun ilovani "muzlatib" qo'yishi mumkin.

| | `VACUUM` | `VACUUM FULL` |
|---|---|---|
| **Fayl hajmini kamaytiradimi** | Yo'q — faqat ichki qayta ishlatish uchun belgilaydi | Ha — faylni qayta yozadi |
| **Qulflash** | Yengil (jadval bilan parallel ishlash mumkin) | Og'ir — `ACCESS EXCLUSIVE`, butun jadvalni bloklaydi |
| **Tezlik** | Tez | Sekin (butun jadvalni qayta yozish kerak) |
| **Qachon ishlatish** | Muntazam, fon rejimida (`autovacuum` orqali) | Kamdan-kam, faqat haqiqiy zarurat bo'lganda, texnik xizmat oynasida |

### `autovacuum` — avtomatik fon jarayoni

Amaliyotda, `VACUUM`ni qo'lda, doimiy ravishda chaqirib turish shart emas — PostgreSQL'da **`autovacuum`** deb ataladigan fon jarayoni bor, u jadvallarni kuzatib, kerak bo'lganda avtomatik `VACUUM` chaqiradi:

```sql
SHOW autovacuum;
SHOW autovacuum_vacuum_scale_factor;
SHOW autovacuum_vacuum_threshold;
```

```
 autovacuum 
------------
 on

 autovacuum_vacuum_scale_factor 
----------------------------------
 0.2

 autovacuum_vacuum_threshold 
-------------------------------
 50
```

`autovacuum` — standart holatda **yoqilgan** (`on`). U har bir jadval uchun, "o'lik" tuple'lar soni quyidagi formuladan oshganda, avtomatik `VACUUM`ni ishga tushiradi:

```
chegara = autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × jonli_qatorlar_soni
```

Bizning 1000 qatorli jadvalimiz uchun: `50 + 0.2 × 1000 = 250` — ya'ni, agar jadvalda **250 tadan ortiq** "o'lik" tuple to'plansa, `autovacuum` avtomatik ishga tushadi. Bu sozlamalarni har bir jadval uchun alohida ham belgilash mumkin (`ALTER TABLE jadval SET (autovacuum_vacuum_scale_factor = 0.05)`) — tez-tez yangilanadigan katta jadvallar uchun, standart `0.2` (20%) juda "kech" bo'lishi mumkin, va uni pasaytirish tavsiya etiladi.

Jadval qachon oxirgi marta tozalanganini kuzatish mumkin:

```sql
SELECT last_vacuum, last_autovacuum, vacuum_count, autovacuum_count
FROM pg_stat_user_tables WHERE relname = 'test_bloat_demo';
```

```
          last_vacuum          | last_autovacuum | vacuum_count | autovacuum_count 
--------------------------------+------------------+---------------+--------------------
 2026-08-30 03:35:58.389949+00 |                  |             1 |                 0
```

### Jadval "shishishi" (bloat) — muammoni erta payqash

Agar `autovacuum` yetarli tez-tez ishlamasa (masalan, juda band server, yoki sozlamalar juda "sust"), jadval **o'lik tuple'lar bilan to'lib**, kutilganidan sezilarli darajada katta bo'lib qolishi mumkin — bu holat **bloat** deb ataladi. Bloat'ning ta'siri: (1) jadval fayli kattalashadi, disk joyi behuda ketadi; (2) `SELECT ... FROM jadval` (hatto `WHERE`siz, to'liq skanerlash) sekinlashadi, chunki PostgreSQL o'lik tuple'larni ham "o'qib o'tishi", faqat keyin e'tiborsiz qoldirishi kerak.

Bloat darajasini taxminiy baholash uchun `n_live_tup`/`n_dead_tup` nisbatidan foydalanish mumkin:

```sql
SELECT relname, n_live_tup, n_dead_tup,
       round(100.0 * n_dead_tup / GREATEST(n_live_tup + n_dead_tup, 1), 1) AS olik_foizi
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 5;
```

Agar biror jadvalda `olik_foizi` doimiy ravishda yuqori (masalan, 20%dan ko'p) bo'lib tursa — bu, o'sha jadval uchun `autovacuum` sozlamalarini "agressivroq" qilish kerakligining belgisi.

## Amaliy misol

**Vazifa:** Bitta jadvalda, `VACUUM`dan oldin va keyin `n_dead_tup` qanday o'zgarishini kuzating.

```sql
CREATE TABLE test_vacuum_kuzatish (id SERIAL PRIMARY KEY, qiymat INTEGER);
INSERT INTO test_vacuum_kuzatish (qiymat) SELECT i FROM generate_series(1, 500) AS i;
UPDATE test_vacuum_kuzatish SET qiymat = qiymat + 1;

SELECT n_live_tup, n_dead_tup FROM pg_stat_user_tables WHERE relname = 'test_vacuum_kuzatish';

VACUUM test_vacuum_kuzatish;

SELECT n_live_tup, n_dead_tup FROM pg_stat_user_tables WHERE relname = 'test_vacuum_kuzatish';
```

## Keng tarqalgan xatolar

**Xato 1:** Disk joyini tejash uchun, muntazam ravishda `VACUUM FULL`ni ishlatish (oddiy `VACUUM` o'rniga).
❌ `VACUUM FULL`ning eksklyuziv qulfi, ishlab turgan tizimda uzoq "to'xtash" (downtime)ga olib kelishi mumkin.
✅ Kundalik texnik xizmat uchun oddiy `VACUUM`ga (yoki `autovacuum`ga) ishoning; `VACUUM FULL`ni faqat rejalashtirilgan texnik xizmat oynasida, haqiqiy zarurat bo'lganda ishlating.

**Xato 2:** `autovacuum`ni "keraksiz resurs sarflaydi" deb, uni butunlay o'chirib qo'yish.
❌ `autovacuum`siz, jadvallar tez orada nazoratsiz shishib ketadi, va bu muammoni keyinroq, ancha qiyinroq holatda (masalan, favqulodda `VACUUM FULL` bilan) yechishga majbur bo'lasiz.
✅ `autovacuum`ni har doim yoqilgan holda qoldiring; agar u "yetarlicha tez-tez ishlamayapti" deb hisoblasangiz, uni **o'chirish** emas, balki sozlamalarini (`scale_factor`, `threshold`) moslashtiring.

**Xato 3:** `VACUUM`dan keyin `pg_relation_size()` o'zgarmaganini ko'rib, "VACUUM ishlamadi" deb xulosa chiqarish.
❌ Bu — `VACUUM`ning **kutilgan, normal** xatti-harakati (yuqorida ko'rganimizdek).
✅ `VACUUM`ning ishlaganini tekshirish uchun, fayl hajmi o'rniga `n_dead_tup` yoki `last_vacuum`/`vacuum_count` ustunlaridan foydalaning.

## Mashq/topshiriq

**(Oson)** `pg_stat_user_tables`dan foydalanib, `dokon_bazasi`dagi barcha jadvallar orasida eng ko'p `n_dead_tup`ga ega bo'lganini toping.

**(O'rtacha)** Yangi test jadval yaratib, uni 3 marta to'liq yangilang, so'ng `VACUUM (VERBOSE)` buyrug'i bilan (qo'shimcha tafsilotlar chiqaradigan variant) tozalang va natijada chiqadigan xabarlarni o'qib chiqing.

**(Qiyin)** Bitta jadval uchun `autovacuum_vacuum_scale_factor`ni standart `0.2`dan `0.05`ga tushiring (`ALTER TABLE ... SET (...)`), va bu o'zgarish amaliy jihatdan nimani anglatishini (jadval necha foiz "o'lik" tuple to'plaganda `autovacuum` ishga tushishini, yangi va eski qiymat bilan) hisoblab tushuntiring.

Bu — tez-tez yangilanadigan jadvallar uchun foydali, chunki ular bloat'ga tezroq erishishning oldini oladi.)

## Qisqacha xulosa

`VACUUM` — 17.1-darsda ko'rgan "o'lik" tuple'larni tozalaydi, lekin fayl hajmini **kamaytirmaydi** (faqat ichki qayta ishlatish uchun bo'shatadi); `VACUUM FULL` esa faylni to'liq qayta yozib, haqiqiy hajm qisqarishini beradi, lekin og'ir, eksklyuziv qulf bilan. `autovacuum` — bu jarayonni fon rejimida, avtomatik boshqaradigan standart yoqilgan mexanizm, va uning sozlamalarini (ayniqsa `scale_factor`) jadvalning yangilanish chastotasiga mos moslashtirish — katta, faol tizimlarda muhim amaliy ko'nikma. Bu — 17-bobni yakunlaydi: MVCC va VACUUM'ning to'liq rasmini oldingiz. Keyingi, 18-bobda **indekslash mexanizmini chuqur** — B-tree, GIN, GiST, BRIN va boshqa indeks turlarini — o'rganamiz.

# 17.1. MVCC — ko'p versiyali parallellik boshqaruvi (ICH-ICHIGA)

## Bu darsda nimalarni o'rganasiz

- **MVCC** (Multi-Version Concurrency Control) nima ekanini va u nima uchun kerakligini tushunasiz
- `xmin`/`xmax` — har bir qatorga "ko'rinmas" biriktirilgan tizim ustunlarini o'rganasiz
- `UPDATE` aslida **yangi tuple versiyasi yaratishi**ni, "joyida o'zgartirish" emasligini jonli ko'rasiz
- MVCC'ning 13.2-darsda ko'rgan izolyatsiya darajalari bilan qanday bog'liqligini tushunasiz

## Nazariy qism

### Muammo: o'qish va yozish bir-biriga xalaqit bermasligi kerak

13-bobda tranzaksiyalar va izolyatsiya darajalarini o'rgandik. Lekin savol tug'iladi: PostgreSQL, bitta qator ustida bir vaqtning o'zida **o'qish** (`SELECT`) va **yozish** (`UPDATE`) amallari sodir bo'layotganda, buni qanday jismonan amalga oshiradi? Eng sodda (lekin yomon) yechim — o'qiyotgan tranzaksiyani, yozish tugaguncha "kutib turish"ga majburlash bo'lardi. Lekin bu — unumdorlikni keskin pasaytirar edi.

PostgreSQL buning o'rniga **MVCC** (Multi-Version Concurrency Control — "ko'p versiyali parallellik boshqaruvi") strategiyasini qo'llaydi: **`UPDATE` hech qachon qatorni "joyida" o'zgartirmaydi**. Buning o'rniga, u qatorning **butunlay yangi nusxasini** yaratadi, eskisini esa "eskirgan" deb belgilaydi (lekin darhol o'chirmaydi). Shu tufayli, o'qiyotgan tranzaksiya eski nusxani ko'rishda davom etaveradi, yozish esa hech kimni to'sib qo'ymaydi.

### `xmin`/`xmax` — har bir qatorning "ko'rinmas" tizim ustunlari

Har bir jadval qatori, siz e'lon qilgan ustunlardan tashqari, PostgreSQL tomonidan avtomatik qo'shiladigan **tizim ustunlari**ga ega — ular odatiy `SELECT *`da ko'rinmaydi, lekin ularni **aniq** so'rash mumkin:

```sql
CREATE TABLE test_mvcc_demo (
    id SERIAL PRIMARY KEY,
    qiymat TEXT
);
INSERT INTO test_mvcc_demo (qiymat) VALUES ('Boshlangich');

SELECT xmin, xmax, id, qiymat FROM test_mvcc_demo;
```

```
 xmin | xmax | id |   qiymat    
------+------+----+-------------
 1079 |    0 |  1 | Boshlangich
```

| Ustun | Ma'nosi |
|---|---|
| `xmin` | Bu tuple versiyasini **yaratgan** tranzaksiyaning ID raqami (`txid`) |
| `xmax` | Bu tuple versiyasini **eskirtirgan** (yangilagan yoki o'chirgan) tranzaksiyaning ID raqami — `0` bo'lsa, hali hech kim eskirtirmagan, ya'ni bu **hozirgi, joriy** versiya |

`xmin = 1079` — bu qator, `txid` raqami `1079` bo'lgan tranzaksiya (bizning `INSERT`imiz) tomonidan yaratilgan. `xmax = 0` — bu qatorni hali hech kim yangilamagan yoki o'chirmagan.

### `UPDATE` amalida nima sodir bo'ladi — jonli tekshiramiz

```sql
UPDATE test_mvcc_demo SET qiymat = 'Yangilangan' WHERE id = 1;
SELECT xmin, xmax, id, qiymat FROM test_mvcc_demo;
```

```
 xmin | xmax | id |   qiymat    
------+------+----+-------------
 1080 |    0 |  1 | Yangilangan
```

Oddiy `SELECT` — faqat **joriy** versiyani ko'rsatadi: `xmin = 1080` (buni yangilagan tranzaksiya), `xmax = 0`. Lekin savol — eski versiya (`xmin=1079`, `qiymat='Boshlangich'`) **fizik jihatdan** qayerga g'oyib bo'ldi? U hali ham, 16.1-darsda o'rgangan sahifada, **jismonan mavjud** — buni `pageinspect` bilan tasdiqlaymiz:

```sql
SELECT lp, t_xmin, t_xmax, t_ctid
FROM heap_page_items(get_raw_page('test_mvcc_demo', 0));
```

```
 lp | t_xmin | t_xmax | t_ctid 
----+--------+--------+--------
  1 |   1079 |   1080 | (0,2)
  2 |   1080 |      0 | (0,2)
```

Bu natija — MVCC'ning ishlashini **aynan** ko'rsatadi:

- **`lp=1`** (eski versiya): `t_xmin=1079` (kim yaratgan), `t_xmax=1080` (**kim eskirtirgan** — bizning `UPDATE`imiz!), `t_ctid=(0,2)` — bu, "yangi versiya qayerda ekanligiga ishora" (16.1-darsdagi `ctid` tushunchasi shu yerda amaliy ma'no kasb etadi).
- **`lp=2`** (yangi versiya): `t_xmin=1080` (`UPDATE` uni yaratdi), `t_xmax=0` (hali hech kim eskirtirmagan — bu joriy versiya), `t_ctid=(0,2)` — **o'ziga** ishora qiladi (bu "men — eng oxirgi versiyaman" degani).

Demak: **`UPDATE 1 ta qator` — aslida 2 ta jismoniy tuple bilan yakunlandi** — eski (endi "o'lik", lekin hali o'chirilmagan) va yangi. Bu — MVCC'ning "narxi": har bir `UPDATE`, jismoniy jihatdan, eski ma'lumotni darhol yo'q qilmaydi, balki uni ortda qoldiradi.

### MVCC va izolyatsiya darajalari — 13.2-dars bilan bog'liqlik

Endi 13.2-darsda ko'rgan "non-repeatable read" hodisasini, MVCC nuqtai nazaridan tushuntirish mumkin: `READ COMMITTED` tranzaksiyasi, har bir yangi `SELECT` uchun, "hozircha eng so'nggi `COMMIT` qilingan `xmax=0` versiya"ni qidiradi — shuning uchun orada boshqa tranzaksiya `COMMIT` qilsa, keyingi `SELECT` **yangi** tuple versiyasini "ko'radi". `REPEATABLE READ` esa, tranzaksiya **boshlangan paytdagi** `txid`ni "eslab qoladi" va faqat o'sha vaqtga mos versiyalarni ko'rsatadi — hatto keyinroq yangi versiyalar paydo bo'lsa ham. Bu — nega `REPEATABLE READ` ma'lumotni "fizik jihatdan o'chirmasdan", faqat **qaysi versiyani ko'rsatishni tanlash** orqali izchillikni ta'minlay olishining sababi: barcha kerakli versiyalar, hali ham, jadval faylida jismonan mavjud.

## Amaliy misol

**Vazifa:** Bitta qatorni ikki marta ketma-ket yangilab, natijada nechta jismoniy tuple versiyasi hosil bo'lishini bashorat qiling va tasdiqlang.

```sql
UPDATE test_mvcc_demo SET qiymat = 'Ikkinchi marta' WHERE id = 1;
UPDATE test_mvcc_demo SET qiymat = 'Uchinchi marta' WHERE id = 1;

SELECT lp, t_xmin, t_xmax FROM heap_page_items(get_raw_page('test_mvcc_demo', 0));
```

Kutilgan natija: endi jami **3 ta** tuple versiyasi bo'lishi kerak — ikkitasi "o'lik" (`t_xmax != 0`), bittasi joriy (`t_xmax = 0`).

## Keng tarqalgan xatolar

**Xato 1:** `UPDATE`ni "arzon", faqat o'zgargan baytlarni qayta yozadigan amal deb tushunish.
❌ MVCC tufayli, `UPDATE` — **butun yangi tuple** yaratadi, hatto siz faqat bitta kichik ustunni o'zgartirgan bo'lsangiz ham (16.2-darsdagi HOT update bu "narx"ni biroz kamaytiradi, lekin uni butunlay yo'qqa chiqarmaydi).
✅ Juda tez-tez, katta hajmda `UPDATE` qilinadigan jadvallarda, bu "narx"ni hisobga oling — bu 17.2-darsdagi VACUUM ehtiyojining asosiy sababi.

**Xato 2:** `xmin`/`xmax`ni ilova darajasida, "versiyalash" (versioning) tizimi sifatida ishlatishga urinish.
❌ Bu — PostgreSQL'ning **ichki**, past darajadagi mexanizmi; `txid` raqamlari, VACUUM tozalagandan keyin, **qayta ishlatilishi** mumkin (17.2-darsda "transaction ID wraparound" muammosi sifatida ko'riladi).
✅ Agar ilovada "tarix" yoki "versiyalash" kerak bo'lsa, 12.2-darsdagi audit jadvali naqshidan foydalaning — bu sizning to'liq nazoratingizdagi, barqaror yechim.

**Xato 3:** "Eski" tuple versiyasi darhol yo'qoladi deb o'ylash.
❌ `UPDATE`/`DELETE`dan keyin, eski versiya **darhol** yo'q bo'lib ketmaydi — u disk fayli ichida qoladi, VACUUM (17.2-dars) ishga tushmaguncha.
✅ Bu — nega tez-tez yangilanadigan jadvallar vaqt o'tishi bilan "shishib" (bloat) ketishining sababini tushunish uchun asosiy kalit.

## Mashq/topshiriq

**(Oson)** `mijozlar` jadvalidagi biror qatorning `xmin`/`xmax` qiymatlarini ko'ring va bu qator hech qachon yangilanmaganini (`xmax = 0`) tasdiqlang.

**(O'rtacha)** Yangi test jadval yarating, bitta qator kiriting, so'ng uni `DELETE` qiling (lekin `COMMIT`dan oldin, boshqa sessiyada `heap_page_items` bilan tekshiring — `xmax`ning qiymati o'zgarganini, lekin tuple hali ham jismonan mavjudligini ko'rasiz).

**(Qiyin)** `test_mvcc_demo` jadvalida 5 marta ketma-ket `UPDATE` bajaring, so'ng `heap_page_items`da nechta tuple versiyasi borligini va ulardan nechtasi "joriy" (`t_xmax = 0`) ekanini hisoblang.

SELECT count(*) AS jami_versiyalar,

## Qisqacha xulosa

MVCC — PostgreSQL'ning o'qish va yozishni bir-biriga xalaqit bermasdan bajarish strategiyasi: `UPDATE`/`DELETE` qatorni "joyida" o'zgartirmaydi, balki har bir qator uchun `xmin` (yaratgan tranzaksiya) va `xmax` (eskirtirgan tranzaksiya) tizim ustunlari orqali **bir nechta versiyani** saqlaydi. Bu — 13.2-darsdagi izolyatsiya darajalarining ichki mexanizmi: turli tranzaksiyalar, o'z "vaqt nuqtasi"ga mos versiyani ko'radi. Bu strategiyaning "narxi" — eski versiyalar darhol yo'q bo'lib ketmaydi, ular jismonan qolib, joy egallaydi. Keyingi darsda bu "qoldiq"ni tozalovchi mexanizmni — **VACUUM**ni — chuqur o'rganamiz.

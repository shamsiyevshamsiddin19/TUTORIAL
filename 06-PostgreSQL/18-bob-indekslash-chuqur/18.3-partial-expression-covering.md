# 18.3. Qisman, ifoda va qamrovchi indekslar — `partial`, `expression`, `INCLUDE` (ICH-ICHIGA)

## Bu darsda nimalarni o'rganasiz

- **Qisman (partial) indeks** — faqat qatorlarning bir qismini qamrab oluvchi, ixchamroq indeksni o'rganasiz
- **Ifoda (expression) indeksi** — ustunning o'zi emas, undan **hisoblangan qiymat** bo'yicha indekslashni bilasiz
- **Qamrovchi (covering) indeks** — `INCLUDE` bandi bilan **Index-Only Scan**ga erishishni jonli ko'rasiz
- Bu uch texnikani birlashtirib, so'rovlarni maksimal darajada optimallashtirishni tushunasiz

## Nazariy qism

### Qisman (partial) indeks — faqat kerakli qismni indekslash

18.1-darsda "indeks bepul emas" degan edik — har bir qo'shimcha indeks, disk joyi va yozish tezligi hisobiga keladi. Lekin ko'pincha, sizga jadvalning **faqat bir qismi** bo'yicha tez qidiruv kerak bo'ladi. Bunday holatda, **qisman indeks** — `CREATE INDEX ... WHERE shart` — ajoyib yechim:

```sql
CREATE INDEX idx_qiymat_katta ON test_index_katta (qiymat) WHERE qiymat > 90000;
```

Bu indeks — faqat `qiymat > 90000` bo'lgan qatorlarni o'z ichiga oladi (50 000 qatordan taxminan 5 000 tasi). Hajmni solishtiramiz:

```sql
SELECT pg_size_pretty(pg_relation_size('idx_qiymat_katta')) AS partial_hajmi,
       pg_size_pretty(pg_relation_size('idx_test_qiymat')) AS toliq_hajmi;
```

```
 partial_hajmi | toliq_hajmi 
----------------+-------------
 128 kB         | 1048 kB
```

Qisman indeks — to'liq indeksdan **~8 marta kichikroq**! Va u, shu shartga mos so'rovlarda, xuddi to'liq indeks kabi samarali ishlaydi:

```sql
EXPLAIN ANALYZE SELECT * FROM test_index_katta WHERE qiymat > 90000 AND qiymat < 95000;
```

```
                                                           QUERY PLAN                                                           
-----------------------------------------------------------------------------------------------------------------------------------
 Bitmap Heap Scan on test_index_katta  (cost=56.35..414.21 rows=2590 width=18) (actual time=0.232..1.072 rows=2539 loops=1)
   Recheck Cond: ((qiymat < 95000) AND (qiymat > 90000))
   Heap Blocks: exact=319
   ->  Bitmap Index Scan on idx_qiymat_katta  (cost=0.00..55.71 rows=2590 width=0) (actual time=0.198..0.198 rows=2539 loops=1)
         Index Cond: (qiymat < 95000)
```

> **Muhim shart:** PostgreSQL, qisman indeksni faqat, so'rovdagi `WHERE` sharti indeksning **o'z shartini "qamrab olishi"** (mantiqiy jihatdan uni nazarda tutishi) mumkin bo'lgandagina ishlatadi. Masalan, `WHERE qiymat > 95000` (indeksning `> 90000` shartidan **qattiqroq**) — ishlaydi; lekin `WHERE qiymat > 50000` (indeksning shartidan **kengroq**) — ishlamaydi, chunki indeks `50000-90000` oralig'idagi qatorlarni **umuman o'z ichiga olmaydi**.

**Amaliy qo'llanish:** qisman indekslar ayniqsa quyidagi holatlarda foydali — "faol" (`holati != 'yakunlangan'`) buyurtmalar, "o'chirilmagan" (`ochirilgan_vaqti IS NULL`) yozuvlar, yoki "muhim" (`muhim = true`) qatorlar kabi, jadvalning kichik, lekin **tez-tez so'raladigan** qismini alohida indekslash.

### Ifoda (expression) indeksi — hisoblangan qiymat bo'yicha indekslash

Ba'zan siz ustunning **o'zi** emas, undan **hisoblangan** natija bo'yicha qidirasiz — masalan, katta-kichik harfga sezgir bo'lmagan qidiruv uchun `LOWER(ustun)`. Oddiy indeks bunga yordam bermaydi:

```sql
CREATE INDEX idx_kategoriya_lower ON test_index_katta (LOWER(kategoriya));

EXPLAIN ANALYZE SELECT * FROM test_index_katta WHERE LOWER(kategoriya) = 'a';
```

```
                                                            QUERY PLAN                                                            
------------------------------------------------------------------------------------------------------------------------------------
 Bitmap Heap Scan on test_index_katta  (cost=6.23..324.34 rows=250 width=18) (actual time=0.266..1.771 rows=8403 loops=1)
   Recheck Cond: (lower(kategoriya) = 'a'::text)
   Heap Blocks: exact=319
   ->  Bitmap Index Scan on idx_kategoriya_lower  (cost=0.00..6.17 rows=250 width=0) (actual time=0.228..0.228 rows=8403 loops=1)
         Index Cond: (lower(kategoriya) = 'a'::text)
```

Diqqat qiling — bu yerda **oddiy** `kategoriya` ustuniga indeks bor edi (18.1-darsdan), lekin u ishlatilmadi! Buni tasdiqlash uchun, `idx_kategoriya_lower`ni o'chirib, qayta sinaymiz:

```sql
DROP INDEX idx_kategoriya_lower;
EXPLAIN SELECT * FROM test_index_katta WHERE LOWER(kategoriya) = 'a';
```

```
                              QUERY PLAN                              
------------------------------------------------------------------------
 Seq Scan on test_index_katta  (cost=0.00..1069.00 rows=250 width=18)
   Filter: (lower(kategoriya) = 'a'::text)
```

Bu **muhim dalil**: oddiy `kategoriya` ustunidagi indeks, `LOWER(kategoriya)` ifodasi bilan **hech qanday aloqasi yo'q** — PostgreSQL uchun bular ikkita butunlay boshqa "kalit". Faqat aynan **shu ifoda** (`LOWER(kategoriya)`) bo'yicha yaratilgan indeks, aynan **shu ifoda** ishlatilgan so'rovlarda qo'llaniladi.

**Amaliy qo'llanish:** katta-kichik harfga sezgir bo'lmagan qidiruv (`LOWER()`), `JSONB`dagi bitta maydonni tez-tez qidirish (`xususiyatlar ->> 'rang'`), yoki matnni normallashtirilgan holatda solishtirish (`TRIM()`, `unaccent()`) — bularning barchasi expression indeksdan foyda ko'radi.

### Qamrovchi (covering) indeks — `INCLUDE` bilan Index-Only Scan

18.1-darsda `Index Scan`ning ikki bosqichi borligini ko'rdik: (1) indeksdan mos yozuvni topish, (2) haqiqiy qator ma'lumotini olish uchun **asosiy jadval** (heap)ga "borish". Agar so'rov, indeksning o'zida **mavjud bo'lmagan** ustunlarni ham so'rasa (masalan, `SELECT qiymat, kategoriya ... WHERE qiymat = ...`, lekin indeks faqat `qiymat`da bo'lsa), PostgreSQL har doim asosiy jadvalga "borishga" majbur.

`INCLUDE` bandi — bu qo'shimcha "borish"ning oldini oladi, ustunlarni indeksning **o'ziga qo'shib qo'yish** orqali:

```sql
CREATE INDEX idx_qiymat_covering ON test_index_katta (qiymat) INCLUDE (kategoriya);

EXPLAIN (ANALYZE, BUFFERS) SELECT qiymat, kategoriya FROM test_index_katta WHERE qiymat = 12345;
```

```
                                                                QUERY PLAN                                                                 
---------------------------------------------------------------------------------------------------------------------------------------------
 Index Only Scan using idx_qiymat_covering on test_index_katta  (cost=0.29..4.31 rows=1 width=6) (actual time=0.036..0.037 rows=2 loops=1)
   Index Cond: (qiymat = 12345)
   Heap Fetches: 0
   Buffers: shared hit=1 read=2
 Planning Time: 0.484 ms
 Execution Time: 0.056 ms
```

Ikkita hal qiluvchi detal: (1) `Index Only Scan` — oddiy `Index Scan` emas, PostgreSQL asosiy jadvalga **umuman murojaat qilmasligi** mumkinligini bildiradi; (2) `Heap Fetches: 0` — bu buni **tasdiqlaydi**: so'rov davomida asosiy jadvaldan **birorta ham** qo'shimcha o'qish bo'lmadi, chunki kerakli barcha ma'lumot (`qiymat` — indekslangan, `kategoriya` — `INCLUDE`langan) indeksning o'zida allaqachon mavjud edi.

`INCLUDE`dagi ustunlar — indeksning **saralash tartibiga kirmaydi** (ular faqat "qo'shimcha yuk" sifatida qo'shiladi), shuning uchun ular bo'yicha qidirish yoki saralash mumkin emas — ular faqat `SELECT` ro'yxatida ishlatilishi mumkin. Bu farq, `CREATE INDEX (qiymat, kategoriya)` (ikkalasi ham "haqiqiy" indeks kaliti) bilan `CREATE INDEX (qiymat) INCLUDE (kategoriya)` orasidagi asosiy farqdir: birinchisida `kategoriya` bo'yicha ham qidirish mumkin (lekin indeks kattaroq va sekinroq yangilanadi), ikkinchisida esa `kategoriya` faqat "qo'shimcha ma'lumot" sifatida qatnashadi (indeks yengilroq).

### Uch texnikani birlashtirib ishlatish

Bu uch texnika — bir-biriga **zid emas**, ularni birlashtirib ishlatish mumkin: masalan, "faqat `holati = 'faol'` bo'lgan buyurtmalar uchun, `mijoz_id` bo'yicha, `sana`ni ham o'z ichiga olgan" indeks:

```sql
CREATE INDEX idx_faol_buyurtmalar ON buyurtmalar (mijoz_id) INCLUDE (sana)
WHERE holati IN ('yangi', 'jarayonda');
```

Bu — bir vaqtning o'zida: qisman (faqat "faol" buyurtmalar), va qamrovchi (`sana`ni ham o'z ichiga oladi, Index-Only Scan imkoniyati bilan).

## Amaliy misol

**Vazifa:** `mijozlar` jadvalida, faqat Toshkent shahridagi mijozlar uchun, ism va email'ni ham qamrab oluvchi optimallashtirilgan indeks yarating.

```sql
CREATE INDEX idx_toshkent_mijozlar ON mijozlar (id) INCLUDE (ism, email)
WHERE shahar = 'Toshkent';

EXPLAIN SELECT id, ism, email FROM mijozlar WHERE shahar = 'Toshkent' AND id = 3;
```

## Keng tarqalgan xatolar

**Xato 1:** Ifoda indeksi yaratib, so'rovda **biroz boshqacha** ifoda yozib, nega indeks ishlamayotganini tushunmaslik.
❌ `CREATE INDEX ... (LOWER(nomi))` yaratib, so'rovda `WHERE UPPER(nomi) = ...` yozish — bular PostgreSQL uchun **butunlay boshqa** ifodalar, indeks ishlamaydi.
✅ So'rovdagi ifoda, indeks yaratishda ishlatilgan ifoda bilan **so'zma-so'z** (yoki mantiqiy ekvivalent, PostgreSQL buni tan olsa) mos kelishi kerak.

**Xato 2:** `INCLUDE`ga juda ko'p ustun qo'shib, indeksni asosiy jadvalning "nusxasi"ga aylantirish.
❌ Bu, indeksning o'zini kattalashtirib, uning "ixcham, tez" degan asosiy afzalligini yo'qqa chiqaradi.
✅ `INCLUDE`ga faqat, aynan shu indeks ishlatiladigan so'rovlarda tez-tez so'raladigan, kam sonli ustunlarni qo'shing.

**Xato 3:** Qisman indeksning shartini, so'rovlar shartidan **kengroq** deb noto'g'ri loyihalash.
❌ Agar indeks sharti (`WHERE qiymat > 90000`) so'rov shartidan (`WHERE qiymat > 50000`) **tor** bo'lsa, indeks ishlatilmaydi — chunki u so'rov talab qilgan barcha ma'lumotni qamrab olmaydi.
✅ Qisman indeks shartini har doim, uni ishlatishi kutilgan so'rovlar shartidan **teng yoki kengroq** qilib loyihalang.

## Mashq/topshiriq

**(Oson)** `buyurtmalar` jadvalida, faqat `holati = 'bekor qilindi'` bo'lgan buyurtmalar uchun qisman indeks yarating va uning hajmini to'liq jadval hajmi bilan solishtiring.

**(O'rtacha)** `xodimlar` jadvalida, `ish_haqi`dan 10% bonus hisoblangan qiymat bo'yicha qidirishni tezlashtiradigan ifoda indeksi yarating (`ish_haqi * 1.1`), va `EXPLAIN` bilan uning ishlatilishini tasdiqlang.

**(Qiyin)** `mahsulotlar` jadvalida, `kategoriya` bo'yicha qidirilganda `nomi` va `narxi`ni ham qamrab oluvchi (`INCLUDE`) indeks yarating, so'ng `EXPLAIN (ANALYZE, BUFFERS)` bilan `Heap Fetches: 0` ekanini tasdiqlang.

## Qisqacha xulosa

Qisman (`WHERE`) indeks — faqat kerakli qatorlarni qamrab olib, hajmni sezilarli kamaytiradi (bizning testimizda ~8 marta); ifoda (`expression`) indeksi — ustunning o'zi emas, undan hisoblangan qiymat bo'yicha qidiruvni tezlashtiradi, lekin so'rovdagi ifoda bilan **aniq mos kelishi shart**; qamrovchi (`INCLUDE`) indeks esa — qo'shimcha ustunlarni "yuklab", **Index-Only Scan** (`Heap Fetches: 0`) orqali asosiy jadvalga umuman murojaat qilmaslikka erishadi. Bu uch texnika birgalikda — indeksni, aynan sizning so'rovlaringiz uchun **mukammal moslashtirilgan** holga keltirish imkonini beradi. Bu — 18-bobni yakunlaydi: B-tree, GIN, BRIN, Hash va indekslarni moslashtirish texnikalarini chuqur o'rgandingiz. Keyingi, 19-bobda **Query Planner va `EXPLAIN`**ni — PostgreSQL har bir so'rov uchun qanday "strategiya" tanlashini — chuqur o'rganamiz.

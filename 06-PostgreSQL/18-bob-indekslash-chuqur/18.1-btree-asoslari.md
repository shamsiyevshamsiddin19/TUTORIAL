# 18.1. B-tree indeks — asosiy mexanizm (ICH-ICHIGA)

## Bu darsda nimalarni o'rganasiz

- Indeks nima ekanini va u nima uchun so'rovlarni tezlashtirishini tushunasiz
- `EXPLAIN ANALYZE` bilan Seq Scan va Index Scan orasidagi farqni **real o'lchov** bilan ko'rasiz
- B-tree — PostgreSQL'ning standart, eng ko'p ishlatiladigan indeks turi — qanday ishlashini bilasiz
- Bitmap Index Scan nima ekanini va u qachon ishlatilishini tushunasiz
- Indeks "bepul emas"ligini — uning yozish tezligiga va disk joyiga ta'sirini — bilasiz

## Nazariy qism

### Indeks nima va u nima uchun kerak

Tasavvur qiling — sizda 50 000 qatorli katta jadval bor, va sizga bitta aniq qiymatga mos qatorni topish kerak. Indekssiz, PostgreSQL **har bir** qatorni, birma-bir tekshirishi kerak bo'ladi — bu **Seq Scan** (ketma-ket skanerlash) deb ataladi. **Indeks** — kitobning oxiridagi alfavit ko'rsatkichiga o'xshaydi: u, qiymatlarni oldindan **tartiblangan** tuzilmada saqlab, PostgreSQL'ga kerakli qatorni butun jadvalni "varaqlab chiqmasdan" topish imkonini beradi.

### Seq Scan vs Index Scan — jonli o'lchov

50 000 qatorli test jadval yaratamiz:

```sql
CREATE TABLE test_index_katta (
    id SERIAL PRIMARY KEY,
    kategoriya TEXT,
    qiymat INTEGER,
    yaratilgan_vaqti TIMESTAMP DEFAULT NOW()
);
INSERT INTO test_index_katta (kategoriya, qiymat)
SELECT
    (ARRAY['A','B','C','D'])[1 + (random()*3)::int],
    (random()*100000)::int
FROM generate_series(1, 50000);

ANALYZE test_index_katta;
```

Indekssiz holda, `qiymat` bo'yicha qidiramiz:

```sql
EXPLAIN ANALYZE SELECT * FROM test_index_katta WHERE qiymat = 12345;
```

```
                                                 QUERY PLAN                                                  
---------------------------------------------------------------------------------------------------------------
 Seq Scan on test_index_katta  (cost=0.00..944.00 rows=1 width=18) (actual time=0.670..2.751 rows=2 loops=1)
   Filter: (qiymat = 12345)
   Rows Removed by Filter: 49998
 Planning Time: 0.281 ms
 Execution Time: 2.777 ms
```

`Rows Removed by Filter: 49998` — bu, PostgreSQL barcha 50 000 qatorni tekshirib, ulardan 49 998 tasini "mos kelmadi" deb rad etganini ko'rsatadi. Butun jarayon **2.777 millisekund** vaqt oldi. Endi `qiymat` ustuniga indeks yaratamiz:

```sql
CREATE INDEX idx_test_qiymat ON test_index_katta (qiymat);
EXPLAIN ANALYZE SELECT * FROM test_index_katta WHERE qiymat = 12345;
```

```
                                                            QUERY PLAN                                                             
-----------------------------------------------------------------------------------------------------------------------------------
 Index Scan using idx_test_qiymat on test_index_katta  (cost=0.29..8.31 rows=1 width=18) (actual time=0.021..0.026 rows=2 loops=1)
   Index Cond: (qiymat = 12345)
 Planning Time: 0.412 ms
 Execution Time: 0.053 ms
```

**0.053 millisekund** — 2.777ms'dan **~52 marta tezroq**! `Index Scan` — PostgreSQL endi barcha qatorlarni emas, faqat indeksdagi mos yozuvni topib, to'g'ridan-to'g'ri kerakli qatorga "sakraydi".

### B-tree — nega aynan bu tuzilma standart

`CREATE INDEX ... ON jadval (ustun)` — hech qanday turni ko'rsatmasangiz, PostgreSQL avtomatik ravishda **B-tree** (Balanced Tree — "muvozanatlashgan daraxt") turini tanlaydi. B-tree — ma'lumotlarni **tartiblangan, daraxtsimon** tuzilmada saqlaydi: har bir "tugun" bir nechta qiymatga va quyi tugunlarga ishora qiladi, shunday qilib istalgan qiymatni topish uchun butun daraxtni emas, faqat uning **balandligiga teng** sonli qadam (odatda 3-4 qadam, hatto millionlab qatorli jadvalda ham) kerak bo'ladi.

B-tree quyidagi operatsiyalarning barchasini samarali qo'llab-quvvatlaydi — bu uning "universal, standart tanlov" bo'lishining sababi:

| Amal | Misol | B-tree qo'llab-quvvatlaydimi |
|---|---|---|
| Tenglik | `WHERE qiymat = 12345` | ✅ |
| Diapazon | `WHERE qiymat BETWEEN 100 AND 200` | ✅ |
| Taqqoslash | `WHERE qiymat > 500` | ✅ |
| Saralash | `ORDER BY qiymat` | ✅ (indeks allaqachon tartiblangan!) |
| Prefiks qidiruv | `WHERE nomi LIKE 'Samsung%'` | ✅ (faqat **boshidan** mos naqsh uchun) |

### Bitmap Index Scan — o'rtacha selektivlik uchun strategiya

Endi kam selektiv (ya'ni ko'p qatorga mos keladigan) ustun bilan sinaymiz — `kategoriya`da atigi 4 xil qiymat bor, demak har biriga ~12 500 qatordan to'g'ri keladi:

```sql
CREATE INDEX idx_test_kategoriya ON test_index_katta (kategoriya);
EXPLAIN ANALYZE SELECT * FROM test_index_katta WHERE kategoriya = 'A';
```

```
                                                            QUERY PLAN                                                             
-----------------------------------------------------------------------------------------------------------------------------------
 Bitmap Heap Scan on test_index_katta  (cost=98.13..523.31 rows=8495 width=18) (actual time=0.234..1.533 rows=8403 loops=1)
   Recheck Cond: (kategoriya = 'A'::text)
   Heap Blocks: exact=319
   ->  Bitmap Index Scan on idx_test_kategoriya  (cost=0.00..96.00 rows=8495 width=0) (actual time=0.198..0.198 rows=8403 loops=1)
         Index Cond: (kategoriya = 'A'::text)
 Planning Time: 0.374 ms
 Execution Time: 1.791 ms
```

Diqqat qiling — bu safar oddiy `Index Scan` emas, **`Bitmap Index Scan` + `Bitmap Heap Scan`** ishlatildi. Bu — oddiy `Index Scan`dan farqli strategiya: avval indeksdan **barcha** mos qatorlarning manzillari (sahifa raqamlari) yig'iladi va xotirada "bitmap" (bitlar xaritasi) shakllantiriladi, so'ng bu sahifalar **sahifa tartibida** (jismoniy joylashuv bo'yicha, tasodifiy emas) o'qiladi. Bu — agar natija **ko'p** qatorni o'z ichiga olsa (bizning holatda ~8400 qator, jadvalning ~17%i), samaraliroq: sahifalarni tasodifiy tartibda emas, ketma-ket o'qish diskdan (ayniqsa an'anaviy HDD'larda) ancha tezroq.

> **Qachon indeks umuman ishlatilmaydi:** agar so'rov natijada jadvalning **katta qismini** (masalan, 50%dan ko'prog'ini) qaytarsa, PostgreSQL'ning rejalashtiruvchisi (query planner — 19-bobda chuqur o'rganiladi) ko'pincha oddiy `Seq Scan`ni tanlaydi, hatto mos indeks mavjud bo'lsa ham — chunki bunday holatda "deyarli hammasini o'qish kerak" bo'lgani uchun, indeks orqali "sakrab yurish" shunchaki qo'shimcha ish qo'shadi.

### Indeksning "narxi" — bepul emas

Indeks — mo''jiza emas, uning aniq narxi bor:

| Narx turi | Tushuntirish |
|---|---|
| **Disk joyi** | Har bir indeks — bu alohida fayl (16.1-dars), o'z joyini egallaydi (ko'pincha jadvalning o'zi kabi katta, ba'zan kattaroq ham) |
| **Yozish tezligi** | Har bir `INSERT`/`UPDATE`/`DELETE`, jadvaldagi o'zgarishdan tashqari, **har bir tegishli indeksni ham** yangilashi kerak (16.2-darsdagi HOT update — bu muammoni qisman yumshatadi) |
| **`VACUUM` vaqti** | Ko'proq indeks — `VACUUM` (17.2-dars) uchun ko'proq ish |

Shu sababli, "har bir ustunga indeks qo'yish" — noto'g'ri strategiya. Indeksni faqat, **haqiqatan tez-tez** `WHERE`, `JOIN` yoki `ORDER BY`da ishlatiladigan ustunlarga qo'shish tavsiya etiladi.

## Amaliy misol

**Vazifa:** `xodimlar` jadvalida `email` bo'yicha qidiruvni tezlashtiring va buni `EXPLAIN` bilan tasdiqlang.

```sql
EXPLAIN SELECT * FROM xodimlar WHERE email = 'aziz.karimov@dokon.uz';
-- (Kichik jadvalda, PostgreSQL Seq Scan'ni tanlashi mumkin — bu normal, 10 qatorli jadval uchun
--  indeks orqali "sakrash" hech qanday amaliy foyda bermaydi)

CREATE INDEX idx_xodim_email ON xodimlar (email);
EXPLAIN SELECT * FROM xodimlar WHERE email = 'aziz.karimov@dokon.uz';
```

## Keng tarqalgan xatolar

**Xato 1:** Kichik jadvalda indeks yaratib, so'ng `EXPLAIN`da u ishlatilmaganini ko'rib, "indeks buzuq" deb o'ylash.
❌ Kichik jadvallarda (bir necha o'nlab-yuzlab qator) `Seq Scan` ko'pincha **haqiqatan tezroq** — indeksni yuklash va undan foydalanishning o'zi ma'lum "qo'shimcha xarajat" talab qiladi.
✅ Indeksning haqiqiy foydasini faqat yetarlicha katta (odatda kamida bir necha ming qatorli) jadvallarda baholang.

**Xato 2:** Har bir ustunga, "ehtiyot shart" tarzida indeks qo'shish.
❌ Bu — yozish tezligini keraksiz pasaytiradi va disk joyini behuda sarflaydi (yuqoridagi jadvalga qarang).
✅ Faqat `WHERE`/`JOIN`/`ORDER BY`da haqiqatan tez-tez ishlatiladigan ustunlarga indeks qo'shing.

**Xato 3:** `Bitmap Heap Scan`ni "sekin" yoki "yomon" strategiya deb hisoblash, chunki u oddiy `Index Scan` emas.
❌ `Bitmap Heap Scan` — o'rtacha selektivlikdagi so'rovlar uchun, aksincha, **eng samarali** strategiya bo'lishi mumkin.
✅ Query planner tanlagan strategiyani "to'g'ri yoki noto'g'ri" deb emas, "berilgan holat uchun eng arzon" deb baholang (19-bobda chuqurroq).

## Mashq/topshiriq

**(Oson)** `mahsulotlar` jadvalida `kategoriya` ustuniga indeks yarating va `EXPLAIN` bilan uning ishlatilish-ishlatilmasligini tekshiring (jadval kichik bo'lgani uchun natijani tushuntiring).

**(O'rtacha)** `test_index_katta`da `qiymat > 50000` shartli so'rovni `EXPLAIN ANALYZE` bilan sinab, natijada nechta qator qaytganini va qanday skanerlash turi (Seq/Index/Bitmap) ishlatilganini aniqlang.

**(Qiyin)** `test_index_katta`dagi barcha indekslarning umumiy hajmini (`pg_indexes_size`) va jadvalning o'zi hajmini solishtiring, so'ng nechta foiz qo'shimcha joy indekslar uchun sarflanganini hisoblang.

## Qisqacha xulosa

Indeks — ma'lumotni oldindan tartiblangan tuzilmada saqlab, PostgreSQL'ga butun jadvalni skanerlamasdan (`Seq Scan`) kerakli qatorlarni topish (`Index Scan`) imkonini beradi — bizning testimizda bu ~52 marta tezlashuvga olib keldi. **B-tree** — standart, universal indeks turi, tenglik, diapazon va saralashning barchasini qo'llab-quvvatlaydi. `Bitmap Index Scan` — o'rtacha selektivlikdagi natijalar uchun muqobil strategiya. Indeks bepul emas — u disk joyi va yozish tezligi hisobiga keladi, shuning uchun uni faqat haqiqiy zaruratga qarab qo'shish kerak. Keyingi darsda B-tree'dan tashqari, maxsus vazifalar uchun mo'ljallangan indeks turlarini — **GIN, GiST, BRIN, Hash**ni — chuqur o'rganamiz.

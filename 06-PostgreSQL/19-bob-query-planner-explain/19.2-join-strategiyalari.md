# 19.2. `JOIN` strategiyalari — Nested Loop, Hash Join, Merge Join (ICH-ICHIGA)

## Bu darsda nimalarni o'rganasiz

- PostgreSQL `JOIN`ni bajarishning **uch xil** algoritmini bilasiz
- Har birini `EXPLAIN` orqali **majburlab**, ularning ishlash mantig'ini jonli ko'rasiz
- Planner qaysi holatda qaysi strategiyani tanlashini tushunasiz
- `EXPLAIN (ANALYZE, BUFFERS)`ni to'liq o'qishni mustahkamlaysiz

## Nazariy qism

### `JOIN` — nima uchun bir nechta algoritm kerak

3-bobda `JOIN`ning **mantig'ini** (qaysi qatorlar birlashtirilishi kerakligini) o'rgandik. Lekin bu mantiqni **jismonan qanday bajarish** — bu butunlay boshqa savol, va PostgreSQL buning uchun **uchta** tubdan farqli algoritmga ega. Planner, 19.1-darsda ko'rgan `cost` formulalari asosida, har bir aniq `JOIN` uchun **eng arzon** algoritmni tanlaydi.

### Nested Loop — eng sodda, kichik natijalar uchun ideal

**Nested Loop** ("ichma-ich tsikl") — eng tushunarli algoritm: tashqi jadvalning **har bir** qatori uchun, ichki jadvalda mos qatorni qidiradi (agar ichki jadvalda indeks bo'lsa, bu qidiruv tez, 18-bob).

```sql
SET enable_hashjoin = off;
SET enable_mergejoin = off;

EXPLAIN SELECT x.ism, b.nomi FROM xodimlar x JOIN bolimlar b ON x.bolim_id = b.id WHERE x.id = 1;

RESET enable_hashjoin;
RESET enable_mergejoin;
```

```
                            QUERY PLAN                            
--------------------------------------------------------------------
 Nested Loop  (cost=0.00..2.24 rows=1 width=236)
   Join Filter: (b.id = x.bolim_id)
   ->  Seq Scan on xodimlar x  (cost=0.00..1.12 rows=1 width=122)
         Filter: (id = 1)
   ->  Seq Scan on bolimlar b  (cost=0.00..1.05 rows=5 width=122)
```

> **Diqqat:** biz bu yerda `enable_hashjoin`/`enable_mergejoin`ni **ataylab o'chirib**, planner'ni Nested Loop'ni tanlashga **majbur qildik** — bu faqat o'qitish maqsadida, real loyihada bu sozlamalarni doimiy o'zgartirish tavsiya etilmaydi (planner odatda o'zi to'g'ri tanlaydi).

Bu yerda: `xodimlar`dan `id=1`ga mos **bitta** qator topiladi, so'ng shu bitta qator uchun `bolimlar`da mos yozuv (5 ta qatorning ichidan) qidiriladi. Jami ish — juda kam, chunki tashqi tomonda faqat **bitta** qator bor.

**Nested Loop qachon eng yaxshi:** tashqi tomonda **kam sonli** qator bo'lganda (ayniqsa, ichki jadvalda indeks orqali tez qidirish mumkin bo'lganda). Agar tashqi tomonda **million** qator bo'lsa, va har biri uchun ichki jadvalda alohida qidiruv kerak bo'lsa — bu strategiya **halokatli sekin** bo'lib qoladi (millionlab alohida qidiruv).

### Hash Join — katta, indekslanmagan natijalar uchun

**Hash Join** — ikkita bosqichli: (1) kichikroq jadvaldan **xesh-jadval** (hash table) tuziladi (xotirada); (2) kattaroq jadval **bir marta** skanerlanadi, har bir qator uchun xesh-jadvaldan mos yozuv qidiriladi.

```sql
EXPLAIN SELECT a.id, b.matn FROM test_planner_katta a JOIN test_planner_katta b ON a.tashqi_id = b.id WHERE a.qiymat < 5;
```

```
                                     QUERY PLAN                                      
---------------------------------------------------------------------------------------
 Hash Join  (cost=1891.88..3907.78 rows=390 width=14)
   Hash Cond: (b.id = a.tashqi_id)
   ->  Seq Scan on test_planner_katta b  (cost=0.00..1637.00 rows=100000 width=14)
   ->  Hash  (cost=1887.00..1887.00 rows=390 width=8)
         ->  Seq Scan on test_planner_katta a  (cost=0.00..1887.00 rows=390 width=8)
               Filter: (qiymat < 5)
```

Bu yerda planner **o'zi**, hech qanday sozlamasiz, `Hash Join`ni tanladi — chunki `a` jadvalidan (filtrlangandan keyin, ~390 qator) kichik xesh-jadval qurish, so'ng `b`ning barcha 100 000 qatorini **bir marta** skanerlab shu xesh-jadval bilan solishtirish, Nested Loop'dan (390 marta alohida qidiruv) ancha arzon.

**Hash Join qachon eng yaxshi:** ikkala tomonda ham katta hajm bo'lganda, va `JOIN` sharti — **tenglik** (`=`) bo'lganda (xesh-jadval faqat tenglik uchun ishlaydi, diapazon uchun emas).

### Merge Join — ikkala tomon ham tartiblangan bo'lsa

**Merge Join** — ikkala jadvalni ham `JOIN` ustuni bo'yicha **tartiblab** (yoki, agar ular allaqachon indekslangan bo'lsa, tartiblangan holda o'qib), so'ng ikkita "ko'rsatkich" bilan, xuddi ikkita tartiblangan ro'yxatni birlashtirish kabi, parallel yuraveradi:

```sql
SET enable_hashjoin = off;
SET enable_nestloop = off;

EXPLAIN SELECT a.id, b.id FROM test_planner_katta a JOIN test_planner_katta b ON a.id = b.id WHERE a.qiymat < 5;

RESET enable_hashjoin;
RESET enable_nestloop;
```

```
                                                      QUERY PLAN                                                       
--------------------------------------------------------------------------------------------------------------------------
 Merge Join  (cost=1904.08..5403.93 rows=390 width=8)
   Merge Cond: (b.id = a.id)
   ->  Index Only Scan using test_planner_katta_pkey on test_planner_katta b  (cost=0.29..3244.29 rows=100000 width=4)
   ->  Sort  (cost=1903.78..1904.76 rows=390 width=4)
         Sort Key: a.id
         ->  Seq Scan on test_planner_katta a  (cost=0.00..1887.00 rows=390 width=4)
               Filter: (qiymat < 5)
```

Diqqat qiling: `b` tomoni `Index Only Scan` orqali **allaqachon tartiblangan** holda keladi (`id` — `PRIMARY KEY`, B-tree — 18.1-dars, tabiatan tartiblangan), `a` tomoni esa maxsus `Sort` qadami bilan tartiblanadi. Shu ikkalasi tartiblangandan keyin, `Merge Join` ularni **bir marta**, parallel "yurish" bilan birlashtiradi.

**Merge Join qachon eng yaxshi:** ikkala tomon ham **allaqachon tartiblangan** (yoki indeks orqali arzon tartiblanadigan) bo'lganda — ayniqsa katta hajmlarda, chunki xesh-jadval qurish uchun xotira kerak emas. Amaliyotda, planner buni Hash Join'dan **kamroq** tanlaydi, chunki tartiblash (`Sort`) qadami ko'pincha o'zi ancha xarajatli.

### Uchtasini solishtirish — xulosa jadvali

| | Nested Loop | Hash Join | Merge Join |
|---|---|---|---|
| **Eng mos holat** | Bir tomon kichik, indeks bor | Ikkala tomon katta, tenglik sharti | Ikkala tomon tartiblangan/indekslangan |
| **Xotira talabi** | Kam | O'rtacha-yuqori (xesh-jadval uchun) | Kam (agar sort kerak bo'lmasa) |
| **`JOIN` sharti** | Istalgan (`=`, `<`, `>` va h.k.) | Faqat tenglik (`=`) | Faqat tenglik (`=`) |
| **Eng yomon holat** | Ikkala tomon ham katta, indekssiz | Xesh-jadval xotiraga sig'maganda | Tartiblash o'zi qimmat bo'lganda |

### Planner qanday tanlaydi — bu barchasi `cost` haqida

Muhim xulosa: siz **hech qachon** "menga Hash Join kerak" deb SQL'da yozmaysiz — bu, 19.1-darsda ko'rgan `cost` formulalari asosida, **to'liq avtomatik** hal qilinadi. Planner, har uch strategiya uchun ham taxminiy narxni hisoblab, eng arzonini tanlaydi. `enable_hashjoin`/`enable_nestloop`/`enable_mergejoin` sozlamalari — faqat **diagnostika** uchun (masalan, "agar Hash Join bo'lmaganida, planner nima qilardi" savolini sinash uchun) ishlatiladi, ular ishlab turgan tizimda **doimiy** o'zgartirilmasligi kerak.

## Amaliy misol

**Vazifa:** `buyurtmalar` va `mijozlar` orasidagi `JOIN`da qaysi strategiya tanlanganini aniqlang va nega aynan shu tanlanganini tushuntiring.

```sql
EXPLAIN ANALYZE
SELECT m.ism, b.sana, b.holati
FROM buyurtmalar b
JOIN mijozlar m ON b.mijoz_id = m.id;
```

(Ikkala jadval ham juda kichik bo'lgani uchun, bu yerda odatda `Nested Loop` yoki `Hash Join` tanlanadi — real, katta hajmdagi jadvallarda farq ko'proq sezilarli bo'ladi.)

## Keng tarqalgan xatolar

**Xato 1:** `enable_nestloop`/`enable_hashjoin`ni ishlab turgan bazada, "biror so'rovni tezlashtirish" umidida, doimiy o'chirib qo'yish.
❌ Bu — faqat **bitta** so'rov uchun vaqtinchalik yaxshilanish berishi mumkin, lekin **boshqa barcha** so'rovlarni yomonlashtiradi (chunki planner endi ularning eng yaxshi strategiyasidan mahrum bo'ladi).
✅ Bu sozlamalarni faqat, **shu sessiya ichida**, diagnostika maqsadida, vaqtincha o'zgartiring — hech qachon global sozlamada o'chirmang.

**Xato 2:** "Nested Loop — har doim yomon, Hash Join — har doim yaxshi" deb umumlashtirish.
❌ Kichik natijalar uchun Nested Loop, aksincha, eng tez strategiya — Hash Join'ning xesh-jadval qurish "boshlang'ich xarajati" behuda ketadi.
✅ Har bir strategiyani, kontekstiga (jadval hajmlari, indekslar mavjudligi) qarab baholang, umumiy "yaxshi/yomon" deb emas.

**Xato 3:** `JOIN` sekin ishlayotganda, avtomatik ravishda "noto'g'ri strategiya tanlangan" deb xulosa chiqarish.
❌ Ko'pincha muammo — strategiyaning o'zida emas, balki 19.1-darsda ko'rgan **noto'g'ri statistika**da (eskirgan `ANALYZE`) yoki yetishmayotgan indeksda (18-bob).
✅ Sekin `JOIN`ni diagnostika qilishda, avval statistika va indekslarni tekshiring, keyin strategiyani "aybdor" deb hisoblang.

## Mashq/topshiriq

**(Oson)** `test_planner_katta` jadvalida, `tashqi_id`ga indeks yaratib (`CREATE INDEX`), shundan keyin ikkita jadval o'rtasidagi `JOIN` qaysi strategiyani tanlashini kuzating (indeks Nested Loop'ni yanada jozibali qilishi mumkin).

**(O'rtacha)** `xodimlar` va `bolimlar` orasidagi `JOIN`ni, `enable_hashjoin`, `enable_nestloop`, `enable_mergejoin`ni birma-bir o'chirib, uchala strategiyaning `cost` qiymatlarini solishtiring.

**(Qiyin)** `test_planner_katta`da `qiymat` ustuni bo'yicha o'z-o'ziga `JOIN` qiling (`a.qiymat = b.qiymat`, `a.id != b.id`), natijada qancha qator kutilishini (`rows` bashorati) hisoblang, va bu son nega juda katta bo'lishi mumkinligini (ko'p-ko'pga munosabat, "fan-out") tushuntiring.

## Qisqacha xulosa

PostgreSQL uchta `JOIN` algoritmiga ega: **Nested Loop** (kichik natijalar, indeks bilan tez), **Hash Join** (katta hajmlar, tenglik sharti, xesh-jadval orqali), **Merge Join** (ikkala tomon tartiblangan bo'lganda). Planner, 19.1-darsdagi `cost` formulalari asosida, har bir aniq so'rov uchun avtomatik ravishda eng arzonini tanlaydi — buni siz to'g'ridan-to'g'ri boshqarmaysiz, faqat statistika va indekslar orqali **bilvosita** ta'sir qilasiz. Bu — 19-bobni yakunlaydi: query planner, `EXPLAIN`, `cost`, statistika va `JOIN` strategiyalarini chuqur o'rgandingiz — bu bilim, real loyihalarda sekin so'rovlarni diagnostika qilishning asosiy vositasi. Keyingi, 20-bobda **WAL va qayta tiklash**ni — PostgreSQL o'zgarishlarni qanday "ishonchli" saqlashini — chuqur o'rganamiz.

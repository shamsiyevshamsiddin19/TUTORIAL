# 22.1. Streaming replikatsiya — real vaqtda ma'lumot nusxalash (ICH-ICHIGA)

## Bu darsda nimalarni o'rganasiz

- Replikatsiya nima ekanini va u 20-bobdagi WAL bilan qanday bog'liqligini tushunasiz
- `pg_basebackup` bilan **haqiqiy, ishlaydigan** standby (kutish) serverini o'zingiz o'rnatasiz
- Standby serverning **faqat o'qish uchun** ekanini jonli tasdiqlaysiz
- Primary'dagi o'zgarish, standby'da **necha soniyada** ko'rinishini real o'lchaysiz

## Nazariy qism

### Replikatsiya nima va u nima uchun kerak

Hozirgacha biz bitta PostgreSQL server bilan ishladik. Lekin real, jiddiy loyihalarda, ko'pincha **bir nechta** server kerak bo'ladi: (1) agar asosiy server (**primary**) ishdan chiqsa, zaxira server (**standby**) uni **darhol almashtira olishi** kerak (yuqori mavjudlik, high availability); (2) o'qish yukini (masalan, hisobotlar) bir nechta serverga **taqsimlash** kerak bo'lishi mumkin (yuklamani balanslash).

**Replikatsiya** — primary serverdagi har bir o'zgarishni, bir yoki bir nechta standby serverga **avtomatik, deyarli real vaqtda** nusxalash jarayoni. Va bu, aslida, sizga allaqachon tanish bo'lgan mexanizmga asoslanadi: **WAL** (20-bob)!

### Replikatsiya g'oyasi — WAL'ni "ikkinchi joyda ham qayta ijro etish"

20.2-darsda crash recovery — WAL'ni qayta o'qib, o'zgarishlarni "qayta bajarish" (redo) ekanini ko'rgan edik. Streaming replikatsiya — aynan **shu g'oyaning** kengaytmasi: standby server, primary'ning WAL oqimini **doimiy ravishda** qabul qilib, uni **doimo** redo rejimida bajarib turadi — xuddi u "abadiy tiklanish jarayonida" turgandek. Shu sababli, standby serverning WAL papkasi mazmuni — primary'nikiga deyarli bir xil bo'ladi.

### `pg_basebackup` — standby'ni "boshlang'ich nusxa" bilan ta'minlash

Standby serverni sozlashning birinchi qadami — primary'ning **to'liq, jismoniy nusxasini** olish (chunki standby "noldan" boshlanmaydi, u primary'ning muayyan vaqtdagi holatidan boshlab, WAL orqali "davom etadi"):

```bash
pg_basebackup -D /tmp/pg_standby -P -R -X stream -c fast
```

```
waiting for checkpoint
31563/31563 kB (100%), 1/1 tablespace
```

Bu buyruq: (1) primary'ning **butun** klaster katalogini (16.1-dars) `/tmp/pg_standby`ga nusxalaydi; (2) `-R` bayrog'i — avtomatik ravishda `postgresql.auto.conf`ga `primary_conninfo` (standby qayerdan WAL olishi kerakligi) yozadi va **`standby.signal`** faylini yaratadi (bu fayl mavjudligi — "men standby rejimida ishlayman" degani); (3) `-X stream` — nusxalash jarayonining o'zi davomida ham WAL oqimini uzatishni boshlaydi (shu tufayli, nusxalash davomida sodir bo'lgan o'zgarishlar ham yo'qolmaydi).

### Standby'ni ishga tushirish

Standby'ni, boshqa portda (`5433`, chunki bir xil serverda ikkita PostgreSQL nusxasini sinamoqdamiz), ishga tushiramiz:

```bash
pg_ctl -D /tmp/pg_standby start
```

Log faylida quyidagilarni ko'ramiz:

```
LOG:  database system was interrupted; last known up at ...
LOG:  entering standby mode
LOG:  starting backup recovery with redo LSN 0/6000028, checkpoint LSN 0/6000060, on timeline ID 1
LOG:  redo starts at 0/6000028
LOG:  completed backup recovery with redo LSN 0/6000028 and end LSN 0/6000100
LOG:  consistent recovery state reached at 0/6000100
LOG:  database system is ready to accept read-only connections
LOG:  started streaming WAL from primary at 0/7000000 on timeline 1
```

Bu loglar — aynan 20.2-darsda o'rgangan crash recovery jarayonining o'zi (`redo LSN`dan boshlab qayta ijro), faqat farqi shundaki, jarayon **tugamaydi** — oxirgi qatorda ko'rinib turibdi: `started streaming WAL from primary` — standby, endi doimiy ravishda, primary'dan **yangi** WAL yozuvlarini kutib, ularni "jonli" qayta ijro etishga o'tdi.

### Standby — faqat o'qish uchun

```sql
SELECT pg_is_in_recovery();
```

```
 pg_is_in_recovery 
---------------------
 t
```

`pg_is_in_recovery() = true` — bu server hozir **standby** rejimida ekanini bildiradi. Standby'da yozishga urinib ko'ramiz:

```sql
INSERT INTO mahsulotlar (nomi, narxi, kategoriya, ombordagi_soni) VALUES ('Test', 100, 'Test', 1);
```

```
ERROR:  cannot execute INSERT in a read-only transaction
```

Bu — **kutilgan, muhim** xatti-harakat: standby, ta'rifiga ko'ra, faqat primary'dan kelayotgan WAL'ni qayta ijro etadi, u **o'zi mustaqil** yangi o'zgarish qabul qila olmaydi. Lekin `SELECT` — muammosiz ishlaydi:

```sql
SELECT count(*) FROM mahsulotlar;
```

```
 count 
-------
    10
```

Bu — replikatsiyaning amaliy foydasi: `SELECT`-og'ir hisobotlarni, primary'ni band qilmasdan, standby'ga yo'naltirish mumkin.

### Real vaqtda replikatsiyani jonli ko'rish

Endi eng qiziq qism — primary'da yangi qator qo'shib, u standby'da **qancha vaqtda** ko'rinishini o'lchaymiz:

```sql
-- Primary'da:
INSERT INTO mahsulotlar (nomi, narxi, kategoriya, ombordagi_soni) VALUES ('Replikatsiya sinovi', 999999, 'Test', 1);
```

```sql
-- Bir soniyadan keyin, standby'da:
SELECT nomi, narxi FROM mahsulotlar WHERE nomi = 'Replikatsiya sinovi';
```

```
         nomi         |   narxi   
------------------------+------------
 Replikatsiya sinovi  | 999999.00
```

**Bitta soniya ichida** paydo bo'ldi! Buni aniqroq, `pg_stat_replication` orqali, **LSN farqi** (lag) sifatida o'lchash mumkin:

```sql
-- Primary'da:
SELECT client_addr, replay_lsn, pg_current_wal_lsn(),
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)) AS lag_hajmi
FROM pg_stat_replication;
```

```
 client_addr | replay_lsn | pg_current_wal_lsn | lag_hajmi 
--------------+-------------+----------------------+------------
              | 0/7004698  | 0/7004698           | 0 bytes
```

`lag_hajmi = 0 bytes` — standby, primary bilan **to'liq sinxron**, hech qanday "orqada qolish" yo'q. `pg_stat_replication` — primary'da ishga tushirilib, unga ulangan **barcha** standby'lar haqida real vaqtda ma'lumot beradi (`state = streaming` — faol oqim rejimida ekanini bildiradi).

## Amaliy misol

**Vazifa:** `xodimlar` jadvaliga primary'da yangi xodim qo'shib, uning standby'da paydo bo'lishini kuzating.

```sql
-- Primary'da:
INSERT INTO xodimlar (ism, familiya, email, lavozim, bolim_id, ish_haqi, ishga_kirgan_sana)
VALUES ('Test', 'Xodim', 'test.xodim@dokon.uz', 'Sinov', 1, 5000000, CURRENT_DATE);

-- Standby'da (bir necha soniyadan keyin):
SELECT ism, familiya FROM xodimlar WHERE email = 'test.xodim@dokon.uz';
```

## Keng tarqalgan xatolar

**Xato 1:** Standby'ni "zaxira nusxa" (backup, 15.2-dars) bilan bir xil narsa deb tushunish.
❌ `pg_dump`/`pg_basebackup` orqali olingan **statik** zaxira, biror vaqtdagi "surat"; standby esa **jonli, doimiy yangilanib turuvchi** nusxa.
✅ Ikkalasini ham ishlatish tavsiya etiladi: standby — tezkor failover uchun, muntazam zaxira nusxa esa — inson xatosidan (masalan, noto'g'ri `DELETE`) himoyalanish uchun (chunki standby, xatoni ham **darhol** ko'chiradi!).

**Xato 2:** Standby'ga to'g'ridan-to'g'ri yozishga urinib, "replikatsiya buzuq" deb xulosa chiqarish.
❌ Bu — standby'ning **ataylab qilingan, to'g'ri** xatti-harakati, xato emas.
✅ Yozish har doim faqat primary'da bajarilishi kerak; agar standby'ga yozish zarurati bo'lsa, bu — architektura darajasida noto'g'ri loyihalash belgisi.

**Xato 3:** Replikatsiya lag'ini (kechikishini) hech qachon kuzatmaslik.
❌ Tarmoq muammolari yoki standby'ning yuklamasi ortishi, lag'ni sekundlardan daqiqalarga, hatto soatlarga oshirib yuborishi mumkin — bu, failover vaqtida **ma'lumot yo'qotilishi** xavfini oshiradi.
✅ Ishlab turgan tizimlarda, `pg_stat_replication`dagi lag'ni muntazam monitoring qiling va, agar u doimiy o'sib borsa, ogohlantirish (alert) sozlang.

## Mashq/topshiriq

**(Oson)** Standby serverda `pg_is_in_recovery()`ni chaqirib, natijani primary serverdagi natija bilan solishtiring.

**(O'rtacha)** Primary'da `buyurtmalar` jadvaliga yangi buyurtma qo'shib, `pg_stat_replication`dagi `lag_hajmi`ning, o'zgarish paytida qanday o'sib, keyin qayta `0 bytes`ga qaytishini kuzating.

**(Qiyin)** Standby serverni to'xtatib (`pg_ctl stop`), primary'da bir nechta o'zgarish kiritib, so'ng standby'ni qayta ishga tushirib, u **avtomatik ravishda**, to'xtagan joyidan davom etib, barcha "sog'inib qolgan" o'zgarishlarni qanday "quvib yetishini" kuzating.

## Qisqacha xulosa

Streaming replikatsiya — 20-bobdagi WAL mexanizmini kengaytirib, primary serverning WAL oqimini standby serverga uzatib, u yerda **doimiy ravishda qayta ijro etish** (xuddi abadiy crash recovery kabi) orqali ishlaydi. `pg_basebackup` — standby uchun boshlang'ich nusxani oladi, `standby.signal` va `primary_conninfo` esa standby rejimini belgilaydi. Standby — faqat o'qish uchun (`pg_is_in_recovery() = true`), va biz jonli ko'rganimizdek, primary'dagi o'zgarish, odatiy sharoitda, **bir soniya ichida** standby'da aks etadi (`pg_stat_replication`dagi `lag_hajmi` orqali aniq o'lchanadi). Keyingi darsda replikatsiyaning qo'shimcha mexanizmlarini — **replication slot**larni, va standby'ni primary'ga aylantirish (**failover**) jarayonini — chuqur o'rganamiz.

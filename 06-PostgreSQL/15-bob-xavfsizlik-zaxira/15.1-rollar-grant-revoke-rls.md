# 15.1. Rollar, `GRANT`/`REVOKE` va Row-Level Security (RLS)

## Bu darsda nimalarni o'rganasiz

- PostgreSQL'da rol (role) tushunchasini va foydalanuvchi yaratishni o'rganasiz
- `GRANT`/`REVOKE` bilan jadval darajasidagi huquqlarni boshqarishni bilasiz
- Rollarni guruhlash orqali huquqlarni qulay boshqarishni o'rganasiz
- **Row-Level Security (RLS)** — qator darajasidagi xavfsizlik — bilan bir xil jadvalning turli foydalanuvchilarga turlicha ko'rinishini ta'minlashni o'rganasiz

## Nazariy qism

### Rol (role) — PostgreSQL'da foydalanuvchi tushunchasi

PostgreSQL'da "foydalanuvchi" alohida tushuncha emas — u shunchaki **`LOGIN` xususiyatiga ega rol**. Rol — huquqlar (privilege) beriladigan yagona ob'ekt, va u ham foydalanuvchini, ham foydalanuvchilar guruhini anglatishi mumkin:

```sql
CREATE ROLE faqat_oquvchi WITH LOGIN PASSWORD 'xavfsiz_parol';
CREATE ROLE sotuv_xodimi WITH LOGIN PASSWORD 'boshqa_xavfsiz_parol';
```

`CREATE USER` — aslida `CREATE ROLE ... WITH LOGIN`ning qisqartmasi (ular deyarli bir xil, faqat `CREATE USER`da `LOGIN` standart bo'yicha yoqilgan). Har ikkala rol ham hozircha **hech qanday huquqqa** ega emas — standart holatda, yangi rol faqat o'ziga tegishli ob'ektlarni ko'rishi mumkin, boshqa hech narsani.

### `GRANT` — huquq berish

```sql
GRANT SELECT ON mahsulotlar, mijozlar TO faqat_oquvchi;
GRANT SELECT, INSERT, UPDATE ON buyurtmalar, buyurtma_elementlari TO sotuv_xodimi;
```

`GRANT huquq(lar) ON jadval(lar) TO rol;` — asosiy sintaksis. Eng ko'p ishlatiladigan huquqlar: `SELECT`, `INSERT`, `UPDATE`, `DELETE` (7-bobdagi DML amallariga mos), shuningdek `TRUNCATE`, `REFERENCES` (boshqa jadvaldan `FOREIGN KEY` yaratish uchun) va boshqalar.

Sinab ko'ramiz — `faqat_oquvchi` sifatida ulanib, `mahsulotlar`ni o'qishga harakat qilamiz:

```sql
SELECT nomi FROM mahsulotlar LIMIT 3;
```

```
          nomi          
-------------------------
 Noutbuk Lenovo IdeaPad
 Sichqoncha Logitech
 Klaviatura mexanik
```

Muvaffaqiyatli — chunki `SELECT` huquqi berilgan edi. Endi shu rol bilan yozishga (`INSERT`) urinib ko'ramiz:

```sql
INSERT INTO mahsulotlar (nomi, narxi, kategoriya, ombordagi_soni) VALUES ('Test', 1000, 'Elektronika', 5);
```

```
ERROR:  permission denied for table mahsulotlar
```

Aniq, tushunarli xato — `faqat_oquvchi`ga faqat `SELECT` berilgan, `INSERT` emas, shuning uchun PostgreSQL amalni butunlay rad etadi. Bu — **eng kam imtiyoz** (principle of least privilege) tamoyilining amaliy namunasi: har bir rolga, aynan uning vazifasi uchun zarur bo'lgan huquqlarnigina berish.

### `REVOKE` — huquqni qaytarib olish

```sql
REVOKE SELECT ON mijozlar FROM faqat_oquvchi;
```

`REVOKE` — `GRANT`ning teskarisi. Endi `faqat_oquvchi` `mijozlar` jadvalini o'qiy olmaydi:

```sql
SELECT * FROM mijozlar LIMIT 1;
```

```
ERROR:  permission denied for table mijozlar
```

### Rollarni guruhlash — huquqlarni markazlashtirilgan boshqarish

Agar sizda o'nlab xodim-rol bo'lsa, har biriga alohida `GRANT` yozish tez orada boshqarib bo'lmaydigan holga keladi. Buning o'rniga, **"guruh roli"** yaratib, unga huquqlarni bir marta berish, so'ng haqiqiy foydalanuvchi-rollarni shu guruhga **a'zo** qilish mumkin:

```sql
CREATE ROLE xodimlar_guruhi;
GRANT SELECT ON xodimlar TO xodimlar_guruhi;
GRANT xodimlar_guruhi TO sotuv_xodimi;
```

Endi `sotuv_xodimi`, garchi unga to'g'ridan-to'g'ri hech qanday `GRANT ON xodimlar` berilmagan bo'lsa ham, `xodimlar_guruhi`ga a'zo bo'lgani uchun uning barcha huquqlarini **meros qilib oladi** (`INHERIT` — bu standart xatti-harakat):

```sql
SELECT ism FROM xodimlar LIMIT 2;
```

```
   ism   
---------
 Dilnoza
 Sardor
```

Bu naqsh — real tashkilotlarda "rol asosidagi kirish nazorati" (Role-Based Access Control, RBAC) deb ataladi: siz lavozimlarga mos guruh-rollar (`hisobchi`, `menejer`, `dasturchi`) yaratasiz, ularga mos huquqlarni berasiz, so'ng har bir yangi xodimni faqat tegishli guruh(lar)ga qo'shasiz — bu huquqlarni boshqarishni sezilarli darajada soddalashtiradi.

### Row-Level Security (RLS) — qator darajasidagi xavfsizlik

`GRANT`/`REVOKE` — **butun jadval** darajasida ishlaydi ("bu rol bu jadvalni o'qiy oladimi yoki yo'qmi"). Lekin ba'zida sizga **bitta jadval ichida, har xil foydalanuvchiga har xil qatorlarni** ko'rsatish kerak bo'ladi — masalan, "har bir mintaqa menejeri faqat o'z mintaqasidagi mijozlarni ko'rishi kerak". Aynan shu vazifa uchun **Row-Level Security (RLS)** mo'ljallangan.

```sql
GRANT SELECT ON mijozlar TO faqat_oquvchi;
ALTER TABLE mijozlar ENABLE ROW LEVEL SECURITY;

CREATE POLICY toshkent_mijozlari ON mijozlar
    FOR SELECT
    TO faqat_oquvchi
    USING (shahar = 'Toshkent');
```

Bu yerda uchta qadam bor: (1) avval `GRANT SELECT` bilan jadvalga **umumiy** kirish huquqi beriladi (RLS `GRANT`ning o'rnini bosmaydi, uni **to'ldiradi**); (2) `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` — jadval uchun RLS'ni yoqadi; (3) `CREATE POLICY` — qaysi qatorlar **ko'rinishi** kerakligini belgilovchi qoida.

Sinab ko'ramiz. Avval, RLS yoqilmagan (yoki uni chetlab o'tadigan, masalan superuser) holatda:

```sql
SELECT count(*) FROM mijozlar;
```

```
 count 
-------
     8
```

Superuser (`postgres`) — u RLS'ni **avtomatik chetlab o'tadi** (`BYPASSRLS` xususiyati bilan, `\du` buyrug'ida ko'rgan edik), shuning uchun barcha 8 ta mijozni ko'radi. Endi `faqat_oquvchi` sifatida ulanib, xuddi shu so'rovni bajaramiz:

```sql
SELECT ism, shahar FROM mijozlar;
```

```
       ism       |  shahar  
-----------------+----------
 Bekzod Rahimov  | Toshkent
 Jamshid Umarov  | Toshkent
 Rustam Xolmatov | Toshkent
 Madina Yusupova | Toshkent
```

**Faqat 4 ta** mijoz ko'rindi — barchasi Toshkent shahridan! `faqat_oquvchi` texnik jihatdan `mijozlar` jadvalining barcha 8 qatoriga `SELECT` huquqiga ega (`GRANT` shuni beradi), lekin `CREATE POLICY`dagi `USING (shahar = 'Toshkent')` sharti, u ko'radigan qatorlarni **avtomatik filtrlaydi** — xuddi har bir so'rov "orqasiga" ko'rinmas `AND shahar = 'Toshkent'` qo'shilgandek. Diqqat qiling — bu 2-bobdagi oddiy `WHERE`dan farqli: dasturchi `WHERE shahar = 'Toshkent'` yozishni **unutsa ham**, RLS siyosati baribir amal qiladi — filtrlash ma'lumotlar bazasi darajasida, ilova kodiga bog'liq bo'lmagan holda ta'minlanadi.

> **Muhim eslatma:** RLS siyosatlari **qo'shimcha** bo'ladi — bir jadvalda bir nechta `CREATE POLICY` bo'lishi mumkin, va standart holatda ular **`OR`** mantig'i bilan birlashadi (istalgan siyosat ruxsat bersa, qator ko'rinadi). `FOR SELECT`, `FOR INSERT`, `FOR UPDATE`, `FOR DELETE` — siyosatni faqat muayyan amal turiga cheklash uchun ishlatiladi (`FOR ALL` — standart, barcha amallarga).

## Amaliy misol

**Vazifa:** `xodimlar_guruhi` a'zolari faqat o'z bo'limidagi xodimlarni ko'ra oladigan RLS siyosati yarating (`current_user` va rol nomini bevosita solishtirish o'rniga, soddalik uchun `bolim_id = 2` kabi qattiq qiymat bilan cheklaymiz — real loyihada bu odatda `current_setting()` yoki sessiya o'zgaruvchisi orqali dinamik qilinadi).

```sql
ALTER TABLE xodimlar ENABLE ROW LEVEL SECURITY;

CREATE POLICY it_bolimi_xodimlari ON xodimlar
    FOR SELECT
    TO xodimlar_guruhi
    USING (bolim_id = 2);
```

## Keng tarqalgan xatolar

**Xato 1:** `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`ni yoqib, lekin hech qanday `CREATE POLICY` yozmaslik.
❌ Bu holda, RLS yoqilgan jadvalga, superuser/egasi bo'lmagan **hech kim** hech qanday qator ko'ra olmaydi (standart — "hamma narsa taqiqlangan").
✅ RLS'ni yoqqandan so'ng, albatta kamida bitta mos `CREATE POLICY` yozing.

**Xato 2:** RLS'ni `GRANT`ning o'rniga ishlatish deb o'ylash.
❌ RLS, agar avval `GRANT SELECT` (yoki tegishli huquq) berilmagan bo'lsa, hech narsani "ochib" bermaydi — ikkalasi birga ishlashi kerak.
✅ Har doim avval jadval darajasidagi `GRANT`ni bering, so'ng RLS bilan qator darajasida qo'shimcha cheklang.

**Xato 3:** Superuser yoki jadval egasi bilan test qilib, "RLS ishlamayapti" deb xulosa chiqarish.
❌ Superuser va jadval egasi, standart holatda, RLS'ni **avtomatik chetlab o'tadi**.
✅ RLS'ni har doim, siyosat qaratilgan **aynan o'sha rol** bilan ulanib sinang.

## Mashq/topshiriq

**(Oson)** `moliya_xodimi` nomli, `LOGIN`li rol yarating va unga `xodimlar` jadvaliga faqat `SELECT` huquqini bering.

**(O'rtacha)** `buyurtmalar` jadvaliga RLS yoqing va faqat `holati = 'yetkazildi'` bo'lgan buyurtmalarni ko'rsatadigan siyosat yarating, `faqat_oquvchi` roliga qarating.

**(Qiyin)** `hisobot_guruhi` nomli guruh-rol yarating, unga `mahsulotlar`, `buyurtmalar` va `buyurtma_elementlari` jadvallariga `SELECT` huquqini bering, so'ng yangi `hisobotchi_1` nomli `LOGIN`li rolni shu guruhga a'zo qiling va uning huquqlarini tekshiring.

## Qisqacha xulosa

PostgreSQL'da "foydalanuvchi" — bu `LOGIN` xususiyatiga ega rol. `GRANT`/`REVOKE` — jadval darajasidagi huquqlarni (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) boshqaradi, rollarni guruhlash esa (`GRANT rol TO rol`) — bu huquqlarni markazlashtirilgan, RBAC uslubida boshqarish imkonini beradi. Row-Level Security (RLS) esa — bir qadam nariga borib, **bitta jadval ichida** turli foydalanuvchilarga turli qatorlarni ko'rsatish, va bu cheklovni ma'lumotlar bazasi darajasida, ilova kodidan mustaqil ravishda ta'minlash imkonini beradi. Keyingi darsda ma'lumotlar bazasining **zaxira nusxasini olish va tiklash**ni — `pg_dump`/`pg_restore`ni — o'rganamiz.

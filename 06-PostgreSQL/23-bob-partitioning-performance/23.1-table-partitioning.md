# 23.1. Table Partitioning — katta jadvallarni bo'laklarga bo'lish (ICH-ICHIGA)

## Bu darsda nimalarni o'rganasiz

- Partitioning nima ekanini va u qachon kerak bo'lishini tushunasiz
- **RANGE**, **LIST** va **HASH** partitioning turlarini o'zingiz yaratib sinaysiz
- **Partition pruning** (kesib tashlash) orqali so'rov tezligini `EXPLAIN` bilan jonli o'lchaysiz
- `ATTACH PARTITION`/`DETACH PARTITION` orqali partitsiyalarni "jonli" boshqarishni o'rganasiz
- Partitsiyalangan jadvallardagi indeks va `UNIQUE` cheklovlarning o'ziga xosligini bilib olasiz

## Nazariy qism

### Partitioning nima va u nima uchun kerak

19-bobda query planner haqida o'rgandik: jadval qanchalik katta bo'lsa, `Seq Scan` shunchalik uzoq davom etadi. 18-bobdagi indekslar bu muammoni ko'p hollarda hal qiladi, lekin ba'zan jadval shunchalik katta bo'ladiki (masalan, o'nlab millionlab qatordan iborat, yillar davomida to'planган buyurtmalar tarixi), hatto indeks ham yetarli bo'lmaydi — chunki indeks o'zi ham katta bo'lib ketadi, `VACUUM` va backup jarayonlari sekinlashadi, eski ma'lumotni o'chirish esa (`DELETE FROM ... WHERE sana < ...`) butun jadval bo'ylab og'ir amaliyotga aylanadi.

**Partitioning** — bitta mantiqiy jadvalni, "sahna orqasida" bir nechta jismoniy jadval (**partitsiya**)ga bo'lish. Foydalanuvchi uchun jadval bitta bo'lib ko'rinadi (bitta nom bilan so'rov yuboriladi), lekin PostgreSQL, so'rovga qarab, faqat **kerakli** partitsiya(lar)ni skanerlaydi — bu **partition pruning** (kesib tashlash) deb ataladi.

PostgreSQL uchta asosiy partitioning turini qo'llab-quvvatlaydi: **RANGE** (diapazon bo'yicha, masalan sana), **LIST** (aniq qiymatlar ro'yxati bo'yicha, masalan shahar), va **HASH** (hash funksiyasi bo'yicha, teng taqsimlash uchun).

### RANGE partitioning — sana bo'yicha bo'lish

Eng keng tarqalgan holat — vaqt bo'yicha o'sib boruvchi jadvallarni yillar yoki oylar bo'yicha bo'lish. Katta hajmdagi buyurtmalar jadvalini yaratamiz:

```sql
CREATE TABLE test_buyurtmalar_katta (
    id BIGINT GENERATED ALWAYS AS IDENTITY,
    mijoz_id INTEGER,
    sana DATE NOT NULL,
    summa NUMERIC(12,2),
    holati VARCHAR(20)
) PARTITION BY RANGE (sana);

CREATE TABLE test_buyurtmalar_2022 PARTITION OF test_buyurtmalar_katta
    FOR VALUES FROM ('2022-01-01') TO ('2023-01-01');
CREATE TABLE test_buyurtmalar_2023 PARTITION OF test_buyurtmalar_katta
    FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');
CREATE TABLE test_buyurtmalar_2024 PARTITION OF test_buyurtmalar_katta
    FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');
```

`PARTITION BY RANGE (sana)` — asosiy ("ota") jadval e'lon qilinadi, lekin unda **hech qanday qator saqlanmaydi** — u faqat "marshrutlovchi" vazifasini bajaradi. Har bir `FOR VALUES FROM ... TO ...` — chegara **quyi qiymatni o'z ichiga oladi, yuqori qiymatni эса olmaydi** (`[quyi, yuqori)`, matematik yarim-yopiq oraliq).

300,000 qatorlik test ma'lumotini yuklaymiz:

```sql
INSERT INTO test_buyurtmalar_katta (mijoz_id, sana, summa, holati)
SELECT
    (random() * 7 + 1)::int,
    ('2022-01-01'::date + (random() * 1094)::int),
    (random() * 5000000 + 10000)::numeric(12,2),
    (ARRAY['yangi','tayyor','yetkazilgan','bekor qilingan'])[floor(random()*4+1)]
FROM generate_series(1, 300000);

SELECT tableoid::regclass AS partitsiya, count(*) FROM test_buyurtmalar_katta GROUP BY tableoid ORDER BY 1;
```

```
      partitsiya       | count  
-----------------------+--------
 test_buyurtmalar_2022 | 100133
 test_buyurtmalar_2023 | 100389
 test_buyurtmalar_2024 |  99478
```

`tableoid::regclass` — har bir qator **qaysi jismoniy partitsiyada** saqlanganini ko'rsatadi. Ma'lumot, sanaga qarab, uchta partitsiya bo'ylab avtomatik taqsimlandi — INSERT paytida biz qaysi partitsiyaga yozish kerakligini ko'rsatmadik, PostgreSQL buni `sana` qiymatidan o'zi aniqladi.

### Partition pruning — nafaqat "bo'lish", balki "tezlashtirish"

Eng muhim savol: partitsiyalash real foydami keltiradimi? `EXPLAIN (ANALYZE, BUFFERS)` bilan tekshiramiz:

```sql
EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)
SELECT count(*) FROM test_buyurtmalar_katta WHERE sana BETWEEN '2023-06-01' AND '2023-06-30';
```

```
 Aggregate  (cost=2316.47..2316.48 rows=1 width=8) (actual rows=1 loops=1)
   Buffers: shared hit=790
   ->  Seq Scan on test_buyurtmalar_2023 test_buyurtmalar_katta  (cost=0.00..2295.84 rows=8253 width=0) (actual rows=8220 loops=1)
         Filter: ((sana >= '2023-06-01'::date) AND (sana <= '2023-06-30'::date))
         Rows Removed by Filter: 92169
         Buffers: shared hit=790
 Planning Time: 0.481 ms
 Execution Time: 8.296 ms
```

E'tibor bering: `Seq Scan on test_buyurtmalar_2023` — **faqat bitta** partitsiya skanerlandi! Planner, `WHERE sana BETWEEN '2023-06-01' AND '2023-06-30'` shartidan, kerakli sana faqat `test_buyurtmalar_2023` partitsiyasida bo'lishi mumkinligini **so'rovni bajarishdan oldinoq** xulosa qildi va `2022`, `2024` partitsiyalarini butunlay e'tiborga olmadi — bu **partition pruning**.

Solishtirish uchun, xuddi shu 300,000 qatorni **bitta, bo'linmagan** jadvalga solamiz va bir xil so'rovni bajaramiz:

```sql
CREATE TABLE test_buyurtmalar_flat AS SELECT * FROM test_buyurtmalar_katta;

EXPLAIN (ANALYZE, BUFFERS, TIMING OFF)
SELECT count(*) FROM test_buyurtmalar_flat WHERE sana BETWEEN '2023-06-01' AND '2023-06-30';
```

```
 Finalize Aggregate  (cost=6027.24..6027.25 rows=1 width=8) (actual rows=1 loops=1)
   Buffers: shared hit=2368
   ->  Gather  (cost=6027.13..6027.24 rows=1 width=8) (actual rows=2 loops=1)
         Workers Launched: 1
         ->  Partial Aggregate  (cost=5027.13..5027.14 rows=1 width=8) (actual rows=1 loops=2)
               ->  Parallel Seq Scan on test_buyurtmalar_flat  (cost=0.00..5015.06 rows=4829 width=0) (actual rows=4110 loops=2)
                     Filter: ((sana >= '2023-06-01'::date) AND (sana <= '2023-06-30'::date))
                     Rows Removed by Filter: 145890
                     Buffers: shared hit=2368
 Execution Time: 16.539 ms
```

Bo'linmagan jadvalda, hatto **parallel** ishlov berishga qaramay (2 worker), PostgreSQL barcha 300,000 qatorni (uch baravar ko'p, `Rows Removed by Filter: 145890`) skanerlashga majbur bo'ldi — `Buffers: 2368`, partitsiyalangan holatdagi `790`ga nisbatan **~3 barobar ko'p**. Sabab oddiy: partitsiyalangan jadvalda, kerakli sanalar mavjud bo'lgan yagona jismoniy jadval — kichikroq va uni skanerlash arzonroq.

### LIST partitioning — aniq qiymatlar ro'yxati bo'yicha

Sana emas, balki **diskret** (chekli to'plamdan) qiymatlar bo'yicha bo'lish kerak bo'lganda — masalan, mijozlarni shahar bo'yicha — `LIST` partitioning ishlatiladi:

```sql
CREATE TABLE test_mijozlar_list (
    id SERIAL,
    ism VARCHAR(50),
    shahar VARCHAR(30) NOT NULL
) PARTITION BY LIST (shahar);

CREATE TABLE test_mijozlar_toshkent PARTITION OF test_mijozlar_list FOR VALUES IN ('Toshkent');
CREATE TABLE test_mijozlar_samarqand PARTITION OF test_mijozlar_list FOR VALUES IN ('Samarqand', 'Buxoro');
CREATE TABLE test_mijozlar_boshqa PARTITION OF test_mijozlar_list DEFAULT;

INSERT INTO test_mijozlar_list (ism, shahar) VALUES
    ('Aziz', 'Toshkent'), ('Vali', 'Toshkent'), ('Karim', 'Samarqand'),
    ('Dilnoza', 'Buxoro'), ('Sardor', 'Andijon');

SELECT tableoid::regclass, * FROM test_mijozlar_list ORDER BY id;
```

```
        tableoid         | id |   ism   |  shahar   
-------------------------+----+---------+-----------
 test_mijozlar_toshkent  |  1 | Aziz    | Toshkent
 test_mijozlar_toshkent  |  2 | Vali    | Toshkent
 test_mijozlar_samarqand |  3 | Karim   | Samarqand
 test_mijozlar_samarqand |  4 | Dilnoza | Buxoro
 test_mijozlar_boshqa    |  5 | Sardor  | Andijon
```

E'tibor bering: bitta partitsiya (`test_mijozlar_samarqand`) bir nechta qiymatni (`'Samarqand'`, `'Buxoro'`) qamrab olishi mumkin. `DEFAULT` partitsiya — ro'yxatdagi hech qaysi qiymatga mos kelmagan qatorlarni (bu misolda `'Andijon'`) qabul qiladi; agar `DEFAULT` bo'lmasa, mos kelmagan qiymat bilan `INSERT` xato beradi.

`shahar = 'Toshkent'` bo'yicha so'rov ham xuddi shunday kesib tashlanadi:

```sql
EXPLAIN (ANALYZE, TIMING OFF) SELECT * FROM test_mijozlar_list WHERE shahar = 'Toshkent';
```

```
 Seq Scan on test_mijozlar_toshkent test_mijozlar_list  (cost=0.00..14.38 rows=2 width=200) (actual rows=2 loops=1)
   Filter: ((shahar)::text = 'Toshkent'::text)
```

Faqat `test_mijozlar_toshkent` skanerlandi — `test_mijozlar_samarqand` va `test_mijozlar_boshqa` umuman tegilmadi.

### HASH partitioning — teng taqsimlash uchun

Ba'zida ma'lumotni **mantiqiy** guruhlarga emas, balki shunchaki **teng** yukni taqsimlash uchun bo'lish kerak bo'ladi (masalan, juda katta jadvalni parallel `VACUUM`/backup uchun bo'laklarga bo'lish). Bunda `HASH` ishlatiladi:

```sql
CREATE TABLE test_xodimlar_hash (
    id INTEGER NOT NULL,
    ism VARCHAR(50)
) PARTITION BY HASH (id);

CREATE TABLE test_xodimlar_hash_0 PARTITION OF test_xodimlar_hash FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE test_xodimlar_hash_1 PARTITION OF test_xodimlar_hash FOR VALUES WITH (MODULUS 4, REMAINDER 1);
CREATE TABLE test_xodimlar_hash_2 PARTITION OF test_xodimlar_hash FOR VALUES WITH (MODULUS 4, REMAINDER 2);
CREATE TABLE test_xodimlar_hash_3 PARTITION OF test_xodimlar_hash FOR VALUES WITH (MODULUS 4, REMAINDER 3);

INSERT INTO test_xodimlar_hash SELECT i, 'xodim_'||i FROM generate_series(1,20) i;

SELECT tableoid::regclass, count(*) FROM test_xodimlar_hash GROUP BY 1 ORDER BY 1;
```

```
       tableoid       | count 
----------------------+-------
 test_xodimlar_hash_0 |     5
 test_xodimlar_hash_1 |     7
 test_xodimlar_hash_2 |     3
 test_xodimlar_hash_3 |     5
```

`MODULUS 4` — jami 4 ta bo'lak borligini, `REMAINDER N` — har bir partitsiya `hash(id) % 4 = N` bo'lgan qatorlarni olishini bildiradi. Natija — deyarli teng taqsimlangan (5, 7, 3, 5), ammo **mantiqiy** ma'no yo'q (masalan, `id`si 1 va 5 bo'lgan xodimlar orasida hech qanday umumiylik yo'q — ular shunchaki bir xil hash guruhiga tushib qolgan).

### Chegaradan tashqari qiymat — nima bo'ladi

`RANGE` partitioning'da, agar hech qaysi partitsiya qamrab olmaydigan sana bilan `INSERT` qilishga urinsak:

```sql
INSERT INTO test_buyurtmalar_katta (mijoz_id, sana, summa, holati) VALUES (1, '2025-05-01', 1000, 'yangi');
```

```
ERROR:  no partition of relation "test_buyurtmalar_katta" found for row
DETAIL:  Partition key of the failing row contains (sana) = (2025-05-01).
```

PostgreSQL bunday qatorni **hech qanday** partitsiyaga "taxminiy" joylashtirmaydi — u aniq xato beradi. Yechim — mos partitsiyani oldindan yaratish (yoki `DEFAULT` partitsiya qo'shish).

### Yangi partitsiya qo'shish va eskisini ajratib olish (ATTACH/DETACH)

Vaqt o'tishi bilan yangi yillar uchun partitsiya qo'shish kerak bo'ladi:

```sql
CREATE TABLE test_buyurtmalar_2025 PARTITION OF test_buyurtmalar_katta
    FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');

INSERT INTO test_buyurtmalar_katta (mijoz_id, sana, summa, holati) VALUES (1, '2025-05-01', 1000, 'yangi');
-- Endi xatosiz o'tadi
```

Eski, arxivga chiqarilishi kerak bo'lgan partitsiyani esa, butun jadvalni qamrab oluvchi og'ir `DELETE` o'rniga, **bir zumda** ajratib olish mumkin:

```sql
ALTER TABLE test_buyurtmalar_katta DETACH PARTITION test_buyurtmalar_2022;

SELECT count(*) FROM test_buyurtmalar_katta;  -- 199868 (2022 yil endi kirmaydi)
SELECT count(*) FROM test_buyurtmalar_2022;   -- 100133 (mustaqil jadval sifatida saqlanib qoldi)
```

`DETACH PARTITION` — ma'lumotni **o'chirmaydi**, faqat uni ota-jadvaldan "uzadi"; `test_buyurtmalar_2022`, endi **mustaqil, oddiy jadval**, uni xohlasa `pg_dump` bilan arxivlash, xohlasa butunlay `DROP TABLE` qilish mumkin — va bu amal, millionlab qatorni `DELETE` qilishdan farqli o'laroq, **metama'lumot darajasida**, deyarli lahzalik bajariladi. Zarurat bo'lsa, orqaga ham ulash mumkin:

```sql
ALTER TABLE test_buyurtmalar_katta ATTACH PARTITION test_buyurtmalar_2022
    FOR VALUES FROM ('2022-01-01') TO ('2023-01-01');

SELECT count(*) FROM test_buyurtmalar_katta;  -- 300001, qayta joyida
```

### Indekslar va UNIQUE cheklovlar partitsiyalangan jadvalda

Ota-jadvalda indeks yaratsak, u **avtomatik ravishda** har bir partitsiyaga tarqaladi:

```sql
CREATE INDEX idx_test_buyurtmalar_mijoz ON test_buyurtmalar_katta (mijoz_id);
```

```sql
\d test_buyurtmalar_katta
```

```
Indexes:
    "idx_test_buyurtmalar_mijoz" btree (mijoz_id)
Number of partitions: 4
```

Sahna orqasida, PostgreSQL har bir partitsiya uchun alohida jismoniy indeks yaratadi (`test_buyurtmalar_2022_mijoz_id_idx`, `test_buyurtmalar_2023_mijoz_id_idx` va h.k.), lekin bu — ota-jadval darajasida bitta **"partitsiyalangan indeks"** sifatida boshqariladi.

`UNIQUE` cheklov esa muhim cheklovga ega — **partition key** ustunini o'z ichiga olishi **shart**:

```sql
ALTER TABLE test_buyurtmalar_katta ADD CONSTRAINT uq_id_only UNIQUE (id);
```

```
ERROR:  unique constraint on partitioned table must include all partitioning columns
DETAIL:  UNIQUE constraint on table "test_buyurtmalar_katta" lacks column "sana" which is part of the partition key.
```

Sabab — PostgreSQL, unikallikni **butun jadval bo'ylab** emas, balki **har bir partitsiya ichida mustaqil** tekshiradi (chunki indekslar alohida-alohida). Agar `sana` unique kalitga kiritilmasa, bir xil `id` ikkita **turli** partitsiyada takrorlanishi mumkin edi va PostgreSQL buni oldindan bila olmaydi. To'g'ri versiyasi:

```sql
ALTER TABLE test_buyurtmalar_katta ADD CONSTRAINT uq_id_sana UNIQUE (id, sana);
-- Muvaffaqiyatli bajariladi
```

## Amaliy misol

**Vazifa:** `mahsulotlar` jadvaliga o'xshash, lekin `kategoriya` bo'yicha `LIST` partitsiyalangan test jadvali yarating: `Elektronika` alohida partitsiyada, qolgan barcha kategoriyalar `DEFAULT` partitsiyada bo'lsin.

```sql
CREATE TABLE test_mahsulotlar_kategoriya (
    id SERIAL,
    nomi VARCHAR(100),
    kategoriya VARCHAR(50) NOT NULL
) PARTITION BY LIST (kategoriya);

CREATE TABLE test_mahsulotlar_elektronika PARTITION OF test_mahsulotlar_kategoriya
    FOR VALUES IN ('Elektronika');
CREATE TABLE test_mahsulotlar_boshqa PARTITION OF test_mahsulotlar_kategoriya DEFAULT;

INSERT INTO test_mahsulotlar_kategoriya (nomi, kategoriya)
SELECT nomi, kategoriya FROM mahsulotlar;

SELECT tableoid::regclass, count(*) FROM test_mahsulotlar_kategoriya GROUP BY 1;
```

## Keng tarqalgan xatolar

**Xato 1:** Partitioning'ni **har qanday** jadval uchun "avtomatik tezlashtiruvchi" deb hisoblash.
❌ Kichik jadvallar (bir necha ming qatorli) uchun partitioning foyda emas, balki qo'shimcha murakkablik va overhead keltiradi — `JOIN` va planning xarajatlari ortishi mumkin.
✅ Partitioning'ni, odatda, millionlab qatorli, vaqt bo'yicha o'sib boruvchi va eski qismlari muntazam arxivlanadigan/o'chiriladigan jadvallar uchun qo'llang.

**Xato 2:** `WHERE` shartida partition key ustunini ishlatmaslik va "nega pruning ishlamayapti" deb hayron bo'lish.
❌ Agar so'rov `WHERE mijoz_id = 5` bo'lsa (partition key `sana` emas), PostgreSQL **barcha** partitsiyalarni skanerlashga majbur — chunki `mijoz_id`ning qaysi partitsiyada ekanini oldindan bilib bo'lmaydi.
✅ Partition key'ni tanlashda, eng ko'p ishlatiladigan `WHERE` shartlarini hisobga oling; kerak bo'lsa, ikkinchi darajali filtrlar uchun indeks qo'shing (bu avtomatik barcha partitsiyalarga tarqaladi).

**Xato 3:** `DETACH PARTITION`ni `DELETE`ga muqobil deb, ma'lumotni ham yo'qotib qo'yish kerak deb o'ylash.
❌ `DETACH PARTITION` ma'lumotni o'chirmaydi — u faqat mustaqil jadvalga aylantiradi; agar diskni bo'shatish maqsad bo'lsa, keyin alohida `DROP TABLE` kerak bo'ladi.
✅ Arxivlash oqimi odatda: `DETACH` → `pg_dump` bilan zaxira olish (15.2-dars) → `DROP TABLE`.

## Mashq/topshiriq

**(Oson)** `test_buyurtmalar_katta`da, `sana = '2024-07-15'` bo'lgan qatorlarni qidiring va `EXPLAIN` orqali faqat qaysi partitsiya skanerlanganini aniqlang.

**(O'rtacha)** `test_mijozlar_list` jadvaliga `'Namangan'` shahridan yana bitta mijoz qo'shing va u qaysi partitsiyaga tushishini (`tableoid::regclass` orqali) tekshiring.

**(Qiyin)** `test_buyurtmalar_katta`dan `test_buyurtmalar_2023` partitsiyasini `DETACH` qiling, so'ng shu partitsiyaga asoslanib qancha qator "yo'qolgani"ni (`count(*)` farqi orqali) hisoblang, va nihoyat uni qayta `ATTACH` qilib, asl holatga qaytaring.

## Qisqacha xulosa

Partitioning — bitta katta mantiqiy jadvalni bir nechta kichik jismoniy jadvalga bo'lib, so'rovlarni tezlashtirish (**partition pruning** orqali, biz `790` va `2368` buffer sonini solishtirib jonli ko'rdik) va boshqaruvni osonlashtirish (yangi partitsiya qo'shish, eskisini `DETACH` orqali lahzalik arxivlash) usuli. `RANGE` — sana/raqam diapazoni uchun, `LIST` — aniq kategoriyalar uchun, `HASH` — teng taqsimlash uchun ishlatiladi. Indekslar ota-jadval darajasida yaratilib, avtomatik barcha partitsiyalarga tarqaladi, lekin `UNIQUE` cheklov partition key'ni albatta o'z ichiga olishi kerak. Keyingi darsda — darsligimizning so'nggi mavzusi — server darajasidagi **performance tuning**: `postgresql.conf`dagi asosiy parametrlar, `pg_stat_statements` orqali sekin so'rovlarni topish, va **connection pooling** (`pgbouncer`) orqali ulanishlarni samarali boshqarishni chuqur o'rganamiz.
